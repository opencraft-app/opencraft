# 代码审查 (CR) 检查规范

> 本 Skill 有两种触发方式：
> 1. **主动 CR**（开发流程内置）：`/feai-start` 阶段 4C 自动触发，对本次所有改动进行检查，在提交代码前发现并修复问题
> 2. **手动 CR**（用户主动请求）：用户在对话中请求对指定文件或 MR 进行代码审查

---

## 主动 CR 流程（开发流程内置）

在 `/feai-start` 开发流程的阶段 4C 中自动执行，位于代码实现完成后、`git commit` 之前。

### 执行步骤

```
1. 获取改动范围 → 通过 git diff 获取本次所有新增/修改的文件
2. 逐文件检查 → 按 P0 → P1 → P2 优先级扫描
3. 问题处理：
   - P0（安全/逻辑）→ 直接修复，说明修复内容，修复后重新检查
   - P1（性能/错误处理）→ 列出问题和建议，询问用户是否修复
   - P2（规范/可维护性）→ 在报告中列出，不阻塞流程
4. 输出 CR 报告 → 无论是否有问题都输出简要报告
5. CR 通过 → 继续执行 git commit（参考 `ai-usage-tracking` 的 FE-AI 标记规范 + global.md G14）
```

### 主动 CR 报告模板

```markdown
## 🔍 主动 CR 检查报告

### 📊 概览
- 检查文件: x 个（新增 x 个，修改 x 个）
- 发现问题: x 个（P0: x 个，P1: x 个，P2: x 个）

### 🔴 P0 严重问题 (x 个) — 已自动修复
1. **[类型] 问题描述** - 位置: `文件名:行号`
   - 问题: 具体问题
   - 修复: 具体修复内容

### 🟠 P1 重要问题 (x 个) — 建议修复
1. **[类型] 问题描述** - 位置: `文件名:行号`
   - 问题: 具体问题
   - 建议: 修复建议

### 🟡 P2 一般问题 (x 个) — 仅提示
...

### ✅ 亮点
- 列出代码中的好的实践

### 📝 结论
- [ ] ✅ CR 通过，可以提交
- [ ] ⚠️ 有 P1 问题待确认，是否修复？
```

## CR 检查维度

| 优先级 | 检查项       | 说明                               |
| :----: | ------------ | ---------------------------------- |
| 🔴 P0  | **安全问题** | XSS、注入、敏感信息泄露            |
| 🔴 P0  | **逻辑错误** | 业务逻辑缺陷、边界条件             |
| 🟠 P1  | **性能问题** | 内存泄漏、不必要的渲染、大数据处理 |
| 🟠 P1  | **错误处理** | 异常捕获、错误提示                 |
| 🟡 P2  | **代码规范** | 命名、格式、注释、lint 规范        |
| 🟡 P2  | **可维护性** | 代码复杂度、重复代码               |

---

## 常见问题速查

### 🔴 P0 - 安全问题

| 问题         | ❌ 错误                                        | ✅ 正确                          |
| ------------ | ---------------------------------------------- | -------------------------------- |
| XSS          | `dangerouslySetInnerHTML={{ __html: input }}`  | `{userInput}` 或 `escapeHtml()`  |
| 敏感信息泄露 | `console.log('密码:', password)`               | 仅记录非敏感信息                 |
| URL 拼接     | `'/page?redirect=' + userInput`                | `encodeURIComponent(userInput)`  |

### 🔴 P0 - 逻辑错误

| 问题     | ❌ 错误                       | ✅ 正确                               |
| -------- | ----------------------------- | ------------------------------------- |
| 空值     | `user.profile.name`           | `user?.profile?.name`                 |
| 数组操作 | `list[0].name`                | `list?.[0]?.name`                     |
| 异步竞态 | 直接 `fetchData().then(set)`  | 使用 cancelled 标志或 AbortController |

### 🟠 P1 - 性能问题

| 问题       | ❌ 错误                                  | ✅ 正确                          |
| ---------- | ---------------------------------------- | -------------------------------- |
| 内存泄漏   | useEffect 中未清理 timer/listener        | return 清理函数                  |
| 重复渲染   | `style={{ color: 'red' }}`               | `useMemo` 或常量                 |
| 大列表     | 直接 map 渲染大量数据                    | 虚拟列表                         |

### 🟠 P1 - 错误处理

| 问题     | ❌ 错误                       | ✅ 正确                                |
| -------- | ----------------------------- | -------------------------------------- |
| 静默失败 | `catch(e) { console.error }` | `catch` 中给用户 `message.error` 反馈  |

### 🟡 P2 - 代码规范

| 问题       | ❌ 错误              | ✅ 正确                       |
| ---------- | -------------------- | ----------------------------- |
| Lint 规范  | 忽略 ESLint/Prettier 报错 | 代码修改后运行 lint 确保通过  |
| 命名       | `const d = getData()` | `const userData = getData()`  |

### 🟡 P2 - 可维护性

- 单个函数不超过 80 行，组件渲染不超过 150 行
- 嵌套不超过 3 层，使用提前返回减少嵌套
- 抽取重复代码为公共函数

## 手动 CR 使用方式

除了开发流程中的主动 CR，用户也可以在对话中手动触发 CR 检查：

```
帮我 CR 检查 src/pages/domain/index.tsx
帮我检查这个文件的性能问题
帮我对本次所有改动做一次 CR
```
