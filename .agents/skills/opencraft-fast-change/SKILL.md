# OpenCraft 快速变更

快速路径仍从源码构建可追溯的候选镜像，不直接修改运行中容器。先读目标仓库 AGENTS.md 与对应维护/设计入口。

## 选择构建范围

沿实际调用链定位修改所属的 Web、Gateway、Brain 或 Hands。依赖、原生 ABI、协议、数据库迁移、跨包契约或多个交付目标变化时，扩大到相应构建与验证范围；不要把网关单文件打包套用于所有改动。

## 核对基线

同时读取源码分支、dirty diff、实际运行容器的镜像 ID/manifest、Compose 合并配置，以及 systemd 的 WorkingDirectory/ExecStart 和恢复脚本。源码 HEAD、镜像标签、容器运行版本与重启入口可能各不相同。

确认本次基线包含已上线补丁。多个服务可以使用不同镜像，分别记录；不能用旧基础镜像加本次补丁覆盖掉已上线的终端、认证或目录迁移。已有候选产物和旧总结只是线索，以现场镜像/配置为准。

隔离其他会话的修改：保存本次源码补丁或明确文件投影，记录构建所用源码及已有补丁链。不要把 dirty worktree 全部打包，也不要为隔离而恢复文件、删除别人的改动或自动退回失去现网功能的 HEAD。

## 先提交到发布分支，再发布

本环境的固定流程是：本次改动提交或合入本部署约定的发布源码分支 → 固定该提交的完整 commit SHA → 从该提交构建候选 → 发布到本环境 → 验证运行结果。先合入，再构建和发布，不以其他临时分支或未提交补丁直接作为发布源码。

仓库不规定发布分支名称：`publish.mjs` 只校验计划的 `sourceRevision` 是完整 SHA，且在 `sourceRepository` 中存在该 commit，不检查所在分支。分支由各部署自行选定并记录，开始前以现场 checkout 为准，不沿用其他环境的名称。

合入前核对差异，仅纳入本次授权的改动；让该提交包含本次完整源码输入及需要保留的已上线补丁，保留其他任务的未提交工作。已有独立分支时将审定提交合入该发布分支，直接在该分支工作时做聚焦提交；不要为合入覆盖、清理或夹带别人的修改。

发布脚本不 push 该分支，也没有提交即自动部署的机制。已获授权更新本环境时，合入后继续完成构建、发布与验证，不停在提交完成；仅要求修改 Skill、文档或分析时遵循本次范围。

## 构建候选

先完成相关类型检查、聚焦测试；UI 还要在真实组件/路由验证触控和键鼠路径。使用项目正式打包参数、外部依赖、资源和 worker 规则，仅重建受影响交付单元。保留已有运行时依赖及产品装配，不能以通用默认构建无意替换现场功能。

以核实过的现网镜像 ID 为基础生成独立候选镜像，覆盖本次构建产物，更新 manifest 的 buildId、文件摘要与补丁来源。若替换 Web，正确移除失效资源并验证入口/动态 chunk，不能将残留文件误记为新版本。保存源码补丁、基线、候选 ID、检查结果和回滚配置；凭据不进入这些记录或 Skill。

## 发布租约边界

构建、安装依赖、类型检查、候选镜像验证和生成完整计划都在部署锁外完成。
不得先取得部署锁再等待构建、ready 文件或用户确认，也不得把部署锁描述符
传给构建进程。候选准备与最终切换是两个 owner，不用部署锁预留发布顺序。

使用仓库的 `scripts/fast-release/release.sh PLAN LOCK -- BUILD_COMMAND [ARGS...]`
让独立监督器执行整个流程。入口在锁外执行构建 argv，封存计划/候选配置，
再进入 publisher；等待部署锁不持有租约。已准备的固定计划可直接交给
`publish.sh`。外层监督器不要另开 fd 9 持锁等待。

只在锁内复核现网、保存回执、切换、验证和回滚。基线变化时拒绝旧计划，
释放锁后重新准备；不能在锁内重建或改写 expectedImages 跳过保护。
回滚也通过同一入口和生命周期契约。凭据、验证脚本和候选目录保持本次独占。

## 切换与恢复

构建不自动授予部署权限，按用户本次及已有会话授权执行。已获授权时无需重复确认。

切换前备份精确配置与原镜像 ID，核对可用资源并串行化部署。修改实际重启使用的配置，保留既有参数、挂载、认证和未受影响服务镜像；检查 compose config 的最终结果。只重建受影响服务。

若代理运行在被替换服务中，先把完整操作交给独立宿主监督器，保存持久状态和日志，避免连接断开导致半次部署。不要依靠当前 shell 存活完成恢复。

验证失败时，依本次备份恢复配置及原镜像，再检查恢复结果；保留失败证据，不在故障环境连续叠加不明候选。

## 验证与交接

确认运行容器镜像 ID、buildId 与产物摘要匹配候选；同时核对启动/恢复入口仍指向它。健康接口通过后，还要检查本次行为和该交付单元已接通的关键能力。网关变更应核对终端路由与连接管理，不用健康绿灯代替功能检查。按范围验证重连/重建后的行为，并确认未受影响服务启动时间未改变。

说明源码、构建、部署与客户端分别验证到哪一步。区分真实端到端、模拟身份/引擎、浏览器触控模拟和物理手机；不把测试通过说成用户手机已经恢复。记录回滚位置和仍未验证的范围。

## 本地分支与加锁入口

当前部署从其约定的本地发布分支发布；候选与发布计划的 `sourceRevision` 必须指向该分支中本次选定的明确 commit（发布器只核对 commit 存在，分支归属由操作者核对），并核对构建实际消费该提交。合入、构建、发布和验证分别记录，不能将“已合入”描述成“环境已更新”。按 [发布入口与计划格式](../../../scripts/fast-release/README.md) 使用同一部署锁，所有临时/人工发布也必须遵守该锁。构建可并行，切换时的基线校验必须在锁内完成。Docker 局部打包细节见 [候选镜像与配置切换](references/docker-overlay.md)。
