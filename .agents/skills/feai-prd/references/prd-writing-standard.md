# 需求写作标准

> `/feai-prd` 生成需求内容时的写作规范。质量检查见 `gate-prd-quality.md`；TAPD 字段格式见 `tapd-story-format.md`。

---

## 核心原则

1. **可测试优先**：每条需求都能被第三方独立验证，不依赖作者的主观判断。
2. **单一职责**：每条需求只描述一个可观察行为；复杂条件用决策表，不用多个段落重复解释。
3. **事实与判断分离**：现状事实、产品判断、假设、待外部确认必须区分状态，不得混写。
4. **不编造**：数字、比例、用户规模、性能基线没有输入来源时标为待外部事实，不臆造。

---

## 需求阶段边界（禁止技术方案）

需求单只描述「要什么、验收什么」，不描述「怎么实现」。以下内容**禁止写入需求单**：

| 禁止项 | 说明 |
|---|---|
| 技术方案 / 解决实现方案 | 实现路径由 `/feai-start` 的 shape 阶段研发 agent 决定 |
| 详细设计 / 架构设计 | 数据结构、接口定义、模块划分 |
| 具体改动文件清单 | 「改 XX.tsx」这类 |
| 可复用组件 / 函数点名 | 「复用 useXxx」这类 |
| 实现步骤 / 分批计划 | 「第一步改 A，第二步改 B」这类 |

影响评估只写 **S/M/L 评级 + 一句话影响范围**（如「涉及 XX 模块」），供研发评审判断工时，不给实现指引。

---

## 禁用表达表

以下表达不可测试，必须改写：

| 类别 | 禁用表达 | 改写方式 |
|---|---|---|
| 不确定 | 可能、大概、也许、应该、似乎、原则上 | 明确为"是/否"，或标为 `[推荐待确认]` |
| 范围模糊 | 等、等若干、一些、相关、部分、之类、若干 | 明确列举全部项 |
| 程度模糊 | 尽快、优先、较快、较多、较慢、大量、少量 | 量化为具体数值、时间或比例 |
| 主观判断 | 合理、适当、良好、友好、简洁、清晰、易用 | 定义可衡量的标准或具体行为 |
| 空泛正确 | 正常、正确展示、符合预期、体验良好、无异常 | 写出具体的可观察结果 |
| 无主体 | 系统应该、需要支持、要能够 | 写明执行角色与触发条件 |
| 隐含全集 | 支持所有、兼容全部、任意场景 | 列出实际支持的枚举与已知不支持项 |
| 伪指标 | 提升效率、优化性能、增强稳定性 | 给出指标名、计算规则与观察窗口 |

## 需求句法

用以下句式之一表达需求，保证可测试：

| 场景 | 句式 |
|---|---|
| 基本行为 | `{角色}在{前置条件}下{操作}，系统{可观察结果}` |
| 条件分支 | `当{条件}时，系统{行为A}；否则{行为B}` |
| 状态流转 | `{对象}从{状态A}进入{状态B}的条件是{触发}，用户可见{反馈}` |
| 约束限制 | `{对象}的{属性}不得{超过/低于}{具体值}，超出时{处理}` |
| 异常处理 | `{失败场景}发生时，系统{默认行为}，用户可{恢复动作}` |
| 权限差异 | `{角色A}可{操作集合}；{角色B}仅可{操作集合}` |
| 默认值 | `{字段}默认为{值}，用户{可否}修改` |

验收标准用 Given/When/Then 精简语义：

```text
Given {前置条件与测试数据}
When {用户操作或系统触发}
Then {第三方可观察、可复现的结果}
```

一条验收只验证一个结果，不为减少条目数而合并独立条件。

## 未决项三分类

每个未决问题必须归入以下三类之一，不得留无归属的"待确认"：

### A 类：`[推荐待确认]` — 产品/研发可自主决定

适用：流程顺序、默认值、次数、阈值、排序、是否允许返回、错误恢复入口、重复提交处理、普通异常行为。

必须给出：**推荐值 + 选择理由 + 主要取舍**。

> 判定方法：不查外部系统、不等外部审批就能选一个合理值 → A 类。

⚠️ 治理与度量数值（灰度时长、观察窗口、SLO、转化目标、比例阈值）没有输入来源时只能标 A 类待确认，不得写成"已采用"。

### B 类：`[待外部事实]` — 必须依赖外部信息

适用：数据基线、系统能力、API/容量上限、价格成本、法务合规、实际工期人力。

必须写明四要素：

```text
缺失事实：{需要确认什么}
来源方：{应提供事实的角色或系统}
影响：{未确认会影响的范围、规则或验收}
临时行为：{未确认期间的安全默认行为}
```

⚠️ 禁止只写"待确认"而不写来源、影响和临时行为。

⚠️ 不得创造外部系统能力：取消、暂停、终止、重试、回滚、补偿等动作，能力未确认时属 B 类，只能定义"不展示入口/关闭新建/保持存量可见"等安全行为。

### C 类：`[待用户选择]` — 显著改变范围、成本或风险

适用：单站/双站、最小/完整方案、是否包含跨账号或不可逆数据处理。

必须给出：**推荐选项 + 备选方案差异**。能提问时一次问一个聚焦问题，不伪造用户批准。

## 状态标记规范

| 标记 | 含义 | 使用条件 |
|---|---|---|
| 无标记 | 已确认事实 | 用户明确提供，或原始材料逐字给出 |
| `[推荐待确认]` | AI 建议，待确认 | AI 基于常规做法给出的选择 |
| `[待外部事实]` | 需查外部系统 | 数据、能力、成本、合规、工期 |
| `[待用户选择]` | 需用户裁决 | 影响范围/成本/风险的方案分叉 |

⚠️ 用户说"直接创建""跳过澄清"只授权生成草稿，不等于批准 AI 的选择。AI 选择的流程、范围和失败策略仍须标 `[推荐待确认]`。

---

## 冲突处理

输入存在互相矛盾的事实或目标时：

1. 不得静默取一边。
2. 记录冲突内容、影响范围、裁决责任方。
3. 冲突影响范围、权限、状态、发布或验收时，先澄清再写正文。
