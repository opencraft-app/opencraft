# UI 实现与视觉复核

用于 OpenCraft 新增、调整或评审界面，也适用于以功能开发名义新增的 UI。只分析时输出差异和证据；实施时将下面的判断落实到实现和验收。路径以 OpenCraft 根为准；设计规范仍由 `design.md` 及其专题持有，本文负责工作方法。

## 先建立设计参照

从 `design.md` 选择用户任务对应的范式，查看它指向的共享 owner 和一个真实消费者。不要只搜索组件名或照搬独立 HTML 原型；消费者本身也要判断是否适合当前任务。

在已有任务记录中简述主任务、参照、容器 owner 与主次动作，并把原则落到可见结果。例如：“沿用 Settings 文档容器，渠道列表按对象扫读；添加为主动作，关联为安静的次动作；创建表单用共享 utility panel，校验在输入下方原位反馈。”不是要求每个页面都采用此组合，也不另建一份审批文档。

## 按完整组合选择共享能力

| 界面部分 | 去哪里确认 | 需要判断的结果 |
|---|---|---|
| 页面与列表 | `apps/workbench-web/src/components/settings-page.tsx`、`packages/extension-react/src/settings-controls.tsx` 及当前路由样式 | 内容宽度、页边距、章节节奏由谁投影；标题、说明和操作在窄容器如何排列。单个 Header/Row 不拥有整页布局 |
| 工具弹窗与表单 | `packages/extension-react/src/settings-panel.tsx`、`apps/workbench-web/src/components/modal/modal-surface.tsx` 及其样式；可参考 `apps/workbench-web/src/components/bot-management.tsx` 的实际消费 | Radix 管行为，宿主 modal surface 管呈现，SettingsPanel 管内容组合；表单 label、输入和校验槽的关系及密度应适合容器 |
| 空态及辅助文字 | `design/ui/typography.md`、当前共享排版和容器 | 语义层级与章节一致，heading/p 的浏览器 margin 不叠加出意外空白；提示和次动作不会压过主任务 |
| 状态、主题与平台输入 | `design/ui/README.md` 命中的主题、当前共享控件 | 原位反馈、文本/背景配对、触控与键盘状态、草稿和焦点连续性 |

以上是 Web 的 owner 定位，不允许插件越过包边界导入 App 内部组件。沿用已导出的能力和宿主公开的视觉 contract；能力缺失时在正确 owner 扩展。Native 从对应共享语义和平台消费者确认呈现，不照搬 DOM 类名。

复用零件后仍要检查组合：例如 `SettingsRow.description` 是说明槽，不是任意表单错误占位；Radix Dialog 负责交互，不自动提供项目的视觉壳。不要为了“统一”把所有局部布局搬到 Shell，也不把功能样式复制成第二套共享规范。

## 用真实使用状态复核

选择与改动有关的路径。新建管理页从没有数据的首次入口走到添加表单，再看提交中、校验或失败反馈；小修只覆盖受影响状态及相关共享消费者。编辑器、只读目录或已有数据的页面按其真实任务选状态，不强造创建流程。

在实际 Shell/路由渲染。局部原型可帮助选择方向，最终产品的 CSS、容器和状态可能不同；原型通过不等于产品通过。用合成数据替换必要的外部边界，并说明验证停在哪里。

按影响检查窄/宽容器、主题和长文案；声称触控验收时使用触控上下文及触摸输入。查看实际页面或打开捕获的图像，具体判断：

- 标题、章节、正文、辅助信息和动作能否按任务顺序扫读，主次动作是否清楚；
- 文本与控件是否沿预期轴线对齐，空态是否出现意外大段间隔，表单标签是否贴近对应输入；
- 窄容器、短视口及校验/处理中状态下操作是否可达，原草稿、焦点、选择和滚动是否保持。

将发现的问题落实到代码后重新查看受影响画面。有可测量的布局缺陷时，优先扩展现有消费方 smoke，并以旧实现负控验证断言；由共享 owner/需求确定预期，避免用截图像素冻结设计。字体 lint、无溢出和截图产出不能替代上述判断；不新增全局截图或部署审批门禁。

## 留下可核实的交接

已有任务记录中写明查看的真实路由、状态、主题/容器/输入方式及图像位置，说明看到的组合、发现的偏差和修正；未能查看时明确写“视觉未复核”。将模型/协议、布局断言、目视检查、已安装产品和真机证据分别陈述，不用“已读规范”或测试数量推导设计合格。
