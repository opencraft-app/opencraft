# CodeDog Lint Fix

## Overview

本 skill 面向 `wisp/mono2` 仓库里的 CodeDog / CodeLint 问题处理。目标是先准确还原扫描问题，再判断问题是否真实、是否仍有效，最后做最小、可验证、低风险的修复，并通过“修复 -> 合入 -> 复扫 -> 回查 -> follow-up”的闭环确认问题生命周期已经更新。

## Workflow

1. 先读根目录 `AGENTS.md`，再根据涉及目录读取对应子服务 `AGENTS.md`。
2. 如果需要提交、推送或创建 MR，先读 `.agents/skills/gongfeng/SKILL.md`，并遵守根 `AGENTS.md` 的确认要求。
3. 打开用户给的 CodeDog 链接，记录项目、分页、筛选条件、问题总数和当前页问题。
4. 若页面登录回跳后异常为空，检查 hash query 是否被 OAuth 参数污染，例如 `state=...` 被 CodeDog 当成 issue filter；去掉非 CodeDog 查询参数后重试。
5. 只选择未处理、仍有效的问题。若当前页未处理数少于用户要求，优先补选同页面、同规则、同严重级别或相邻列表里的未处理问题，并在回复里说明选择依据。
6. 对每个问题记录：issue id、文件、行号、规则名、状态、问题摘要、预期修复策略。
7. 先判断问题类型和风险面：安全、可靠性、性能、可维护性、类型、格式、复杂度、死代码、依赖配置等，选择匹配的修复方式。
8. 改代码前优先写或调整聚焦测试；若存量测试结构不足，至少明确一个可复现验证方式。
9. 使用 `apply_patch` 做手工编辑，保持改动局部，不顺手重构无关逻辑。
10. 修复后跑相关测试、语法/类型/格式检查，并用 `rg` 复查同类模式。
11. 代码合入目标分支后，按 “Rescan / Recheck” 触发或等待 CodeDog 重新分析，并确认问题生命周期已经更新。
12. 若复扫后仍有残留，不要把它视作失败终点；定位残留命中的新代码位置或同类漏点，形成 follow-up 修复，再继续复扫确认。

## CodeDog Issue Collection

- 优先使用页面已有登录态查看问题；如果浏览器 DevTools / Network 能看到 CodeDog API 响应，可用 API JSON 辅助提取字段。
- 不要把用户提供或工具返回的 token、cookie、密码、private_token 写入文件、提交信息、MR 描述或最终回复。
- 区分“已修复/已关闭/已忽略”和“未处理”。用户要求选 N 个时，N 只统计真正要改代码的问题。
- 如果链接中带 `limit`、`offset`，保留这些分页参数；清理登录回跳造成的多余 `state`、`code` 等参数。
- 如果页面和 API 结果不一致，以可复现的 API/页面状态为准，并在结论里说明异常。

## Analysis

每个 CodeDog 问题都先做一次小型 triage，不要机械按扫描结果改：

- 确认告警行是否仍存在，扫描分支是否与当前工作区一致。
- 阅读告警所在函数和调用链，判断输入来源、边界条件、错误处理和业务影响。
- 查找同类代码的既有修法，优先沿用仓库已有模式。
- 判断是真问题、误报、已修、历史分支残留，还是需要更上游的架构改动。
- 对误报只在有充分证据时抑制，并把理由写在代码注释或 MR 描述里。
- 用户要求“选 N 个”时，优先选范围清晰、可验证、互不牵扯的 N 个；避免把大规模重构和小修混在一个 MR。

## Fix Strategy

按问题类型选择修复策略：

- 安全类：优先消除真实风险，收紧输入、权限、逃逸、序列化、命令/SQL/路径/模板边界；不要只加忽略标记。
- 可靠性类：补齐错误处理、超时、空值、边界条件、资源释放和重试语义。
- 类型/空值类：让类型收敛到真实数据结构，避免用宽泛类型压掉问题。
- 复杂度/重复类：只在局部抽取有明确收益的 helper，避免顺手大重构。
- 格式/风格类：按项目 lint/formatter 处理，不改业务行为。
- 配置/依赖类：确认影响范围，避免升级或配置改动牵连无关服务。
- 误报类：需要有代码级证据；抑制标记要贴近告警行，并写清楚为什么安全。

修复完成后，再对同一文件或同一模块用 `rg` 查一遍同类模式，避免只修扫描命中的一处而漏掉相邻代码。

## Testing

每类修复至少覆盖一个风险边界：

- 正常路径行为不变。
- 告警指出的异常输入、边界条件或风险路径被覆盖。
- 改动语言对应的单测、类型检查、lint、语法检查按项目约定运行。
- 对变更运行 `git diff --check`。
- 若本地无法完整复现 CodeDog，至少运行最接近的项目检查，并说明剩余风险。
- 修复后用 `rg` 检索同类代码模式，确认没有明显相邻遗漏。

## Rescan / Recheck

CodeDog 问题修复合入后，不要只凭本地测试宣布 CodeDog 已消失。先确认 CodeDog 当前分析版本是否已经包含目标 commit。

### 触发入口

1. 打开对应 CodeDog 项目页。
2. 确认页面顶部的 `代码分支` 是目标分支，通常是 `master`。
3. 确认 `分析方案` 是用户期望的方案，例如 `CSIG代码质量检查`。
4. 点击页面上的 `启动分析`。
5. 弹窗中通常默认是 `在线分析 + 增量分析`；按下面的选择思路决定是否切换。
6. 启动后进入 `分析历史`，记录新的分析 ID、启动时间、版本、类型、状态、启动人。
7. 若任务刚启动，轮询 `分析历史`；任务成功后再回到问题列表确认目标问题状态。

### 增量还是全量

- 选择增量分析：只想验证刚合入的 diff 是否新增 CodeDog 问题，或用户明确说“增量就行”。增量速度快，但未必会重新计算历史旧问题的关闭状态。
- 选择全量分析：要确认历史未处理问题是否被关闭/消失、规则配置变更后需要全仓复算、或者问题引入时间远早于本次 MR。全量更慢，但最适合验证旧问题生命周期。
- 如果修复的是 CodeDog 页面里很早之前发现的未处理问题，优先选择全量分析；否则可能出现代码已修但旧问题列表还没关闭的情况。
- 如果已经误触发了全量分析，通常不要取消；确认它扫描的版本已是目标 commit 后，等待完成即可。

### 完成确认

- 在 `分析历史` 中确认新任务状态为成功，且 `版本` 与目标分支最新 commit 前缀一致。
- 回到问题列表，使用原分页、筛选条件或 issue/file/rule 定位目标问题。
- 记录每个目标问题的新状态：已关闭、已修复、仍未处理、或已从未处理列表消失。
- 如果任务成功但问题仍未关闭，重新检查代码是否真的落在扫描版本、问题行是否仍存在、是否需要全量分析、是否是另一个同类问题或误报抑制不足。
- 如果全量任务耗时较长，可以设置线程后续检查或自动化提醒，但最终回复必须基于完成后的页面状态。

## Optimization Loop

把 CodeDog 修复视为一个 Agent 辅助优化循环，而不是一次性代码修改：

```text
CodeDog 发现问题
-> Agent 获取并筛选未处理项
-> Agent 分析规则、代码上下文和真实风险
-> Agent 最小修复并补验证
-> 提交 MR 并合入目标分支
-> 触发或等待 CodeDog 复扫
-> Agent 回查问题状态
-> 问题关闭则闭环；仍未关闭则定位残留并进入 follow-up
```

执行原则：

- 以 CodeDog 复扫后的页面状态作为闭环依据，不以“代码看起来修了”作为完成依据。
- 复扫后只关闭部分问题时，明确列出已关闭项和残留项。
- 对残留项优先查同一文件、同一规则、同一调用模式，确认是否有未覆盖的相邻代码或扫描命中点漂移。
- follow-up MR 应该尽量小，只处理复扫暴露出的残留原因，避免把新需求混入闭环。
- 每轮都保留证据：分析 ID、扫描版本、问题状态、验证命令、残留判断。

## MR Notes

MR 描述建议包含：

- 背景：CodeDog 页面或规则来源。
- 范围：选取了哪些问题，若不是全量处理，说明选择依据。
- 修复：按文件列出修复策略，不贴敏感信息。
- 验证：列出实际跑过的命令。
- 风险：说明正常路径是否变化，以及任何需要 CodeDog 重新扫描确认的点。

提交、推送、创建 MR 前必须向用户展示变更范围并等待确认，除非当前对话已经明确确认了该批操作。
