# Feature introduction

Use to explain one real LightVela capability and why users should care.

Suggested arc: benefit-led title → hero recommendation → answer-first definition → user problem/context → what it is → why it matters → how it works in plain language → what users can do → what comes next.

- Verify the capability in repo code/docs before drafting.
- Code is evidence, not prose: do not expose service names, file paths, endpoints, fields, proto/config names, or implementation details unless the user explicitly wants a developer audience.
- Keep the feature definition crisp: one feature, one job, one user-facing benefit.
