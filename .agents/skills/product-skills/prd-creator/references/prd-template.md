# PRD Template And Product Draft Rules

读取时机：形成产品输入稿、判断国内/国际站发布范围、判断 Demo 或原型需要时读取本文件。

## 国内站 / 国际站发布范围判断

LightVela 同时有国内站 `lightvela.com` 和国际站 `lightvela.ai`。任何用户可见产品需求都必须在 PRD 中写清楚站点范围，不要默认双站同步，也不要默认只做国内站。

| 发布类型 | 适用情况 | 产品处理 |
| --- | --- | --- |
| 国内站 only | 需求依赖国内登录、实名、支付、微信/企微、国内运营活动、国内合规或国内专属渠道 | PRD 写明国际站不本次同步，并给出原因；若未来可能同步，列入待确认或后续需求 |
| 国际站 only | 需求面向海外用户、英文/zh-sg 文档、国际 SEO/GEO、海外渠道、国际支付/登录或 `lightvela.ai` 独立体验 | PRD 写明国内站不本次同步或后续评估；必要时联动 `lv-international-docs`、`lv-seo-geo` |
| 双站同步 | 用户价值、交互、权限、数据和技术依赖基本一致，只需要文案/i18n/图片/metadata 差异 | 可以用一个产品父单覆盖双站，但必须列出中英文内容、路由、SEO/GEO、灰度和验收差异 |
| 分阶段发布 | 目标一致但两站依赖、审核、内容、运营或风险不同，需要不同上线节奏 | 用一个父单写总体目标和阶段策略；如果两站范围或验收差异较大，建议拆成两个关联产品父单 |

拆单建议：

- 一个父单：目标用户和产品行为一致，只是语言、文案、图片、metadata 或轻量入口差异。
- 两个关联父单：国内站和国际站的目标用户、合规/支付/登录、渠道、上线节奏、验收标准或运营目标明显不同。
- 不要按设计、研发、内容、QA、发布或运营方向创建产品父单的子单；若拆单，只拆产品父单，或在产物交接里建议对应承接角色或事项负责人创建独立执行事项并回链父单。

## 产品输入稿结构

按这个结构整理：

```markdown
# <产品需求标题>

## 基本信息
- 当前产品：例如 LightVela
- 需求单状态：草稿 / 评审中 / 已确认
- 创建人：可以和 PRD 文档 MR 的提交者保持一致
- 创建日期 / 最后更新时间：

## 需求背景
- 为什么要做？市场/用户/业务层面的驱动力是什么？
- 不做会怎么样？
- 用户价值：解决了用户什么痛点
- 业务价值：能为产品带来的价值

## 目标用户与场景
- 目标用户画像：谁会使用这个功能
- 典型场景：

## 目标
- 产品结果：为产品带来哪方面的提升，可以是相对定性的目标描述
- 业务目标：可以提供可量化的目标（如转化率提升 X%、日活增加 Y）

## 范围
- 本次包含：
- 本次不包含：
- 优先级：P0 / P1 / P2
- 已知依赖：

## 功能详细描述
- 功能点拆解：每个功能点的交互逻辑、状态变化
- Demo / 页面结构说明：默认输出 Demo；仅在当前项目明确需要时补交互设计稿或原型设计稿链接
- 交互说明：点击、滑动、弹窗、跳转等行为
- 边界条件与异常处理：空状态、加载态、错误态、网络异常、权限不足等
- 数据埋点需求：如有

## 发布站点与同步策略
- 发布范围：国内站 lightvela.com / 国际站 lightvela.ai / 双站同步 / 分阶段发布 / 待确认
- 国际站是否同步：是 / 否 / 后续单独评估 / 不适用
- 国内站是否同步：是 / 否 / 后续单独评估 / 不适用
- 差异化原因：用户、语言、合规、支付、登录、渠道、内容、SEO/GEO、运营节奏、技术依赖
- 路由与内容影响：页面/文档/入口/文案/i18n/图片/metadata/sitemap
- 上线顺序：同步上线 / 国内站先行 / 国际站先行 / 灰度后同步

- 兼容性：平台、浏览器、分辨率；如不适用写“沿用现有兼容性要求”
- 安全与权限：角色权限、数据脱敏；如不适用写“无新增权限或安全要求”
```

## 产品输入稿集中自检

写入本地 PRD、TAPD 或进入工蜂 MR 前，重新通读并在原稿内修正：

- 占位符与未完成内容，如 TBD、TODO、空字段、模糊表述。
- 目标、范围、方案、验收之间的矛盾或断链。
- 范围是否仍可作为一个产品需求独立交付和验收，过大则拆分。
- 可能产生两种解释的歧义，选择一种并写清。

自检未通过不得写入或提交。

## 文档输出约定

- LightVela 的代码仓库是 mono2。产品输入稿确认后，必须实际写入 `<mono2-repo-root>/wiki/prd-docs/YYYY-MM-DD-<short-title>.md`，不要只停留在聊天内容或 TAPD 描述草稿里。
- 如果当前工作目录已经是 mono2 仓库根目录，使用相对路径 `wiki/prd-docs/YYYY-MM-DD-<short-title>.md`；不要再额外创建一层 `mono2/` 目录。
- `YYYY-MM-DD` 使用文档首次创建日期，`<short-title>` 使用稳定、简短、可读的需求标识。修改已有 PRD 时更新原文件，不要仅因日期变化重复创建。
- `wiki/prd-docs/` 不存在时创建该目录。不要再把 LightVela PRD 写入 `product/prd/` 或 `docs/reqs/lightvela/`。
- 产品输入稿、方案决策、验收标准、产品原型说明和待确认问题默认保存在同一份 Markdown PRD 中；单独的设计稿或图片只在确有产物时由 PRD 链接引用。
- 写入后在回复中给出实际文件路径，再进入后续 TAPD 与工蜂 MR 环节。PRD 只有进入远端 MR 评审后才算完成落库。

## Demo、原型和交互评审稿判断

PRD 草稿完成后，先判断是否需要原型或交互评审稿。默认情况下直接输出 Demo，不输出交互设计稿或者原型设计稿。

需要原型的场景：

- 新增或重构页面、设置项、弹窗、抽屉、列表、详情、安装流程或诊断流程。
- 产品、设计、前端需要在研发评估前确认页面结构、主路径、异常状态或空态。
- 涉及 `/agents`、专家/工具卡片、SkillHub 安装、Hermes 命令反馈、MCP 权限提示等用户可见流程。
- PRD 中存在多个状态或跨页面跳转，仅靠文字容易误解。

可跳过原型的场景：

- 纯后端/运行时能力，没有用户可见行为。
- 纯文案或配置调整，不改变页面结构和交互路径。
- 已有可复用设计稿、截图或线上页面，且本次只是小幅扩展。

需要原型时，在产品输入稿后补这一段：

```markdown
## 产品原型说明
- 目标页面/入口：
- 用户主路径：
- 页面结构：
- 关键组件：
- 状态：加载 / 空态 / 错误 / 禁用 / 权限不足
- 主要操作：
- 需要设计确认：
- 需要前端确认：
```

跳过原型时，也要在父单或 PRD 中写明跳过原因。
