# Completion Checklist And Exceptions

读取时机：最终汇报前、异常兜底时，或需要判断是否可以宣布完成时读取本文件。

## 完成输出格式

产品前置结束时，用这个格式汇报：

```markdown
## LightVela 产品前置完成

| 项目 | 结果 |
| --- | --- |
| 输入状态 | 想法输入 / 来源单转换 / PRD 草稿 / 产品已通过 / 下游已就绪 |
| 产品父单 | #xxx，当前状态 |
| 产品文档 | wiki/prd-docs/YYYY-MM-DD-<short-title>.md（mono2）/ 未落地：原因 |
| 产品原型 | 已生成：位置 / 未生成：跳过原因 |
| 发布站点 | 国内站 / 国际站 / 双站同步 / 分阶段发布 / 待确认 |
| 国际站同步 | 是 / 否 / 后续评估 / 不适用 |
| TAPD 写入 | 已创建/已更新/未写入：原因 |
| 工蜂 MR | !xxx，完整链接 / 未创建：原因 |
| 产物交接建议 | 已整理：方向与承接角色 / 未整理：原因 |
| 建议后续执行事项 | 设计 / 前端 / 后端运行时 / Skill 内容文档 / 国内国际站 / 安全合规 / QA / 发布运维 / 运营支持 / 无 |
| 待确认问题 | 列出问题或“无” |
| 下一步 | 进入澄清 / 产品评审 / 产物交接确认 / 排期 / 执行 |
```

如果没有实际写入 TAPD（例如 Token 一直无效），把"建议标题、建议字段、建议描述、手动建单步骤"放在总结后面。

## 异常处理

- 本地没有有效 TAPD Token：这是 TAPD 环境阶段唯一允许打扰用户的点，按 `tapd-write.md` 的话术索要 Token；拿到后自动完成剩余配置，不要再追问其他 TAPD 配置。
- Token 无效（写入后重新探测仍失败）：如实告知报错信息（如 401/权限不足），请用户确认 Token 是否正确或是否有该工作区权限，不要假装创建成功。
- `mcporter-internal` 安装失败或 `.codebuddy/mcp.json` 无法写入：如实报告失败原因，输出本地 PRD、TAPD 标题、描述、字段和手动操作步骤兜底。
- 当前工作区有无关改动：基于最新 `origin/master` 创建独立 worktree，只复制并提交本次 PRD 与明确要求的直接相关文件，不处理用户的其他改动。
- 工蜂未鉴权或 Token 无效：保留本地 PRD、来源分支和提交/MR 预览，只索要或修复工蜂个人 Token；鉴权成功前不执行 commit、push 或创建 MR，也不宣称远端已落库。
- 分支已 push 但 MR 创建失败：先按来源分支查询是否已有 MR；有则返回真实编号和链接，无则保留分支并报告工蜂错误，不把 push 当作完成。
- 未找到名为 `LightVela` 的分类：不阻塞创建，省略 `category_id`，在完成总结里注明。
- 状态未知：现场发现 backlog 等价状态值，不需要用户确认这次映射结果。
- TAPD 必填字段缺失：创建或更新前停止，并列出缺失字段。
- 富文本写入失败：改用更简单的 HTML 标签（如只保留 `<h3>`/`<p>`/`<ul><li>`）重试，不要退回到裸 Markdown 符号，同时保留链接和验收标准。
- 用户要求产品侧创建下游子单：说明 LightVela 产品前置不创建产品父单的子需求，改为输出后续执行事项建议，由对应承接角色或事项负责人按自身流程建单并回链产品父单。

## 完成前先确定交付范围

判断本次属于哪种交付范围，完成检查按范围套用：

- `完整前置`：用户要求建 TAPD、提评审，或未特别限定。TAPD 写入与工蜂 MR 是硬性完成项。
- `仅 PRD`：用户明确只要一份 PRD、只梳理需求、不建 TAPD、不提 MR。PRD 实际写入 mono2 `wiki/prd-docs/` 即为完成；TAPD 写入与工蜂 MR 不作为完成门禁，但必须在总结里标为"未触发（用户仅要求 PRD）"。

不确定时按 `完整前置` 处理。

## 完成检查

- 已判断产品输入状态，并在收到初始材料后、详细澄清前完成范围预判；多目标需求已拆分为相互关联、可独立交付和验收的子需求。
- 已完成需求澄清，或用户明确要求跳过澄清。
- 澄清期间每条消息最多只有一个需要用户回答的问题，并在可枚举时优先使用了选择题。
- 对尚未定案的需求，AI 已提出 2-3 个产品方案、说明取舍并给出推荐，用户已选择方案或明确授权按推荐方案继续。
- 对尚未定案的需求，推荐方案已执行 YAGNI，非必要能力已移到“本次不包含”、延后项或后续方向。
- 对需要形成或修订产品输入稿的需求，输入稿已逐步展示并获得确认；发现冲突时已回退澄清，没有把猜测写成既定事实。
- 写入本地 PRD、TAPD 或进入工蜂 MR 前，集中自检未发现占位符、目标链路矛盾、范围过大或未消除的歧义。
- 已将确认后的 PRD 实际写入 mono2 的 `wiki/prd-docs/YYYY-MM-DD-<short-title>.md`；产品原型说明默认包含在同一文件中，并已向用户给出实际路径。
- 已从最新 `origin/master` 准备干净来源分支；存在无关脏改动时使用了独立 worktree，提交范围没有夹带其他文件。
- commit、push 和 MR 创建前已展示文件范围、diff 摘要、Lore commit message、MR 标题/描述和 TAPD 关联，并获得用户明确确认。
- （`完整前置` 适用）已把 PRD 提交到目标为 `master` 的工蜂 MR；创建后已核对真实 MR 编号、来源/目标分支和完整链接，并主动发给用户。仅本地写入、commit 或 push 不算完成。`仅 PRD` 范围下本项不适用，只需确认 PRD 已写入 mono2 并已在总结标注 MR 未触发。
- LightVela 产品输入稿足够进入评审。
- 如果本地无有效 TAPD Token，已按 `tapd-write.md` 向用户索要且仅索要 Token 本身，没有额外追问 TAPD 配置。
- TAPD 写入使用固定 `workspace_id: 10132091`、标题格式 `【产品需求】【LightVela】<标题>`、分类 `LightVela`，创建前已展示最小一行信息。
- PRD 已明确国内站/国际站发布范围；如果无法确认，已把“是否国际站同步发布”写入待确认问题。
- 写入 `description` 前已把 Markdown 转成 HTML 标签，没有留下裸露的 `**`/`##`/`- ` 等符号。
- 创建或更新成功后，已在回复中主动给出 TAPD 详情链接（`detail_link`），不是等用户追问才给。
- 产品父单状态和描述反映当前产品阶段。
- 产物交接建议已经写入 PRD、父单或总结；每个需要交接的方向均说明了承接角色、交付物、依赖、时序和完成标准，不包含产品父单的子需求创建动作。
- 待确认问题和跳过的方向都清楚可见。
