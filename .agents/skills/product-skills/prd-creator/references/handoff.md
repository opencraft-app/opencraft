# Product Artifact Handoff

读取时机：产品已通过，或用户要求整理 PRD 定稿后的后续承接信息时读取本文件。

## 产物交接原则

产品通过后，识别所有需要承接的交接方向。产品侧把产物交接清单写入 PRD 和产品父单，但不代替设计、研发、内容、国际化、合规、QA、发布、运维或运营角色创建执行单。需要持续跟踪时，由对应承接角色或事项负责人按自身流程创建独立执行单或协作单，并回链产品父单。

每个需要交接的方向至少写清：建议承接角色/事项负责人、交付目标、交付物、输入与依赖、时序和上线节点、验收与完成标志、责任人或待确认人。不要只列团队名称，也不要把产物交接写成单纯的“研发交接”。

## 交接方向判断

| 交接方向 | 什么时候需要写入交接建议 | 什么时候通常不需要 |
| --- | --- | --- |
| 设计 / UX | 有新交互、控制台流程变化、新页面状态、文案层级变化，或需要视觉评审 | 纯后端/运行时变化，没有用户可见行为 |
| 前端研发 | 涉及路由、组件、状态、API 客户端、i18n、设置页、Agents 页、工具/专家 UI 或 SDK 驱动的 UI 变化 | 现有 UI 已支持，只是数据变化 |
| 后端 / 运行时研发 | 涉及 Hermes/OpenClaw 命令行为、`acli`、MCP、实例状态、鉴权、配置、`debug/exec`、API 契约或持久化 | 纯前端展示或文案变化 |
| Skill / 内容 / 文档 | 需要新增或修改 skill、prompt、模板、用户指南、新手引导、发布说明或支持手册 | 产品行为不需要用户可见说明 |
| 国内站 / 国际站协作 | 需求涉及 `lightvela.com` 与 `lightvela.ai` 的路由、入口、文案、i18n、图片、metadata、sitemap、SEO/GEO、登录/支付/渠道差异或发布节奏 | 明确为单站内部能力，且另一站无用户可见影响 |
| 安全 / 合规 / 法务 | 涉及权限、隐私、数据跨境、实名、支付、内容规范或对外条款 | 不新增数据、权限、支付、合规或外部承诺 |
| QA / 质量保障 | 涉及跨产品面链路、兼容性、异常恢复、浏览器冒烟、数据迁移或高风险验收 | 低风险改动且已有测试范围足以覆盖 |
| 发布 / 运维 / SRE | 涉及灰度、特性开关、配置迁移、监控告警、容量、回滚或多环境发布 | 不改变部署、配置、容量和运行风险 |
| 运营 / 增长 / 用户支持 | 涉及运营活动、公告、用户教育、渠道、客服话术、指标运营或上线节奏 | 用户无需感知且没有运营、增长或支持动作 |

## 建议后续执行事项标题格式

- `[设计] <产品标题>`
- `[前端] <产品标题>`
- `[后端/运行时] <产品标题>`
- `[Skill/内容/文档] <产品标题>`
- `[国内站/国际站] <产品标题>`
- `[安全/合规] <产品标题>`
- `[QA] <产品标题>`
- `[发布/运维] <产品标题>`
- `[运营/用户支持] <产品标题>`

  - 输入与依赖：
  - 时序和上线节点：
  - 验收与完成标志：
  - 责任人/待确认：

## 后续执行事项描述模板

对应承接角色或事项负责人需要建单时，可参考这个通用描述格式，但产品侧不代创建：

```markdown
## 关联产品需求
- 产品 TAPD：
- PRD：
- 评审结论：

## 承接信息
- 交接方向：
- 建议承接角色/事项负责人：
- 责任人/待确认：

## 交付目标与范围
- 目标：
- 包含：
- 不包含：

## 输入、依赖与时序
- 上游输入：
- 依赖：
- 前后置关系：
- 计划完成/上线节点：

## 交付物与验收
- 交付物：
- 验收标准：
- 完成标志：

## 待确认问题
- 问题 1：
```

如果某个方向、承接角色或责任人不确定，就在父单里标为待确认，不要臆测建单。交接完成后，把建议方向、跳过原因、责任边界、依赖时序、待确认问题和建议后续流程回写到父单。

## 产物交接后的后续推进

- 原始想法、PRD 梳理、产品父单创建：继续使用本技能。
- 项目组内相关角色收到交接后，如果产品目标、范围或验收仍不清楚，回到本技能继续澄清；执行细节使用对应角色的流程或 skill。
- 对应承接角色或事项负责人自行创建独立执行单或协作单后，按各自流程完成评估、排期和执行。
- 只有当交接项已经明确承接角色、交付物、依赖、时序和完成标准时，才进入对应下游执行流程。
