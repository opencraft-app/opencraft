# LightVela 产品前置与需求建单

## 概览

这个技能用于把粗粒度的 LightVela 产品（git@git.woa.com:wisp/mono2.git）输入，整理成可评审的产品需求 PRD 文档、可选的 TAPD 产品父单，以及边界清晰的产物交接清单。

PRD 是本技能的核心产物；产物交接用于说明 PRD 定稿后项目组内相关角色继续评审、实现、发布或运营所需的信息。它只覆盖下游执行前的产品阶段：需求发现、PRD、验收标准、Demo 判断、评审推进和产物交接。

交付范围分两档：用户要求走完整产品前置（建 TAPD、提评审）时，TAPD 父单与工蜂 MR 是完成门禁；用户只要一份 PRD 时，PRD 写入 mono2 即为完成，TAPD 与 MR 按需触发。详见第 8 步与 `references/checklist.md`。

## 什么时候使用

- LightVela 的想法还没有被产品化，不能直接进入研发。
- 用户要求创建 TAPD 产品需求、产品父单、PRD、验收标准或产物交接建议。
- 已有 Issue，但缺少清晰的用户场景、范围、非目标或验收标准。
- 需求涉及 LightVela 的用户可见产品体验，例如 Agent 创建与管理、模型与渠道配置、Skills 安装使用、Agent 人设、自动任务、记忆与云端文件、对话与工作台、诊断及备份恢复、账号套餐与订单，或相关产品文档。
- 需求可能影响国内站 `lightvela.com`、国际站 `lightvela.ai`，或需要判断国际站是否同步上线。

## 什么时候不要使用

- 研发 TAPD 已经有评审通过的需求、接口细节和验收标准。此时交给实现流程或 TAPD 研发流水线技能。
- 请求只是在做代码评审、调试、CI、发布或重构。
- 用户只想了解事实，并没有要求梳理、创建产品需求或准备产物交接。

## 先看上下文

如果当前在代码仓库里工作，先看最近的产品和实现上下文：`AGENTS.md`、`CLAUDE.md`、`DESIGN.md`、相关 `docs/`、关联 Issue/TAPD，以及受影响的 LightVela 文件。

## Reference 路由

只在进入对应阶段时读取 reference，不要一开始全部加载：

- 形成 PRD、判断国内/国际站范围、判断 Demo 或原型需要时，读取 `references/prd-template.md`。
- PRD 定稿后需要创建或更新 TAPD 产品父单时，读取 `references/tapd-write.md`。
- 需要把 PRD 提交到 mono2 工蜂 MR 或推进产品评审时，读取 `references/mr-flow.md`。
- 产品已通过或用户要求整理后续承接信息时，读取 `references/handoff.md`。
- 最终汇报前、异常兜底或需要判断是否可以宣布完成时，读取 `references/checklist.md`。

## 核心原则

- **一次只问一个问题**：每条消息最多包含一个需要用户回答的问题。需要澄清多个主题时，按影响程度逐轮询问。
- **优先使用选择题**：问题存在有限选项时，给出 2-4 个互斥选项、推荐项和简短理由；只有无法安全预设答案时才使用开放式问题。
- **严格执行 YAGNI**：只保留实现当前用户目标和验收标准所必需的能力，把锦上添花、预留扩展和没有证据支持的功能移到“本次不包含”或后续方向。
- **先比较再定方案**：对尚未定案的需求，由 AI 在收敛前提出 2-3 个可行产品方案，说明范围、收益、代价和风险，并明确推荐；用户负责选择、补充或要求修改，不要求用户先自行设计方案。
- **逐步获得确认**：按“澄清摘要 -> 方案选择 -> 产品输入稿”逐步展示和确认，当前阶段未对齐时不要直接进入下一阶段。
- **允许回退澄清**：发现事实冲突、范围不清或方案无法解释时，回到最早的未决问题继续澄清，不要用猜测填补关键产品决策。
- **不代创建执行子单**：产品侧只创建或更新产品父单；设计、研发、内容、QA、发布、运营等后续执行事项由对应承接角色或事项负责人按自身流程创建并回链父单。

## 工作流

### 1. 判断输入状态

- `想法输入`：原始想法、反馈、老板口头需求、用户抱怨或市场信号。
- `来源单转换`：需要分析旧 Issue 或旧 TAPD，并转成新的产品需求。
- `PRD 草稿`：已有 PRD，但还缺 LightVela 专属约束、验收标准或边界。
- `产品已通过`：产品方案已经接受，需要准备产物交接清单；需要独立执行事项时，由对应承接角色或事项负责人按自身流程创建并回链产品父单。
- `下游已就绪`：产品工作和产物交接已经完成，不再继续运行本技能。

如果状态不清楚，只问一个会改变路径的关键问题。状态明确且收到初始材料后、开始详细澄清前，先判断输入是否包含多个可以独立交付、独立验收的产品目标；如果是，先拆成相互关联的子需求，说明关系和建议顺序，并只对第一个子需求继续澄清。

### 2. 需求澄清

在形成产品输入稿、TAPD 写入计划或产品父单之前，必须先做一轮需求澄清，除非用户明确说“跳过澄清”“直接出稿”“只按现有材料转写”。

澄清目标不是长问卷，而是先把产品需求的最小边界对齐清楚：

- 用户是谁：目标用户、使用角色、国内站/国际站、个人/团队。
- 发布站点：本次面向国内站、国际站、双站同步，还是分阶段发布。
- 场景是什么：用户在什么入口、什么时机、为了什么结果使用这个能力。
- 当前卡点：用户现在怎么做，具体卡在哪里，是否有已有反馈、Issue、TAPD、截图、竞品参考或交互原型。
- 成功结果：做完后用户能完成什么，产品希望观测到什么变化。
- 范围边界：本次必须包含什么，明确不包含什么，有哪些不能碰的技术或业务边界。
- 影响面：前端、Hermes/OpenClaw、SkillHub/MCP、SDK/文档/运营、权限/安全/数据是否受影响。
- 约束和优先级：上线时间、灰度要求、兼容要求、风险接受度。

澄清方式按输入清晰度选择：

- 输入很模糊：先问 1 个最关键问题，等待用户回答后再继续。
- 输入中等清晰：先识别 3-5 个关键澄清点，但每条消息只问其中最影响范围的 1 个；优先给出选择项、推荐项和默认假设，收到回答后再问下一个。
- 输入已经较清晰：先输出“需求澄清摘要”，列出已确认事实、默认假设和待确认问题；如果仍有会改变方案的关键问题，只问其中 1 个，否则进入调研和方案探索。

需求澄清摘要格式：

```markdown
## 需求澄清摘要
- 已确认：
- 默认假设：
- 待确认：
- 本轮先按什么范围出稿：
```

执行规则（在“核心原则”一次一问、选择题优先、不虚构已确认事实的基础上，补充澄清阶段专属约束）：

- 不要把“待确认问题”只放到 PRD 末尾就结束；PRD 之前也要先让用户看到澄清摘要或关键问题。
- 如果用户没有回复但要求继续，才可以按默认假设出稿，并在 PRD 中标明这些是假设。
- 如果澄清问题会影响范围、数据、权限、状态流、发布站点或 TAPD 写入，不要跳过。

### 3. 做 LightVela 调研分层

先按复杂度决定要补到什么程度，不要所有需求都走重流程。

| 类型 | 适用场景 | 必补内容 | 可选内容 |
| --- | --- | --- | --- |
| 轻量需求 | 文案、入口、状态展示、小范围配置、已有页面上的小交互 | 需求背景、目标用户、目标、范围/非目标、验收标准 | 简单流程图、截图标注 |
| 标准需求 | 新增或调整控制台流程、安装链路、工具/专家体验、MCP 或 SDK 可见行为 | 轻量需求全部内容、用户场景、影响面、依赖、异常/空态、发布与观测 | Demo、数据/接口约束 |
| 复杂需求 | 跨 `/agents`、Hermes/OpenClaw、SkillHub、MCP、SDK、权限、发布或运营多面协同 | 标准需求全部内容、调研结论、替代方案、风险、灰度/回滚、产物交接建议、评审材料 | 用户访谈、竞品/内部替代方案分析、指标口径 |

调研输出不需要长篇论文，但必须回答三个问题：谁在什么场景卡住了；这次解决到什么边界；怎么判断做完。

### 3.1 国内站 / 国际站发布范围判断

任何用户可见产品需求都必须在 PRD 中写清楚站点范围，不要默认双站同步，也不要默认只做国内站。详细判断表、拆单规则和站点字段见 `references/prd-template.md`。

站点范围不明确时，优先问这一个关键问题：

```markdown
这个需求本次是只做国内站 lightvela.com、只做国际站 lightvela.ai、双站同步，还是先一站灰度后再同步？
```

如果用户要求先出稿但没回答，PRD 中把发布范围标为“待确认”，并把“是否国际站同步发布”放入待确认问题；不要在验收标准里假设已经双站同步。

### 3.2 方案探索与收敛

- 对 `想法输入`、`来源单转换` 和方案尚未定稿的 `PRD 草稿` 执行本环节；`产品已通过` 或 `下游已就绪` 不要为了满足流程而重新打开方案决策，除非发现关键事实冲突。
- 在形成产品输入稿前，由 AI 提出 2-3 个可行产品方案；即使需求简单，也要用简短版本完成比较。
- 先展示推荐方案，再展示其他方案。每个方案至少说明：解决路径、包含范围、用户体验、主要代价或风险。
- 至少包含一个满足当前目标的最小方案。没有明确证据支持的扩展能力不要塞进推荐方案。
- 方案比较结束时只问一个选择问题，例如“建议按方案 A 推进，是否以此形成产品输入稿？”。
- 用户未确认时不要把某个方案写成既定事实；如果用户明确要求继续，则按推荐方案出稿，并把未确认部分标为默认假设。

### 4. 形成产品输入稿

进入本步骤前读取 `references/prd-template.md`，按其中模板形成 PRD。产品输入稿必须基于用户已选择的方案，或用户已明确授权按推荐方案继续。

轻量需求可以一次展示完整输入稿；标准和复杂需求按“问题/目标/范围”“方案/流程/状态”“验收/发布/产物交接”分段展示，每段后只问一个确认问题。收到修改意见时先修订当前部分，确认后再继续；产品输入稿未确认前不要进入 TAPD 写入。

### 5. 判断是否需要 Demo、原型或交互评审稿

PRD 草稿完成后，按 `references/prd-template.md` 判断是否需要 Demo、原型或交互评审稿。默认情况下直接输出 Demo，不输出交互设计稿或者原型设计稿；仅当前项目明确要求时才补交互设计稿或原型设计稿链接。

### 6. 自动准备 TAPD 环境并写入

PRD 定稿后，如果用户需要 TAPD 产品父单，读取 `references/tapd-write.md`。TAPD 环境准备全部由 AI 自动静默完成；在本阶段，唯一需要打扰用户的动作是索要 TAPD 个人 Token（仅当本地没有有效 Token 时才问）。后续工蜂鉴权与不可逆操作确认按第 8 步处理。

### 7. 创建或复用产品父单

按 `references/tapd-write.md` 创建或更新产品父单。父单描述保持为产品事实源：PRD、评审记录、产物交接建议和未解决问题都放在这里。产品父单必须写明发布站点与同步策略。

### 8. 提交 PRD 到工蜂 MR

**先判断本次交付范围**：

- `完整前置`（用户要求建 TAPD、提评审、走完整产品前置，或未特别限定）：PRD 已定稿、Demo/原型说明已补齐且 TAPD 父单已创建或复用后，读取 `references/mr-flow.md`，把 PRD 提交到 mono2 远端工蜂仓库的 MR。此时工蜂 MR 是完成门禁；仅写出本地 Markdown、仅创建 TAPD、仅提交 commit 或仅 push 分支都不算完整落库。
- `仅 PRD`（用户明确只要一份 PRD、只梳理需求、不建 TAPD、不提 MR）：PRD 实际写入 mono2 `product/prd/YYYY-MM-DD-<short-title>.md` 并返回路径即视为完成，不强制创建 TAPD 或工蜂 MR。在完成总结里把 TAPD、工蜂 MR 标为"未触发（用户仅要求 PRD）"，并说明后续如需评审可再走完整前置。

不确定属于哪种范围时，按 `完整前置` 处理，但可在进入 MR 前用一个选择题向用户确认是否需要建 TAPD / 提评审。

### 9. 推进产品评审

按 `references/mr-flow.md` 推进评审状态。产品完成只表示产品前置阶段完成，不表示功能已经上线。

### 10. 准备产物交接建议

产品通过后，读取 `references/handoff.md`，识别所有需要承接的交接方向。产物交接清单写入 PRD 和产品父单，但不代替设计、研发、内容、国际化、合规、QA、发布、运维或运营角色创建执行单。

## 完成前

最终汇报前读取 `references/checklist.md`：

- 按完成输出格式汇报。
- 遇到异常时按异常处理兜底。
- 对照完成检查判断是否可以宣布“LightVela 产品前置完成”。
