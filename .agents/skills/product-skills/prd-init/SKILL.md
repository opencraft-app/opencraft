# LightVela 产品需求建单

## 概览

这个技能用于把粗粒度的 LightVela 产品（git@git.woa.com:wisp/mono2.git）输入，整理成可评审的产品需求、落在 mono2 仓库的 Markdown PRD、可选的 TAPD 产品父单，以及边界清晰的研发交接建议。它只覆盖研发前的产品阶段：需求发现、PRD、验收标准、原型判断、评审推进和研发交接。

## 什么时候使用

- LightVela 的想法还没有被产品化，不能直接进入研发。
- 用户要求创建 TAPD 产品需求、产品父单、PRD、验收标准或研发交接建议。
- 已有 TAPD 或 Issue，但缺少清晰的用户场景、范围、非目标或验收标准。
- 需求影响 `/agents`、设置页、专家/工具、Hermes Agent 运行时、SkillHub 底层 API、MCP 工具、诊断、SDK 流程、记忆/配置或新手引导等产品面。

## 什么时候不要使用

- 研发 TAPD 已经有评审通过的需求、接口细节和验收标准。此时交给实现流程或 TAPD 研发流水线技能。
- 请求只是在做代码评审、调试、CI、发布或重构。
- 用户只想了解事实，并没有要求梳理、创建产品需求或准备研发交接。

## 先看上下文

如果当前在代码仓库里工作，先看最近的产品和实现上下文：`AGENTS.md`、`DESIGN.md`、相关 `docs/`、关联 Issue/TAPD，以及受影响的 LightVela 文件。

## 工作流

### 1. 判断输入状态

- `想法输入`：原始想法、反馈、老板口头需求、用户抱怨或市场信号。
- `来源单转换`：需要分析旧 Issue 或旧 TAPD，并转成新的产品需求。
- `PRD 草稿`：已有 PRD，但还缺 LightVela 专属约束、验收标准或边界。
- `产品已通过`：产品方案已经接受，需要准备研发交接建议；如果研发同学需要技术需求单，由研发自行创建独立需求单。
- `研发已就绪`：产品工作已经完成，不再继续运行本技能。

如果状态不清楚，只问一个会改变路径的关键问题。否则先进入需求澄清。只有当需求边界已经足够清楚，或用户明确要求“继续出稿”“按这些假设出稿”“跳过澄清”时，才产出 `product/prd/` 下的 PRD Markdown 草稿。TAPD 需求单是用户确认后的可选动作，不是默认必选动作。

### 2. 需求澄清

在形成产品输入稿、PRD Markdown、TAPD 写入计划或产品父单之前，必须先做一轮需求澄清，除非用户明确说“跳过澄清”“直接出稿”“只按现有材料转写”。

不要把用户只给出的页面、模块或方向当成已经确定的功能需求。例如“优化 `/agents/experts`”“优化技能包功能”“优化设置页体验”只说明了对象，不说明要做什么功能；此时必须先请用户用一句话描述真实需求，不能自行扩写成安装确认、状态筛选、卸载、重试、推荐、管理分组等方案，也不要先给一组推荐功能选项。

澄清目标不是长问卷，而是先把产品需求的最小边界对齐清楚：

- 具体功能是什么：本次要新增、优化、删除或调整哪个用户可见能力。
- 用户是谁：目标用户、使用角色、国内站/国际站、个人/团队。
- 场景是什么：用户在什么入口、什么时机、为了什么结果使用这个能力。
- 当前卡点：用户现在怎么做，具体卡在哪里，是否有已有反馈、Issue、TAPD 或截图。
- 成功结果：做完后用户能完成什么，产品希望观测到什么变化。
- 范围边界：本次必须包含什么，明确不包含什么，有哪些不能碰的技术或业务边界。
- 影响面：前端、Hermes Agent、SkillHub 底层 API/MCP、SDK/文档/运营、权限/安全/数据是否受影响。
- 约束和优先级：上线时间、灰度要求、兼容要求、风险接受度。

澄清方式按输入清晰度选择：

- 输入很模糊，或只给了页面、模块、方向：先请用户用一句话简单描述这次想解决什么问题或新增什么能力，等待用户回答后再继续。
- 输入中等清晰：围绕用户的一句话需求列出 3-5 个关键澄清点；可以给默认假设，但不要把默认假设伪装成推荐路线。
- 输入已经较清晰：先输出“需求澄清摘要”，列出已确认事实、默认假设、待确认问题，再基于该摘要生成 PRD 草稿。

功能未明确时的优先问题：

```markdown
请先用一句话描述这次想做的具体需求：用户现在遇到什么问题，或你希望新增/优化什么能力？
```

拿到这句话之前，不列功能选项、不推荐范围、不输出方案。拿到一句话需求后，才可以基于用户原话、现有实现和已知反馈展开澄清问题；选项只能用于收窄用户已经描述过的方向，不能替用户发明需求。

需求澄清摘要格式：

```markdown
## 需求澄清摘要
- 已确认：
- 默认假设：
- 待确认：
- 本轮先按什么范围出稿：
```

执行规则：

- 页面或模块名不是功能边界。只知道对象时，只请求用户先用一句话描述需求后停止，不创建 PRD、不写 TAPD 计划、不补完整方案、不列推荐功能选项。
- 不要把“待确认问题”只放到 PRD 末尾就结束；PRD 之前也要先让用户看到澄清摘要或关键问题。
- 如果用户没有回复但要求继续，才可以按默认假设出稿，并在 PRD 中标明这些是假设；如果用户没有要求继续，就停在澄清。
- 如果澄清问题会影响范围、数据、权限、状态流、PRD 落地或 TAPD 写入，不要跳过。
- 对低风险文案、小入口、已有 PRD 修补类需求，可以只做一段简短澄清摘要，但仍要显式出现。
- 不要把调研时看到的现有能力直接升级成需求范围；现有实现只能在用户给出一句话需求后，作为澄清问题或背景证据。

### 3. 做 LightVela 调研分层

先按复杂度决定要补到什么程度，不要所有需求都走重流程。

| 类型 | 适用场景 | 必补内容 | 可选内容 |
| --- | --- | --- | --- |
| 轻量需求 | 文案、入口、状态展示、小范围配置、已有页面上的小交互 | 来源、目标用户、当前问题、目标状态、范围/非目标、验收标准 | 简单流程图、截图标注 |
| 标准需求 | 新增或调整控制台流程、安装链路、工具/专家体验、MCP 或 SDK 可见行为 | 轻量需求全部内容、用户场景、影响面、依赖、异常/空态、发布与观测 | 交互草图、数据/接口约束 |
| 复杂需求 | 跨 `/agents`、Hermes Agent、SkillHub 底层 API、MCP、SDK、权限、发布或运营多面协同 | 标准需求全部内容、调研结论、替代方案、风险、灰度/回滚、研发交接建议、评审材料 | 用户访谈、竞品/内部替代方案分析、指标口径 |

调研输出不需要长篇论文，但必须回答三个问题：谁在什么场景卡住了；这次解决到什么边界；怎么判断做完。

### 4. 形成产品输入稿并落地 PRD Markdown

按这个结构整理：

```markdown
# <产品需求标题>

## 来源
- 需求来源：
- 相关链接：
- 提出人/干系人：

## 背景与问题
- 当前用户怎么做：
- 现在卡在哪里：
- 为什么现在要做：

## 目标用户与场景
- 目标用户：
- 典型场景：
- 频率和重要性：

## 目标
- 用户结果：
- 产品结果：
- 不做会怎样：

## 范围
- 本次包含：
- 本次不包含：
- 已知依赖：

## LightVela 影响面
- 前端页面/路由：
- Hermes Agent/运行时：
- SkillHub 底层 API/MCP/工具：
- SDK/文档/运营：
- 权限/安全/数据：

## 方案
- 交互或流程：
- 状态变化：
- 数据或接口：
- 异常和空态：

## 验收标准
- 验收 1：
- 验收 2：
- 验收 3：

## 发布与观测
- 灰度/开关：
- 日志/埋点/指标：
- 回滚：

## 待确认问题
- 问题 1：
```

PRD 草稿必须优先以 Markdown 文件落到 mono2 仓库的 `product/prd/` 目录下，建议路径为：

```text
product/prd/<yyyy-mm-dd>-<short-title>.md
```

文件名用短横线连接，标题要能看出产品意图，例如 `product/prd/2026-06-30-agents-skill-uninstall.md`。如果当前工作区不是 mono2 仓库，先说明建议落地路径，并把完整 Markdown 内容产出给用户；不要因为暂时无法写文件就跳过 PRD。

PRD Markdown 是后续评审、TAPD 描述和研发交接的事实源。除非用户明确要求直接整理 TAPD 字段，否则不要先创建 TAPD 再回补 PRD。

### 5. 判断是否需要产品原型

PRD 草稿完成后，先判断是否需要原型或交互评审稿。这里不要沿用 BKUI 原型，除非当前项目明确要求；默认产出适合 LightVela 的页面结构、状态和交互说明。

需要原型的场景：

- 新增或重构页面、设置项、弹窗、抽屉、列表、详情、安装流程或诊断流程。
- 产品、设计、前端需要在研发评估前确认页面结构、主路径、异常状态或空态。
- 涉及 `/agents`、专家/工具卡片、SkillHub 底层 API 调用、Hermes Agent 命令反馈、MCP 权限提示等用户可见流程。
- PRD 中存在多个状态或跨页面跳转，仅靠文字容易误解。

可跳过原型的场景：

- 纯后端/运行时能力，没有用户可见行为。
- 纯文案或配置调整，不改变页面结构和交互路径。
- 已有可复用设计稿、截图或线上页面，且本次只是小幅扩展。

需要原型时，在产品输入稿后补这一段：

```markdown
## 产品原型说明
- 目标页面/入口：
- 用户主路径：
- 页面结构：
- 关键组件：
- 状态：加载 / 空态 / 错误 / 禁用 / 权限不足
- 主要操作：
- 需要设计确认：
- 需要前端确认：
```

跳过原型时，也要在父单或 PRD 中写明跳过原因。

### 6. 询问是否需要创建或更新 TAPD

PRD Markdown 准备好后，先向用户展示 PRD 路径和摘要，再询问是否需要同步创建或更新 TAPD 产品需求单。用户可以选择：

- `只保留 PRD`：本轮不写 TAPD，只输出 PRD 路径、摘要、待确认问题和下一步建议。
- `创建 TAPD`：进入 TAPD 字段发现和写入计划。
- `更新已有 TAPD`：读取已有 TAPD 后，用 PRD Markdown 内容更新描述或状态。

用户没有明确选择前，不创建、不更新、不流转 TAPD。

### 7. 准备 TAPD 写入

用户选择创建或更新 TAPD 后，先完成这些动作：

- 发现当前工作区、分类、必填字段和状态值。
- 把实际状态映射到 backlog（待办）、评审中、已通过、产品完成等概念状态。
- 准备精确的标题、描述、字段、父子关系和状态流转。
- 把写入计划展示给用户，并拿到明确确认。

写入计划格式：

```markdown
## TAPD 写入计划
- 动作：创建 | 更新 | 流转状态
- 工作区：
- 产品父单：
- PRD Markdown：
- 分类：
- 目标状态：
- 标题：
- 必填字段：
- 描述来源：
- 研发交接建议：
- 假设：
- 不写入时的替代方案：
```

没有确认就不写 TAPD。如果 TAPD MCP 不可用，返回本地 PRD、建议字段和手动建单步骤。不要硬编码历史项目里的工作区 ID、分类 ID 或状态字符串，除非本轮已经验证过。

推荐创建产品父单 payload 模板：

```yaml
workspace_id: <本轮发现的工作区 ID>
name: <产品需求标题>
description: <PRD Markdown 正文摘要 + 原型说明 + 待确认问题 + PRD 路径>
with_v_status: "1"
v_status: <backlog 等价状态>
owner: <产品负责人或当前处理人>
creator: <当前处理人>
priority_label: <High|Middle|Low，按项目约定>
category_id: <本轮发现的分类 ID，如项目要求>
```

推荐更新父单 payload 模板：

```yaml
workspace_id: <本轮发现的工作区 ID>
id: <产品父单 ID>
description: <更新后的 PRD Markdown 摘要、评审结论、研发交接建议、跳过原因>
with_v_status: "1"
v_status: <目标状态：评审中 / 已通过 / 产品完成的等价状态>
```

推荐研发交接说明模板：

```markdown
## 研发交接建议
- 前端关注点：
- 后端/运行时关注点：
- Skill/内容/文档关注点：
- QA/发布/运营关注点：
- 建议研发自行创建的独立技术需求单：
  - 标题：
  - 范围：
  - 依赖：
  - 验收：
  - 备注：此单不作为产品父单的子需求创建
```

产品侧不创建前端、后端或 QA 子需求单，也不写 `parent_id` 子单关系。如果研发需要跟踪实现，可以由对应研发同学基于这份交接建议自行创建独立技术需求单。

这些模板只是写入形状。实际字段以本轮 TAPD 字段发现结果为准；项目没有的字段不要硬填，项目必填但模板没有的字段必须补上。

### 8. 创建或复用产品父单

- 如果已有父单，先读取它的实际字段和状态，再从当前状态继续。
- 如果没有父单，并且用户确认创建，就以 backlog（待办）等价状态创建。
- PRD Markdown 保持为产品事实源；父单描述同步 PRD 摘要、PRD 路径、评审记录、研发交接建议和未解决问题。
- PRD 和验收标准要写进 Markdown 文件，并在 TAPD 描述里保留摘要和路径，不只留在聊天记录。
- 避免使用 `<value>` 这类占位包裹，它可能被 TAPD 富文本处理吞掉。

### 9. 推进产品评审

当 PRD 和验收标准准备好后：

- 先更新 `product/prd/` 下的 PRD Markdown。
- 如果用户选择使用 TAPD，再更新父单描述。
- 用户确认后，把父单移动到评审中等价状态。
- 产品评审通过后，再移动到已通过等价状态。

产品完成只表示产品前置阶段完成，不表示功能已经上线。

### 10. 准备研发交接建议

产品通过后，不创建前端、后端、QA 或文档子需求单。产品侧只在产品父单里整理研发交接建议，说明哪些方向可能需要研发自行创建独立技术需求单。

| 方向 | 什么时候需要写入交接建议 | 什么时候通常不需要 |
| --- | --- | --- |
| 设计 / UX | 有新交互、控制台流程变化、新页面状态、文案层级变化，或需要视觉评审 | 纯后端/运行时变化，没有用户可见行为 |
| 前端 | 涉及路由、组件、状态、API 客户端、i18n、设置页、Agents 页、工具/专家 UI 或 SDK 驱动的 UI 变化 | 现有 UI 已支持，只是数据变化 |
| 后端 / 运行时 | 涉及 Hermes Agent 命令行为、SkillHub 底层 API、`acli`、MCP、实例状态、鉴权、配置、`debug/exec`、API 契约或持久化 | 纯前端展示或文案变化 |
| Skill / 内容 / 文档 | 需要新增或修改 skill、prompt、模板、用户指南、新手引导、发布说明或支持手册 | 产品行为不需要用户可见说明 |
| QA / 发布 / 运营 | 涉及跨产品面发布、迁移、特性开关、观测、回滚、浏览器冒烟或高风险链路验证 | 小范围改动可由研发技术需求单自行覆盖 |

建议独立技术需求单标题格式：

- `[设计] <产品标题>`
- `[前端] <产品标题>`
- `[后端] <产品标题>`
- `[Skill/文档] <产品标题>`
- `[QA/发布] <产品标题>`

研发同学需要建单时，可参考这个描述格式，但产品侧不代创建：

```markdown
## 关联产品需求
- 产品 TAPD：
- PRD：
- 评审结论：

## 技术范围
- 包含：
- 不包含：
- 依赖：

## 方案要点
- 关键路径：
- 数据/接口/状态：
- 异常和空态：

## 验收标准
- 验收 1：
- 验收 2：
- 验收 3：

## 交付物
- 代码/设计/文档：
- 验证方式：

## 待确认问题
- 问题 1：
```

如果某个方向不确定，就在父单里标为待确认，不要臆测创建技术需求单。交接完成后，把建议方向、跳过原因、待确认问题和建议下游流程回写到父单。

## 下游交接

- 原始想法、PRD 梳理、产品父单创建：继续使用本技能。
- 已有研发需求但还需要澄清，需使用研发自己的 skill。
- 研发同学自行创建独立技术需求单后，需要评估或排期，需使用研发自己的 skill。
- 只有当独立技术需求单已经有清晰验收标准和依赖时，才进入实现流程。

## 完成输出格式

产品前置结束时，用这个格式汇报：

```markdown
## LightVela 产品前置完成

| 项目 | 结果 |
| --- | --- |
| 输入状态 | 想法输入 / 来源单转换 / PRD 草稿 / 产品已通过 / 研发已就绪 |
| 产品父单 | #xxx，当前状态 |
| 产品文档 | product/prd/xxx.md / 未落地：原因 |
| 产品原型 | 已生成：位置 / 未生成：跳过原因 |
| TAPD 写入 | 已创建/已更新/用户选择不创建/未写入：原因 |
| 研发交接建议 | 已整理：方向 / 未整理：原因 |
| 建议独立技术需求单 | 前端 / 后端运行时 / Skill 文档 / QA 发布 / 无 |
| 待确认问题 | 列出问题或“无” |
| 下一步 | 进入澄清 / 评估 / 迭代规划 / 实现 |
```

如果用户选择不创建 TAPD，不需要输出手动建单步骤，只说明 PRD 路径、后续可选建单时需要的信息。如果用户想建但因 TAPD MCP 不可用而没有实际写入，再把“建议标题、建议字段、建议描述、手动建单步骤”放在总结后面。

## 异常处理

- TAPD MCP 不可用：保留 `product/prd/` 下的 PRD Markdown；如果用户仍要建单，再输出 TAPD 标题、描述、字段和手动操作步骤。
- 工作区 / 分类 / 状态未知：先检查或只问这一个配置问题，再写入。
- TAPD 必填字段缺失：创建或更新前停止，并列出缺失字段。
- 富文本写入失败：用更简单的 markdown 或纯文本重试，同时保留链接和验收标准。
- 用户要求创建研发子单：说明 LightVela 产品前置不创建子需求单，改为输出独立技术需求单建议，由研发同学自行建单。

## 完成检查

- 已判断产品输入状态。
- 已完成需求澄清，或用户明确要求跳过澄清。
- LightVela 产品输入稿足够进入评审。
- PRD Markdown 已落到 `product/prd/`，或已说明未落地原因并输出完整内容。
- 已询问用户是否需要创建或更新 TAPD。
- 如果有 TAPD 写入，已经拿到明确确认。
- 产品父单状态和描述反映当前产品阶段；如果用户选择不创建 TAPD，最终总结要明确说明。
- 研发交接建议已经写入父单或总结，不包含产品父单的子需求创建动作。
- 待确认问题和跳过的方向都清楚可见。
