# LightVela 产品前置与需求建单

## 概览

这个技能用于把粗粒度的 LightVela 产品（git@git.woa.com:wisp/mono2.git）输入，整理成可评审的产品需求、可选的 TAPD 产品父单，以及边界清晰的研发交接建议。它只覆盖研发前的产品阶段：需求发现、PRD、验收标准、原型判断、评审推进和研发交接。

## 什么时候使用

- LightVela 的想法还没有被产品化，不能直接进入研发。
- 用户要求创建 TAPD 产品需求、产品父单、PRD、验收标准或研发交接建议。
- 已有 TAPD 或 Issue，但缺少清晰的用户场景、范围、非目标或验收标准。
- 需求影响 `/agents`、设置页、专家/工具、Hermes/OpenClaw 运行时、SkillHub、MCP 工具、诊断、SDK 流程、记忆/配置或新手引导等产品面。
- 需求可能影响国内站 `lightvela.com`、国际站 `lightvela.ai`，或需要判断国际站是否同步上线。

## 什么时候不要使用

- 研发 TAPD 已经有评审通过的需求、接口细节和验收标准。此时交给实现流程或 TAPD 研发流水线技能。
- 请求只是在做代码评审、调试、CI、发布或重构。
- 用户只想了解事实，并没有要求梳理、创建产品需求或准备研发交接。

## 先看上下文

如果当前在代码仓库里工作，先看最近的产品和实现上下文：`AGENTS.md`、`CLAUDE.md`、`DESIGN.md`、相关 `docs/`、关联 Issue/TAPD，以及受影响的 LightVela 文件。

## 核心原则

- **一次只问一个问题**：每条消息最多包含一个需要用户回答的问题。需要澄清多个主题时，按影响程度逐轮询问。
- **优先使用选择题**：问题存在有限选项时，给出 2-4 个互斥选项、推荐项和简短理由；只有无法安全预设答案时才使用开放式问题。
- **严格执行 YAGNI**：只保留实现当前用户目标和验收标准所必需的能力，把锦上添花、预留扩展和没有证据支持的功能移到“本次不包含”或后续方向。
- **先比较再定方案**：对尚未定案的需求，由 AI 在收敛前提出 2-3 个可行产品方案，说明范围、收益、代价和风险，并明确推荐；用户负责选择、补充或要求修改，不要求用户先自行设计方案。
- **逐步获得确认**：按“澄清摘要 -> 方案选择 -> 产品输入稿”逐步展示和确认，当前阶段未对齐时不要直接进入下一阶段。
- **允许回退澄清**：发现事实冲突、范围不清或方案无法解释时，回到最早的未决问题继续澄清，不要用猜测填补关键产品决策。

## 工作流

### 1. 判断输入状态

- `想法输入`：原始想法、反馈、老板口头需求、用户抱怨或市场信号。
- `来源单转换`：需要分析旧 Issue 或旧 TAPD，并转成新的产品需求。
- `PRD 草稿`：已有 PRD，但还缺 LightVela 专属约束、验收标准或边界。
- `产品已通过`：产品方案已经接受，需要准备研发交接建议；如果研发同学需要技术需求单，由研发自行创建独立需求单。
- `研发已就绪`：产品工作已经完成，不再继续运行本技能。

如果状态不清楚，只问一个会改变路径的关键问题。否则进入需求澄清环节。不要因为能猜到大致方向就直接输出需求单。
### 2. 需求澄清

在形成产品输入稿、TAPD 写入计划或产品父单之前，必须先做一轮需求澄清，除非用户明确说“跳过澄清”“直接出稿”“只按现有材料转写”。

澄清目标不是长问卷，而是先把产品需求的最小边界对齐清楚：

- 用户是谁：目标用户、使用角色、国内站/国际站、个人/团队。
- 发布站点：本次面向国内站、国际站、双站同步，还是分阶段发布。
- 国际站同步判断：如果只提到国内站，必须确认国际站是否同步；如果只提到国际站，必须确认国内站是否不做或后续再做。
- 场景是什么：用户在什么入口、什么时机、为了什么结果使用这个能力。
- 当前卡点：用户现在怎么做，具体卡在哪里，是否有已有反馈、Issue、TAPD 或截图。
- 成功结果：做完后用户能完成什么，产品希望观测到什么变化。
- 范围边界：本次必须包含什么，明确不包含什么，有哪些不能碰的技术或业务边界。
- 影响面：前端、Hermes/OpenClaw、SkillHub/MCP、SDK/文档/运营、权限/安全/数据是否受影响。
- 约束和优先级：上线时间、灰度要求、兼容要求、风险接受度。

澄清方式按输入清晰度选择：

- 输入很模糊：先问 1 个最关键问题，等待用户回答后再继续。
- 输入中等清晰：先识别 3-5 个关键澄清点，但每条消息只问其中最影响范围的 1 个；优先给出选择项、推荐项和默认假设，收到回答后再问下一个。
- 输入已经较清晰：先输出“需求澄清摘要”，列出已确认事实、默认假设和待确认问题；如果仍有会改变方案的关键问题，只问其中 1 个，否则进入调研和方案探索。

需求澄清摘要格式：

```markdown
## 需求澄清摘要
- 已确认：
- 默认假设：
- 待确认：
- 本轮先按什么范围出稿：
```

执行规则：

- 每条消息只能出现一个需要用户作答的问题，不要把多个问号、问题清单或表格问卷塞进同一轮。
- 能用选择题表达时，不要先抛宽泛开放题；推荐项必须说明依据，不能替用户虚构已确认事实。
- 不要把“待确认问题”只放到 PRD 末尾就结束；PRD 之前也要先让用户看到澄清摘要或关键问题。
- 如果用户没有回复但要求继续，才可以按默认假设出稿，并在 PRD 中标明这些是假设。
- 如果澄清问题会影响范围、数据、权限、状态流或 TAPD 写入，不要跳过。
- 对低风险文案、小入口、已有 PRD 修补类需求，可以只做一段简短澄清摘要，但仍要显式出现。

### 3. 做 LightVela 调研分层

先按复杂度决定要补到什么程度，不要所有需求都走重流程。

| 类型 | 适用场景 | 必补内容 | 可选内容 |
| --- | --- | --- | --- |
| 轻量需求 | 文案、入口、状态展示、小范围配置、已有页面上的小交互 | 来源、目标用户、当前问题、目标状态、范围/非目标、验收标准 | 简单流程图、截图标注 |
| 标准需求 | 新增或调整控制台流程、安装链路、工具/专家体验、MCP 或 SDK 可见行为 | 轻量需求全部内容、用户场景、影响面、依赖、异常/空态、发布与观测 | 交互草图、数据/接口约束 |
| 复杂需求 | 跨 `/agents`、Hermes/OpenClaw、SkillHub、MCP、SDK、权限、发布或运营多面协同 | 标准需求全部内容、调研结论、替代方案、风险、灰度/回滚、研发交接建议、评审材料 | 用户访谈、竞品/内部替代方案分析、指标口径 |

调研输出不需要长篇论文，但必须回答三个问题：谁在什么场景卡住了；这次解决到什么边界；怎么判断做完。

### 3.1 国内站 / 国际站发布范围判断

LightVela 同时有国内站 `lightvela.com` 和国际站 `lightvela.ai`。任何用户可见产品需求都必须在 PRD 中写清楚站点范围，不要默认双站同步，也不要默认只做国内站。

先按以下四类判断：

| 发布类型 | 适用情况 | 产品处理 |
| --- | --- | --- |
| 国内站 only | 需求依赖国内登录、实名、支付、微信/企微、国内运营活动、国内合规或国内专属渠道 | PRD 写明国际站不本次同步，并给出原因；若未来可能同步，列入待确认或后续需求 |
| 国际站 only | 需求面向海外用户、英文/zh-sg 文档、国际 SEO/GEO、海外渠道、国际支付/登录或 `lightvela.ai` 独立体验 | PRD 写明国内站不本次同步或后续评估；必要时联动 `lv-international-docs`、`lv-seo-geo` |
| 双站同步 | 用户价值、交互、权限、数据和技术依赖基本一致，只需要文案/i18n/图片/metadata 差异 | 可以用一个产品父单覆盖双站，但必须列出中英文内容、路由、SEO/GEO、灰度和验收差异 |
| 分阶段发布 | 目标一致但两站依赖、审核、内容、运营或风险不同，需要不同上线节奏 | 用一个父单写总体目标和阶段策略；如果两站范围或验收差异较大，建议拆成两个关联产品父单 |

拆单建议：

- 一个父单：目标用户和产品行为一致，只是语言、文案、图片、metadata 或轻量入口差异。
- 两个关联父单：国内站和国际站的目标用户、合规/支付/登录、渠道、上线节奏、验收标准或运营目标明显不同。
- 不要创建前端/后端/QA 子单；若拆单，只拆产品父单或在研发交接里建议研发自行建独立技术需求单。

站点范围不明确时，优先问这一个关键问题：

```markdown
这个需求本次是只做国内站 lightvela.com、只做国际站 lightvela.ai、双站同步，还是先一站灰度后再同步？
```

如果用户要求先出稿但没回答，PRD 中把发布范围标为“待确认”，并把“是否国际站同步发布”放入待确认问题；不要在验收标准里假设已经双站同步。

**方案探索与收敛：**

- 对 `想法输入`、`来源单转换` 和方案尚未定稿的 `PRD 草稿` 执行本环节；`产品已通过` 或 `研发已就绪` 不要为了满足流程而重新打开方案决策，除非发现关键事实冲突。
- 在形成产品输入稿前，由 AI 提出 2-3 个可行产品方案；即使需求简单，也要用简短版本完成比较。
- 先展示推荐方案，再展示其他方案。每个方案至少说明：解决路径、包含范围、用户体验、主要代价或风险。
- 至少包含一个满足当前目标的最小方案。没有明确证据支持的扩展能力不要塞进推荐方案。
- 方案比较结束时只问一个选择问题，例如“建议按方案 A 推进，是否以此形成产品输入稿？”。
- 用户未确认时不要把某个方案写成既定事实；如果用户明确要求继续，则按推荐方案出稿，并把未确认部分标为默认假设。
- 如果任何方案都解释不通、约束互相冲突或用户否定了共同前提，回到需求澄清，每轮只补一个关键问题。

产品输入稿必须基于用户已选择的方案，或用户已明确授权按推荐方案继续。轻量需求可以一次展示完整输入稿；标准和复杂需求按“问题/目标/范围”“方案/流程/状态”“验收/发布/观测”分段展示，每段后只问一个确认问题。收到修改意见时先修订当前部分，确认后再继续；产品输入稿未确认前不要进入 TAPD 写入。

**文档输出约定：**

- LightVela 的代码仓库是 mono2。产品输入稿确认后，必须实际写入 `<mono2-repo-root>/product/prd/YYYY-MM-DD-<short-title>.md`，不要只停留在聊天内容或 TAPD 描述草稿里。
- 如果当前工作目录已经是 mono2 仓库根目录，使用相对路径 `product/prd/YYYY-MM-DD-<short-title>.md`；不要再额外创建一层 `mono2/` 目录。
- `YYYY-MM-DD` 使用文档首次创建日期，`<short-title>` 使用稳定、简短、可读的需求标识。修改已有 PRD 时更新原文件，不要仅因日期变化重复创建。
- `product/prd/` 不存在时创建该目录。不要再把 LightVela PRD 写入 `docs/reqs/lightvela/`。
- 产品输入稿、方案决策、验收标准、产品原型说明和待确认问题默认保存在同一份 Markdown PRD 中；单独的设计稿或图片只在确有产物时由 PRD 链接引用。
- 写入后在回复中给出实际文件路径，再进入后续 TAPD 环节。

### 5. 判断是否需要产品原型

PRD 草稿完成后，先判断是否需要原型或交互评审稿。这里不要沿用 BKUI 原型，除非当前项目明确要求；默认产出适合 LightVela 的页面结构、状态和交互说明。

需要原型的场景：

- 新增或重构页面、设置项、弹窗、抽屉、列表、详情、安装流程或诊断流程。
- 产品、设计、前端需要在研发评估前确认页面结构、主路径、异常状态或空态。
- 涉及 `/agents`、专家/工具卡片、SkillHub 安装、Hermes 命令反馈、MCP 权限提示等用户可见流程。
- PRD 中存在多个状态或跨页面跳转，仅靠文字容易误解。

可跳过原型的场景：

- 纯后端/运行时能力，没有用户可见行为。
- 纯文案或配置调整，不改变页面结构和交互路径。
- 已有可复用设计稿、截图或线上页面，且本次只是小幅扩展。

需要原型时，在产品输入稿后补这一段：

```markdown
## 产品原型说明
- 目标页面/入口：
- 用户主路径：
- 页面结构：
- 关键组件：
- 状态：加载 / 空态 / 错误 / 禁用 / 权限不足
- 主要操作：
- 需要设计确认：
- 需要前端确认：
```

跳过原型时，也要在父单或 PRD 中写明跳过原因。

### 6. 自动准备 TAPD 环境并写入

PRD 定稿后立即进入这一步。原则：环境准备全部由 AI 自动静默完成，唯一需要打扰用户的动作是索要 TAPD 个人 Token（仅当本地没有有效 Token 时才问）。

**6.1 自动环境自检（静默执行，不向用户逐项汇报）**

- 检查 `mcporter-internal` 是否已安装（`mcporter-internal list` 能正常返回即视为已装）。未安装则静默执行：
  ```bash
  npm install -g @tencent/mcporter-internal --registry=https://mirrors.tencent.com/npm
  ```
- 检查 `.codebuddy/mcp.json` 是否存在且包含 `tapd_mcp_http` 配置。不存在则基于 `.codebuddy/mcp.json.example` 自动生成/合并，保留文件中已有的其他 MCP 配置（例如 `gongfeng_mcp_http`），不覆盖。
- 用一次只读接口探测当前 Token 是否可用（例如 `mcporter-internal call tapd.<只读接口>`）：
  - 探测成功：本地已有有效 Token，直接进入 6.3，不问用户。
  - 探测失败（401 / unauthorized / token missing / token expired / permission denied）：进入 6.2。

**6.2 唯一需要打扰用户的动作：索要个人 Token**

只有 6.1 探测不到有效 Token 时才触发，话术示例：
> PRD 已经准备好了，我需要你的 TAPD 个人访问令牌才能直接建单。
> 获取地址：https://tapd.woa.com/platform/myhome?not_direct=1&from=mcp#tab=tab-mytoken
> 拿到后发给我，我会自动完成剩下所有配置和建单，不会再打扰你其他内容。

**6.4.1 描述字段必须写 HTML，不要写 Markdown 语法**

TAPD 需求描述框是富文本编辑器，底层存储是 HTML，不是 Markdown 渲染引擎。即使工具参数提示"建议使用 Markdown 格式"，实际写入 `**加粗**`、`## 标题`、`- 列表` 这类 Markdown 语法都不会被解析，会原样把符号显示给用户。

因此，写入或更新 `description` 字段前，必须把产品输入稿从 Markdown 转成 HTML 标签后再提交，例如：

- 标题：`## 二、背景` → `<h3>二、背景</h3>`
- 加粗：`**本次包含**` → `<p><b>本次包含</b></p>`
- 列表：`- 要点` → `<ul><li>要点</li></ul>`

禁止直接把带 `**`、`##`、`- ` 等 Markdown 符号的原始文本塞进 `description` 字段。仓库本地保存的 PRD 文件（`.md`）仍然可以是标准 Markdown，只有写入 TAPD 时才需要转成 HTML。

推荐创建产品父单 payload 模板：

```yaml
workspace_id: "10132091"
name: 【产品需求】【LightVela】<产品需求标题>
description: <产品输入稿 + 原型说明 + 待确认问题，转成 HTML 标签后写入，不要留 Markdown 符号>
with_v_status: "1"
v_status: <backlog 等价状态>
owner: <产品负责人或当前处理人>
creator: <当前处理人>
priority_label: <High|Middle|Low，按项目约定>
category_id: <按名称"LightVela"现场匹配得到的分类 ID，未匹配到则省略>
```

推荐更新父单 payload 模板：

```yaml
workspace_id: "10132091"
id: <产品父单 ID>
description: <更新后的产品输入稿、评审结论、研发交接建议、跳过原因，转成 HTML 标签后写入，不要留 Markdown 符号>
with_v_status: "1"
v_status: <目标状态：评审中 / 已通过 / 产品完成的等价状态>
```

**6.4.2 创建或更新成功后，必须主动把链接发给用户**

调用创建/更新工具成功后，返回结果里通常带 `detail_link`（形如 `https://tapd.woa.com/tapd_fe/<workspace_id>/story/detail/<id>`）。这个链接必须在本轮回复中直接、主动地发给用户，不能只说"已创建成功"而不给链接，也不要等用户追问才给。至少包含一次可点击的完整 URL。

推荐研发交接说明模板：

```markdown
## 研发交接建议
- 前端关注点：
- 后端/运行时关注点：
- Skill/内容/文档关注点：
- 国内站/国际站同步关注点：
- QA/发布/运营关注点：
- 建议研发自行创建的独立技术需求单：
  - 标题：
  - 范围：
  - 依赖：
  - 验收：
  - 备注：此单不作为产品父单的子需求创建
```

产品侧不创建前端、后端或 QA 子需求单，也不写 `parent_id` 子单关系。如果研发需要跟踪实现，可以由对应研发同学基于这份交接建议自行创建独立技术需求单。

这些模板只是写入形状。实际字段以本轮 TAPD 字段发现结果为准；项目没有的字段不要硬填，项目必填但模板没有的字段必须补上。

### 7. 创建或复用产品父单

- 如果已有父单，先读取它的实际字段和状态，再从当前状态继续。
- 如果没有父单，PRD 定稿且 Token 可用后直接以 backlog（待办）等价状态创建，不需要用户对写入内容做二次确认（6.4 的一行展示已经足够）。
- 父单描述保持为产品事实源：PRD、评审记录、研发交接建议和未解决问题都放在这里。
- PRD 和验收标准要写进需求描述里，不只留在聊天记录。
- 产品父单必须写明发布站点与同步策略；如果站点范围待确认，必须把“是否国际站同步发布”写入待确认问题。
- 描述字段必须是 HTML（见 6.4.1），不要把 Markdown 符号原样写进 `description`。
- 避免使用 `<value>` 这类占位包裹，它可能被 TAPD 富文本处理吞掉。
- 创建或更新调用成功后，从返回结果里取出 `detail_link`（或按 `https://tapd.woa.com/tapd_fe/<workspace_id>/story/detail/<id>` 拼出链接），在当前回复中直接发给用户，不要等用户问才给。

### 8. 推进产品评审

当 PRD 和验收标准准备好后：

- 更新父单描述。
- 用户确认后，把父单移动到评审中等价状态。
- 产品评审通过后，再移动到已通过等价状态。

产品完成只表示产品前置阶段完成，不表示功能已经上线。

### 9. 准备研发交接建议

产品通过后，不创建前端、后端、QA 或文档子需求单。产品侧只在产品父单里整理研发交接建议，说明哪些方向可能需要研发自行创建独立技术需求单。

| 方向 | 什么时候需要写入交接建议 | 什么时候通常不需要 |
| --- | --- | --- |
| 设计 / UX | 有新交互、控制台流程变化、新页面状态、文案层级变化，或需要视觉评审 | 纯后端/运行时变化，没有用户可见行为 |
| 前端 | 涉及路由、组件、状态、API 客户端、i18n、设置页、Agents 页、工具/专家 UI 或 SDK 驱动的 UI 变化 | 现有 UI 已支持，只是数据变化 |
| 后端 / 运行时 | 涉及 Hermes/OpenClaw 命令行为、`acli`、MCP、实例状态、鉴权、配置、`debug/exec`、API 契约或持久化 | 纯前端展示或文案变化 |
| Skill / 内容 / 文档 | 需要新增或修改 skill、prompt、模板、用户指南、新手引导、发布说明或支持手册 | 产品行为不需要用户可见说明 |
| 国内站 / 国际站同步 | 需求涉及 `lightvela.com` 与 `lightvela.ai` 的路由、入口、文案、i18n、图片、metadata、sitemap、SEO/GEO、登录/支付/渠道差异或发布节奏 | 明确为单站内部能力，且另一站无用户可见影响 |
| QA / 发布 / 运营 | 涉及跨产品面发布、迁移、特性开关、观测、回滚、浏览器冒烟或高风险链路验证 | 小范围改动可由研发技术需求单自行覆盖 |

建议独立技术需求单标题格式：
