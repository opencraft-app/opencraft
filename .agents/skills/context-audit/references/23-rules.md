# 23 条上下文工程通用规则

成熟度与实现状态必须分开：`ADOPT/PILOT/RESEARCH` 表示建议成熟度；`implemented/partial/design-only` 表示目标仓库当前证据。只有文件、Git、Validator、测试或真实消费收据可复现时才能升级实现状态。

| # | 规则 | 为什么 | 最低证据与检查 |
|---:|---|---|---|
| 1 | 入口是路由，不是百科全书 | 默认注入必须为所有任务支付，长入口会稀释局部规则 | 根入口 ≤8 KiB；最大祖先链 ≤16 KiB；入口只含边界、算法、命令、链接 |
| 2 | 规则分层、作用域明确、近者优先 | Team、Project、Domain、Service、Task 的适用范围不同 | Schema 有 `scope/precedence`；检查最近 `AGENTS.md` 与冲突规则 |
| 3 | 默认动态发现，不默认全量注入 | 任务只需要相关知识，全量加载同时增加成本与冲突 | Router 有路径/符号/关键词/显式文件通道；smoke case 验证必读与禁入 |
| 4 | 一个窗口承载一个主要目标 | 多目标混合会让验收、压缩和交接失去边界 | Task Pack 有一个 `goal`、明确 `non_goals` 和 acceptance |
| 5 | 达到窗口压力阈值后主动 compact | 保留足够推理空间比被动截断更可控；收益过小仍反复压缩会增加抖动和信息损失 | 只有存在窗口利用率、触发阈值、最小回收收益或滞回、compact 事件、事实保留率和溢出恢复测试才可标 implemented |
| 6 | 先清可重取工具结果，再做有损 compact | 日志、扫描和重复输出可重新获取，事实摘要不可轻易恢复；近期结果和超大单条结果不应只有“全留/全删”两种选择 | Checkpoint `discard`；运行时有 tool-clear、近期保护、释放量证据；部分截断时保留定位信息并提示重新调用工具 |
| 7 | compact 必须可恢复 | 压缩的目标不是更短，而是能继续完成任务；重载后旧输出复活会让同一任务再次溢出 | `restore`、verified/unverified、next action、摘要 hash；压缩状态持久化；近期原文或可重取定位保留；恢复与重载回归 |
| 8 | 大规模检索下沉隔离任务 | 扫描噪声不应污染主窗口 | 有界 `scan_scope/scan_output`；隔离执行只返回证据摘要 |
| 9 | 结构化交接，不传完整聊天 | 完整聊天包含噪声、被否决方向和过期状态 | 交接仅含目标、事实、风险、验证、下一步；跨会话恢复抽检 |
| 10 | 多路检索，不用单一语义检索冒充万能 | 精确路径、符号、文本、历史、关系图各自擅长不同 Query | Router 记录通道命中；按任务类型组合而不是只用向量 |
| 11 | 精确命中不能被语义结果覆盖 | 用户点名的文件/符号是高置信信号 | 显式路径和 deferred path 受保护；smoke case 断言排序/包含 |
| 12 | 上下文必须有来源、版本与权威度 | 无来源摘要无法判断冲突、时效和责任 | owner、authority、revision、review 日期、source_of_truth 全覆盖 |
| 13 | Wiki/Catalog 只能是派生视图 | 生成索引若成为平行真相，会与源码和正式文档漂移 | Catalog 记录 source hash；派生页面回链真源；可重建 |
| 14 | 记忆写入经过验证门禁 | 未确认经验自动持久化会把偶然结论扩散为规则 | candidate→pilot→active；owner 接受/拒绝记录和过期策略 |
| 15 | 保留有效失败，压缩重复噪声 | 失败条件和根因能防复发，重复日志只消耗注意力 | feedback 有触发、影响、证据、根因、修复和回归 |
| 16 | 提示前缀与工具定义保持稳定 | 稳定前缀有利于缓存、工具契约和可比较行为 | Tool contract 版本化输入/输出/错误；变化有兼容策略 |
| 17 | 状态外部化 | 任务状态不能只活在会话里；压缩、清理和恢复状态若只存在内存，历史重载会产生行为漂移 | Task、Checkpoint、Todo、feedback 与必要的压缩状态落盘；恢复边界明确；重载前后语义一致 |
| 18 | 默认检索优先，允许受控回退 | Router 提高效率，但必须允许新问题通过精确搜索找到事实 | route→must_read→bounded exact search→记录失败 Query→扩大范围 |
| 19 | 观测取了什么、注入了什么、用了什么 | 没有消费证据就无法区分“文档存在”和“上下文生效” | receipt；进一步需要 retrieve/rerank/assemble/utilization Trace |
| 20 | 失败回流评测、索引或规则 | 只有闭环才能让 Context 随真实问题演进 | 每个关闭案例链接到 route/rule/content/evaluation 修复和回归 |
| 21 | 模型按难度与可验证性路由 | 成本、风险、推理深度和可验收性决定模型需求 | requested/actual model、原因、预算与结果 Trace；无证据保持试点 |
| 22 | 工具集少而精 | 大量相似工具增加选择错误和工具描述 Token | 核心工具有清晰不重叠的输入、输出、失败策略与使用指标 |
| 23 | 经验经人工确认后增量沉淀 | 长期记忆需要责任、范围和失效机制 | Candidate 有来源、owner、范围、有效期、接受/拒绝与复用记录 |

## 23 条规则与目录的关系

- 规则 1–3、10–11、18：由 `AGENTS.md`、Router 和路由 smoke case 承载。
- 规则 4–9、17：由 Task Pack、Checkpoint 和隔离扫描承载。
- 规则 12–14、23：由正式文档、Catalog、Source Map、Authority、Lifecycle 承载。
- 规则 15、19–20：由 Feedback、Receipt、Trace 和回归测试承载。
- 规则 16、21–22：由 Tool Contract、模型路由策略和实际使用观测承载。
- `docs/engineering/` 的全仓文档治理不是第 24 条 Context 规则，而是 23 条规则得以获得可靠事实源的互补基础。

## 状态判定

- `implemented`：已有机制，且能用命令、测试或消费记录复现。
- `partial`：已有文件或人工流程，但缺自动化、覆盖或长期证据。
- `design-only`：只有目标和边界，运行能力尚不存在。

不得仅修改矩阵状态来提高分数；必须先增加对应证据。
