## 第 4 页：共识 1 — 入口文件是路由，不是百科全书

### PPT 画面提示
- 左上角标签：共识 1 · ADOPT（绿色）
- 主标题：入口文件是路由，不是百科全书
- 共识原文：Give Codex a map, not a 1,000-page instruction manual.
- 中文翻译：给 Codex 一张地图，而不是一千页说明书。
- 要点：
  1. 来源：OpenAI Harness Engineering · 证据 S
  2. 业界参考：入口文档控制在 ~100 行，详细内容按需读
  3. LightVela 实验：全仓静态地图对 28 个目标文件命中 0 个
  4. 落地：根入口只放安全边界、事实源优先级、工作流入口和子服务地图
- 视觉：左侧大号编号「01」，右侧内容卡片

### 演讲稿

第一条共识来自 OpenAI，原话是「给 Agent 一张地图，而不是一千页说明书」。

什么意思呢？Agent 进入仓库时加载的第一个文件——对我们来说就是 AGENTS.md——这个文件应该是一张路由表。它告诉 Agent 三件事：安全红线是什么、事实源优先级是什么、子服务在哪。它不应该把所有业务知识、所有 API 细节、所有规范都塞进去。

在 LightVela 里，我们的 mono2 是一个大型 monorepo，有 frontend、ctl、service-gateway、auth、subscription、payment 等十几个子服务。根目录的 AGENTS.md 只放了一张子服务导航表和安全红线，每个子服务的技术栈细节放在各自目录下的 AGENTS.md 里。这样 Agent 进入 frontend 目录时读 frontend/AGENTS.md，进入 ctl 目录时读 ctl/AGENTS.md，各看各的。

我们做了实验验证。用 Aider 这个工具把整个 mono2 的一万两千个文件压缩成一张 1千 token 的仓库地图。拿这张地图去匹配 6 个真实任务需要找的 28 个文件，结果是什么？一个都没找到。零命中。

类似地，在其他项目中也可以这样做：不管你的项目是 monorepo 还是单仓库，根入口文件只放路由——安全边界、子模块在哪、工作流入口在哪。深层规则放到各自子目录的入口文件里。OpenAI 自己的 Codex 文档大概 100 行，Anthropic 的 CLAUDE.md 建议低于 200 行。

不这样做会怎样？Agent 把过期规则当硬约束执行；真正相关的文档反而进不了 context window——被入口文件占满了；规则冲突由 Agent 静默猜测，导致错误改动。

## 第 5 页：共识 2 — 规则分层、作用域明确、近者优先

### PPT 画面提示
- 左上角标签：共识 2 · ADOPT（绿色）
- 主标题：规则分层、作用域明确、近者优先
- 共识原文：Closer instructions override farther ones along the root→cwd chain.
- 中文翻译：沿 root→cwd 链，近处的指令覆盖远处的指令。
- 要点：
  1. 来源：OpenAI Codex AGENTS.md · 证据 S
  2. 业界参考：Anthropic CLAUDE.md 分层加载
  3. LightVela 实验：搜索范围缩到前端代码后，命中从 0 提升到 2
  4. 落地：五层分层，每条规则标明 owner 和作用域
- 视觉：树状层级图（root → service → module → task），标注「近者优先」

### 演讲稿

第二条共识也是来自 OpenAI：沿目录链，近处的指令覆盖远处的指令。

在 LightVela 里这个场景很常见。我们有全局规则——比如安全红线「不许推到生产桶」；有仓库级规则——比如 git workflow 和 TAPD 关联；有服务级规则——frontend 用 React + Vite + pnpm，ctl 用 Go + Makefile；还有模块级规则——某个 package 有特殊约束。当这些规则冲突时，更近的、更具体的规则优先。

举个 LightVela 的例子。全局规则里提到测试用 Jest，但 ctl 是纯 Go 项目，只有 go test。如果全局规则没有标注作用域，Agent 在 ctl 目录下执行时就会试图找 Jest 配置，找不到就报错。有了分层机制，ctl/AGENTS.md 里的「用 go test」会覆盖根目录的通用描述。

我们的实验也支持这一点。把搜索范围从整个仓库缩小到只看 frontend 代码，结果能找到的正确文件从 0 个变成了 2 个。作用域越精准，检索越有效。

类似地，在其他项目中也可以这样做：不管是 monorepo 还是多仓库，都可以做五层分层——全局、仓库、服务、模块、任务。每条规则标注四个属性：谁负责维护、作用域是什么、权威度多高、什么时候过期。同层规则冲突时必须阻断并要求人工裁决，不能让 Agent 自己猜。

不这样做会怎样？服务级约束被全局口号覆盖；同层冲突静默猜测导致错误改动。

## 第 6 页：共识 3 — 默认动态发现，不默认全量注入

### PPT 画面提示
- 左上角标签：共识 3 · ADOPT（绿色）
- 主标题：默认动态发现，不默认全量注入
- 共识原文：Fewer static details, just-in-time retrieval.
- 中文翻译：更少静态细节，即时按需检索。
- 要点：
  1. 来源：Cursor Dynamic Context Discovery · 证据 S
  2. 业界数据：工具定义从 150K tokens 降到 2K（降 98.7%）
  3. LightVela 实验：静态仓库概览命中 0/28；按需检索能命中
  4. 落地：起步只放目录+工具名+短描述，完整信息按需获取
- 视觉：对比图——左侧「全量注入」（满屏文字）vs 右侧「动态发现」（简洁+按需展开）

### 演讲稿

第三条来自 Cursor：更少静态细节，即时按需检索。

核心思想是：Agent 启动时，prompt 里只放最小必要信息——目录结构、工具名和一句话描述。完整的工具参数、文档全文、日志这些内容，在需要的时候才按需获取。不是「不提供」，而是「不在一开始就全量灌进去」。

在 LightVela 里，我们的 mono2 有十几个子服务、几百个 API、上千个文件。如果把所有工具定义、所有 API 文档全塞进 Agent 的起始 prompt，那光这些就消耗了几十万 token，真正需要的任务信息反而进不来。我们的做法是：起步只放目录结构和工具名，Agent 需要哪个工具的详细参数时再动态加载。

业界数据很惊人。Anthropic 做了个对比：把工具定义静态注入要约 15 万 token，改成动态按需获取只需要 2 千 token，降了 98.7%。Anthropic 内测的 Tool Search 功能把任务完成率从 49% 提升到 74%。

我们的实验也验证了：静态的仓库概览对 28 个目标文件命中 0 个，但做按需检索——需要什么查什么——能命中。

类似地，在其他项目中也可以这样做：不管项目大小，起步 prompt 只放目录、工具名和短描述。完整信息按需获取。高频工具常驻，低频工具需要的时候才加载。MCP 就是一个很好的动态发现机制——工具定义不在 prompt 里常驻，Agent 需要时才通过 MCP 获取。

不这样做会怎样？有效证据被噪声淹没；cache 前缀频繁失效；延迟与费用失控。

## 第 7 页：共识 4 — 一个上下文窗口只承载一个目标域

### PPT 画面提示
- 左上角标签：共识 4 · PILOT（橙色）
- 主标题：一个 context window 只承载一个目标域
- 共识原文：Specialized subagents with isolated context windows.
- 中文翻译：使用独立 context window 的专用子代理。
- 要点：
  1. 来源：Anthropic Effective Context Engineering · 证据 A
  2. 核心场景：需求分析+实现+审查+排障不能挤在一个窗口
  3. 落地：单窗口 1-2 个目标，阶段切换时只带结构化交接
  4. 注意：短程多步骤不需要切窗口
- 视觉：四个独立窗口示意图（分析/实现/审查/排障），箭头表示结构化交接

### 演讲稿

第四条来自 Anthropic：使用独立 context window 的专用子代理。

什么场景适用？重型阶段混杂：需求分析、全仓实现、独立审查、发布排障，这些如果全挤在一个超长会话里做，会互相污染。分析阶段的假设会带进实现阶段，实现阶段的代码输出会干扰审查阶段。

在 LightVela 里，一个典型的复杂需求——比如「给 Skills 增加批量卸载功能」——涉及前端组件、后端 API、测试和部署。如果在一个会话里从头做到尾，分析阶段的假设会污染实现阶段，实现阶段的 diff 会干扰审查阶段。我们的做法是：需求分析用一个窗口，实现用另一个窗口，审查再用一个。切换时只带结构化交接——目标、已完成、变更文件、决策、风险、下一步。

类似地，在其他项目中也可以这样做：凡是涉及多个重型阶段的任务，都可以拆成独立窗口。单窗口只做 1 到 2 个高度相关的目标。阶段切换时开新窗口，只带结构化交接，不把完整聊天记录搬过去。

但要注意：这不是说每执行一个 grep 就开新窗口。短程多步骤完全可以在同一个窗口里做。这条针对的是重型阶段混杂。

不这样做会怎样？目标漂移——原本要做 A 做着做变成 B。错误假设跨阶段传染。审查被实现噪声带偏。

Anthropic 的多代理研究数据是质量提升 90%，但代价是 15 倍 token。这是研究任务的数据，不能直接外推到编码任务。所以标 PILOT。

## 第 8 页：共识 5 — 使用率达约 40% 后进入主动 compact

### PPT 画面提示
- 左上角标签：共识 5 · RESEARCH（蓝色）
- 主标题：使用率达约 40% 后进入主动 compact（双阈值）
- 共识原文：Context is a finite attention budget with diminishing returns.
- 中文翻译：context window 是有限注意力预算，窗口变大仍有收益递减。
- 要点：
  1. 来源：Anthropic Effective Context Engineering · 证据 A
  2. 双阈值策略：预防性 compact + 安全兜底
  3. 暂定：<40% 健康 / 40-60% 检查 / 60-75% compact / >75% 新会话
  4. 关键：40% 须本地校准，不是业界公认拐点
- 视觉：进度条图示（绿色<40% / 黄色40-60% / 橙色60-75% / 红色>75%）

### 演讲稿

第五条共识叫「使用率达约 40% 后进入主动 compact」，成熟度 RESEARCH。来自 Anthropic 的原话是：context window 是有限的注意力预算，窗口变大仍然有收益递减。

什么意思呢？就是不要等 context window 快满了才被动去 compact，而是在用到大约 40% 的时候就主动开始 compact——提前检查有没有偏离目标、提前压缩。打个比方，开车不能等油箱见底了才找加油站，而是剩一半的时候就开始留意——这就是「主动 compact」和「被动清理」的区别。

在 LightVela 里，一个典型的长调试会话——比如排查一个跨 frontend、service-gateway 和 auth 的 bug——可能跑 50 轮以上。如果不主动 compact，跑到 30 轮的时候 context window 已经塞满了工具输出，关键决策被挤到中间位置，Agent 开始遗忘前面的约束。我们的暂定策略是分四档：40% 以下健康，不用管；40% 到 60% 开始检查有没有偏离目标，准备 compact；60% 到 75% 倾向 compact 或拆阶段；75% 以上必须开新会话，带上结构化交接。

类似地，在其他项目中也可以这样做：任何长 Agent 任务——不管是代码重构、跨模块调试还是大规模搜索——都可以用双阈值策略。不过具体数字要根据自己的任务和模型校准。Hermes 公开实现用的是约 50% 主 compact、约 85% 安全兜底，思路跟我们一样。

为什么要主动 compact 而不是等满了再说？因为长上下文有「中间遗忘」现象——放在窗口中间位置的信息容易被忽略。等 95% 满了再 compact，关键决策可能早就被挤没了。

但 40% 这个数字是我们的预防性政策，不是业界公认的拐点。不同模型、不同任务类型的拐点不一样。需要本地校准，所以标 RESEARCH。

## 第 9 页：共识 6 — 先清理旧工具结果，再做有损 compact

### PPT 画面提示
- 左上角标签：共识 6 · PILOT（橙色）
- 主标题：先清理旧工具结果，再做有损 compact
- 共识原文：Clear old tool results before aggressive summarization.
- 中文翻译：在激进摘要之前，先清理旧的工具结果。
- 要点：
  1. 来源：Anthropic Effective Context Engineering · 证据 A
  2. 两步：先清理低信息内容 → 再做有损 compact
  3. 清理：旧终端输出、重复文件、已看过的搜索结果
  4. 保留：决策、未决问题、当前 diff、验证证据

第六条来自 Anthropic：在激进摘要之前，先清理旧的工具结果。

正确做法是分两步。第一步先清理——把已经看过的搜索结果、重复的终端输出、读过的文件内容移出去。第二步才做有损 compact——保留决策、未决问题、当前修改的代码、验证证据和最近改的文件。

打个比方，你要搬家，先扔掉不需要的旧东西，再打包剩下的。如果你不分两步，直接把所有东西压缩打包，你可能把重要的文件和废纸一起扔了。

类似地，在其他项目中也可以这样做：任何多轮 Agent 任务在 compact 之前，先区分「有效内容」和「已消费内容」。已消费的搜索结果、已经读过的文件、重复的终端输出——这些占位高但信息密度低，先移出去。决策、未决问题、当前 diff、验证证据——这些必须保留。

不这样做会怎样？要么关键决策被 compact 压没了——和重复日志一起被删。要么重复日志留在窗口——50 个相同的 error 堆栈占满预算。

一个边界：清理不等于删除原文。原文应该落盘保存，compact 后还能按需回读。这跟下一条共识直接相关。

类似地，在其他项目中也可以这样做：全仓搜索、依赖链盘点、跨服务影响分析优先用子代理。主代理只收结论、关键证据和未决问题。但日常的精确查找不需要——你 grep 一下一个符号名，没必要为此开一个子代理。

不这样做会怎样？主会话被搜索结果淹没——搜了 50 个文件，全部结果都在窗口里。或者误以为多代理总是更强——Anthropic 的数据显示质量提升 90%，但代价是 15 倍 token。多代理的增益很多时候来自额外算力。编码任务的并行性通常低于研究任务，不能直接外推。

## 第 12 页：共识 9 — 交接必须结构化，不传完整聊天

### PPT 画面提示
- 左上角标签：共识 9 · PILOT（橙色）
- 主标题：交接必须结构化，不传完整聊天
- 共识原文：Pass a structured handoff, not the entire chat transcript.
- 中文翻译：传递结构化交接，而不是完整聊天记录。
- 要点：
  1. 来源：综合 OpenAI/Anthropic 实践 · 证据 A
  2. 交接必含：目标/成功标准/已完成/变更文件/决策/风险/下一步/禁改范围
  3. LightVela：已有 handoff 设计，尚无量化恢复质量
  4. 边界：交接与实际代码状态不一致时必须失效重建
- 视觉：左侧「完整聊天记录」（巨大文档打叉）vs 右侧「结构化交接卡片」

### 演讲稿

第九条综合了 OpenAI 和 Anthropic 的实践：传递结构化交接，而不是完整聊天记录。

在 LightVela 里，一个常见的场景：一个开发者用 Agent 做了半天需求分析，要交接给另一个开发者做实现。如果传完整聊天记录，接手的人需要从几万 token 的记录里提取出当前状态——这本身就是一个搜索任务。而且聊天记录里的过期假设会误导接手者——之前讨论过又否决了的方案，接手者看到记录以为可以做。

我们的做法是：交接时传一张结构化卡片。卡片包含：目标是什么、成功标准是什么、完成了什么、改了哪些文件、做了什么决策及为什么、测试结果、有什么风险、下一步做什么、哪些地方不能动。

类似地，在其他项目中也可以这样做：凡是需要把任务状态传给另一个执行者的场景——换人接手、Agent 重启、多 Agent 协作——都用结构化交接。不用完整聊天记录。Microsoft 的 Magentic-One 也是用外部账本来记录任务事实和计划。

不这样做会怎样？接手的人重复踩坑——已经试过并排除了的方案被重新尝试。目标和成功标准丢失——做着做着忘了原本要做什么。改错分支——不知道当前在哪个分支。

一个重要边界：如果交接说在 branch A，但实际 git 状态在 branch B，交接就不可信，必须重新建立。

## 第 13 页：共识 10 — 检索多路路由，不用单一向量检索冒充万能

### PPT 画面提示

- 主标题：检索多路路由，不用单一向量检索冒充万能
- 共识原文：Hybrid retrieval and reranking reduce failure rates versus embedding alone.
- 中文翻译：相对纯向量，混合检索与重排可降低失败率。
- 要点：

  2. 五条通道：精确→关键词 / 语义→向量 / 结构→符号图 / 历史→提交 / 影响→diff+图+测试

### 演讲稿

第十条是 ADOPT，来自 Anthropic：相对纯向量搜索，混合检索和重排能降低失败率。

这是整个共识体系里证据最充分的一条。核心观点是：不同类型的查询需要不同的搜索方法。找一个具体的函数名，用关键词搜索最快最准。找「怎么处理退款超时」这种自然语言意图，用语义搜索更好。找谁调用了这个函数，用符号关系图最靠谱。每种方法各有所长，没有一个能包办一切。

在 LightVela 里，我们的实测数据很具体。用 QMD 做语义搜索，召回率大概 50%——能找到一半的正确答案。但用关键词搜索中文内容，命中率是 0——因为搜索引擎没有中文分词，你搜「批量卸载」，它切不出有效的词。而用 Zoekt 做精确搜索，0.11 秒就能找到中文内容。用 Serena 做符号搜索，253 毫秒就能精确定位到行。

所以如果你只用语义搜索，中文内容完全找不到。如果你只用关键词搜索，自然语言意图又匹配不上。正确做法是多个通道同时搜，然后把结果合并排序——再加上权威度和新鲜度权重。

类似地，在其他项目中也可以这样做：不管项目用什么语言、什么技术栈，都可以做多路检索。精确符号走 grep 或 Zoekt，自然语言走向量或 embedding，结构关系走 LSP 或符号图，历史变更走 git log，影响面走 diff 加调用图。多通道用 RRF（就是倒数排名融合，把多个搜索结果按排名合并）融合。

不这样做会怎样？中文搜不到。精确的文件路径被语义噪声挤掉——明明 grep 到了正确文件，但语义搜索觉得另一个文件「更像」，把正确的挤下去了。影响面和测试文件漏掉——你要改一个函数，语义搜索帮你找到了定义，但没找到调用它的地方和测试它的文件。

### 演讲稿

第十一条是 ADOPT：精确命中必须对语义候选保持优先级。

什么意思？当你用关键词搜索和语义搜索同时找到了候选文件时，关键词搜索找到的精确结果应该排在前面。重排不能无理由地把精确结果往后挪。语义搜索只是补充——当你不知道确切的名字时，用语义搜找候选。但当你确切知道要找什么时，精确结果就是对的，不需要语义来「纠正」。

在 LightVela 里，一个典型场景：Agent 查找 mergeInstalledSources 这个函数。用 Zoekt 做精确搜索，同时找到了源文件和测试文件——都对。但用 codebase-memory 做语义搜索，前 20 个结果全部偏离目标——一个都不对，返回的是 Figma 组件和 juicefs 等无关节点。如果按语义排序，正确的文件被挤到了后面。

我们还发现一个现象：加了重排之后，召回率略微上升，但 F1 分数反而下降了——说明重排不总是好事，有时候会把正确结果搞乱。

类似地，在其他项目中也可以这样做：符号名、错误码、API 名、配置键、用户指定的路径——这些都是硬事实，精确匹配优先。重排不能无理由删除强精确命中。语义结果只作为补充，填补关键词搜不到的「词汇鸿沟」——比如你搜「退款」但代码里叫 refund，这时候语义搜索能帮忙。

不这样做会怎样？明明 grep 到了正确文件，但语义重排把它排到了第 20 名，把一个「看起来更像」的错误文件排到了第 1 名，Agent 就会改错文件。Cognition 的 SWE-grep 文章说得好：上下文被污染比漏掉一些结果更危险。

### 演讲稿

第十二条是 ADOPT：每条注入 Agent 的上下文都需要标注三个东西——来源、版本、权威度。没有出处的总结就是「假权威」——看起来很专业，但你不知道它来自哪次提交、哪个文档、还能不能信。

在 LightVela 里，我们设了一个权威度金字塔。最顶层是代码、API 定义、active spec——这些是真理来源。第二层是 runbook 和架构决策。第三层是自动生成的文档——派生视图。第四层是变更记录和事故记录。最底层是归档和废弃内容。当这些冲突时，高权威度的压过低权威度的。

这个不是假想的——我们真实踩过一个坑。第一轮跑 QMD 检索 benchmark 的时候，发现评测用的测试数据文件被一起索引进去了。结果你猜怎么着？所有搜索都首先命中评测文件本身——因为评测文件里包含了答案。所有指标看起来都很好，但完全不能信。评测作废了。

这说明什么？评测数据和被搜索的语料必须物理隔离。你把答案和考题放在同一个数据库里，当然每次都「答对」了。修复之后，我们从语料里剔除了评测文件，加了一个黑名单防止以后再犯。

类似地，在其他项目中也可以这样做：每条注入带稳定标识、来源文件路径和 git commit hash、谁负责维护、权威度等级、生命周期和权限。没有来源的总结不能进入高权威层。泄漏率等于 0 是硬门禁——不能有任何评测数据或敏感数据混进搜索语料。

不这样做会怎样？评测答案泄漏进索引，所有指标虚高。过期文档压过代码真源。无法追溯错误上下文来自哪次提交。

### PPT 画面提示
- 左上角标签：共识 13 · ADOPT（绿色）
- 主标题：生成 Wiki 只能是派生视图
- 共识原文：Generated docs are derived views, never source of truth.
- 中文翻译：生成文档是派生视图，绝不是真理来源。
- 要点：
  1. 来源：CodeWiki 研究 + 本地分叉观察 · 证据 A/本地
  2. LLM 生成的文档可读性强，但会与代码漂移
  3. 实测：语义搜索返回旧文档「不支持面板卸载」与实际代码冲突
  4. 落地：源 hash 变则标过期，冲突必须展示
- 视觉：代码（真源）→ 箭头 → Wiki（派生视图），Wiki 上标「过期?」状态

### 演讲稿

第十三条是 ADOPT：生成文档是派生视图，绝不是真理来源。

在 LightVela 里，我们用各种工具自动生成项目文档。这些工具生成的文档看起来很专业——格式好、语言通顺、结构清晰。但这里有个陷阱：LLM 生成的内容会跟实际代码漂移。代码改了，文档没跟着改，就过期了。

我们有一个真实的验证。用 ChunkHound 做语义搜索，问了一个关于 Skills 卸载的问题。返回的前几个结果里，有几个是旧用户文档，声称「当前不支持面板卸载，只能对话删除」。但我们的 active spec 和 plan 明确要求支持面板卸载，代码里也实现了。也就是说，语义搜索把过时的文档排在了当前正确的代码前面——因为它「语义更像」。

类似地，在其他项目中也可以这样做：生成的 Wiki 不能覆盖代码和 active spec。源文件变了就标记文档为「可能过期」。如果文档和代码冲突，必须展示冲突，不能让 Agent 自己选。文档的「质量评分」不等于「事实权威度」——一篇看起来很专业的文档可能全是过时信息。

不这样做会怎样？按过期文档改接口——文档说有这个 API，实际代码里已经删了。测试对着旧行为写——文档描述的行为已经是旧版本的了。Cognition 的文章也提到：模型自己写的 SUMMARY.md 仍然会漏关键内容。

### 演讲稿

第十四条共识叫「记忆写入必须经过验证门禁」，成熟度 RESEARCH。来自 Google 的 ReasoningBank：把成功与失败轨迹提炼为未来护栏。

什么意思呢？Agent 完成任务后，从成功或失败中提取经验写入长期记忆。但这里有个门禁：自动总结只进候选区，不能直接变成正式记忆。必须经过测试通过、负责人审核、用户确认或者事故复盘，才能升级为正式记忆。

在 LightVela 里，一个典型场景：Agent 调试一个 auth 模块的 bug，发现改一个配置项就好了。它想把这个写成经验：「auth 模块出问题就改这个配置项」。但如果直接写进去，下次遇到 auth 模块的问题，Agent 就盲目改这个配置项——可能这次能改好是因为别的原因，不是配置项本身的问题。

类似地，在其他项目中也可以这样做：模型只提交变更提案——包含来源任务、原始证据、适用范围、反例、置信度、负责人和过期时间。候选存放在独立区域，状态标记为「候选」。正式搜索只读「已发布」的内容。负责人审核后才能从「候选」升到「已发布」。支持合并、替代、冲突处理、过期和遗忘。

不这样做会怎样？错误经验反复误导后续任务。模型把一次巧合当成了规律，写进记忆，后续每次都按这个错误规律操作，越错越远。Microsoft 的 ACE 研究也指出：要避免全量重写导致简短偏见和上下文坍缩，增量更新优于整篇重写。

明确禁止几件事：模型做对一次就把经验升为规则。整篇重写知识。用模型自评分数替代回归测试。线上自动调参但没有版本和回滚机制。

我们的记忆写入精确率和复用实验还没跑，所以标 RESEARCH。

## 第 18 页：共识 15 — 保留有效失败证据，压缩重复噪声

### PPT 画面提示
- 左上角标签：共识 15 · ADOPT（绿色）
- 主标题：保留有效失败证据，压缩重复噪声
- 共识原文：Keep failed actions and stack traces as self-correction signals.
- 中文翻译：保留失败动作与堆栈，作为自纠正信号。
- 要点：
  1. 来源：Manus Context Engineering · 证据 A
  2. 有效失败 = 导致方向转变的错误
  3. 重复日志 = 压缩为摘要+指针
  4. 修复后转回归测试
- 视觉：分类图——左侧「保留」（错误堆栈、失败测试）vs 右侧「压缩」（重复日志、相同 error）

### 演讲稿

第十五条是 ADOPT，来自 Manus：保留失败动作和堆栈，作为自纠正信号。

在 LightVela 里，一个典型场景：Agent 调试一个 payment 模块的 bug，试了三种方法，前两种报错了，第三种成功了。前两种的报错堆栈要保留——因为它告诉 Agent「这条路走不通，别再试了」。但如果同一个 error 输出了 50 遍，保留一个加原文指针就够了。

关键区分两种东西：「有效失败」和「重复噪声」。有效失败是导致方向转变的——Agent 试了一种方法，报错了，它知道这条路走不通，转而试另一种。这个错误要保留。重复噪声是同一行 error 输出了 50 遍——保留一个就够了。

我们有一个完整的失败回流案例：评测泄漏被发现后，被保存为失败证据，然后变成了一个失败测试，修复后变成永久回归测试。以后每次改代码都会自动跑这个测试，确保不会再泄漏。

类似地，在其他项目中也可以这样做：导致方向转变的错误和堆栈保留。重复日志压缩成一个摘要加原文指针。修复后转成回归测试，加入 CI。这样同类故障就不会再犯。

不这样做会怎样？抹掉失败后反复同一错法——Agent 忘了之前试过并失败了，又试了一遍。或者保留海量重复日志挤掉决策——50 个相同的 error 堆栈占满了窗口。

一个边界：保留失败不等于把所有 stderr 都堆在窗口里。只保留「有效」的——排除了某种可能性的、让 Agent 知道不该再试的。

## 第 19 页：共识 16 — 提示前缀与工具定义必须稳定

### PPT 画面提示
- 左上角标签：共识 16 · PILOT（橙色）
- 主标题：提示前缀与工具定义必须稳定
- 共识原文：Exact prefix matching is required for prompt cache hits.
- 中文翻译：prompt cache 命中依赖精确前缀匹配。
- 要点：
  1. 来源：OpenAI Codex Agent Loop · 证据 S
  2. 业界数据：首字延迟最多降 80%，输入成本最多降 90%
  3. 前缀一个字变了 → 整条 cache 失效
  4. 落地：静态指令放前面，动态内容放后面
- 视觉：前缀稳定性图示——稳定前缀（绿色，cache hit）vs 抖动前缀（红色，cache miss）

### 演讲稿

第十六条是 PILOT，来自 OpenAI：prompt cache 命中依赖精确前缀匹配。

什么是 prompt cache？大模型的 API 有个优化：如果你连续两次请求的前缀一模一样，第二次就不用重新处理前缀部分，直接复用 cache。这样延迟更低、成本更低。OpenAI 的数据是首字延迟最多降 80%，输入成本最多降 90%。Manus 的数据是输入输出比常达 100 比 1——cache 命中的影响非常大。

但前提是：前缀必须一模一样。一个字变了，整条 cache 就失效了。

在 LightVela 里，Agent 的系统 prompt、工具定义、AGENTS.md 规则——这些在每个请求中都会发送的内容，必须保持前缀稳定。如果工具列表的顺序每次都变，或者前缀里塞了当前时间戳，cache 每次都失效，每次都像冷启动。

类似地，在其他项目中也可以这样做：静态的东西——系统指令、工具定义、规则文件——放在前面。动态的东西——当前任务描述、用户输入——放在后面。工具列表的顺序要固定。不能在前缀里放会变的东西，比如时间戳或随机 ID。cache 命中率的目标是大于 70% 算健康，40% 到 70% 预警，低于 40% 要重点治理。

不这样做会怎样？每次请求都像冷启动——没有 cache 命中，延迟和成本都翻倍。工具顺序乱跳导致行为不稳定——同一个任务每次跑结果不同。

我们的本地实验还没测 cache 命中率，所以标 PILOT。

- 中文翻译：将任务状态写入外部文件，周期性复述当前 Todo，并保留有效失败证据。

  2. 外部文件：goal.md / todo.md / decisions.jsonl / failures.jsonl / artifacts/ / handoff.md

### 演讲稿

第十七条是 PILOT，来自 Manus：将任务状态写入外部文件，周期性复述当前 Todo，并保留有效失败证据。

核心思想：context window 是临时工作区，不适合当任务状态的唯一存储。长任务跑着跑着，目标和计划会被中间的工具输出挤到注意力后面，也可能在 compact、切换会话或程序崩溃后丢失。所以要把关键状态写到外部文件里。

在 LightVela 里，我们设计了一套外部文件。goal.md 记录任务目标、成功标准和约束。todo.md 记录当前阶段、完成了什么、下一步、什么阻塞了。decisions.jsonl 记录做了什么决策、为什么、有什么替代方案。failures.jsonl 记录试了什么、为什么失败、排除了什么可能。artifacts 目录存长日志、搜索结果和中间产物。每次恢复任务时先读 goal.md 和最新 todo.md，需要的时候再按指针回读决策和失败细节。

还有一个重要的实践叫「Todo 复述」：每隔一段时间，把当前待办重新说一遍——一句话：我现在在做什么、下一步做什么。这样把当前目标重新拉回到注意力的前面，防止跑偏。

类似地，在其他项目中也可以这样做：任何长 Agent 任务都可以用这套外部文件。目标落盘、计划落盘、决策落盘、失败落盘。每次恢复时先读目标文件和待办，不把全部运行历史重新灌进窗口。Microsoft 的 Magentic-One 也是用外部账本来记录任务事实和计划。

不这样做会怎样？目标逐渐漂移——做着做着忘了原本要做什么。compact 或重开会话后无法恢复进度。已经验证失败的方案被反复执行。重要决策只存在聊天记录中，无法审计和交接。

验证方法：对比「只依赖聊天记录」和「状态落盘加 Todo 复述」的长任务。看目标漂移率——试点目标 10% 以下。看重启后恢复成功率。这些基线我们还在建。

在 LightVela 里，Agent 需要在 mono2 仓库里找信息时，默认先走结构化检索——通过索引或者检索服务。当索引失效或者明确搜不到时，允许用 grep 做定向回退。但每次回退都要记录原因和范围——这就是「收据」。

为什么要默认检索优先？因为随意的全仓 grep 不可审计——你不知道 Agent 为什么 grep、grep 了什么、范围多大。但完全禁止 grep 又不行——索引坏了的时候 Agent 就卡死了，什么都找不到。

类似地，在其他项目中也可以这样做：中高风险任务在广泛 grep 之前先走检索。用户明确指定了路径或者索引确实坏了，可以定向回退，但要记录原因和范围。先观察回退率，再对高风险任务改为失败关闭——也就是高风险任务不允许回退，必须走结构化检索。Cognition 的 SWE-grep 文章提供了一个思路：用专用的快速检索服务来辅助主 Agent，减少污染。不是禁止 grep，而是让 grep 有结构、有边界。

不这样做会怎样？索引搜不到的时候 Agent 就放弃或者瞎猜。或者回退范围太大造成污染——Agent grep 了整个仓库，结果全堆在窗口里，没有任何记录。

我们的实验验证了：不同搜索通道各有所长，先路由再回退比禁止 grep 或者只用一个通道都好。

## 第 22 页：共识 19 — 观测：取了什么 / 注入了什么 / 用了什么

### PPT 画面提示
- 左上角标签：共识 19 · PILOT（橙色）
- 主标题：观测——取了什么 / 注入了什么 / 用了什么
- 共识原文：Separate retrieved, injected, and utilized evidence.
- 中文翻译：把「取到」「注入」「用到」的证据分开记账。
- 要点：
  1. 来源：ContextBench · 证据 S
  2. 五层口径：请求了 / 返回了 / 注入了 / 确认进请求了 / 实际用到了
  3. 关键数据：找到但最终丢弃的正确答案占 17.9%-43.5%
  4. 拿不到的数据标「不可得」，不能用 0 冒充
- 视觉：五层漏斗图（请求 → 返回 → 注入 → 确认 → 使用）

### 演讲稿

第十九条是 PILOT，来自 ContextBench：把「取到」「注入」「用到」的证据分开记账。

这是诊断 Agent 任务失败原因的关键。只看最终成功率，你不知道是哪一环节出了问题。

在 LightVela 里，我们至少要分五层来看。第一层是请求了——Agent 请求了某项上下文。第二层是返回了——工具或服务返回了结果。第三层是注入了——我们的系统确认把结果放进了 context window。第四层是确认了——宿主确认进了最终发给模型的请求。第五层是用到了——模型的输出确实依赖了这个证据。

为什么要分这么多层？因为「读过文件」不等于「进了最终请求」，「进了请求」也不等于「模型真的用了」。在 LightVela 里，我们遇到过一个问题：QMD 搜索返回了正确结果，但结果里有隐藏目录的文件没被索引到。如果不分层观测，你只知道「结果不对」，不知道是搜索层、索引层还是排序层的问题。拆开看才发现是索引层漏了以点开头的目录。

ContextBench 的数据很说明问题：找到但最终丢弃的正确答案占 17.9% 到 43.5%。也就是说，很多时候系统确实搜到了正确答案，但在后续环节被丢掉了。如果不分层，你会以为是搜索的问题，去优化搜索，实际上搜索已经做对了。

类似地，在其他项目中也可以这样做：每次调用记录候选、注入及 token 位置、最终引用或补丁依赖、cache、compact、回退、索引版本。拿不到的数据标「不可得」，不能用 0 冒充。比如第四层「确认进入最终请求」通常拿不到——宿主不暴露这个——那就标不可得，不要写 0。

- 中文翻译：每次逃逸失败都应变成永久回归测试。
- 要点：

  2. 故障归因到具体层 → 回流成永久回归测试
  3. 真实案例：评测泄漏→黑名单 / 目录不可见→索引标准 / 图谱假边→跳数约束

- 视觉：循环图（失败 → 归因 → 回流 → 回归测试 → 防止再犯）

### 演讲稿

第二十条是 ADOPT：每次逃逸失败都应变成永久回归测试。

核心含义：没有回流就没有自进化，只会重复踩坑。Agent 今天在这里犯了错，下次还会犯，因为没有回归测试阻止它。

在 LightVela 里，我们已经有好几个真实的回流案例。

第一个：评测数据泄漏。第一轮跑 QMD 检索的时候，评测文件被一起索引了，搜索结果全部命中评测文件本身。我们把它变成了一个永久测试——每次构建语料都自动检查有没有把评测文件混进去。修复后测试转绿。

第二个：隐藏目录搜不到。QMD 这个工具默认不索引以点开头的目录——像 .workflow 和 .codebuddy 这些。导致两条搜索在四个通道全部返回 0。我们把它回流成索引覆盖标准——以后索引必须提供覆盖检查。

第三个：Aider 自动写盘。Aider 默认会往工作目录写 .gitignore、history 和 tag cache。我们回流成隔离 worktree 的要求——任何候选工具必须在隔离环境运行。

第四个：图谱假关联。codebase-memory 的调用关系图在多跳传播中产生了假关联——把一个不相关的测试文件关联了过来。我们回流成跳数和置信约束——图谱深度增加后必须限制跳数和置信度过滤。

类似地，在其他项目中也可以这样做：故障归因到具体层——是数据源的问题、索引的问题、搜索的问题、排序的问题、还是模型没用——然后回流成永久回归测试。逃逸回归必须加正确答案、失败轨迹、不变量、永久测试和负责人。

不这样做会怎样？同类故障反复出现。文档与实现持续分叉。闭环完成前不能宣称系统已「自进化完成」。

## 第 24 页：共识 21 — 模型按任务难度与可验证性路由

### PPT 画面提示
- 左上角标签：共识 21 · PILOT（橙色）
- 主标题：模型按任务难度与可验证性路由
- 共识原文：模型选择同时看任务复杂度、不确定性、失败风险和结果可验证性。
- 要点：
  1. 轻量模型：格式化/信息抽取/样板代码（结果可自动校验）
  2. 标准模型：功能开发/普通 bug 修复（有测试和验收标准）
  3. 强模型：架构设计/疑难故障/跨模块重构（需人工验收）
  4. 升级条件：连续两次无效尝试时升级
- 视觉：三列表格——轻量/标准/强，各列标任务特征、验证方式、失败代价

### 演讲稿

第二十一条是 PILOT：模型选择同时看任务复杂度、不确定性、失败风险和结果可验证性。

核心思想：不是所有任务都用最强模型。打个比方，你不会请一个主任医师来给你贴创可贴。

在 LightVela 里，我们分三档。轻量模型处理范围小、步骤固定、信息完整的任务——比如格式化提交说明、信息抽取、生成样板测试。标准模型处理单模块实现、约束清楚、需要一定推理的任务——比如明确需求的功能开发、普通 bug 修复。强模型处理需求模糊、跨模块、存在多种权衡的任务——比如架构设计、疑难故障、跨模块重构。

在 Skill 或 Agent 配置里声明用什么档位的模型。如果连续两次无效尝试、或者关键约束满足不了、或者任务范围扩大了，就升级模型并记录原因。

类似地，在其他项目中也可以这样做：在 Skill、Agent 或工作阶段配置里声明 model_tier。出现连续失败或约束无法满足时升级。同一稳定阶段不要频繁切换模型——会破坏 cache 和结果可比性。

不这样做会怎样？所有任务都用强模型，成本和延迟浪费。所有任务都用轻量模型，在模糊需求和高风险变更中产生错误自信、反复重试和返工。

边界：路由表是可评测的策略配置，不是永久规则。模型能力和价格变化后要重新校准。安全和生产高风险任务不能因为成本压力自动降级。

## 第 25 页：共识 22 — 工具集要少而精

### PPT 画面提示
- 左上角标签：共识 22 · ADOPT（绿色）
- 主标题：工具集要少而精——边界明确、参数精确、返回可控
- 共识原文：只向模型提供当前阶段真正需要、职责单一且描述精确的工具。
- 要点：
  1. 来源：内部 Effective Token 工具成本规范
  2. 工具定义本身是上下文成本：单次 grep 往返可能超 3,500 token
  3. 设计要求：数量少、职责单一、命名清楚、参数精简、返回结构化
  4. 对照实验：全量工具集 vs 阶段精确工具集
- 视觉：对比图——左侧「大而全」（15个重叠工具）vs 右侧「少而精」（3个精确工具）

### 演讲稿

第二十二条是 ADOPT：只向模型提供当前阶段真正需要、职责单一且描述精确的工具。宁可少给几个高质量工具，也不要堆一堆能力重叠、边界模糊的工具。

在 LightVela 里，我们的 Agent 有搜索代码、读取文件、修改文件、执行命令等工具。如果我们同时提供三个搜索工具——grep、ripgrep、向量搜索——模型光选哪个就纠结半天。而且工具定义本身是上下文成本——内部规范记录单次 grep 工具往返可能超过 3500 token。不光是返回内容占 token，工具的名字、描述、参数定义都占。

类似地，在其他项目中也可以这样做：每个阶段只给必要工具，一个意图保留一个首选工具。一个工具只做一件事，明确是读还是写、有没有副作用。用动作加对象命名——「搜索代码」「读取文件」——不要用 execute 这种看不懂的。参数必填项最少，用枚举和默认值约束。返回给结论、来源和引用，不要直接返回几千行日志。高频工具常驻，低频工具需要时才加载。

打个比方，你给一个人 15 把形状不同的锤子，他光选哪把锤子就纠结半天。你给他一把锤子、一把螺丝刀、一把扳手，他马上知道该用哪个。

不这样做会怎样？同一个意图有好几个差不多的工具，Agent 随机选或者反复试。工具参数太多，Agent 猜组合，生成无效调用。返回几千行原始日志污染 context window。工具定义频繁变化还破坏 prompt cache。

边界：少而精不等于隐藏必要能力。低频但关键的诊断工具可以按需加载。完整内容要保留可回源地址，不能为了缩短输出删掉排障需要的原始证据。

## 第 26 页：共识 23 — 经验增量沉淀：人工确认后进入正式知识库

### PPT 画面提示
- 左上角标签：共识 23 · PILOT（橙色）
- 主标题：经验增量沉淀：人工确认后进入正式知识库
- 共识原文：模型只能生成经验候选；经人工确认来源、正确性和适用范围后，才能进入正式知识库。禁止模型直接整篇重写或自动发布正式知识。
- 要点：
  1. 来源：ACE 对 Context Collapse 与增量更新的研究
  2. 流程：候选 → 人工确认 → 正式发布 → 持续治理
  3. 硬门禁：人工审批覆盖率 100%，未审批候选进入正式检索 = 0
  4. 禁止：模型做对一次就升规则 / 整篇重写 / 自评替代回归测试
- 视觉：流水线图（轨迹 → 候选 → Owner审核 → 发布 → 灰度 → 监控 → 回滚）

### 演讲稿

第二十三条是 PILOT：模型只能生成经验候选，经人工确认后才能进入正式知识库。禁止模型直接整篇重写或自动发布正式知识。

在 LightVela 里，一个典型场景：Agent 调试一个 payment 退款超时的 bug，发现查队列积压就能定位问题。它想把这个写成经验：「退款超时就查队列积压」。但这个经验适不适用于其他场景？是不是因果结论？有没有更优的排查路径？这些需要人工判断。

我们的做法是：模型只提交变更提案——包含来源任务、原始证据、适用范围、反例、置信度、负责人和过期时间。提案放在独立的候选区，正式搜索默认只读已发布的内容。负责人审核——核对事实对不对、因果关系成不成立、适用范围准不准、有没有跟现有知识冲突、有没有敏感信息——审核通过后才从候选升为已发布。到期或者被新事实替代了，就标记为废弃。

类似地，在其他项目中也可以这样做：用 GitOps 式的流程管理经验——候选变更、Owner 评审、合并发布，保留责任人、版本与变更历史。支持合并、替代、冲突处理、过期和遗忘。不搞整篇重写——增量更新避免逐轮抹去具体步骤、反例和来源。

不这样做会怎样？未经验证的推断被正式搜索反复检索和传播，形成错误自强化——越搜越觉得对，因为知识库里有。整篇重写让知识越来越泛，关键步骤消失，无法定位哪次修改引入了错误。

明确禁止：模型做对一次就把经验升为规则。整篇重写知识。用模型自评分数替代回归测试。线上自动调参但没有版本和回滚机制。

硬门禁：正式知识人工审批覆盖率必须 100%。未审批候选进入正式搜索的数量必须为 0。

### 演讲稿

做个总结。

我们已验证的工程结论有五条。第一，大仓必须把「全局导航」和「任务检索」分开评价——全仓静态地图一个目标都没命中。第二，缩小搜索范围确实有帮助——从全仓缩到前端代码，命中从 0 提升到 2。第三，任何工具必须在隔离环境运行——Aider 默认会往工作目录写文件。第四，工具的默认行为本身需要治理，不能只比搜索分数。第五，多路路由对找测试文件有统计显著收益——提升 11 个百分点。

落地路线分五个阶段。第一阶段 2 周，把规则源、知识格式、20 到 40 条测试用例、关键词搜索基线和事件标准跑通。第二阶段 3 到 4 周，建 Context Gateway——支持多路搜索、权限控制、引用追踪。第三阶段 3 周，接 MCP 适配器和跨宿主观测。第四阶段 3 到 4 周，加语义搜索、结果融合和重排。第五阶段持续做，建经验闭环——候选、审批、灰度、失败回流。

核心原则四条。事实源优先：代码大于文档大于生成内容大于历史。证据驱动：Stars 数不等于质量，必须用自己的测试数据验证。本地安全优先：默认离线、只读。强制但可降级：默认走检索，索引坏了允许有控制的 grep 回退。
