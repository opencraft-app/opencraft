# Product Requirements Document - mono (OpenClaw SaaS 控制面)

**Author:** Mason
**Date:** 2026-03-17
**Last Modified:** 2026-03-19（架构转型 + 矫正）

## 执行摘要

OpenClaw SaaS 控制面是一个 Go 后端 API 服务，为外部客户提供 AI Agent 运行时（OpenClaw）的全托管实例管理能力。用户通过购买 Coding Plan 套餐获得 OpenClaw 实例，无需了解任何云服务概念。

控制面通过调用沙箱服务 API 管理 OpenClaw 实例的生命周期。沙箱服务托管了底层网络隔离、资源调度和监控，控制面专注于配额管理和业务逻辑。创建/销毁操作通过沙箱 API 完成，大幅简化架构复杂度。

### 核心差异化

- **零门槛入口**：挂载在 Coding Plan 套餐下，手机登录即可获得实例，彻底消除"购买云服务器"的概念
- **沙箱服务托管**：底层网络隔离、资源调度由成熟的沙箱服务处理，控制面专注业务逻辑
- **成本优化**：支持暂停/恢复实例，节省闲置资源成本
- **完整生命周期**：创建、查询、暂停、恢复、销毁一体化管理

### 架构转型说明（2026-03-19）

原方案为控制面直接调用腾讯云 API 管理 VPC、CVM、安全组等云资源。现改为使用现成的沙箱服务（基于 E2B API），实现了以下变化：

| 方面 | 原方案 | 新方案 |
|------|--------|--------|
| 云资源管理 | 控制面直接管理 VPC/子网/SG/CVM/CLB/COS | 沙箱服务托管 |
| 网络隔离 | 自定义 VPC 隔离方案 | 沙箱服务自动隔离 |
| 运维操作 | 重启/重装/一键更新 | 不支持（沙箱限制） |
| 新增能力 | - | 暂停/恢复/超时设置/日志查询 |
| 异步流程 | 8步创建 / 5步销毁 | 控制面标记状态 + 调用沙箱 API |

### 矫正说明（2026-03-19）

文档审查发现以下过度设计问题并已矫正：
- **Template 管理**：从 MVP 移除。Template 是运维侧概念（我们预先准备的运行环境镜像），用户不感知。控制面通过配置指定默认 templateID，Template 的构建/管理作为内部运维流程处理
- **指标查询 API**：移除独立的 `GET /instances/{id}/metrics` 端点。沙箱 API 没有对应的单实例指标查询接口，实例资源信息可从详情接口获取
- **冗余抽象层**：SandboxProvider 接口 + 适配器两层合并为一层适配器

## 用户旅程

### 旅程 1：小白用户"小李"创建首个实例（核心路径）

小李是一位对 AI Agent 感兴趣的产品经理，从朋友那里听说了 OpenClaw。他在产品页面用手机号注册登录，购买了 Coding Plan 套餐。

系统后台收到创建请求，控制面 API 执行：检查配额 → 调用沙箱服务创建实例 → 记录实例信息。小李在页面上看到"创建中"的状态，几秒后刷新，实例变为"运行中"，获得访问入口。

**关键时刻**：全程零技术操作，几秒内获得可用实例。

### 旅程 2：企业用户"张经理"管理多个实例

张经理为团队购买了多个实例。他通过实例列表查看所有实例的状态。某个实例暂时不用，他执行暂停操作节省成本。一周后需要使用，他执行恢复操作，实例立即可用。

**关键时刻**：成本优化灵活，暂停/恢复一键完成。

### 旅程 3：实例创建失败的恢复路径

小李的创建请求因为沙箱服务资源不足而失败。控制面检测到失败，自动重试。重试 3 次后仍然失败，返回详细错误信息。上层系统通知用户创建失败并建议稍后重试。

**关键时刻**：系统自动重试，失败有清晰的错误信息。

### 旅程 4：运维监控

运维人员通过监控系统观察所有实例的状态分布、资源使用情况。发现某个用户实例异常，通过日志查询定位到具体问题。

**关键时刻**：状态可感知，日志可追溯。

### 旅程需求摘要

| 旅程 | 揭示的能力需求 |
|------|----------------|
| 小李创建实例 | 实例创建 API、配额检查、沙箱服务调用、状态查询 |
| 张经理多实例管理 | 实例列表、暂停、恢复 |
| 创建失败恢复 | 重试机制、错误信息记录 |
| 运维监控 | 状态可观测、日志查询 |

## API Backend 特定需求

### API 端点概览

| 端点 | 方法 | 说明 | 类型 |
|------|------|------|------|
| `/v1/instances` | POST | 创建实例 | 同步 |
| `/v1/instances` | GET | 查询实例列表（按用户） | 同步 |
| `/v1/instances/{id}` | GET | 查询实例详情 | 同步 |
| `/v1/instances/{id}` | DELETE | 销毁实例 | 同步 |
| `/v1/instances/{id}/pause` | POST | 暂停实例 | 同步 |
| `/v1/instances/{id}/resume` | POST | 恢复实例 | 同步 |
| `/v1/instances/{id}/timeout` | POST | 设置实例超时 | 同步 |
| `/v1/instances/{id}/logs` | GET | 查询实例日志 | 同步 |
| `/v1/instances/{id}/tasks` | GET | 查询操作历史 | 同步 |
| `/v1/quotas` | GET | 查询用户配额 | 同步 |

### API 响应约定

- 所有 API 响应的 `code` 字段均为字符串，而非整数
- 成功响应统一为 `{"code":"OK","message":"success","data":...}`
- 错误响应统一为 `{"code":"INSTANCE_STATUS_INVALID","message":"..."}` 这类结构，不再使用额外 `error_code` 字段
- 参数校验错误统一使用 `INSTANCE_INVALID_PARAM`

### 鉴权模型

API 鉴权由上层 Coding Plan 平台负责，不在当前控制面范围内。控制面接收已鉴权的请求，通过用户 ID 标识租户。

### 数据模型核心实体

- **Instance**：实例记录（用户ID、实例ID、沙箱ID、状态、创建时间等）
- **Task**：操作记录（操作ID、类型、状态、实例ID、创建时间等，用于审计追踪）
- **Quota**：用户配额记录（用户ID、最大实例数、已使用数）

**注意**：Template（镜像模板）由运维团队通过内部工具/CI 流程管理，不作为控制面数据模型。控制面通过配置获取默认 templateID。

### 沙箱服务集成

沙箱服务提供以下核心能力（控制面使用的部分）：

| 能力 | API | 说明 |
|------|-----|------|
| 创建沙箱 | POST /sandboxes | 指定 templateID 创建实例 |
| 查询沙箱 | GET /sandboxes/{id} | 获取实例详情和状态 |
| 查询沙箱列表 | GET /sandboxes | 按 metadata 筛选实例列表 |
| 销毁沙箱 | DELETE /sandboxes/{id} | 释放实例资源 |
| 暂停沙箱 | POST /sandboxes/{id}/pause | 暂停实例，节省成本 |
| 恢复沙箱 | POST /sandboxes/{id}/resume | 恢复暂停的实例 |
| 设置超时 | POST /sandboxes/{id}/timeout | 设置自动过期时间 |
| 刷新存活 | POST /sandboxes/{id}/refreshes | 延长实例存活时间 |
| 查询日志 | GET /sandboxes/{id}/logs | 获取实例运行日志 |

### 实现考量

- **语言**：Go
- **项目结构**：mono repo 下独立目录
- **沙箱服务集成**：通过 HTTP API 调用沙箱服务，封装为单层适配器（pkg/adapter/sandbox/）
- **配额管理**：控制面本地实现，数据库持久化
- **重试机制**：沙箱服务调用失败时自动重试（指数退避）
- **幂等性**：创建请求通过 idempotency key 保证幂等
- **Template 管理**：通过配置指定默认 templateID，Template 构建为内部运维流程

## 项目范围与分阶段开发

### MVP 策略

**MVP 方式**：问题解决型 MVP —— 解决用户"无法简单获得 OpenClaw 实例"的核心问题。

**核心用户旅程**：小白用户创建首个实例（旅程 1）。

### MVP 必备能力

1. 实例创建（配额检查 + 调用沙箱 API）
2. 实例查询和列表
3. 实例销毁
4. 实例暂停/恢复
5. 实例超时设置
6. 用户配额管理
7. 基础监控和可观测性（含沙箱日志查询）

### Phase 2：池化加速

- 沙箱资源池预创建和管理
- 用户创建时优先从池中分配
- 定时补充和过期回收机制

### Phase 3：运营能力

- 运营后台
- 批量管理操作
- 数据报表和统计
- 多规格支持

### 风险缓解

| 风险类型 | 风险 | 缓解策略 |
|----------|------|----------|
| 技术风险 | 沙箱服务 API 调用失败或超时 | 重试机制（指数退避），最大重试 3 次 |
| 技术风险 | 沙箱服务不可用 | 健康检查 + 告警，降级返回服务不可用错误 |
| 业务风险 | 用户创建并发超限 | 配额控制 + 请求排队 |
| 市场风险 | 用户增长超预期 | 架构设计支持水平扩展 |

## 功能需求

### 实例生命周期管理

- FR1: 上层系统可通过 API 为指定用户创建 OpenClaw 实例（调用沙箱服务）
- FR2: 上层系统可查询指定实例的详细信息和当前状态
- FR3: 上层系统可查询指定用户的所有实例列表
- FR4: 上层系统可销毁指定实例
- FR5: 上层系统可暂停指定实例（节省资源成本）
- FR6: 上层系统可恢复已暂停的实例
- FR7: 上层系统可设置实例的超时时间（自动过期）

### 沙箱服务集成

- FR8: 系统调用沙箱服务 API 创建 Sandbox 实例
- FR9: 系统调用沙箱服务 API 查询 Sandbox 状态和列表
- FR10: 系统调用沙箱服务 API 销毁 Sandbox 实例
- FR11: 系统调用沙箱服务 API 暂停/恢复 Sandbox 实例
- FR12: 系统调用沙箱服务 API 设置 Sandbox 超时和刷新存活时间
- FR13: 系统调用沙箱服务 API 查询 Sandbox 日志

### 配额管理

- FR14: 系统维护每个用户的实例配额（最大实例数）
- FR15: 创建实例前检查用户配额，超限拒绝创建
- FR16: 实例销毁后自动释放配额

### 监控与可观测性

- FR17: 系统记录所有 API 请求的结构化日志
- FR18: 系统暴露关键业务指标（创建成功率、实例状态分布、配额使用率）
- FR19: 系统支持查询实例的操作历史记录

## 非功能需求

### 性能

- NFR1: 同步 API 端点 P99 响应时间 ≤ 500ms
- NFR2: 实例创建端到端耗时 ≤ 30 秒（P95）
- NFR3: 系统支持 200 个并发用户的实例管理操作

### 可靠性

- NFR4: API 可用性 ≥ 99.9%
- NFR5: 沙箱服务调用失败后自动重试，最终成功率 ≥ 99%
- NFR6: 所有沙箱服务调用保证幂等性（使用 idempotency key）

### 安全

- NFR7: 租户间数据隔离（按用户 ID 过滤所有查询）
- NFR8: 沙箱服务 API 密钥加密存储，不在日志中泄露
- NFR9: 所有操作记录审计日志（操作人、操作类型、操作时间、结果）

### 可扩展性

- NFR10: 架构设计支持水平扩展（无状态 API 服务）
- NFR11: 数据模型预留池化资源管理扩展点（Phase 2）

### 集成

- NFR12: 通过 HTTP API 集成沙箱服务
- NFR13: 提供标准 RESTful API 供上层 Coding Plan 平台调用
