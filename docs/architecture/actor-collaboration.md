# 原生主体与 Hub 协作设计纲领

状态：目标设计，依据 2026-10-15 用户裁决整理，2026-10-17 收敛为四个核心概念并明确 Hub 的网络定位，保留核心/插件边界与威胁模型。本文件规定后续身份与协作建模的方向，不表示对应协议、准入服务或多租户隔离已经实现。当前执行契约与兼容边界见[执行所有权](../execution-ownership.md)。

## 单 Hub 首期协作闭环

Headless 已实现认证 Actor 的持久私聊消息、接收/已读回执、显式 Codex 运行绑定及 queue / 指定 Turn steer 请求；目标授权与绑定代次在接纳及队列领取前复核。消息、投递、执行请求和原生执行回执分别保留。范围、HTTP 契约、恢复和未实现边界见[主体协作接口](../actor-collaboration-api.md)。这不表示跨 Hub 或共享 Shell/文件隔离已经实现。Headless本地Codex适配器的会话引用、上下文读取和服务端工具属于同一核心协作入口，实际能力及旧会话边界见[会话互通](conversation-interoperability.md)。

会话互通沿用本纲领，实现遵循[会话引用、读取与投递](conversation-interoperability.md)规定的统一核心。Conversation 是资源，Session 是主体；稳定引用不随运行绑定变化，不强制将所有历史 Thread 发行成 Actor。

## 四个核心概念

| 概念 | 要回答的问题 |
|---|---|
| 主体 Actor | 谁在行动：人类、持久 Bot/Session；身份不随机器、连接或模型实例变化 |
| Hub | 从哪里接入、如何找到并联系目标：具有自身身份的逻辑网络节点 |
| 资源 Resource | 操作什么：消息通道、文件、运行、配置；主体本身也可作为被操作的资源 |
| 权限 Permission | 谁可以对什么做什么，以及作用域、有效期和必须遵守的限制 |

交互统一表达为：

```text
主体发起动作 → Hub 路由与入口校验 → 目标资源权威检查权限并执行
```

其余概念分别是四者下的地址、属性、关系、资源种类或过程记录，不再并列为额外的顶层领域概念，也不据此要求独立服务：Endpoint 是 Hub 的接入地址；租户、组织和项目是资源与权限的作用域；Channel 是协作资源；运行绑定关联执行实例与主体；消息、投递和执行记录保存交互过程。简化顶层概念不合并这些事实的身份、状态或唯一写入者。

人类与 Bot 对称；主体身份稳定；网络可达、身份可信、动作获准相互独立。

## 主体性与权限相互独立

人类与持久的 Agent / Bot / Session 都是原生协作主体（Actor）。Session 可以接收任务、主动发起消息、订阅状态，并在授权范围内连接或控制另一个 Session；不能只把它建模成人类操作下的被动容器。产品语境中的 Agent、Bot、Session 可以是同一个主体的不同称呼，不因称呼不同自动创建三套身份。

主体性不意味着无限权限。受预设权限约束的 Session，与受管理的人类一样，仍以自己的身份行动。模型、工具与运行实例是主体的执行能力，不是主体身份本身；一次 Turn、一个连接或临时引擎对象也不自动成为新主体。

| 维度 | 要回答的问题 | 不可混同的事实 |
|---|---|---|
| 身份 | 谁在行动？ | 不由模型、机器、连接或创建者决定 |
| 能力 | 它能执行什么？ | 有工具不代表被授权使用 |
| 授权 | 对什么资源允许做什么？ | 人类身份不天然高于 Session 身份 |
| 管理关系 | 谁能配置、限制或撤销它的权限？ | 创建者、管理者、执行者与代办者不是同一角色 |
| 运行绑定 | 目前在哪里执行、如何联系？ | 断线、迁移、卸载实例不删除主体 |

创建 Session 不自动复制创建者的全部权限。默认操作以 Session 自身身份审计；代表人类或其他主体执行时，必须有显式委托，并同时保留实际行动者和委托链。委托不能扩大授权，也不能因代理层数增加而绕过撤销或有效期。

权限同时表达授予与强制限制；新增授予不能隐式解除已有强制限制。配置模型、停止运行、授予权限与解除限制分别授权，创建者记录不自动产生永久管理权。因果链只说明动作来源，不自动构成委托链。

## 主体、协作对话与执行上下文分开

| 对象 | 身份与生命周期 |
|---|---|
| Actor | 持久协作主体；本纲领中的 Session 指具有主体性的持久实体 |
| Channel / 协作对话 | 多个主体交流的空间，拥有成员和协作消息历史 |
| 执行上下文 | 引擎的 Thread、模型上下文与具体运行实例；通过显式绑定确定行动主体 |

不规定 Actor 与引擎 Thread 一对一。同一个主体可以参与多个 Channel，并在明确授权与运行协调下使用多个执行上下文；共享对话也不能因只有一个页面或一份历史而被推导成只有一个主体。每次执行都须确定行动者，不能从最近消息作者或当前查看者猜测。

复制执行历史、Fork Thread 和克隆主体是不同操作。历史分叉本身不决定是否发行新主体；产品若提供“克隆主体”，须单独定义新身份、管理关系、权限及凭据处置，不能默认复制原主体的凭据或授权。旧 Thread 到主体的兼容映射应保留这种区分，不把执行坐标作为永久身份。

## 可寻址身份与通用准入

主体使用 URI 表达稳定身份，目标形式为：

```text
human://<identity-domain>/<immutable-id>
session://<identity-domain>/<immutable-id>
```

这是身份命名约定，具体编码与规范化规则仍须在协议落地时定义。identity-domain 是身份发行命名空间，不等于当前机器、连接地址或某个 Hub 的部署域名。显示名是别名，不作为授权、审计或存储主键；身份 URI 也不是可直接使用的 HTTP 地址、凭据或持有即授权的 capability。

同一主体可以经多个 Hub 接入或被联系、绑定不同 Runtime；这些变化不改变身份。解析身份、发现路由与建立连接分层进行，不能把当前可达地址写成永久身份，也不要求先建立一个全球统一身份数据库。

人类注册和 Session 注册共用身份准入机制；证明方式可以不同，例如人类使用已有登录体系，Session 使用可信运行时签发的注册证明与自身凭据。身份注册、接入 Hub、加入协作资源和取得显式权限是独立事实，各自可以更新或撤销；已有用户登录不能直接推导出 Bot 准入已经完成，接入某 Hub 也不自动获得组织或租户成员关系。

“可信调用上下文”必须有可验证的构造边界，不能只是可由任意调用方填写的类型。核心从受信任身份来源、已认证连接或受限运行凭据建立主体绑定；来源、适用 Hub/受众、有效期、撤销与运行代次均须纳入验证。Runtime 只可代表明确绑定给它的主体，旧连接或旧实例的证明不能继承后继绑定。URI、签名有效但用途不匹配的断言、安装插件和进程内传入的 `actor` 字段都不能单独证明调用资格。具体证明格式留待协议定义，不把秘密凭据交给模型。

## 多种登录方式绑定同一自然人

**自然人身份是主对象，登录方式是身份绑定；多种登录方式落到同一个 human Actor。**
此处的唯一性限于同一身份发行域，不要求全球统一账号库，也不按相似资料自动识别或合并不同域中的人。

```text
本地账号 ─┐
OIDC 身份 ┼─ 身份来源验证 → 核心解析身份绑定 → human Actor → 登录态与准入检查 → 资源授权
企业身份 身份 ─┘
```

1. **一个人可绑定多种登录方式。** 同一身份域中，每个登录身份只能绑定一个 human Actor；增加登录方式不发行另一个人。权限、资源归属与操作审计关联稳定 Actor，不能以用户名、邮箱、插件 ID 或当前登录方式作为主体主键。操作审计可以另外记录本次认证来源。
2. **外部身份使用稳定标识。** 本地账号使用不可变账号 ID；OIDC 使用受信任的 `issuer + sub`；企业身份 使用受信任 provider 与不变员工 ID。用户名、显示名、邮箱、照片属于可变资料，不作为自动合并依据。OIDC 是接入协议，企业 SSO 是使用场景，企业可以直接使用 OIDC 接入同一体系。
3. **绑定与解绑有独立验证和授权。** 增加绑定须验证已有主体的控制权和待绑定身份，不能仅凭邮箱一致认领已有 Actor；管理恢复须走明确授权并审计的独立流程。不能将已绑定身份静默改绑给另一人。解绑或轮换凭据不自动删除 Actor、迁移资源或复制权限；须明确撤销范围并避免意外失去最后一种恢复方式。
4. **核心拥有统一身份与授权。** 身份来源适配器负责自己的凭据或外部证明验证，只向核心交付已验证的稳定身份及有效性信息；核心管理绑定、主体生命周期、登录态、准入、授权和撤销。客户端自报 `actorId`、安装插件或认证来源宣称管理员均不构成授权。登录成功不自动获得实例成员或资源权限。
5. **开源分发可以独立完成登录。** 标准分发应自带本地账号登录与可配置的通用 OIDC 接入；企业身份 等专用企业验证通过可选插件提供。不要求部署者依赖官方云账号、企业内部服务或另行部署身份平台，才能使用本地登录。管理员初始化、邀请与恢复是部署策略，不能让首个匿名访问者自动获得管理员权限。
6. **登录态与 Session 主体分开。** 浏览器或客户端登录态证明自然人的当前接入；持久 Bot/Session 是独立 Actor，使用自己的可撤销凭据。退出一次登录、撤销某个绑定、禁用自然人和撤销 Bot Session 凭据是不同操作；创建者关系不使 Bot 自动继承自然人的身份或权限。

本节是持续有效的设计约束。Headless 已实现本地账号、通用 OIDC、浏览器登录与显式绑定/解绑；初始化、配置、权限及恢复边界见[服务器登录](../server-authentication.md)。没有公开注册、邮件找回或跨 Actor 自动合并。
已有本机匿名工作区、产品服务账号与资源连接仍遵循各自契约；提供登录能力本身不改变匿名准入策略，也不自动合并其他产品账号或授予其服务权益。
当前主体核心的已实现范围见[首期主体核心](#首期主体核心自然人与-session)。

## Hub 是网络节点，Runtime 是执行载体

Hub 是有自身稳定身份的逻辑网络节点，承担接入、身份/目标解析、路由选择、转发资格校验与分发；订阅及事件投递同样受资源权限约束。Endpoint 是连接 Hub 的具体地址，一个 Hub 可以有多个 Endpoint；地址改变不自动改变 Hub 身份。Runtime 承担模型、工具、文件和具体执行。

Hub 与组织、项目、租户及 Channel 的归属分别建模。一个 Hub 可以承载多个作用域的流量，同一主体或资源也可以经多个 Hub 被联系；不能从接入节点推导成员关系或资源权限。Hub 可以与身份目录、授权及协作资源服务同进程部署，但网络拓扑不决定这些资源的授权权威。

逻辑责任不要求物理拆分：单进程或单机也能承载 Hub、持久收件箱和 Runtime；多进程与远程部署是拓扑选择。现有 Client / Hub / Server 仍可作为连接、适配与执行协议的术语，不能据此把 Server、Host 或 Renderer 当成人类和 Session 的上位身份。

跨 Hub 需要显式信任、路由及逐跳转发资格校验，目标资源权威仍复核具体动作的权限。不能因经过同一 Hub 或同一主体出现在两个 Hub，就合并权限或放宽可见范围。经多个 Hub 可达的同一个 Session 仍是同一个主体。

## Hub 通过级联形成网络

**Hub 可以通过直连、中继等方式相互连接、级联，组成更大的协作网络。** 单 Hub 是这一网络的最小部署形态；首先实现单 Hub 多租户，不改变后续通过多 Hub 互联扩展网络的纲领。网络不要求所有 Hub 彼此直连，也不预设唯一中心或固定父子树。

中继提供连接与转发路径，不自动成为新的主体身份发行方或目标资源授权权威。经中继或多个 Hub 联系同一个主体，不复制主体身份、租户成员关系或资源所有权；网络接通不产生隐式信任、委托或权限。Hub 间须明确对端身份、信任范围与可转发的目标/作用域，逐跳校验转发资格，目标资源权威仍校验实际行动者及具体动作。

级联必须有有界跳数、环路拒绝、路由代次、撤销和故障恢复约束。中继断开、路由切换或 Hub 重连不删除主体及目标资源状态；旧路径不能沿用过期授权，替代路径不能扩大作用域。多路径与重试沿用稳定交互标识和现有投递/执行权威进行去重、查询及对账，不能将中继接受等同于目标执行完成，也不能因路径变化重复执行。Web 传输切片已在核心 `hub-network` 实现稳定节点密钥、签名邀请、连接代次路由、有界逐跳 HTTP/WS 转发与撤销。它复用普通 relay 流式通道；原始外部身份发行方签向末端实例，管理员显式接受发行方，目标核心复核本地成员。设置、离线首次接入和独立转发节点配置见[中继部署](../relay-deployment.md#hub-network-and-cascading-connections)。该切片不复制 Actor registry 或 Session 授权，不实现通用资源联邦，也不自动重放中断的业务写入；目标动作去重、执行对账及完整故障切换仍按后续实现切片定义。

## 核心与插件的边界

**主体、授权和 Hub 分发进入核心；身份来源、执行引擎和通信渠道通过插件接入。** 这是上述目标设计的实现边界，不表示这些能力已经全部实现。

| 责任 | 核心拥有 | 插件接入 |
|---|---|---|
| 主体 | 稳定身份、证明验证后的绑定、准入与运行绑定生命周期 | 人类登录、Session 注册证明等身份来源及其验证适配 |
| 授权 | 资源与动作权限、委托约束、撤销、授权判定与审计 | 将外部证明交给核心，执行目标资源所属权威要求的校验 |
| Hub 分发 | 接入与目标解析、路由选择、转发资格校验、授权后分发、订阅撤销及投递证据 | 执行引擎和通信渠道的具体协议、连接与能力适配 |

调用遵循同一个入口关系：

```text
身份或渠道适配 → 核心验证并绑定行动主体 → Hub 解析目标与检查转发资格
             → 目标资源权威复核 → 引擎或渠道适配执行
```

插件不能通过请求体自报的 `from`、显示名或原消息作者指定调用主体，也不能因安装、激活或提供某项能力而自动取得主体权限。核心只接受受信任验证路径建立的主体上下文；适配器携带该上下文与受限授权依据，不能替调用者扩大权限。目标资源权威仍拥有最终校验，队列领取、延后执行与持续订阅均须响应权限失效。

这条边界同时适用于浏览器请求、原生入口、后台任务、模型工具和渠道消息。Session 收到 A 的消息后继续行动，默认行动者仍是该 Session；只有显式委托才代表 A 执行。消息的不可变作者、当前行动主体和承载执行的 Runtime 必须分别保存，创建者或参与人记录不自动成为资源授权。

核心可用内部模块或 Cordis 组装，可以与 Hub 同进程运行，核心服务生命周期独立于界面和可选插件；关闭界面、卸载渠道或身份插件不能关闭授权检查。具体插件不可用时，对依赖它且无法重新验证的操作拒绝或保持待处理，不能降级为匿名放行。可信本地插件仍不是安全沙箱；需要隔离不受信代码时，另由受限进程和窄能力接口承担。

## 授权能约束的实际边界

Hub 授权直接约束经过其受控入口的交互。若主体或插件仍可使用共享高权限 Shell、原生 RPC、数据库、文件或进程控制通道绕过 Hub，拒绝 Hub 请求不能证明目标资源已被隔离。例如，中断权限被拒后仍能直接杀死目标进程，不能算作控制权限隔离通过。

实现前须枚举浏览器、IPC、原生 AppServer、后台调度、引擎工具和外部渠道等入口，以及执行侧实际持有的资源权限。每条可产生相关副作用的路径都须接入授权检查，或由独立安全边界限制。共享进程中的可信代码不能仅靠 TypeScript 类型限制；面对不受信插件或敌对租户，必须落实所需的进程、文件、数据库和凭据隔离，并按真实部署拓扑验证。连接 lease、插件化和统一分发本身不构成这些隔离。

## Channel 与 Session 分开建模

Channel 是协作资源，承载私聊或多人消息；人类与 Session 都可以是成员。Session 不是 Channel 下的被动聊天记录。普通消息面向 Channel，控制命令面向目标 Session 的运行、配置等资源；直接联系另一个主体可以解析为双方的私聊 Channel。

Channel 的消息历史、每个主体的投递状态、Runtime 的模型上下文与执行记录是不同事实。加入 Channel 不表示自动获得其他成员的文件、凭据、运行控制或其他 Channel 的权限。模型 transcript 可以消费消息，但不替代协作历史真源。

Session 何时需要回应，由显式注意力与唤醒策略决定，例如定向消息、提及或任务分派；不能把所有消息和回执都自动注入所有模型，造成互相唤醒循环。

## Session 之间可以联系，也可以受权控制

通过 Hub，Session 可以像人类一样发现其他主体、读取获准状态、订阅事件、发送消息与分派工作。控制是独立的授权动作，不能用“能发消息”推导“能中断执行”。以下名称仅表达目标动作分类，不是已经发布的 API：

| 动作分类 | 授权边界 |
|---|---|
| 发现、读状态、订阅 | 按资源与可见范围授权，持续订阅响应撤销 |
| 消息与工作投递 | 校验目标 Channel 或 Session 的投递权限 |
| `run.interrupt` / `run.cancel` | 明确到目标 Session 与执行范围 |
| `config.update` / `lifecycle.manage` | 与普通消息、读状态分开授权 |
| `grant.manage` | 显式管理权限；不因能控制运行而取得 |

控制 Session 不意味着能读取其凭据。Hub 从已验证的连接或凭据确定实际发送者，不能相信请求体自行声明的 `from`、显示名或 `senderThreadId`。目标执行端还必须校验授权的适用范围、有效期和撤销状态；排队后执行也要重新确认，不能只在 UI 或入队瞬间检查一次。

投递权限也不自动成为目标主体能力的间接使用权。A 即使只能给 B 发消息，也可能诱导 B 利用自身权限读文件并把内容发回。B 以自身身份执行只解决归因，不能防止这种代理滥用。目标须分别约束消息接收、可接受的服务/任务、内部资源操作和结果返回的对象及范围；消息正文不能自行授予其中任何权限。面向调用者提供受控服务时，应显式定义服务能力和输出约束，不能一律用双方权限的交集替代，也不能让普通消息隐式兑换成 B 的全部能力。

## 撤销、领取与副作用边界

权限检查和执行之间存在竞态。请求应保留可核对的授权依据与策略/运行代次；领取与撤销由明确权威仲裁，并在同一权威可控制的范围内使用事务或执行栅栏。执行前再次检查只是必要步骤，不能承诺任意外部副作用都可撤回。

| 状态 | 撤销及恢复要求 |
|---|---|
| 尚未领取 | 撤销后不得取得新的执行资格；持久接受不等于已获不可撤销的执行权 |
| 已领取、尚未提交副作用 | 执行权威用撤销/代次栅栏阻止过期领取继续提交，明确判定边界 |
| 已向引擎或外部系统提交 | 依动作能力尝试取消；不能保证回滚已经发生的副作用，须记录已提交事实 |
| 是否提交或执行结果未知 | 先查询、对账或进入显式处置；不能把超时当失败直接重发 |

持续订阅也要定义撤销生效点：在受控投递边界停止新的未授权事件，不能宣称已经发送或被读取的数据可被收回。跨进程、远端系统和其他无法原子提交的边界须分别声明取消、幂等与结果查询能力。

## 可靠投递与执行分层

每个 Session 的待办与收件箱应有明确的单一权威，可以位于 Hub 侧或现有后端。不能因为 Runtime 是执行载体，就要求所有队列必须物理放入 Runtime；也不能在已有可执行队列旁新增一套会重复派发的队列。

持久消息、每个收件人的投递状态和执行任务是三个事实，可以共库但不能合并成一个状态对象。接收成功不要求立即启动模型，离线、忙碌或等待批准的主体仍可按策略接收消息。消息转换为执行任务须有明确的单一协调权威、稳定关联和幂等交接；复用现有执行队列不等于用 Turn 队列替代协作消息或收件箱。

投递证据至少区分 Hub 已持久接受、已投递到收件箱、唤醒信息已注入、模型已读取，以及执行已完成。它们不是一个 `success` 状态，也不一定是严格线性步骤：模型可能读取持久收件箱，唤醒通知则可能合并或重试。收到 ACK、收到通知、模型处理和业务完成不能互相替代。

重试使用稳定消息标识、幂等键与可查询结果。断线后的未知结果先查询再决定重试，不承诺所有引擎和外部工具的副作用都能端到端“恰好一次”。队列编辑、取回、取消与领取的竞争由队列权威仲裁，UI 隐藏不等于撤销执行权。

自动协作须保存关联链和因果来源，定义唤醒资格、去重、链路预算及终止条件；普通回执、重复通知和状态广播不默认唤醒模型。A/B 互相回复也须受明确预算和策略约束，不能仅以单条消息合法推导整条自动协作链可以无限继续。

## 多租户是这一模型的局部落地

个人本地协作、团队协作、Agent 之间协作、多 Hub 和多租户共用上述四个概念。租户是需要隔离的管理与资源作用域，不替代主体身份，也不对应某个固定 Hub 或 Endpoint；主体加入多个租户也不获得跨租户隐式访问权。

要宣称多租户隔离成立，除成员关系与路由外，还必须验证历史、文件、凭据、数据库访问、订阅、缓存和执行资源的隔离与撤销。只有 `tenantId` 字段、侧栏筛选或连接租约不足以证明完成。

## 从当前实现演进

现有源码的 `ConversationKey` 仍是 `(hostId, threadId)`，见 [`chat-core/identity.ts`](../../packages/chat-core/src/identity.ts)；Client / Hub / Server 的 attachment、route 与 lease 类型见 [`client-hub-server.ts`](../../packages/workbench-runtime/src/client-hub-server.ts)。这些类型和连接隔离不等于原生 Actor 准入与多租户体系已经落地。

[执行所有权](../execution-ownership.md)中的 `(serverId, threadId)` 是现有执行命名空间契约。演进时应通过显式映射关联稳定 Session URI，保留旧链接、历史与持久标识；不能直接把现有 `hostId` 拼成新身份并宣称迁移完成。引擎适配、历史和 Turn 的既有唯一所有权继续有效。

建议按可验证闭环推进，各步再独立形成协议与数据迁移设计：

1. 围绕主体、Hub、资源、权限四者明确对象关系、部署信任边界和所有副作用入口；定义身份发行、网络路由、受限运行绑定与旧 Thread 兼容映射，不预设主体与 Thread 一对一，也不把 Hub 等同于租户。
2. 定义授权、服务能力、输出范围、领取/撤销生效点和未知结果恢复；再落地统一动作入口及目标执行端校验。
3. 在单 Hub 打通人类和两个 Session 的真实投递/回复闭环，复用现有执行权威，同时验证下表失败与攻击序列；浏览器关闭后仍可运行，不以成功演示代替安全验收。
4. 扩展多人 Channel、多 Hub 与租户隔离，逐项验证跨 Hub 信任、权限不扩散及部署资源隔离，未覆盖部分明确保留为未实现。

首个闭环的验收须同时覆盖：

| 序列 | 必须证明的性质 |
|---|---|
| 伪造 Actor、自报 from、旧连接重放、错误受众证明 | 无法建立冒名调用；原消息作者不能冒充当前行动者 |
| 同一主体绑定多个上下文、Fork 历史、运行迁移 | 身份与上下文分离，旧绑定无法控制后继实例 |
| 同一 Hub 承载不同作用域、同一主体经多个 Hub 可达、Endpoint 变更 | 主体/Hub 身份稳定，路由不复制主体，网络接入不授予资源权限或合并作用域 |
| 经中继多跳联系、环路、断链重连与替代路径重试 | 跳数有界、拒绝环路及过期路由，身份/资源归属稳定，权限不扩散，未知结果先对账且不重复执行 |
| A 可发送但无中断/管理权限 | 发送、控制与管理权限分离；已声明受控的其他入口也不能绕过 |
| A 诱导高权限 B 读取并返回受限资源 | 服务与输出约束真实生效，不以 B 自身身份掩盖信息泄漏 |
| 入队后撤销、领取期间撤销、已提交后取消 | 按上述生效点阻止或报告，已发生副作用不冒称撤回 |
| ACK 丢失、重复投递、Hub 重启、目标离线或迁移 | 消息可查、交接可恢复，未知结果不盲重试，无两个独立派发者 |
| A/B 自动互相回复、重复通知与回执 | 因果链、唤醒策略与预算能终止循环 |
| 声明租户隔离的部署中尝试共享 Shell/文件/库/凭据访问 | 实际资源隔离成立；未隔离部署不能宣称敌对租户安全 |

主体注册协议、授权存储、URI 规范化、Channel 存储、跨 Hub 信任与引擎兼容策略仍需后续具体设计。本纲领先统一模型，不预设数据库选型，也不以新增名词替代真实实现与验收。


## 首期主体核心：自然人与 Session

`identity-core/actors` 定义 human / session 的共用 Actor 和受信任调用上下文；
`access-control/actors` 在 Headless 私有数据目录的 `actors.sqlite` 持久保存主体、
外部身份绑定、Session 凭据摘要、精确授权和变更审计。企业身份 插件只输出已验证的
provider + 不变 StaffId，核心将它绑定到 human Actor。登录名变化仅更新显示名；
不按别名合并账号，不从请求正文中的 actorId / sender 认领身份。

地址为 `human://<identity-authority>/<id>` 或 `session://<identity-authority>/<id>`。
identity-authority 是本地身份库中持久生成的标识，不是 HTTP 域名、部署地址、组织或
Hub 路由身份。恢复同一身份库保留身份；复制库不是创建一个新的独立身份域。
本期 Session 需显式注册，Thread、fork 历史和执行进程不会自动生成或复制 Actor。
尚未实现 Session 到执行引擎的绑定，以及跨 Hub 的 Actor registry / Session 身份与资源授权联邦。后续 Web 中继切片对原始外部自然人发行方的显式信任，不等于复制或联合这些主体库。

自然人用已验证外部证明接入，Session 用独立 bearer 接入，同一个 `/__opencraft_actors/me`
返回主体。Session 凭据绑定本身份域、主体代次和有效期（最长 30 日），仅签发时返回
明文，持久化只存摘要；撤销、过期和主体禁用均阻断后续调用，重新启用不复活旧凭据。
具名自然人禁用后不能降级为匿名，已有具名 WebSocket 通过核心轮询复核撤销。
creator 只记录来源，不继承权限。`ActorContext` 是服务端构造的上下文，不能反序列化
客户端提交的同名结构后当作身份证明。

授权按精确的 Actor / Resource / Action 存储；人和 Session 使用同一判断逻辑，默认拒绝，
无隐式父路径、通配、角色继承或 creator 权限。本身份库仅能为自身 registry 和本地
Actor 资源记录授权，不能代其他 Hub、工作区或引擎授予权限。`actors.manage` 对
`actor-registry://<identity-authority>` 的授权允许维护本库；既有实例管理员仅作为
本地管理能力的兼容启动入口，不因此获得其他业务资源权限。管理请求读完正文后再次
检查准入、过期、主体代次和授权，撤权不能被慢请求绕过。

这是持久主体与接入基础，不是完整多租户或可互相控制的 Bot 网络。旧共享执行接口尚未
接入资源级 Actor 授权，新 Session bearer 被明确拒绝进入这些 HTTP / WebSocket 接口；
不能以新身份接口存在宣称历史会话、文件、模型凭据或执行资源已隔离。自然人的原有实例
准入仍由既有成员策略决定，不因创建主体库自动启用门禁。执行适配、资源控制 API、
领取队列时的权限重检与撤销 fencing 继续按前述纲领分步落地。
