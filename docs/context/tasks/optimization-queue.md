## 队列规则

1. 新需求按收到顺序追加到队尾，并分配稳定 ID 和独立分支；仅用户明确指定极特殊插队时调整处理顺序，记录原因。
2. 队首从 `queued` 进入 `active` 后，只在该分支排查、实现和验证。已完成本地实现的项也继续占据队首，直到交付流程完成；历史上的 `done_local` 不表示已出队。需要用户决定产品规则或外部配置时，状态改为 `pending_user`，在会话中提出具体问题，等待回复后恢复同一项；此时不取出下一项。
3. 每项本地完成后，按项目规范在同一独立分支提交并推送预览，记录实际预览地址与验收结果；完成提交前 CR，修复发现的问题并复验；准备指向 `master` 的 MR 标题、描述和验证证据。把预览、CR、MR 草稿与剩余风险汇总给用户，状态为 `pending_user`，等用户确认后创建 MR。MR 创建后按项目规范继续 Fanny 与负责人 CR。创建 MR 前不得宣称这两项已完成。
4. 用户确认后的 MR 操作及后续评审完成才标记 `done` 并出队；再处理下一项。发现外部依赖导致不能继续时记录证据与阻塞条件，不把未解决项默默跳过。
5. 队列文件记录需求和状态；每项的代码、测试、任务记录都留在对应分支。Git 与发布操作仍遵守仓库 `AGENTS.md` 的确认要求；用户本次已明确要求推送预览，创建 MR 仍需等待本项汇总后的确认。
6. 每个优化需求对应「Vela体验优化」TAPD 轻协作项目 `70234090` 的一张需求卡。入队时建卡并放入「待优化」；开始处理移至「进行中」；需要用户决策或外部条件时移至「待确认」并写明问题；MR 创建后待 Fanny/owner CR 与预览验收时移至「待验收」；所有交付与验收完成后移至「已完成」，同时把 TAPD 原生状态从 `open` 改为 `done`。每次流转均同步卡片描述、队列文件和会话进度；TAPD 卡片是真实看板记录，不以本文件替代。
