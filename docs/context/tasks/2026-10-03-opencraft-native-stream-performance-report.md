# OpenCraft RN 长会话流式输出性能报告

日期：2026-10-03。范围：`workbench-expo` 的原生对话列表及共享 Markdown 渲染。本文是代码路径审查，**没有真机帧率、内存或触摸延迟数据**。

## 当前路径与已确认成本

| 阶段 | 当前实现 | 可确认的成本和边界 |
|---|---|---|
| 流式内容变更 | `WorkbenchConversation` 在 `timeline` 变更时重新 `groupTimelineFramesByTurn`，生成 `entries`。 | 每次新时间线对象都会重新分组；是否每个网络 delta 都触发一次更新，取决于上游批处理，本文未实测。 |
| 虚拟布局 | `NativeVirtualizedConversationTurns` 根据 `entries` 和已测高度执行 `buildTurnLayout`。 | 布局遍历全部 Turn，生成高度、顶部和底部偏移及 key 索引；通常挂载可见 Turn 加前后各 2 条 overscan，待定位时额外挂载目标的有界邻域，重叠行不重复挂载。数据规模增长时，重建布局仍是 O(总 Turn 数)，即使只更新最新回复。 |
| Markdown | `NativeChatDocument` 通过共享 `ChatDocumentSessionView` 编译 `source`，再映射文档节点到原生组件。 | 正在增长的消息会进入 JS 的编译与 React 渲染路径；是否重用旧节点由文档 session 决定，重 Markdown 下的每次耗时需性能采样，不能按源码推断帧率。 |
| 高度测量 | 挂载的 Turn 用 RN `onLayout` 回传高度；每帧批处理变化，`createTurnMeasurementTransaction` 在高度改变时复制高度表并重建布局。 | 测量回调、批处理、事务和 React 状态提交均经过 JS。已用挂载租约过滤旧行回调，避免过期高度污染几何；这不等于消除 JS 工作。 |
| 物理滚动 | Native `ScrollView` 报告 `onScroll`/`onContentSizeChange`；`NativeConversationViewportOwner` 合并位置写入，流式回复的跟随由共享状态机决定。 | 平台滚动由原生执行，但窗口更新、内容高度补偿与跟随判定仍依赖 JS 及时收到布局/滚动事件。 |

## 与 Paseo 的关系

固定参考 `/data/mono2/ref/paseo/packages/app/src/agent-stream/strategy-native.tsx` 使用倒置 `FlatList`、`maintainVisibleContentPosition`、`windowSize=10`，并把 live head 与历史行分开。其性能文档记录服务端 60 ms leading/trailing 合并、客户端每帧提交、按积压节奏显示文字，以及稳定历史行身份；这些是 Paseo 的数据与列表契约，不是本项目现成的性能结果。OpenCraft 当前以 Turn 为窗口单位，维护精确的折叠高度、响应留白、恢复位置和项内锚点。直接替换成倒置 `FlatList` 会改变这些几何与恢复语义，必须先证明等价，不能将 Paseo 的测量数字套用到 OpenCraft。

## 风险判断

1. **最高优先级：最新回复高度持续变化。** 长 Markdown、代码高亮、表格、公式或图表会增加 JS 渲染与异步重新测量。若同一帧内的编译、React 提交及测量事务合计超过设备帧预算，用户会看到字符更新不均匀、滚动跟随迟滞或输入响应变慢。这是基于执行路径的风险推断，尚无真机证据。
2. **总 Turn 数的线性工作。** 单条最新回复增长时仍可能重新分组和重建整份 Turn 布局；10,000 Turn 的纯算法单测只证明窗口有界，不能证明流式情况下的 JS 帧耗时或内存稳定。
3. **可见窗口内的重节点。** 虚拟化按 Turn 而非 Markdown 块裁剪；一条极长 Turn 即使只有一部分在屏幕上，也可能挂载完整原生文档。公式或图表的离线 WebView 节点、图片解码与代码着色还会增加非 JS 内存和布局成本。
4. **测量与滚动事件竞态。** 图片尺寸、折叠状态、键盘和输入区高度会在流式输出期间改变几何。当前事务与单一滚动 Owner 提供一致性模型，但实际低端设备上事件滞后、跟随恢复和用户上滑接管仍须设备观察。

## 真机验证方案

在发布构建或接近发布的构建上，用同一离线回放数据比较 iPhone 60 Hz / ProMotion、iPad 分栏及一台 Android 中端机；场景至少覆盖 100、1,000、5,000 Turn，纯文本和包含长代码、表格、图片、公式的 Markdown，以及连续流式、上滑后继续输出、折叠与键盘开合。

采集每次内容更新的间隔、JS 线程任务耗时、React 提交耗时、`onLayout` 次数和每帧测量批量、布局事务耗时、掉帧/冻结时长、输入触摸到响应时间、滚动位置误差，以及峰值内存与 GC。同时记录设备、系统、刷新率、构建模式和回放数据版本；只统计可见正文的增长，避免把原始网络 token 速率当作屏幕流畅度。按设备刷新率比较帧预算（60 Hz 约 16.7 ms，120 Hz 约 8.3 ms），不要只报平均值，至少报 p95、最长停顿和最差场景。

若确认瓶颈，再按证据选择优化：优先检查时间线更新是否可以批处理、历史 Turn 身份是否稳定、布局是否能增量更新；其次考虑对超长单 Turn 做块级窗口化或降低异步媒体同时挂载数。任何改动都须保留用户上滑接管、折叠补偿、恢复位置、项内锚点及响应跟随的现有语义。

## 本次结论

代码已具备有界的 **Turn 挂载窗口** 与测量事务，但 **JS 侧的全量布局重建和可见长 Turn 渲染仍是待测风险**。目前无法判断“重 Markdown 长会话是否足够流畅”，也不能以 Paseo 的 `FlatList` 方案或其历史性能数据替代 OpenCraft 真机采样。

后续布局事务整改已加入内容/宽度测量代次、当前窗口与远处目标的双窗口挂载，以及动画中语义目标的几何重算。上述改动处理位置正确性和迟到回调，不将测量迁往 UI 线程，也不消除全量布局重建；本报告的真机采样要求仍适用。
