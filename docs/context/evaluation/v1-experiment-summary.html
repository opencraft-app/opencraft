结论

方向正确，但还不能下“显著有效”的结论。 Treatment 在 Top-5 Recall、MRR、Full Recall 上都高于 Control，平均 Token 消耗下降约 9.9%，样本层面 21 胜 / 15 平 / 14 负。但 Bootstrap 95% 置信区间为 [-0.032, +0.120]，包含 0，所以还不能宣称统计显著的收益。

更重要的是：50 条里只有 23 条 Treatment 真的读取了 docs/context。当前阶段的最大问题不是“上下文不够多”，而是“上下文没有被稳定消费”。下一步应优先让上下文变成必读、可验证的工作流入口，而不是继续堆文档。

指标中文释义

指标中文含义好方向
Control对照组，使用仓库原有上下文（原 AGENTS.md、服务级 AGENTS.md、OpenSpec、Skills）。作为基线
Treatment实验组，使用本次建设的上下文（docs/context、路由、23 条规则、任务模板、Skill 清单）。作为改进
Top-5 RecallAI 提出的前 5 个改动文件中，有多少比例是真实 MR 改过的文件；衡量“能不能快速定位到要改哪些文件”。越高越好
MRR第一个正确文件在候选列表里的排名倒数（1/名次）；衡量“第一个答对的改动文件排得够不够靠前”。越高越好
Full RecallAI 提出的全部文件里，命中真实 MR 改动文件的比例；衡量整体覆盖率，而不是只看前 5 个。越高越好
Tokens单个任务实际消耗的 token 数；越低说明越省成本。越低越好
Wall Time单个任务从开始到结束的墙钟耗时；越低说明越快。越低越好
Tool Calls模型执行 shell 命令的次数；反映探索是否克制、是否高效。通常越低越好
Paired Difference同一个任务下 Treatment 减去 Control 的差值；正数表示实验组更好。正数且越大越好
Bootstrap 95% CI对配对差值反复重采样得到的 95% 置信区间；如果区间包含 0，说明还不能证明显著有效。区间不包含 0 才算显著
Context ConsumptionTreatment 日志中是否真的读取过 docs/context；衡量上下文是“放进了仓库”还是“真的被消费了”。越高越好

简单说：Recall/MRR 看“找得准不准、排得靠不靠前”，Tokens/Time/Tool Calls 看“省不省钱、快不快”，CI 看“结论稳不稳”。

下一步

  • 让 docs/context/README.md 和 context-routing.yaml 成为任务开始前的必读项。
  • 注入高信号紧凑 Context Pack，避免模型自己找文档。
  • 在 runner 中增加 consumption preflight，未消费上下文标记为 context_not_consumed。
  • 扩大并分层样本，至少 120 条有效 paired 数据，并做 held-out 验证。
  • 固定同一模型后，再做 reasoning low / medium / high 对照。
