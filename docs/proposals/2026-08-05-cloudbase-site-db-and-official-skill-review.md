## 0. 结论速览

| # | 问题 | 结论 |
|---|---|---|
| 1 | **共享 TCB 环境 + TCB 原生数据库能否做到用户间数据隔离？** | **不能。** 只能做到「靠 siteId 猜不到」的混淆级隔离，不是安全隔离。详见 §1 |

## 1. 多租户隔离：先说风险（这条最重要）

### 1.1 结论

在**「共享 TCB 环境 + 站点静态文件直连 TCB 数据库」**这个形态下，
**做不到 LightVela 用户之间的数据隔离**。如果按这个形态上线，属于可预期的数据泄露事故。

### 1.2 为什么做不到（事实链）

**事实 1：浏览器端凭据是环境级的，不是站点级的。**
TCB Web SDK 的初始化参数是 `env` + `region` + `accessKey`（publishable key）。
publishable key 从「云开发平台 / ApiKey 管理页」按**环境**签发，权限等级是「匿名用户权限」，
官方明确说明「可以暴露在浏览器中」。
（来源：官方 Skill `references/http-api-cloudbase/SKILL.md`、`references/auth-web-cloudbase/SKILL.md`）

我们的部署模型是**多个用户的站点共享同一个 TCB 环境**（`workers/internal/website/tcb_env.go`，
按 `TCB_ENV_ALLOWLIST` 从 COS 桶名发现环境）。
因此**同一把 publishable key 会出现在所有用户的站点页面里**。任何人打开任意一个 LightVela 站点、
查看源码，就拿到了访问该环境**全部集合**的入场券。

**事实 2：TCB 安全规则的隔离维度是「访客身份」，不是「站点身份」。**
安全规则的内置变量只有 `auth`（`auth.uid` / `auth.openid` / `auth.loginType`）、`doc`、`request`、`now`。
**没有任何变量能表达「这个请求来自哪个站点」**。
规则能写出「用户只能读自己的文档」，写不出「站点 A 的访客只能读站点 A 的集合」。
（来源：官方 Skill `references/cloudbase-document-database-web-sdk/security-rules.md`）

**事实 3：安全规则是「校验」不是「过滤」。**
官方原文：*Security rules validate queries, they don't filter results.*
系统校验「输入的查询条件是否为规则的子集」，不满足直接拒绝。
这带来两个后果：
- 很多直觉写法（`.doc(id).get()`）会因为查询条件里只有 `_id`、不含规则要求的字段而被直接拒绝；
- 规则变更有 **2–5 分钟缓存**，调试期极易误判"规则写错了"而反复改错方向。

**事实 4：「匿名登录默认关闭」不能当作安全依据。**
官方两处明确：新环境匿名登录默认关闭，**但用 `accessKey` 初始化的 SDK 依然会创建一个轻量匿名会话**用于 API 访问。
官方原文提醒：不要用 `getLoginState()` 的返回值当登录凭证，因为带 `accessKey` 时它在未登录状态下也会返回一个 uid。
也就是说，"没开匿名登录 = 外人进不来"是错的。

### 1.3 攻击路径（具体到可复现的步骤）

假设按「每站点一个集合命名空间 `ws_{siteId}_messages`」来做隔离：

1. 攻击者访问自己的（或任意一个）LightVela 站点，从 HTML/JS 里读出 `env_id`、`region`、`publishable key`。
2. 攻击者拿到另一个用户的站点链接 —— 站点 URL 形如
   `https://{env}-{app}.tcloudbaseapp.com/sites/{siteId}/current/index.html`，
   **siteId 直接写在 URL 里**，而站点本来就是给人分享用的公开页面。
3. 攻击者在自己的页面里用同一把 key 初始化 SDK，直接 `db.collection('ws_{受害者siteId}_messages').get()`。
4. 只要该集合的规则允许读（留言板必须允许公开读），**受害者的数据直接被读走**；
   若允许写，还能写脏数据、刷爆共享环境的资源点。

**结论：这是"security by obscurity"**。而且这里连 obscurity 都不成立 —— siteId 是站点自身公开 URL 的一部分。
一旦有人做的是「活动报名表」（含手机号、姓名），这就是直接的个人信息泄露。

### 1.4 残余风险（即使采用推荐方案）

推荐方案（§3.3 形态 C）能**结构性解决租户之间的隔离**，但下面两类风险**任何方案都消不掉**，必须产品侧接受：

| 残余风险 | 说明 | 缓解 |
|---|---|---|
| 站点自身的写入端点是公开的 | 留言板/报名表本质就是「谁都能提交」。攻击者可以脚本刷提交 | 服务端限速（IP + siteId 双维度）、单站点记录数上限、单条大小上限、`Origin` 校验、站长可一键清空 |
| 站长自己把敏感数据设成公开读 | AI 生成留言板时如果把「报名信息」也做成公开列表 | Skill 层面强约束：**默认「公开写 + 仅站长可读」**，公开读必须是用户显式要求的场景（留言板） |

## 2. 子任务一：官方 CloudBase Skill 调研

### 2.1 调研对象与获取方式（含一条事实纠正）

`https://skillhub.cn/skills/tencent-adm/cloudbase` 是一个纯前端 SPA，
HTTP 抓取只能拿到 7KB 的空壳 HTML，拿不到 Skill 正文。
真正的源在 **`TencentCloudBase/cloudbase-skills`**（同时镜像在 `cnb.cool/tencent/cloud/cloudbase/cloudbase-skills`）。
本次已完整 clone 并通读：commit `c51c30b`（2026-08-05），Skill 版本 `2.25.10`。

结构上它**不是 22 个平级 Skill**，而是：
- 1 个主入口 `skills/cloudbase/SKILL.md`（163 行，只做路由，不含实现细节）
- `references/` 下 30+ 个子技能目录，各自带 `SKILL.md` + `checklist.md` + `references/`
- 1 个 `references/activation-map.yaml` 作为路由契约的唯一真源，主入口的路由表由它**自动生成**

### 2.2 它的建站编排 vs 我们的

| 环节 | 官方 | 我们 |
|---|---|---|
| 入口 | 场景识别 → 路由表选子技能 → **读完整 SKILL.md 才允许写代码** | 单文件 Skill，直接顺序执行八步 |
| 资源准备 | **阶段 2a 必须先于前端代码**：MCP 建集合/开登录方式/配安全规则 | 无（一期纯静态） |
| 需求澄清 | `spec-workflow` / `ui-design` 先出规格；最小 demo 路径明确**跳过**这些仪式 | 第三步四个问题（类型/风格/板块/语言），追问不超过 1–2 个 |
| 产物约束 | 无体积/文件数上限（他们按对象存储计费）；强调相对路径、SPA 404 文档 | 有 `max_artifact_size` / `max_files`，强制根目录 `index.html`，强烈建议单文件 |
| 部署 | 首次必须 `manageApps createApp`（独立子域），增量才用 `manageHosting` | 单一路径：创建 release → PUT zip → worker 同步到 `current/` |
| 失败处理 | **同一路径失败 2–3 次强制停止重路由**；同一根因 3 次强制停止打补丁并输出根因 | 只有错误码 → 用户语言的翻译表，没有"何时放弃" |
| 完成判定 | 静态层（tsc/lint/build）+ 运行层（`agent-browser` 真开页面）双层，都跑过才能说完成 | 轮询 operation 状态到 success |
| 破坏性操作 | Deployment Gate：输出 checklist 模板 → **等用户确认**才动手 | 无确认步骤 |
| 留痕 | 部署信息写回 README.md，供下次更新复用 | 靠"站点地址固定不变"这条语义 |

### 2.3 建议纳入（9 条，按投入产出比排序）

> 说明：以下只是建议清单，**本次未改动 `.agents/skills/cloudbase-site-builder/SKILL.md`**。

| # | 建议 | 理由 | 预估改动 |
|---|---|---|---|
| **A1** | **加入简化版 UI 设计规范**：生成页面前先输出 3 行设计声明（用途 / 美学方向 / 配色+字体），并给禁用清单（紫/靛/品红渐变、Inter/Roboto/system-ui、纯居中卡片布局、emoji 当图标） | 我们的第四步只写了体积和路径约束，**完全没有审美约束**。结果就是所有用户拿到同一张"白底紫渐变居中卡片"。官方为此专门写了一整个 `ui-design` 技能 + 自检 grep 清单。这是**用户第一眼就能感知**的质量差距，改动最小、收益最大 | SKILL.md 加约 25 行 |
| **A2** | **明确禁止 History 模式路由** | 官方明确：SPA History 路由必须把静态托管的 404 文档指向 `index.html`，否则刷新子路由 404。**我们走的是共享 COS 对象前缀，根本没有 errorDocument 这个配置项**，所以这个坑在我们这里无解。必须写死"多页请用 hash 路由或真实 `.html` 文件"。这是我们**当前真实存在但没写**的坑 | 加 2 行 |
| **A3** | **失败重路由上限** | 官方："同一路径失败 2–3 次就停止改路"、"同一根因出现 3 次就停止打补丁并输出根因"。我们现在只翻译错误码，没有停止条件 → AI 可能反复重建站点，**每次重建都吃一个席位**，直接触发配额投诉。建议：发布失败 2 次后停止，改为提示用户精简内容；**任何情况下不要为了重试而新建站点** | 加 5 行 |
| **A4** | **会话内记住 site_id，禁止重复建站** | 官方的等价物是「部署信息写回 README」。我们的席位很贵（启航 1 站），AI 忘了已建的站点就会再建一个。建议明确："同一会话中已经建过站点，后续修改一律走"新建发布"，不要再调创建站点接口" | 加 3 行 |
| **A5** | **破坏性操作前置确认** | 官方 Deployment Gate 要求输出 checklist 并等确认。我们的「重新发布」会**覆盖 `current/` 并删除上一版残留文件**（deployer 的 `syncToCurrent`），用户无感。建议对"重新部署已有内容的站点"和"删除站点"加一句确认 | 加 3 行 |
| **A6** | **加一张「做不了什么」的能力边界表** | 官方有 `scenarios.md` 做需求→能力映射。我们缺反向表：需要登录 / 支付 / 后台管理 / SSR / 长连接 / 定时任务 → 明确告诉用户不支持，而不是硬生成一个"假的"登录页骗用户。这条直接减少"页面点了没反应"的投诉 | 加一张 6 行小表 |
| **A7** | **上传成功不等于成功** | 官方反复强调"不要把 resolved promise 当成功，要检查返回体字段"。我们的 zip PUT 只看 HTTP 码。建议至少显式区分「上传失败」和「部署失败」两类错误，给用户不同的话术 | 加 2 行 |
| **A8** | **先生成产物、再创建发布** | 我们有"创建发布后约 60 秒内必须上传"的硬窗口（handover §2.12）。官方的做法是把耗时准备工作和凭据等待并行。建议在 Skill 里明确顺序："先把 zip 准备好，再调创建发布"，把 60 秒窗口全部留给网络传输 | 加 1 行 |
| **A9** | **回滚到上一版**（官方**没有**，但我们几乎白送） | 我们已经有 `website_releases` 历史 + `superseded` 状态 + `executeResume`「从保留制品重新上传」的完整代码路径。加一个「回滚到上一版」只是复用现成能力，用户感知很强 | 后端约 2–3 人日 + Skill 3 行 |

### 2.4 不适用于我们的模型（6 类）

| 内容 | 为什么不适用 |
|---|---|
| 全套鉴权体系（`auth-tool-cloudbase` / `auth-web-cloudbase` / publishable key / provider 配置 / `getSession()` 守卫） | 已决策：鉴权用我们自己的，腾讯云凭据平台侧统一持有，**用户不感知**。这部分整体不采纳 |
| CloudBase MCP（39 个工具）与 `tcb` CLI 作为管理面 | 我们的管理面是 `/v1/websites/*`，AI 不直接碰腾讯云。官方"必须先装 MCP 插件"的前置在我们这里是负资产 |
| `manageApps createApp` 独立子域 / `manageHosting` / `setWebsiteDocument` | 已决策共享 COS 目录，不回 CloudApp（handover 已论证：每站一应用会撞环境应用数上限 + 构建管道拖慢部署） |
| 自定义域名 / ICP 备案 / SSL 证书门禁 | 一期明确不做。若要做，备案责任落在平台侧，成本远超收益 |
| 云函数 / CloudRun / AI 模型 / 小程序 / Agent SDK / PostgreSQL RLS 章节 | 不在建站范围内 |
| `agent-browser` 强制浏览器自检 | Hermes 侧不保证有浏览器工具，且会显著拉长一次建站的耗时。建议只在用户主动说"帮我看看效果"时才做 |

### 2.5 他们有、我们有意不做（3 项）

| 能力 | 官方做法 | 我们的判断 |
|---|---|---|
| **先预览再发布** | 本地 dev server 起预览，用户确认后才部署（`minimal-web-baas-demo` 的 "Preview first, deploy second"） | **不做**。我们没有本地 server 的概念，而且我们的站点地址固定不变、重发即生效，"直接发了再改"的成本比引入预览态更低。引入预览会多一套状态机 |
| **自定义域名** | 完整门禁（套餐档位 / ICP / 证书 / `bindCustomDomain` vs `createRoute`） | **一期不做，长期也建议只给高档套餐**。ICP 备案是强监管环节，平台代办的责任和人力成本都很高 |
| **回滚到上一版** | 官方其实**也没有**显式回滚 | 见 A9 —— 这是我们**比官方多**的机会点，建议做 |

## 3. 子任务二：TCB 数据库能力接入方案

### 3.1 TCB 数据库的形态与访问方式（事实）

| 形态 | 说明 | 来源 |
|---|---|---|
| **文档型数据库（NoSQL）** | 集合 / 文档，支持 CRUD、聚合、事务、实时 `watch()`、索引；权限由「基础权限」（READONLY / PRIVATE / ADMINWRITE / ADMINONLY）或 CUSTOM 安全规则控制 | 官方 Skill `cloudbase-document-database-web-sdk/` |
| **MySQL（关系型）** | 完整 SQL，数据模型、索引；JS SDK / Node SDK / HTTP API | 腾讯云文档 876/121348 |
| **PostgreSQL（CloudBase PG）** | `app.rdb()`、行级安全 RLS、迁移、pgstore；**环境创建后架构不可切换** | 官方 Skill `postgresql-development-cloudbase/`；PRD §86 |

访问方式与鉴权模型：

| 访问方式 | 凭据 | 权限等级 | 能否放浏览器 |
|---|---|---|---|
| Web SDK (`@cloudbase/js-sdk`) | `env` + `region` + **publishable key** | 匿名用户权限，受安全规则约束 | 可以（官方明说可暴露） |
| Web SDK + 登录后 | 上面 + 用户 session | 该登录用户权限 | 可以 |
| HTTP API | `Authorization: Bearer <access_token / apikey / publishable_key>` | 分别是登录用户 / **管理员** / 匿名 | 只有 publishable key 可以，**API Key 绝对不行** |
| Node SDK（服务端） | 主账号/API Key | 管理员，**完全绕过安全规则** | 不可以 |
| 云函数内 | 环境内置身份 | 管理员，**绕过安全规则** | N/A |

**关键约束（必须记住）**：
- **单账号最多同时存在 50 个 TCB 环境**（腾讯云文档 876/47177，「系统限制 - 环境」）。
- 单集合索引数量上限 20 个；数据库单次出包 16MB。
- 资源点（数据库读写、云函数、CDN 流量、存储）**同一环境共享一个资源池**（876/19343、876/120713）。
  → 共享环境下，**一个用户站点被刷，会烧掉同环境所有用户的资源点配额，并可能触发 QPS 超限计费**。

### 3.2 「用户不感知 TCB」前提下的四种可行形态

#### 形态 A：TCB Web SDK 直连 + 安全规则

站点代码长这样：
```html
<script src="https://static.cloudbase.net/cloudbase-js-sdk/latest/cloudbase.full.js"></script>
<script>
  const app = cloudbase.init({ env: 'xxx-yyy', region: 'ap-shanghai', accessKey: '<publishable key>' });
  const db = app.database();
  await db.collection('ws_<siteId>_messages').add({ name, content });
</script>
```

| 维度 | 评价 |
|---|---|
| 凭据从哪来 | 平台在「开通站点数据能力」时把 env/region/publishable key 通过 API 下发给 AI，AI 写进页面 |
| 用户感知 | **会破功**。env_id、`tcloudbaseapp.com`、`cloudbase-js-sdk` 全部出现在用户自己的页面源码里 |
| 隔离性 | ❌ **不成立**，见 §1.3 |
| 后端新增 | 少（下发凭据 + 建集合 + 配规则） |
| AI 生成难度 | 中（要处理规则子集校验、`_openid` 自动注入、写返回体检查、2–5 分钟规则缓存） |
| 结论 | **否决**。安全不过关，且违反"用户不感知 TCB"的产品硬决策 |

#### 形态 B：TCB 云函数中转

在共享环境里为每个站点部署一个云函数做数据网关。

| 维度 | 评价 |
|---|---|
| 现状差距 | 我们现在只上传静态文件（`deployer.go` 走 COS）。要新增 SCF/Manager SDK 的创建、更新、删除、权限配置全套生命周期 |
| 凭据问题 | **没解决**。浏览器调云函数仍然要 publishable key 或函数的公开 HTTP 地址 + 某种 token |
| 隔离性 | 函数内部可以按 siteId 隔离（函数以管理员身份运行、绕过安全规则），但前提是**函数能可信地知道调用方是哪个站点** —— 又回到"浏览器凭据"这个原问题 |
| 成本 | 函数数量随站点数线性增长；冷启动；官方自己的 `minimal-web-baas-demo` 明确"CRUD 场景云函数数量 = 0" |
| 结论 | **否决**。工作量最大、收益最小，且没解决核心矛盾 |

#### 形态 C：LightVela 自有数据代理（**推荐**）

站点代码长这样（无 SDK、无 npm、单文件站点也能用）：
```html
<script>
  const API = 'https://api.lightvela.com/v1/site-data';
  const SITE_KEY = 'sk_pub_xxxxxxxx';   // 平台下发的站点级公开密钥
  await fetch(`${API}/messages/records`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'X-Vela-Site-Key': SITE_KEY },
    body: JSON.stringify({ name, content })
  });
</script>
```

| 维度 | 评价 |
|---|---|
| 凭据从哪来 | 平台按 **站点** 签发 `site_public_key`，与 `site_id` 一一绑定，存我们自己的库 |
| 用户感知 | ✅ 完全不感知 TCB。页面里只有 `api.lightvela.com` |
| **隔离性** | ✅ **结构性隔离**。key → siteId 的映射在服务端，A 站的 key 在协议层就够不到 B 站的数据。不依赖任何"猜不到"的假设 |
| 读写模型 | 可以做 TCB 做不到的事：**每个集合独立配置「公开读 / 仅站长可读」**。报名表默认「公开写 + 仅站长可读」，留言板才开公开读 |
| 后端新增 | 数据面接口（增删查改 + 分页）、site key 签发与轮换、限速与反滥用、记录数/大小配额、站长侧查看与导出 |
| 存储后端 | **一期直接落 ctl 的 MySQL**（`website_site_records`，`payload JSON`）。不依赖 TCB 企业版采购 |
| AI 生成难度 | ✅ **最低**。纯 `fetch`，无 SDK、无 init、无登录态、无安全规则子集这套心智负担 |
| 结论 | **推荐** |

#### 形态 D：每用户一个独立 TCB 环境（PRD 原定的二期方案）

| 维度 | 评价 |
|---|---|
| 隔离性 | ✅ 最彻底（环境之间资源完全隔离） |
| **致命约束** | **单账号最多 50 个环境**（876/47177）。按 500 新用户/周，即使只给付费用户开，也会在极短时间内耗尽 |
| 其他成本 | 每环境独立计费、独立套餐、`CreateEnv` 限频 20 次/秒但账号级配额是硬墙；环境创建后 NoSQL/PG 架构不可切换 |
| 结论 | **一期二期都不可行**。只可能作为「高档套餐的独享环境」这种小规模特权，需要先跟腾讯云确认能否提额，且要有跨主账号的分片方案 |

### 3.3 推荐方案（形态 C）的分层设计

```
用户站点（静态 HTML，共享 COS）
    │  fetch + X-Vela-Site-Key（站点级公开密钥）
    ▼
service-gateway  ── 新增一条 public（免 Bearer）路由 /v1/site-data/*
    │              ⚠️ 这是本方案唯一的新增公网攻击面，必须单独安全评审
    ▼
ctl  site-data logic
    ├─ key → site_id 解析（含站点 status 校验：suspended/deleting 直接拒）
    ├─ 限速：IP 维度 + siteId 维度双闸（复用现有 Redis limiter）
    ├─ 配额：单站集合数 / 记录数 / 单条大小
    ├─ 集合读写模式：public-read | owner-only-read
    └─ 落库：ctl MySQL  website_site_collections / website_site_records
                                    ▲
「我的网站」前端 ─ 走用户 Bearer ────┘（查看、导出 CSV、删除、清空）
```

要点：
- **数据面（站点调用）和控制面（站长调用）用两套完全不同的鉴权**：前者 site key、后者用户 Bearer。
- 站点 `suspended`（套餐到期下线）时，数据面接口必须**同步拒绝**，与静态文件下线保持语义一致。
- 站点删除时，数据一并删除（与制品清理同一个 `executeDelete` 语义）。
- 一期**不做**跨站点查询、聚合、实时推送、全文检索。

### 3.4 配额设计

现有配额（`user_resource_quota`，`resource_name = 'WEBSITE_STATIC_SITE'`）是**按用户的席位账本**，
每用户单行、按 `(user_id, resource_name)` 定位（handover §2.8 刚修完重复行超卖）。

**建议不要把「记录数」塞进这张表。** 理由：席位账本是"占用/释放"语义，记录数是 per-site 的运行时计数，
放进同一张表会重新引入 2.7/2.8 那类"多行/匹配不到行"的缺陷。

推荐做法：

| 维度 | 落在哪 | 启航(free) | 巡游/ai | 说明 |
|---|---|---|---|---|
| 是否开通数据能力 | `user_resource_quota` 新增 `WEBSITE_SITE_DATA`（只做档位开关，不做计数） | 开通 | 开通 | 与建站一样全量开通 |
| 单站点集合数 | 站点级校验（`bundle_static_site_quota` 扩字段） | 2 | 5 | 防止 AI 乱建集合 |
| 单站点记录数 | `website_sites` 加计数列 或 `website_site_data_usage` 表 | 500 | 5000 | **这条必须做**，见下 |
| 单条记录大小 | 入参校验 | 16 KB | 16 KB | 与 TCB 单次出包 16MB 的量级对齐留足余量 |
| 写入速率 | Redis 限速器（复用 `WEBSITE_REQUIRE_REDIS_LIMITER` 的 fail-closed 语义） | 10 次/分/IP，200 次/天/站 | 30 / 2000 | |

> ⚠️ **不要照搬「存储和流量后端一期不做限制」这条既定决策。**
> 那条决策成立的前提是：静态托管的写入面只有站长自己（经过我们的鉴权）。
> 数据能力的写入面是**公网任何人**，不设上限等于开放一个免费的匿名存储写入服务。
> 记录数上限和写入限速是**必须做的**，不是"顺手补上"。

## 4. 是否建议本次一起上：**否**

### 4.1 理由

1. **一期自己还没落地。** 生产 GitOps 接线一项都没做（gateway 路由、SOPS、`workers-website-deployer` 的 overlay 与 Argo App、worker 跨集群访问 ctl 的架构决策），
   TCB 企业版采购是外部依赖仍未闭环。在一个还没上线的链路上叠加新能力，回归面会失控。
2. **风险等级不同。** 一期是「只读静态托管 + 平台侧鉴权写入」。
   DB 能力引入的是**公网免登录写入端点**，这是一条全新的攻击面，需要独立的安全评审、限流方案和滥用应急预案。
   把它和一期上线挤在同一个窗口，等于让上线评审同时背两个量级的风险。
3. **一期还有未清的账。** handover §4 记着 7 处实现与 TAPD 文档不一致待回写、
   国际站入口门控未定、`docs/superpowers/plans/` 的 checkbox 与实际进度不符。
4. **如果走 TCB 原生 DB，方案根本定不下来。** 环境模型（50 上限）、资源点隔离、企业版 key 作用域，
   三个关键输入全部依赖尚未完成的采购。

### 4.2 对一期上线时间的影响（如果强行并入）

- 乐观：+3 周（形态 C，且安全评审一次过）
- 现实：+4~6 周（含 gateway public 路由的安全评审往返、反滥用方案定稿、越权 PoC 与回归）
- 若选形态 A/D：**不可估**，因为方案本身定不下来

### 4.3 建议节奏

| 阶段 | 内容 | 时间 |
|---|---|---|
| 一期 | 按现状上线（采购到位 → GitOps 接线 → 迁移 → 灰度） | 不变 |
| 并行（不占一期工期） | 越权 PoC（0.5 人日）+ 形态 C 的接口契约评审 | 一期上线前 |
| 1.5 期 | 形态 C 最小可用：**单站点默认 1 个集合 + 公开写 + 仅站长可读 + 限速 + 记录数上限 + 站长查看/导出** | 一期上线后 2 周启动，16–26 人日 |
| 二期 | 公开读（留言板）、多集合、简单查询/排序/分页、A9 的版本回滚 | 8–12 人日 |
| 三期（视需求） | 真正的 TCB PG + RLS + 独立环境（仅限高档套餐，且需先解决 50 环境上限） | 10–20 人日 + 采购 |

## 5. 分期建议汇总

**1.5 期（最小可用，推荐范围）**
- 每站点 1 个默认集合（名字固定，比如 `submissions`），不让 AI 自由建集合 → 大幅降低出错面
- 只支持：提交一条记录（公开写）、站长在「我的网站」查看/导出/删除（仅站长可读）
- 不支持：站点页面读取数据（也就是**一期不做留言板，只做表单**）
- 限速 + 记录数上限 + 单条大小上限，全部 fail-closed
- Skill 提供一个「报名/联系表单」的单文件模板

> 之所以把「公开读」留到二期：公开读一旦上线，用户数据是否泄露就取决于 AI 有没有正确判断场景。
> 先只做「写进去、只有站长看得到」，是零判断风险的起点。

**二期**
- 公开读集合（留言板场景），Skill 里明确区分两种集合类型并强制 AI 二选一
- 多集合、简单 where/orderBy/分页
- A9 版本回滚

**三期（可选）**
- TCB PG + RLS + 独立环境。**先决条件：确认 50 环境上限能否提额**

## 6. 与你描述不符 / 需要纠正的事实

1. **「产品还希望加 DB，本次一起加」与 PRD 的既有决策直接冲突。**
   `wiki/prd-docs/2026-07-31-cloudbase-static-site-entitlement.md` 已经明确写了：
   - §38「NoSQL … **不向一期用户直接开放**」
   - §55「当前未验证 … **用户隔离数据库** … 是本需求的验收前置或后续范围，**不是既成事实**」
   - §86「共享环境**无法只凭目录隔离数据库** … 二期按独立环境提供；PG + RLS 是首选」
   所以这不是"新增一个功能"，而是**推翻一条已经论证过的决策**。我的结论和 PRD 当时的结论一致。

2. **「二期按独立环境提供」这条 PRD 决策本身也站不住。**
   腾讯云文档 876/47177 明确：**每个账号最多可同时存在 50 个环境**。
   按 500 新用户/周，一人一环境的模型在极短时间内就会撞墙。二期方案需要重新设计。

3. **skillhub 页面抓不到内容。** 它是 SPA，`curl` 只能拿到 7KB 空壳。
   真正的源是 GitHub / cnb.cool 上的 `TencentCloudBase/cloudbase-skills`。
   另外它不是"一个 Skill"，是 1 个路由入口 + 30 多个子技能。

4. **「TCB 匿名登录默认关闭」不能当安全依据。**
   官方两处明确：用 `accessKey`（publishable key）初始化的 SDK **仍会创建轻量匿名会话**，
   且被弃用的 `getLoginState()` 在未登录时也会返回一个看起来合法的 uid。

5. **我们现有 Skill 里有一条会和 DB 能力打架的表述。**
   `.agents/skills/cloudbase-site-builder/SKILL.md` 第 96 行：「不使用后端代码、数据库连接、API 密钥」。
   引入数据能力后这条要**改写**（改成"不使用服务端代码和任何腾讯云凭据；数据读写只能走平台提供的站点数据接口"），
   而不是简单删掉 —— 否则 AI 会开始自己往页面里塞第三方数据库连接串。
