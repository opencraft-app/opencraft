## สรุป

**บุคลิกภาพของเอเจนต์ Hermes ไม่ใช่เพียงบล็อกคงที่ของสำเนาตัวละคร แต่จะเกิดขึ้นจากสามส่วนที่ทำงานร่วมกัน: `SOUL.md` กำหนดว่าเอเจนต์คือใครและทำงานอย่างไร — กฎพฤติกรรมที่เสถียร; `USER.md` บันทึกว่าคุณต้องการได้รับการปฏิบัติอย่างไร — ค่าปริยายของความสัมพันธ์; `MEMORY.md` และ `memories/` เก็บสิ่งที่คุณทั้งสองได้สร้างขึ้นแล้ว — หลักฐานของประวัติร่วม การทำให้บทบาทของแต่ละส่วนแตกต่างกันเป็นสิ่งที่ทำให้เอเจนต์มีความเสถียรและมีเอกลักษณ์ในเวลาเดียวกัน: เพียงแค่บุคลิกภาพจะทำให้เหมือนกันสำหรับทุกคน ความทรงจำเพียงอย่างเดียวทำให้พฤติกรรมเปลี่ยนแปลงอย่างไม่แน่นอน พวกมันไม่ควรแทนที่ซึ่งกันและกัน — บุคลิกภาพไม่ได้เก็บข้อเท็จจริงเฉพาะ, `USER.md` ไม่เก็บอารมณ์ชั่วคราว, และ `MEMORY.md` ไม่ถือกฎพฤติกรรม ทั้งสามจะยังคงอยู่เมื่อคุณสลับโมเดล ดังนั้นความเสถียรของบุคลิกภาพไม่ขึ้นอยู่กับโมเดลใดโมเดลหนึ่ง**

## ทำไมตัวละครเดียวกันควรมีพฤติกรรมแตกต่างกับคนต่างกัน

ลองนึกภาพผู้ใช้สองคนที่ตั้งค่าเอเจนต์ของตนเป็น 'ผู้ช่วยนักวิจัยที่อดทน'

คนแรกคือผู้จัดการผลิตภัณฑ์ที่มักต้องการข้อสรุปก่อนเหตุผล และส่วนใหญ่จะพูดคุยเกี่ยวกับจังหวะการปล่อยสินค้าและความสำคัญของงาน คนที่สองคือ นักเรียนที่ต้องการกระบวนการหาคำตอบทั้งหมด และส่วนใหญ่จะพูดคุยเกี่ยวกับแนวคิดและการบ้าน

ถ้าทั้งสองเอเจนต์พูดสิ่งเดียวกันเป๊ะ ๆ ดังนั้น “ผู้ช่วยวิจัยที่อดทน” ก็ไม่เคยเกิดขึ้นจริง ๆ — มันยังคงเป็นแค่ป้ายกำกับแทนที่จะกลายเป็นวิธีการทำงานร่วมกันที่ชัดเจน

ในทางกลับกัน หากการปรับให้เหมาะกับบุคคลหมายถึงการปล่อยให้พฤติกรรมล่องลอยไปตามทุกบทสนทนา เอเจนต์จะสูญเสียความสามารถในการคาดเดา: เข้มงวดในวันนี้ ประมาทในวันพรุ่งนี้ คุณจะไม่สามารถพึ่งพามันได้

**บุคลิกภาพต้องตอบสนองความต้องการที่ขัดแย้งกันสองอย่างพร้อมกัน: ต้องมั่นคง และต้องเฉพาะบุคคลHermes** ซึ่งสิ่งนี้แก้ไขโดยการแบ่งความต้องการทั้งสองออกเป็นชั้น ๆ ซึ่งแต่ละชั้นถูกนำไปโดยไฟล์ที่ต่างกัน

## 2. บุคลิกภาพ: กฎพฤติกรรมที่มั่นคง

`SOUL.md` คือคู่มือกฎของเอเจนต์ และโดยปกติจะครอบคลุม:

- **บทบาท** — สิ่งที่มันมีบทบาท: ผู้ช่วยวิจัย, คู่หูในการเขียน, ผู้ช่วยหน้าที่ในชุมชน
- **น้ำเสียงและการแสดงออก** — เป็นทางการหรือผ่อนคลาย, การใช้การเปรียบเทียบ, การยอมรับอารมณ์ขัน
- **การจัดลำดับความสำคัญ** — สิ่งใดมีน้ำหนักเมื่อต้องเลือกความถูกต้องกับความรวดเร็ว, หรือความกระชับกับความครบถ้วน
- **ข้อจำกัดด้านพฤติกรรม** — สิ่งที่มันจะไม่ทำ, สิ่งที่มันจะไม่ขยายความ, การกระทำใดที่ต้องขอการยืนยันก่อน

สามประเด็นที่ใช้ได้จริงเมื่อเขียนบุคลิกของผู้ใช้

**ก่อนอื่น เขียนหลักการ ไม่ใช่ข้อเท็จจริง** "ฉันทำงานให้ผู้จัดการผลิตภัณฑ์ในโครงการ agent-demo" ไม่ควรอยู่ใน `SOUL.md` — นั่นคือข้อเท็จจริง และควรอยู่ใน `USER.md` หรือความทรงจำ ลักษณะบุคลิกภาพควรระบุหลักการที่ยืนยาว เช่น "สำหรับคำถามเกี่ยวกับผลิตภัณฑ์ ให้สรุปข้อสรุปก่อนเหตุผล"

**ประการที่สอง ให้กำหนดขอบเขตให้ชัดเจนพอที่จะสามารถประเมินได้** “อยู่ในความเป็นมืออาชีพ” ไม่สามารถประเมินได้ว่าปฏิบัติตามหรือไม่ แต่ “อย่าให้คำตัดสินทางการแพทย์ กฎหมาย หรือลงทุน; ให้ข้อมูลสาธารณะและแนะนำให้ปรึกษาผู้เชี่ยวชาญ” สามารถประเมินได้ กฎนามธรรมมักทำให้การปฏิบัติตามแตกต่างกันอย่างมากในแต่ละโมเดล

**ประการที่สาม ระบุลำดับความสำคัญอย่างชัดเจนเมื่อเกิดความขัดแย้ง** กฎมักจะขัดแย้งกัน — ความกระชับและความครบถ้วนเป็นตัวอย่างหนึ่ง หากไม่มีการจัดลำดับอย่างชัดเจน เอเจนต์จะต้องเดาทุกครั้ง และพฤติกรรมของมันจะไม่สอดคล้องกัน

## 3. ความพึงพอใจของผู้ใช้: ค่าเริ่มต้นของความสัมพันธ์

`USER.md` ถือ **ข้อมูลที่เสถียรเกี่ยวกับคุณ** ดังนั้นผู้แทนไม่จำเป็นต้องถามซ้ำทุกครั้ง ผู้สมัครที่ดี:

- **ภาษาและการแสดงออก** — ใช้ภาษาอะไร, จะเก็บคำศัพท์ไว้ในรูปแบบเดิมหรือไม่, ตัวอย่างช่วยได้หรือไม่
- **จังหวะการสื่อสาร** — สรุปก่อน หรือตามลำดับเหตุผลทั้งหมด
- **เครื่องมือและสภาพแวดล้อมปกติ** — สแตก, แพลตฟอร์ม, และรูปแบบการทำงานที่คุณใช้ในชีวิตประจำวัน
- **สิ่งที่ชัดเจนว่าควรหลีกเลี่ยง** — ทิศทางที่คุณไม่ต้องการให้สอบถาม, การใช้วลีที่คุณไม่ต้องการ

มีวิธีทดสอบง่าย ๆ ว่าสิ่งใดควรอยู่ใน `USER.md` หรือไม่: **มันจะยังคงเป็นจริงในอีกสามเดือนข้างหน้าหรือไม่?** “ฉันชอบคำตอบที่กระชับ” น่าจะเป็นจริง ดังนั้นจึงเหมาะสม “วันนี้ฉันรีบ” จะไม่ใช่ — นั่นเป็นบริบทชั่วคราวและควรอยู่นอกนั้น

การทดสอบนี้มีความสำคัญ การเขียนอารมณ์แบบครั้งเดียวลงใน `USER.md` ทำให้เอเจนต์มองสถานะชั่วคราวเป็นสถานะถาวร หากคุณเคยพูดว่า "ให้สั้นๆ" ในขณะที่รีบ และสิ่งนั้นแข็งตัวเป็นความชอบระยะยาว มันจะเก็บรายละเอียดไว้ในภายหลังเมื่อคุณจำเป็นต้องใช้จริงๆ

## 4. ความทรงจำระยะยาว: หลักฐานของประวัติศาสตร์ที่แบ่งปันกัน

`MEMORY.md` และ `memories/` เก็บ **ข้อเท็จจริงที่เกิดขึ้นแล้วและควรเก็บรักษาไว้**: สถานะของโครงการ การตัดสินใจที่ทำไปแล้ว ข้อสรุปที่สามารถนำกลับมาใช้ใหม่ได้ เหตุผลที่กำหนดค่าพารามิเตอร์ในลักษณะนั้น

ความสัมพันธ์ของมันกับอีกสองอัน

- บุคลิกกำหนด **หลักการทางพฤติกรรม**
- `USER.md` กำหนด **สไตล์การโต้ตอบเริ่มต้น**
- ความจำกำหนด **พื้นหลังที่คุณทั้งสองได้แชร์ร่วมกัน**

การเรียกคืนเป็นแบบตามความต้องการ: Hermes สร้างดัชนีข้อความเต็ม SQLite + FTS5 สำหรับรายการและดึงรายการที่ตรงกันเข้ามาในบริบทเมื่อคุณหยิบยกหัวข้อที่เกี่ยวข้อง แทนที่จะดันประวัติทั้งหมดเข้าไป การเขียนก็ไม่ได้เป็นการต่อเติมแบบไม่จำกัด — มันถูกดูแลผ่านการดำเนินการอะตอม `add` / `replace` / `remove` และสามารถตรวจสอบได้ผ่าน `/memory pending` สำหรับตรรกะการคัดสรรทั้งหมด ดูที่ "ทำไมหน่วยความจำมากขึ้นจึงไม่ดีกว่า: วิธีที่ Hermes Agent เลือก คัดสรร และอัปเดตหน่วยความจำระยะยาว".

**ความทรงจำไม่ควรแทนตัวตน.** ข้อผิดพลาดทั่วไปคือการเขียนกฎพฤติกรรมเป็นรายการความทรงจำ เช่น 'จำไว้: ให้ข้อสรุปก่อนเสมอ' ซึ่งสร้างปัญหาได้สองประการ: รายการนั้นอาจไม่ถูกเรียกใช้ถ้าคำถามไม่ตรงกับมัน และอาจถูกลบออกโดยรายการที่ตามมา กฎพฤติกรรมควรอยู่ใน `SOUL.md` ซึ่งอยู่ในหน่วยความจำถาวรเสมอ.

## 5. วิธีที่สามสิ่งรวมกันเพื่อให้คำตอบเดียว

สถานการณ์ที่เป็นรูปธรรมซึ่งเชื่อมโยงเลเยอร์ต่าง ๆ เข้าด้วยกัน

**การตั้งค่า**:

- `SOUL.md`: ผู้ช่วยวิจัย; สรุปก่อนการให้เหตุผล; แสดงความไม่แน่นอนอย่างชัดเจน; อย่าขยายคำแนะนำทางการแพทย์หรือการลงทุน  
- `USER.md`: ชอบภาษาอังกฤษ; เก็บคำศัพท์ทางเทคนิคไว้ตามเดิม; ทำให้คำตอบสามารถสแกนได้ง่าย  
- `MEMORY.md`: ปัจจุบันทำงานที่เว็บไซต์ระดับโลกสำหรับโปรเจกต์ agent-demo; สัปดาห์ที่แล้วตัดสินใจเปลี่ยนหน้าแรกเป็น animated gradient; โปรเจกต์นั้นรันบน Next.js

**คำถามของคุณ**: "สำหรับแนวทางหน้าโฮมเพจปัจจุบัน มีความเสี่ยงอะไรบ้างในการเพิ่มพื้นหลังวิดีโอ?"

**สิ่งที่แต่ละชั้นมีส่วน**:

1. **ความจำ** จัดเตรียมบริบท: เอเจนต์รู้ว่าเพจ "หน้าแรก" หมายถึงหน้าใดและว่ามันเพิ่งถูกเปลี่ยนเป็นกราเดียนต์เคลื่อนไหว ดังนั้นมันจึงสามารถมองพื้นหลังวิดีโอเป็นการเปลี่ยนแปลงบนสิ่งนั้นได้ แทนที่จะเป็นการตัดสินใจจากศูนย์  
2. **บุคลิกภาพ** กำหนดโครงสร้าง: สรุปผลลัพธ์ก่อน ("ความเสี่ยงหลักคือประสิทธิภาพด้านบนของหน้าและการใช้ข้อมูลมือถือ") จากนั้นจึงเป็นเหตุผล พร้อมระบุความไม่แน่นอนอย่างชัดเจน  
3. **`USER.md`** กำหนดการแสดงออก: ตอบเป็นภาษาอังกฤษ รักษาคำเช่น `LCP` และ `autoplay` ไว้ตามเดิม และทำให้ความยาวอ่านได้ง่าย

ถ้าเอาเลเยอร์ใดเลเยอร์หนึ่งออก ผลลัพธ์จะลดลงอย่างเห็นได้ชัด: ถ้าไม่มีความทรงจำ คำตอบจะยังคงเป็นแบบทั่วไป; ถ้าไม่มีบุคลิกภาพ โครงสร้างจะคลอนและความไม่แน่นอนไม่ถูกสังเกต; ถ้าไม่มีความชอบ ภาษาและความยาวจะไม่ตรงกับวิธีที่คุณอ่าน

## 7. วิธีของ LightVela: บุคลิกภาพและความชอบในฐานะทรัพย์สินที่จัดการได้

Hermes แยกชั้นทั้งสามนี้ออกจากกันอย่างชัดเจน แต่ยังคงมุ่งเป้าไปที่ผู้ที่แก้ไข Markdown โดยตรง LightVela รันโมเดลที่โฮสต์บนคลาวด์และไม่เปิดเผยการทำงานของระบบไฟล์ที่ผู้ใช้เข้าถึงได้ ดังนั้นชั้นเหล่านี้จึงถูกจัดการแตกต่างจากในการตั้งค่าโฮสต์ด้วยตนเอง:

- **Persona ถูกตั้งค่าผ่านฟีเจอร์ Persona** — ส่วน Persona ในหน้าการตั้งค่าของ Agent มีสองวิธีในการเข้าถึง คือ เลือก Persona แบบสุ่มหรือทำแบบทดสอบสั้น ๆ ตรวจสอบบทบาท น้ำเสียง และบันทึกพฤติกรรมในการ์ด Persona แล้วเลือก Inject Persona เพื่อนำไปใช้ ซึ่งจะสร้างและฉีด Soul โดยไม่จำเป็นต้องเข้าถึงระบบไฟล์บนคลาวด์ แม้ว่าจะไม่ใช่โปรแกรมแก้ไขทั่วไปสำหรับไฟล์คลาวด์ใด ๆ
- **หน่วยความจำสามารถดูได้ในคอนโซล** — หน้าหน่วยความจำจะแสดงสิ่งที่ Agent เก็บไว้ โดยมีแท็บแยกสำหรับ Memory และ User Profile ซึ่งสอดคล้องกับการแยกระหว่างข้อเท็จจริงและความชอบที่เสถียร
- **การเพิ่มและลบเกิดขึ้นผ่านการสนทนา** — คุณไม่จำเป็นต้องตั้งใจ "กรอก" หน่วยความจำ ระหว่างการสนทนาปกติ Hermes จะตัดสินใจว่าอะไรควรเก็บไว้ เมื่อคุณต้องการให้มันจำหรือจำอะไรให้ลืม ก็เพียงพูดในแชท
- **ความจุปรับได้** — คอนโซลช่วยให้คุณสามารถเพิ่มหรือลดขีดจำกัดความจุของหน่วยความจำ ป้องกันไม่ให้บริบทระยะยาวเติบโตอย่างไม่จำกัด
- **เสถียรในทุกโมเดล** — การสลับโมเดลจะไม่ลบหน่วยความจำ ทักษะ หรือภารกิจที่ตั้งเวลาไว้ ดังนั้นความมั่นคงของบุคลิกภาพไม่ขึ้นกับโมเดลใดโมเดลหนึ่ง
- **สม่ำเสมอในทุกช่องทาง** — Agent หนึ่งตัวใช้หน่วยความจำและบุคลิกภาพเดียวกันในทุกช่องทางที่เชื่อมต่ออยู่; การสลับโทรศัพท์หรือช่องทางจะไม่สูญหาย และไม่จำเป็นต้องทำซ้ำในแต่ละแพลตฟอร์ม

## ประเด็นสำคัญ

- บุคลิกภาพเกิดจากสามส่วน: `SOUL.md` (กฎพฤติกรรม), `USER.md` (รูปแบบการโต้ตอบเริ่มต้น), `MEMORY.md` / `memories/` (ภูมิหลังที่ใช้ร่วมกัน)  
- เหตุผลหลักในการแยกส่วนเหล่านี้คือ **ความถี่ในการเปลี่ยนแปลงที่แตกต่างกัน**: กฎอยู่คงที่เป็นเดือน ๆ ในขณะที่ความทรงจำเพิ่มขึ้นเกือบทุกวัน  
- บุคลิกภาพบอกหลักการมากกว่าข้อเท็จจริง รักษาขอบเขตให้ชัดเจนพอที่จะตัดสิน และประกาศลำดับความสำคัญสำหรับกฎที่ขัดกัน  
- ทดสอบการเป็นสมาชิก `USER.md`: **ยังคงเป็นจริงในสามเดือนข้างหน้าหรือไม่?**  
- อย่าจัดเก็บกฎพฤติกรรมเป็นความทรงจำ มิฉะนั้นจะเกิดข้อผิดพลาดเป็นระยะ ๆ จากการเรียกคืนพลาดหรือถูกแทนที่  
- การเปลี่ยนโทนหลังจากสลับโมเดลสะท้อนถึงการยึดมั่นที่แตกต่างกัน ไม่ใช่บุคลิกภาพหรือความทรงจำที่หายไป
