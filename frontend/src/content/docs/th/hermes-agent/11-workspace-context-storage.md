## สรุป

**ไฟล์ของ Hermes Agent ไม่ใช่โฟลเดอร์ยุ่งเหยิงเดียว พวกมันอยู่ในสามที่ที่มีหน้าที่แตกต่างกัน โฟลเดอร์ทำงานถือครองอินพุต เอาต์พุต และการทำงานของเครื่องมือสำหรับงานปัจจุบัน และมีขอบเขตจริง — เครื่องมือไม่สามารถเคลื่อนตัวไปเกินพื้นที่ทำงานเข้าถึงเส้นทางระบบโดยไม่จำกัด ไฟล์บริบท (`SOUL.md`, `USER.md`, `MEMORY.md`) ไม่ใช่เอกสารแนบธรรมดา; พวกมันเป็นข้อตกลงระยะยาวที่กำหนดวิธีที่ Agent เข้าใจความสัมพันธ์และงาน การจัดเก็บบนคลาวด์เป็นพื้นที่เก็บไฟล์ของ Agent สำหรับวัสดุและผลลัพธ์ของงาน: การอัปโหลดและดาวน์โหลดไฟล์เดี่ยวรองรับได้สูงสุด 1 GB การลบจะลบเพียงสำเนาที่โฮสต์บนคลาวด์ของ Agent นั้นเท่านั้นและไม่เคยแตะไฟล์ต้นฉบับบนคอมพิวเตอร์ของคุณ และไฟล์ของ Agent หนึ่งไม่สามารถใช้งานโดย Agent อื่นโดยอัตโนมัติ คุณค่าที่เป็นประโยชน์ของการแยกสามส่วนนี้คือคุณจะรู้เสมอว่าเอกสารอยู่ที่ไหน ใครสามารถอ่านได้ และมันคงอยู่ได้นานเท่าใด — ซึ่งเก็บความลับไว้ให้อยู่ข้างนอกบริบทระยะยาวและป้องกันไม่ให้เนื้อหาสำคัญปรากฏอยู่เฉพาะในบันทึกการสนทนาเพียงอย่างเดียว

## ตำแหน่งที่ไฟล์อยู่จะกำหนดว่าเอเจนต์สามารถเริ่มต่อจากที่ค้างไว้ได้หรือไม่

ลองนึกภาพความล้มเหลวทั่วไป คุณวางโครงการย่อไว้ในแชท ขอให้เอเจนต์สรุปประเด็นสำคัญ และมันทำได้ดี สามวันต่อมาคุณกลับมา: "ตามโครงร่างนั้น ร่างตารางเวลา" ตารางเวลาที่มันสร้างขึ้นชัดเจนว่าไม่ตรงกัน — เพราะโครงการย่อมีอยู่เฉพาะในบทสนทนาจากสามวันที่แล้วเท่านั้น ไม่ได้อยู่ในที่ใดที่สามารถดึงกลับมาได้อย่างเชื่อถือได้

ลองนึกถึงความล้มเหลวครั้งที่สอง เพื่อช่วยให้เอเจนต์ "จำ" การตั้งค่าเซิร์ฟเวอร์ของคุณ คุณได้เขียนบล็อกการกำหนดค่าที่มีคีย์ลับลงในไฟล์บริบทระยะยาว จากนั้นบล็อกนั้นจะถูกอ่านเป็นข้อมูลพื้นหลังในทุกเซสชัน ซึ่งนี่ไม่ใช่วิธีการใช้ความจำตามที่ตั้งใจไว้ มันเป็นการเปิดเผยข้อมูลที่ละเอียดอ่อนในระยะยาวโดยไม่จำเป็น

ทั้งสองชี้ไปที่ประเด็นเดียวกัน: **ที่ที่ไฟล์อยู่ไม่ได้เป็นเพียงความชอบเรื่องความเรียบร้อย แต่กำหนดว่าข้อมูลสามารถถูกดึงกลับมาได้อย่างน่าเชื่อถือ ใครเป็นผู้ที่อ่านมัน และมันคงอยู่ได้นานเท่าไร** บทความนี้อธิบายถึงสามตำแหน่งและขอบเขตของแต่ละตำแหน่ง

ความแตกต่างนั้นกำหนดโดยตรงว่าข้อมูลที่มีความละเอียดอ่อนควรถูกจัดการอย่างไร — จะกล่าวถึงด้านล่าง

## 2. ไดเรกทอรีทำงาน: ที่ซึ่งงานเกิดขึ้น และที่ซึ่งขอบเขตตั้งอยู่

ไดเรกทอรีการทำงานให้บริการอินพุต เอาต์พุต และการทำงานของเครื่องมือของงานปัจจุบัน มันมีคุณสมบัติเด่นสองประการ

**ก่อนอื่น มันคือไซต์งาน** การอ่านไฟล์ การเขียนไฟล์ การสั่งคำสั่ง และการสร้างสิ่งประดิษฐ์ทั้งหมดเกิดขึ้นที่นี่ เอเจนต์ที่สามารถดำเนินงานต่อได้จริง ๆ จำเป็นต้องมีสถานะระหว่างขั้นตอนเก็บไว้ที่นี่ แทนที่จะเริ่มจากศูนย์ทุกครั้ง

**ประการที่สอง มันมีขอบเขตที่ชัดเจน** เครื่องมือไม่สามารถเข้าถึงนอกพื้นที่ทำงานไปยังเส้นทางระบบใด ๆ ก็ได้ ข้อจำกัดนี้ไม่ใช่ความสามารถที่ขาดหายไป; แต่เป็นเงื่อนไขเบื้องต้นที่ทำให้การอ่าน/เขียนไฟล์ใช้งานได้และสามารถควบคุมได้ เอเจนต์ที่มีสิทธิ์อ่าน/เขียนไม่จำกัดทั่วทั้งระบบไฟล์สามารถเปลี่ยนความผิดพลาดเพียงครั้งเดียวให้กลายเป็นผลลัพธ์ที่อาจไม่สามารถย้อนกลับได้

การเข้าใจขอบเขตนี้มีผลต่อการปฏิบัติจริง: เมื่อคุณต้องการให้เอเจนต์ประมวลผลเอกสาร ให้วางเอกสารไว้ในที่ที่มันเข้าถึงได้ แทนที่จะคาดหวังให้มันค้นหาไฟล์ในไดเรกทอรีต่าง ๆ บนเครื่องของคุณเอง

## 3. ไฟล์บริบท: ไม่ใช่ไฟล์แนบ แต่เป็นข้อตกลงระยะยาว

ไฟล์สามไฟล์นี้มักถูกเข้าใจผิดว่าเป็น "วัสดุที่ฉันอัปโหลดให้กับเอเจนต์" แต่บทบาทของพวกมันแตกต่างออกไปโดยสิ้นเชิง — พวกมันกำหนดว่าเอเจนต์เข้าใจความสัมพันธ์และงานนี้อย่างไร

| ไฟล์ | บทบาทหลัก | เนื้อหาที่พบบ่อย |
|---|---|---|
| `SOUL.md` | บทบาท น้ำเสียง ขอบเขตพฤติกรรม | ข้อสรุปก่อนการให้เหตุผล; ไม่มีคำแนะนำการลงทุน |
| `USER.md` | ความชอบและโปรไฟล์ผู้ใช้ที่คงที่ | ชอบภาษาอังกฤษ; เก็บคำศัพท์ตามเดิม |
| `MEMORY.md` | ข้อเท็จจริงระหว่างเซสชัน สถานะโครงการ การตัดสินใจ | ชื่อโครงการ; การตัดสินใจของสัปดาห์ที่แล้ว |

สามวิธีที่พวกเขาแตกต่างจากวัสดุที่อัปโหลด:

**ความแตกต่างข้อหนึ่ง: เวลาในการอ่าน** ไฟล์บริบทจะอยู่เบื้องหลังและถูกใช้งานทุกครั้งที่เริ่มเซสชัน; ไฟล์ที่เก็บในคลาวด์จะถูกดึงมาใช้งานเฉพาะเมื่อจำเป็น

**ความแตกต่างข้อสอง: รูปแบบเนื้อหา** ไฟล์บริบทเหมาะกับกฎที่มั่นคง ความชอบ และรายการข้อเท็จจริง — ไม่ใช่บล็อกข้อมูลดิบขนาดใหญ่ การยัดรายงานยาวสิบหน้าเข้า `MEMORY.md` จะทำให้ทุกเซสชันถัดไปมีภาระหนักขึ้น

**ความแตกต่างข้อที่สาม: ข้อกำหนดความไวต่อข้อมูล.** เนื่องจากพวกเขาเป็นผู้อยู่อาศัย, **อย่าเขียนรหัสผ่าน, กุญแจ, หรือข้อมูลที่มีความไวไม่จำเป็นลงในไฟล์บริบทระยะยาว.** เมื่อเอเจนต์ต้องจัดการการกำหนดค่าที่มีความไว ให้จัดส่งผ่านเส้นทางที่ควบคุมได้และทำความสะอาดหลังจากนั้น แทนที่จะปล่อยให้มันอยู่ในเบื้องหลังอย่างไม่มีกำหนด.

หัวข้อที่สามนั้นเป็นกฎปฏิบัติที่สำคัญที่สุดในบทความนี้

สำหรับวิธีที่ไฟล์บริบททั้งสามร่วมกันกำหนดพฤติกรรม ดูได้ที่ "ที่มาของบุคลิกภาพของเอเจนต์ Hermes: บุคลิก ความชอบ และความทรงจำระยะยาว"

## 4. การจัดเก็บข้อมูลบนคลาวด์: พื้นที่ทำงานไฟล์ของเอเจนต์

การจัดเก็บข้อมูลบนคลาวด์ถูกจัดวางให้เป็นพื้นที่ทำงานไฟล์ของเอเจนต์: เก็บวัสดุงานในที่เดียว อัปโหลดและจัดระเบียบไฟล์ หรือติดตั้งไฟล์ที่คุณต้องการในเครื่องได้ทั้งหมดจากคอนโซล

### 4.1 เมื่อไหร่ควรใช้

ใช้การเก็บข้อมูลบนคลาวด์เมื่อใดก็ตามที่เอเจนต์ต้องการวัสดุอ้างอิง เอกสารทำงาน หรือสถานที่ชัดเจนในการเก็บผลลัพธ์ — แทนที่จะพึ่งพาการคัดลอกและวางครั้งเดียวในแชท รูปแบบสองแบบที่พบบ่อย:

- **อัปโหลดก่อน แล้วค่อยประมวลผล** — อัปโหลดโครงการย่อ จากนั้นให้ Agent สกัดประเด็นสำคัญ วัสดุจะยังคงสามารถเข้าถึงได้สำหรับการอ้างอิงในอนาคต
- **สร้างโฟลเดอร์สำหรับงานที่ทำซ้ำๆ** — ให้โฟลเดอร์กับงานที่ทำเป็นประจำและดูแลรักษาไว้ เพื่อให้ผลลัพธ์มีตำแหน่งที่มั่นคง

### 4.2 ขีดจำกัดคอนกรีตที่ควรรู้

นี่คือข้อเท็จจริงที่ต้องตรวจสอบก่อนที่คุณจะพึ่งพามัน:

- **การอัปโหลดและดาวน์โหลดไฟล์เดี่ยวรองรับขนาดสูงสุด 1 GB** ไฟล์ที่ใหญ่กว่านี้จำเป็นต้องแยกหรือบีบอัดก่อน  
- **การลบจะลบเพียงสำเนาที่โฮสต์ในคลาวด์ของ Agent นั้น** ไม่มีผลกับไฟล์ต้นฉบับบนคอมพิวเตอร์ของคุณ แต่ยังไงก็ตาม ควรดาวน์โหลดสิ่งที่คุณอาจยังต้องใช้ก่อนลบ — สำเนาที่โฮสต์จะหายไปเมื่อถูกลบแล้ว  
- **ไฟล์ของ Agent หนึ่งจะไม่สามารถเข้าถึงได้โดยอัตโนมัติจาก Agent อื่น** การย้ายไฟล์ระหว่าง Agents จำเป็นต้องทำตามขั้นตอนที่ชัดเจน; อย่าสมมติว่ามีพื้นที่แชร์ไฟล์  
- **เปิดหน้าเว็บไว้ขณะอัปโหลด** รอจนเสร็จสิ้น และตรวจสอบว่าไฟล์ปรากฏในโฟลเดอร์ปัจจุบันก่อนทำอย่างอื่น

### 4.3 โครงสร้างโฟลเดอร์ไม่จำเป็นต้องซับซ้อน

คำแนะนำที่เป็นประโยชน์: ลำดับชั้นที่ซับซ้อนมักไม่จำเป็น แค่สามโฟลเดอร์ — วัสดุ, กำลังดำเนินการ, เสร็จสิ้น — สามารถจัดการสถานการณ์ส่วนใหญ่ได้ เพิ่มความลึกก็ต่อเมื่อมันช่วยให้คุณหาสิ่งต่าง ๆ ได้เร็วขึ้นอย่างแท้จริง

การทดสอบหนึ่งว่ารูปแบบโครงสร้างนั้นมีความสมบูรณ์หรือไม่: **ชื่อโฟลเดอร์สามารถบอกได้ชัดเจนว่าวัสดุเป็นของงานใด?** หากคุณต้องเปิดโฟลเดอร์เพื่อจำว่าข้างในมีอะไร ชื่อนั้นก็ล้มเหลว — และตัวเอเจนต์ก็พึ่งพาชื่อเหล่านั้นในการตัดสินว่าวัสดุมีไว้สำหรับอะไรเช่นกัน

**คำถามที่สอง: สิ่งนี้เป็นวัสดุหรือผลลัพธ์ที่ควรเก็บและน่าจะถูกอ้างอิงซ้ำบ่อยหรือไม่?**  
ใช่ → เก็บในคลาวด์ อัพโหลดไปยังโฟลเดอร์ที่เหมาะสมพร้อมชื่อที่อธิบายวัตถุประสงค์ของมัน

**คำถามที่สาม: มันทำหน้าที่เพียงงานนี้งานเดียวหรือไม่?** ใช่ → จัดการในไดเรกทอรีทำงาน; ไม่จำเป็นต้องเก็บรักษาในระยะยาว

**คำถามที่สี่: มีรหัสผ่าน กุญแจ หรือข้อมูลส่วนตัวที่ละเอียดอ่อนหรือไม่?** ใช่ → **อย่าเก็บไว้ในไฟล์บริบทระยะยาว** ให้ส่งผ่านช่องทางที่ควบคุมได้ และล้างข้อมูลเมื่อภารกิจสิ้นสุดลง

คุณค่าของเส้นทางนี้คือการเปลี่ยน 'วางที่ไหนก็ได้' ให้กลายเป็นการเลือกที่มีเหตุผล ความขัดแย้งในชีวิตประจำวันส่วนใหญ่เกิดจากการสับสนระหว่างคำถามหนึ่งและสอง — การผลักวัสดุจำนวนมากไปยังไฟล์บริบท หรือการปล่อยวัสดุที่ควรถูกเก็บไว้ภายในบันทึกการสนทนา

## 6. อาการทั่วไปและจุดที่ควรมอง

| อาการ | สาเหตุที่มีแนวโน้มมากกว่า | การดำเนินการที่แนะนำ |
|---|---|---|
| เอเจนต์ไม่พบเนื้อหาที่คุณเคยแชร์มาก่อน | มีอยู่เฉพาะในประวัติการแชท ไม่ได้ถูกเก็บไว้อย่างถาวร | อัปโหลดไปยังพื้นที่จัดเก็บบนคลาวด์ จากนั้นอ้างอิงถึงไฟล์นั้น |
| การอัปโหลดหรือดาวน์โหลดล้มเหลว | ไฟล์มีขนาดเกิน 1GB หรือคุณออกจากหน้าในระหว่างการอัปโหลด | ตรวจสอบขนาดไฟล์; อัปโหลดใหม่และเปิดหน้าไว้ |
| ไฟล์ "หาย" หลังจากย้ายไปยังเอเจนต์อื่น | ไฟล์เป็นของพื้นที่จัดเก็บของเอเจนต์เดิมและไม่ได้ถูกแชร์ | ดาวน์โหลดจากเอเจนต์เดิม แล้วอัปโหลดไปยังเอเจนต์ใหม่ |
| กังวลว่าการลบไฟล์บนคลาวด์จะลบไฟล์ในเครื่องด้วย | ความเข้าใจผิดเกี่ยวกับขอบเขตการลบ | การลบจะส่งผลเฉพาะไฟล์ที่อยู่บนโฮสต์ ไม่ใช่ไฟล์ต้นฉบับในเครื่องของคุณ |
| ทุกเซสชันรู้สึกหนักและช้า | วัสดุดิบจำนวนมากถูกผลักเข้าสู่ไฟล์บริบทระยะยาว | ย้ายออกจากไฟล์บริบทไปยังพื้นที่จัดเก็บบนคลาวด์ |
| กังวลเกี่ยวกับการเปิดเผยความลับระยะยาว | กุญแจหรือรหัสผ่านถูกเขียนลงในไฟล์บริบท | ลบออกทันที; ให้ผ่านช่องทางที่ควบคุมได้แทน |

สองแถวสุดท้ายคือสองด้านของความผิดพลาดเดียวกัน: **การปฏิบัติต่อไฟล์บริบทเหมือนเป็นคลังเอกสาร** การทดสอบนั้นง่าย — หากเนื้อหาชิ้นหนึ่งไม่จำเป็นต้องอ่านในทุกเซสชัน มันก็ไม่ควรอยู่ในไฟล์บริบท

## 7. วิธีของ LightVela: ทำให้สถานที่มองเห็นและควบคุมได้

Hermes แยกไดเรกทอรีทำงานออกจากไฟล์บริบทในระดับกลไก แต่การโฮสต์และการดึงข้อมูลยังคงถูกจัดโดยผู้ปฏิบัติงาน ทิศทางของ LightVela คือการทำให้พื้นที่ทำงานไฟล์เป็นความสามารถของผลิตภัณฑ์ที่มองเห็นและควบคุมได้:

- **พื้นที่ทำงานไฟล์รวม** — อัปโหลด สร้าง จัดระเบียบ ดาวน์โหลด เปลี่ยนชื่อ และลบจากคอนโซลโดยไม่ต้องออกจากผลิตภัณฑ์  
- **ขอบเขตชัดเจน** — โฟลเดอร์ทำงานถูกจำกัด และเครื่องมือไม่สามารถเข้าถึงเส้นทางระบบอื่นนอกพื้นที่ทำงาน  
- **ความหมายการลบชัดเจน** — การลบจะลบเพียงสำเนาในพื้นที่จัดเก็บของ Agent นั้น ๆ ทิ้งต้นฉบับในเครื่องไว้อย่างปลอดภัย และจะแจ้งให้ดาวน์โหลดก่อนลบ  
- **แยกขอบเขตระหว่าง Agent** — พื้นที่ไฟล์แยกกันสำหรับแต่ละ Agent เพื่อไม่ให้ข้อมูลรั่วไหลไปยังที่ที่ไม่ควรแชร์  
- **แยกจากความสามารถอื่น ๆ** — การสลับโมเดลจะไม่เขียนทับไฟล์ในที่เก็บข้อมูลบนคลาวด์

## ประเด็นสำคัญ

- สถานที่สามแห่ง บทบาทสามอย่าง: **ไดเรกทอรีทำงาน** (พื้นที่ทำงานจำกัด), **ไฟล์บริบท** (สัญญาระยะยาวที่อยู่ประจำ), **คลาวด์สตอเรจ** (วัสดุและผลลัพธ์ที่ดึงตามความต้องการ)  
- ไฟล์บริบทและคลาวด์สตอเรจแตกต่างกันในเรื่องเวลาการอ่าน: ไฟล์บริบทจะอยู่ประจำทุกเซสชัน ในขณะที่คลาวด์สตอเรจจะดึงตามความต้องการ  
- ข้อเท็จจริงเกี่ยวกับคลาวด์สตอเรจ: ขีดจำกัดการอัปโหลด/ดาวน์โหลดไฟล์ละ **1 GB**; การลบจะลบเพียงสำเนาที่โฮสต์เท่านั้น; **ไฟล์ของ Agent หนึ่งจะไม่สามารถเข้าถึงได้โดยอัตโนมัติโดย Agent อื่น**  
- โครงสร้างโฟลเดอร์ควรง่าย — วัสดุ / กำลังทำ / เสร็จ มักเพียงพอ โดยตั้งชื่อเพื่ออธิบายวัตถุประสงค์  
- กฎข้อหนึ่งที่ต้องปฏิบัติ: **ห้ามเขียนรหัสผ่าน คีย์ หรือข้อมูลที่ละเอียดอ่อนเกินจำเป็นลงในไฟล์บริบทระยะยาว**  
- เมื่อเซสชันรู้สึกหนักหรือช้า ให้ตรวจสอบก่อนว่ามีการดันวัสดุจำนวนมากเข้าไปในไฟล์บริบทแล้วหรือไม่
