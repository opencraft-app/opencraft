## สรุป

**เอเจนต์หนึ่งคนสามารถปรากฏในหลายแอปส่งข้อความได้เพราะแอปเหล่านั้นเป็นเพียงจุดเข้าถึง — เอเจนต์ต่างหากที่ทำงานจริงๆ เกตเวย์ข้อความทำงานสามอย่าง: มันปรับข้อความที่มีโครงสร้างแตกต่างจาก Telegram, WhatsApp, Discord, Slack, WeChat และอื่นๆ ให้เป็นรูปแบบคำขอเดียว; มันกำหนดเส้นทางแต่ละคำขอไปยังเอเจนต์เดียวกันตามการตั้งค่าการเชื่อมต่อของคุณ แทนที่จะทำสำเนาบุคลิกภาพและความจำตามแต่ละแพลตฟอร์ม; และหลังจากดำเนินการ มันส่งผลลัพธ์กลับไปยังการสนทนาที่มาของมันโดยตรง เพราะตัวตน (`SOUL.md`), ความจำ (`USER.md`, `MEMORY.md`), ทักษะ (`skills/`) และงานที่กำหนดเวลาไว้อยู่นอกชั้นช่องทาง สิ่งที่คุณกล่าวถึงบน Telegram ก็ยังคงทราบเมื่อคุณติดตามใน WhatsApp แต่การรวมกันไม่ได้หมายความว่าไร้ขอบเขต: แต่ละช่องทางมีขั้นตอนการอนุมัติ รูปแบบข้อความ และข้อจำกัดการส่งของตัวเอง ชุดช่องทางที่รองรับแตกต่างกันระหว่างภูมิภาคโลกและจีน และ หลังจากเชื่อมต่อช่องทางใหม่ คุณต้องส่งข้อความทดสอบเพื่อยืนยันว่าการตอบกลับไปปรากฏในบทสนทนาที่คาดไว้

## สถานการณ์ที่สิ่งนี้แก้ไข

จินตนาการถึงการใช้งานเพียงวันเดียว ในTelegramคุณขอให้เอเจนต์ของคุณสรุปสถานะของโครงการ ออกไปตอนเที่ยง คุณติดตามWhatsApp: “ความเสี่ยงในตัวเลือกที่สองที่คุณกล่าวถึงคืออะไร?” ในตอนเย็นคุณขอให้เขาโพสต์ข้อสรุปในทีมSlackหรือDiscordช่องทาง

หากปฏิสัมพันธ์ทั้งสามนี้ทำงานเหมือนบอทสามตัวที่ไม่เกี่ยวข้องกัน การเข้าถึงหลายแพลตฟอร์มจะไม่มีประโยชน์ — คุณจะต้องอธิบายบริบทซ้ำทุกครั้ง รูปร่างที่มีประโยชน์แตกต่างออกไป: สามจุดเข้าถึง ผู้ช่วยหนึ่งตัว

ความยากที่นี่มักจะถูกเข้าใจผิดว่าเป็นเพียงการ "รวม API เพิ่มอีกไม่กี่ตัว" API การรวมระบบเป็นเพียงงานในระดับพื้นผิว ปัญหาจริงคือ: **ทำให้ทุกจุดเข้าใช้งานสามารถระบุตัวตนและบริบทเดียวกันได้ โดยไม่ละเมิดกฎของแต่ละแพลตฟอร์ม** เกตเวย์ข้อความคือชั้นที่แก้ความตึงเครียดนั้น

## 1. ก่อนอื่น ข้อแก้ไข: ช่องทางไม่ใช่เอเจนต์

ความแตกต่างนี้คือเงื่อนไขเบื้องต้นสำหรับทุกสิ่งทุกอย่างอื่น

| แนวคิด | คืออะไร | ความสัมพันธ์เชิงตัวเลข |
|---|---|---|
| **ช่องทาง** | จุดเข้าออกสำหรับข้อความ เช่น Telegram, WhatsApp, Discord, Slack, WeChat | เอเจนต์หนึ่งคนสามารถเชื่อมต่อได้หลายช่องทาง |
| **เอเจนต์** | สิ่งที่ทำงานต่อเนื่อง มีเอกลักษณ์ ความจำ ทักษะ งาน | ถูกใช้งานโดยหลายช่องทาง |

ผู้คนมักปฏิบัติต่อ "บอท Telegram ของฉัน" ราวกับเป็นสิ่งมีชีวิตอิสระ ซึ่งโดยธรรมชาติก่อให้เกิดคำถามว่า "แล้วบอท WhatsApp ของฉันต่างกันหรือไม่?" เมื่อเข้าใจว่าช่องทางต่าง ๆ คือจุดเข้าใช้งานมากกว่าการเป็นหัวข้อ คำถามนั้นก็จะหมดไป

เส้นทางเต็มมีลักษณะดังนี้:

```text
Messaging apps (multiple entry points)
    ↓  platform-native messages
Message gateway (normalise / route / deliver)
    ↓  unified request
The same Hermes Agent
    ↓
model inference + tool execution + memory recall + skill loading
    ↓  execution result
Message gateway
    ↓  delivered in platform format
Original conversation on the original channel
```

โปรดทราบขั้นตอนสุดท้าย — *การสนทนาเดิมในช่องเดิม* นั่นไม่ใช่หมายเหตุท้ายหน้า; นั่นเป็นหนึ่งในปัญหาหลักที่เกตเวย์ต้องทำให้ถูกต้องอย่างแท้จริง ซึ่งจะกล่าวถึงด้านล่าง

## 2. งานเกตเวย์งานแรก: รับและทำให้เป็นมาตรฐาน

แพลตฟอร์มแตกต่างกันในเกือบทุกมิติ:

- **ตัวระบุผู้ใช้ที่แตกต่างกัน** — รหัสตัวเลข หมายเลขโทรศัพท์ หรือชื่อผู้ใช้ภายในแพลตฟอร์ม  
- **ตัวระบุการสนทนาที่แตกต่างกัน** — ข้อความตรง กลุ่ม ช่อง และกระทู้แต่ละแบบจะแสดงผลแตกต่างกัน  
- **โครงสร้างข้อความที่แตกต่างกัน** — ข้อความ รูปภาพ เสียง ไฟล์ การตอบกลับอ้างอิง และปฏิกิริยามีการออกแบบฟิลด์ของตนเอง  
- **รูปแบบเหตุการณ์ที่แตกต่างกัน** — บางอันส่งผ่านเว็บฮุค บางอันต้องเชื่อมต่อแบบคงที่หรือใช้การดึงข้อมูล

ถ้าเอเจนต์เผชิญกับความแตกต่างเหล่านี้โดยตรง การแบ่งแยกตามแพลตฟอร์มจะกระจายไปทั่วแกนหลักของมัน และทุกแพลตฟอร์มใหม่จะหมายถึงการต้องแก้ไขตรรกะหลัก การทำให้เป็นมาตรฐานจำกัดความแตกต่างเหล่านั้นไว้ที่เกตเวย์: ข้อความที่เป็นเนทีฟของแพลตฟอร์มจะกลายเป็นคำขอแบบเดียวกัน ดังนั้นเอเจนต์จึงจำเป็นต้องเข้าใจเพียงรูปแบบอินพุตเดียวเท่านั้น

ผลตอบแทนที่เป็นประโยชน์จริง: **การเพิ่มช่องทางไม่ควรต้องเปลี่ยนแปลงตัวตน หน่วยความจำ หรือตรรกะของทักษะ** เอเจนต์สนใจในสิ่งที่ถูกถาม ไม่ใช่เลย์เอาต์ของฟิลด์ของแอปใดที่ส่งคำถามนั้นมา

## 3. งานเกตเวย์ที่สอง: เส้นทางไปยังเอเจนต์เดียวกัน

นี่คือขั้นตอนที่ทำให้ 'บุคลิกภาพเดียวกันในทุกแพลตฟอร์ม' เป็นไปได้

เมื่อคำขอถูกปรับให้อยู่ในรูปแบบปกติแล้ว เกตเวย์จะใช้ **การกำหนดค่าการเชื่อมต่อ** ของคุณเพื่อกำหนดว่าเป็นของเอเจนต์ใด จากนั้นจะส่งคำขอไปยังเอเจนต์นั้น มันจะไม่สร้างบุคลิกหรือที่เก็บความทรงจำใหม่เพียงเพราะข้อความมาจากแพลตฟอร์มที่เพิ่งเชื่อมต่อใหม่

เรื่องนี้สำคัญเพราะมันเป็นตัวกำหนดว่า สินทรัพย์ระยะยาวจะถูกแชร์หรือแบ่งแยก:

| สินทรัพย์ | อยู่ที่ไหน | พฤติกรรมข้ามช่องทาง |
|---|---|---|
| กฎอัตลักษณ์และพฤติกรรม | `SOUL.md` | สำเนาเดียว, ใช้ร่วมกันทุกช่องทาง |
| โปรไฟล์ผู้ใช้ | `USER.md` | สำเนาเดียว, ใช้ร่วมกันทุกช่องทาง |
| ข้อมูลข้ามเซสชัน | `MEMORY.md` / `memories/` | สำเนาเดียว, ใช้ร่วมกันทุกช่องทาง |
| วิธีการที่จับได้ | `skills/` | สำเนาเดียว, ใช้ร่วมกันทุกช่องทาง |
| งานที่กำหนดเวลา | การกำหนดค่าชั้นเอเจนต์ | แยกจากช่องทาง; กำหนดเป้าหมายการส่งได้

เพราะทั้งหมดนี้อยู่ภายนอกชั้นแชนเนล "มันยังรู้ชื่อโครงการที่ฉันกล่าวถึงใน Telegram" ไม่ใช่คุณสมบัติการซิงโครไนซ์ที่ใครบางคนต้องสร้างขึ้น — มันเป็นผลลัพธ์ตามธรรมชาติของการที่มีเพียงสำเนาเดียวเท่านั้น

นี่คือหลักการแยกส่วนเดียวกันกับ "การสลับโมเดลไม่ทำให้ความทรงจำหาย": **แยกชั้นการเข้าถึงที่เปลี่ยนแปลงได้ออกจากชั้นทรัพย์สินที่เสถียร** สำหรับเวอร์ชันที่เกี่ยวกับด้านโมเดลของข้อโต้แย้งนี้ ดูที่ "สมองของเอเจนต์ Hermes สามารถถูกแทนที่ได้หรือไม่? ชั้นโมเดลกับชั้นเอเจนต์"

## 4. งานเกตเวย์สาม: ส่งกลับไปยังที่ที่ถูกต้อง

เมื่อเอเจนต์เสร็จสิ้น เกตเวย์จะส่งผลลัพธ์กลับ การ "ส่งกลับ" นั้นยากกว่าที่คิด เพราะมันต้องตอบคำถามสามข้อให้ถูกต้องพร้อมกัน:

1. **แพลตฟอร์มใด** — ข้อความจาก Telegram ต้องกลับไปที่ Telegram ไม่ใช่ WhatsApp
2. **การสนทนาใด** — บนหนึ่งแพลตฟอร์ม คุณอาจมีข้อความโดยตรงรวมถึงหลายกลุ่มและช่องทาง การตอบกลับไปยังการสนทนาที่ผิดไม่ใช่แค่เรื่องน่าอึดอัด; ในบริบทของกลุ่มอาจทำให้ข้อมูลรั่วไหลได้
3. **รูปแบบใด** — แพลตฟอร์มต่างกันในข้อจำกัดความยาวข้อความ การสนับสนุน Markdown วิธีการส่งรูปภาพและไฟล์ และว่ามีการอ้างอิงตอบกลับหรือไม่ เนื้อหาเดียวกันจำเป็นต้องนำเสนอแตกต่างกันตามแพลตฟอร์ม

ข้อที่สองควรได้รับการเน้นย้ำ **เป้าหมายการส่งที่ผิดพลาดถือเป็นปัญหาระดับร้ายแรงที่สุดในระบบหลายช่องทาง**: เนื้อหาส่วนตัวที่โพสต์ในกลุ่ม หรือข้อสรุปของทีมหนึ่งที่ส่งไปยังช่องทางของทีมอื่น นั่นคือเหตุผลที่ทุกช่องทางที่เชื่อมต่อใหม่ควรถูกตรวจสอบด้วยข้อความทดสอบในบทสนทนาที่ปลอดภัยก่อน

## 5. การรวมเป็นหนึ่งไม่ได้หมายความว่าไร้ขอบเขต

"เอเจนต์หนึ่งคน หลายจุดเข้า" มักถูกมองเกินจริงว่า "ทุกแพลตฟอร์มทำงานเหมือนกันหมด" ในความเป็นจริง แต่ละช่องทางมีข้อจำกัดของตัวเอง และการแชร์เอเจนต์ไม่ได้ลบข้อจำกัดเหล่านั้น

### 5.1 การอนุญาตแตกต่างกัน

แต่ละแพลตฟอร์มมีขั้นตอนการเชื่อมต่อและรูปแบบข้อมูลรับรองของตัวเอง: บางแพลตฟอร์มต้องสร้างบอทในพอร์ทัลนักพัฒนาแล้วคัดลอกโทเค็น บางแพลตฟอร์มต้องสแกนรหัส QR และบางแพลตฟอร์มต้องใช้ AppID และ AppSecret กล่าวคือ **การเชื่อมต่อแต่ละช่องทางเป็นขั้นตอนการอนุญาตอิสระ** — การตั้งค่าเพียงครั้งเดียวไม่ครอบคลุมทั้งหมด

### 5.2 ช่องทางที่รองรับแตกต่างกันตามภูมิภาค

นี่เป็นกับดักที่ง่ายเมื่ออ่านเอกสาร: ภูมิภาคทั่วโลกและจีนของ LightVela ไม่สนับสนุนชุดช่องทางเดียวกัน ลำดับช่องทางในภูมิภาคทั่วโลกคือ Telegram, WhatsApp, Discord, Slack, WeChat, QQ, WeCom, Lark ภูมิภาคจีนสนับสนุน WeChat, QQ, WeCom, Lark และ DingTalk.

ดังนั้นเมื่อคุณเห็นคำกล่าวอ้างเช่น "Telegram ได้รับการสนับสนุน" ให้ยืนยันว่ามันใช้กับภูมิภาคใด แทนที่จะสมมติว่ามันใช้ได้ทั่วทั้งภูมิภาค

### 5.3 บริบทของกลุ่มแตกต่างจากข้อความโดยตรง

ในการส่งข้อความโดยตรง เอเจนต์จะเผชิญหน้ากับคนเพียงคนเดียว; ในกลุ่มเอเจนต์จะเผชิญหน้ากับหลายคน กลุ่มจะเพิ่มคำถาม: ควรตอบเมื่อไหร่ ควรเงียบเมื่อไหร่ เนื้อหาใดที่ไม่เหมาะสมในการขยายต่อสาธารณะ และใครที่ได้รับอนุญาตให้กระตุ้นการกระทำที่ละเอียดอ่อน เหล่านี้เป็นกฎพฤติกรรมและการออกแบบสิทธิ์ — เกตเวย์ไม่สามารถตัดสินใจเรื่องเหล่านี้โดยอัตโนมัติ

### 5.4 ความสามารถในการจัดส่งแตกต่างกัน

ขีดจำกัดความยาวข้อความ การสนับสนุนข้อความรูปแบบรวย การส่งไฟล์ และความสามารถในการอ้างอิงข้อความเฉพาะรูปแบบทั้งหมดส่งผลต่อผลลัพธ์ การตอบกลับยาวที่แสดงผลได้อย่างเรียบร้อยใน Discord อาจจำเป็นต้องแบ่งหรือทำให้ง่ายขึ้นในที่อื่น

## 6. ลำดับปฏิบัติที่เป็นประโยชน์สำหรับการเชื่อมต่อช่องทางใหม่

การเปลี่ยนหลักการข้างต้นเป็นขั้นตอน ลำดับนี้ช่วยหลีกเลี่ยงปัญหาเกือบทั้งหมด

1. **ยืนยันการรองรับในภูมิภาค** — ตรวจสอบให้แน่ใจว่าช่องทางนี้มีให้บริการในภูมิภาคของคุณ เพื่อที่คุณจะได้ไม่ติดตามเอกสารที่เขียนสำหรับภูมิภาคอื่น  
2. **ทำการอนุญาตฝั่งแพลตฟอร์มให้สมบูรณ์** — ทำตามคู่มือของช่องทางนั้นเพื่อสร้างบอทหรือให้สิทธิ์การเข้าถึงและรับข้อมูลรับรอง ข้อมูลรับรองมีความละเอียดอ่อน: อย่าเขียนลงในไฟล์บริบทระยะยาวหรือวางลงในแชท  
3. **เชื่อมต่อฝั่งผลิตภัณฑ์** — กรอกข้อมูลรับรอง บันทึก และยืนยันสถานะว่าแสดงว่าเชื่อมต่อแล้ว  
4. **ส่งข้อความทดสอบ** — ใช้การสนทนาที่ปลอดภัย (ข้อความตรงหรือกลุ่มทดสอบ) และยืนยันว่า Agent ตอบกลับ  
5. **ยืนยันเป้าหมายการส่ง** — ตรวจสอบโดยเฉพาะว่าการตอบกลับไปถึง **การสนทนาเดียวกับที่คุณส่งข้อความไป** ไม่ใช่ไปยังการสนทนาอื่น
6. **ตรวจสอบหน่วยความจำที่ใช้ร่วมกัน** — ถามเกี่ยวกับสิ่งที่คุณบอกมันในช่องทางอื่น คำตอบที่ถูกต้องพิสูจน์ว่าช่องทางนี้จริงๆ แล้วเชื่อมต่อกับเอเจนต์เดียวกัน
7. **หลังจากนั้นจึงเพิ่มการเข้าถึงกลุ่ม** — หลังจากตรวจสอบข้อความโดยตรงแล้ว เข้าร่วมกลุ่มและยืนยันขอบเขตการตอบสนองภายในกลุ่มเป็นไปตามที่คาดไว้

ขั้นตอนที่ 6 เป็นขั้นตอนที่คนส่วนใหญ่มักข้าม และเป็นขั้นตอนที่มีคุณค่ามากที่สุด: นี่เป็นวิธีที่ตรงที่สุดในการยืนยันว่าช่องต่างๆ แบ่งปัน Agent หนึ่งตัวจริง ๆ

## 7. อาการทั่วไปและวิธีการอ่านอาการเหล่านี้

| อาการ | สาเหตุที่เป็นไปได้มากกว่า | การดำเนินการที่แนะนำ |
|---|---|---|
| ไม่มีการตอบกลับเลยในช่องทางใหม่ | การอนุญาตไม่สมบูรณ์หรือข้อมูลประจำตัวผิดพลาด | ตรวจสอบสถานะการเชื่อมต่อและข้อมูลประจำตัว ทำการอนุญาตใหม่ |
| การตอบกลับปรากฏในบทสนทนาต่างกัน | การระบุเป้าหมายการส่งหรือการตั้งค่ามีข้อผิดพลาด | หยุดใช้งานในกลุ่ม; ย้ายไปส่งข้อความตรงเพื่อตรวจสอบ |
| ตอบกลับแต่ "ไม่รู้จักฉัน" | อาจเชื่อมต่อกับเอเจนต์คนละตัว | ตรวจสอบด้วยข้อมูลที่รู้และดูว่าเชื่อมต่อกับเอเจนต์ใด |
| กลุ่มเงียบ, ข้อความตรงใช้งานได้ | กฎทริกเกอร์ในกลุ่มหรือสิทธิ์การเข้าถึง | ตรวจสอบกฎการตอบในกลุ่มและสิทธิ์ที่ต้องใช้ |
| การตอบกลับยาวถูกตัดหรือรูปแบบผิด | ขีดจำกัดการส่งของแพลตฟอร์ม | ปรับความยาวและรูปแบบของเอาต์พุตให้เหมาะสมกับแพลตฟอร์มนั้น |

แถวที่สามควรได้รับความสนใจ: **"ไม่รู้จักฉัน" มีความหมายแตกต่างออกไปที่นี่เมื่อเทียบกับหลังจากเปลี่ยนโมเดล** หลังจากเปลี่ยนโมเดล มันมักจะเป็นความแตกต่างด้านสไตล์; แต่บนช่องทางที่เพิ่งเชื่อมต่อ มันมีแนวโน้มมากกว่าที่หมายถึงช่องทางนี้ไม่ได้ชี้ไปที่เอเจนต์ที่คุณคิดว่าจะเป็น การวินิจฉัยก็เหมือนเดิม — ถามเกี่ยวกับข้อเท็จจริงหนึ่งข้อที่คุณมั่นใจว่ามันควรรู้

## 8. วิธีการของ LightVela: ช่องทางเป็นจุดเข้าแบบเสียบได้

Hermes แยกช่องทางออกจากเอเจนต์ในระดับกลไก แต่การเชื่อมต่อแต่ละแพลตฟอร์มยังหมายถึงการจัดการข้อมูลรับรอง การเรียกกลับ และเวลารันด้วยตัวเอง ทิศทางของ LightVela คือทำให้ชั้นนั้นเป็นจุดเข้าที่เป็นผลิตภัณฑ์และเสียบได้:

- **ช่องทางเป็นการตั้งค่า** — เชื่อมต่อหรือยกเลิกการเชื่อมต่อภายใต้เจ้าหน้าที่หนึ่งคน โดยไม่จำเป็นต้องสร้างเจ้าหน้าที่แยกตามแต่ละแพลตฟอร์ม  
- **ทรัพย์สินถูกแชร์โดยค่าเริ่มต้น** — บุคลิก ความทรงจำ ชุดทักษะ และชุดงานที่กำหนดเวลาหนึ่งชุด; ช่องทางใหม่จะใช้สิ่งเหล่านี้ได้ทันทีโดยไม่ต้องย้ายอะไร  
- **สถานะการเชื่อมต่อมองเห็นได้** — แผงควบคุมแสดงว่าช่องทางเชื่อมต่ออยู่หรือไม่ ทำให้ง่ายต่อการแยกความแตกต่างระหว่าง "ไม่เคยเชื่อมต่อสำเร็จ" กับ "เชื่อมต่อแต่ไม่ตอบกลับ"  
- **ความแตกต่างของภูมิภาคชัดเจน** — ภูมิภาคโลกและจีนจะแสดงช่องทางที่รองรับของแต่ละภูมิภาค เพื่อป้องกันความผิดพลาดข้ามภูมิภาค  
- **ปัญหาสามารถติดตามได้** — บันทึกล่าสุดใน Diagnostics ช่วยแยกปัญหาการอนุญาตจากปัญหาการส่งข้อมูลจากปัญหางาน

## ประเด็นสำคัญ

- ช่องทางคือจุดเข้า; เอเจนต์ (Agent) คือหัวข้อ หลายช่องทางสามารถใช้เอเจนต์เดียวกัน แทนที่จะใช้บอทหนึ่งตัวต่อแพลตฟอร์ม
- เกตเวย์ทำสามอย่าง: **ปรับให้เหมือนกัน** ความแตกต่างของแพลตฟอร์ม, **ส่งเส้นทาง** ไปยังเอเจนต์เดียวกัน, และ **ส่งกลับ** ไปยังการสนทนาที่เดิม
- เอกลักษณ์, ความจำ, ทักษะ, และงานที่ตั้งเวลาไว้ อยู่ภายนอกชั้นของช่องทาง ดังนั้นความต่อเนื่องระหว่างช่องทางเป็นผลสถาปัตยกรรม ไม่ใช่ฟีเจอร์ซิงค์ที่เพิ่มเข้ามา
- การรวมเป็นหนึ่งเดียวไม่ได้หมายถึงไม่จำกัด: การอนุญาต, การสนับสนุนตามภูมิภาค, บริบทกลุ่ม, และข้อจำกัดการส่ง แตกต่างกันในแต่ละช่องทาง
- หลังจากเชื่อมต่อช่องทางแล้ว ให้ยืนยันสองสิ่ง: ว่าการตอบกลับไปในบทสนทนาที่คาดหวัง และว่าสมาชิกหน่วยความจำเดียวกันจริง
