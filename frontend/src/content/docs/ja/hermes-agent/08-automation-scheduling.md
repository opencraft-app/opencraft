## 概要

**Hermes Agent は、チャットウィンドウで待機しているからスケジュール通りに連絡できるのではなく、オートメーションが三つのこと—いつ実行するか、何をするか、結果をどこに送るか—を設定として保存し、繰り返しスケジュールできるようにすることで、スケジュール通りに連絡できます。時間が来ると、スケジューラーは独立した実行を開始します：古い会話を再生するのではなく、タスク指示から作業をやり直し、その後通知設定に従って出力を届けます。LightVela では、オートメーションは次の要素で構成されます：名前、スケジュール（固定曜日、固定間隔、または一度きりのいずれかを選択）、タスク指示、アクティブ時間帯、通知チャネル。広く信じられている主張への一つの訂正：「このタスクを特定のモデルに固定する」フィールドなので、モデルを切り替えた後に自動化モデルを再同期するというアドバイスは適用されません。信頼性を決定する部分はタスク指示です — 実行時に誰も確認できないため、プロンプト自体が目標、範囲、出力形式を持つ必要があります。**

---

## 「プロアクティブ」とは、常にあなたを監視するという意味ではありません

「毎朝ニュースの要約を教えて」といった指示は通常の指示のように聞こえますが、「今ニュースの要約を教えて」とは根本的に異なります。

二つ目は会話です：あなたがその場にいるので、いつでもフォローアップしたり、修正したり、文脈を追加したりすることができます。一つ目は**あなたが不在の間に実行される必要がある作業**です：誰も正しく理解したことを確認せず、出力が期待に沿わない場合も止めず、結果を実際に確認できる場所に送るよう指示もありません。

ですので、「先回り」の難しい部分はタイマーによるトリガーではありません—それは簡単な部分です。難しいのは次のことです：**あなたの存在に依存していた会話を、不在でも成功する作業指示書に書き直すこと。** この記事では、その作業指示書に何を含め、どのように書けば確実に機能するかを解説します。

---

## 1. 自動化が実際に含むもの

LightVelaで自動化を作成するには、これらのフィールドが必要です。

| フィールド | それが答える質問 | 備考 |
|---|---|---|
| **名前** | このタスクは何と呼ばれますか？ | リストで識別するために使用します。名前は「タスク1」ではなく、アクションにちなんで付けてください |
| **スケジュール** | いつ実行されますか？ | 固定曜日、固定間隔、または一度だけ — いずれかを選択してください |
| **タスクの指示** | 何を達成すべきですか？ | エージェントが実行時に使用するプロンプト |
| **有効時間ウィンドウ** | どの時間帯が有効ですか？ | タスクの実行可能時間を制限します。空白のままにすると24時間いつでも実行可能です |
| **通知チャネル** | 結果はどこに送られますか？ | どのチャネルが実行通知を受け取るかを選択する任意のトグル |

**はっきり言っておくべき点：『モデル』フィールドは存在しません。** オートメーションは特定のモデルに固定されているわけではないため、モデルを切り替えた後に各オートメーションのモデルを確認して再同期する必要があるというよくあるアドバイスは、この製品形状には当てはまりません。モデルを切り替えた後に確認すべきなのは、存在しないフィールドではなく出力の**品質**です。この背景にあるレイヤリングについては、「Hermes Agentの脳は置き換えられるか？ モデルレイヤーとエージェントレイヤー」を参照してください。

また、スケジュールは固定曜日、固定間隔、または一回限りのいずれかから選択するものであり、任意のcron式ではないことにも注意してください。これを最初に理解しておくと、cron形式のスケジュールを設計しても、それを入力する場所がないという事態を避けられます。

## 2. 3つのスケジュールタイプからの選択

この3つのモードはそれぞれ異なるニーズに対応しており、間違ったものを選ぶと期待通りの動作にならない場合があります。

**固定曜日**は、人間のリズムや作業サイクルに結びついた作業に適しています — 月曜の朝に先週の進捗をまとめる、日曜に植物に水をやるリマインダーなど。その特徴は**特定の時間に固定されている**ことで、「その瞬間にこれを見たい」というニーズに合っています。

**固定間隔**は、タイミングは重要でなく、頻度だけが重要な作業に適しています — 例えば数時間ごとに情報源をチェックする場合などです。その特徴は、**前回の実行からカウントされる**ことで、「このリズムを維持してほしい」というニーズに合っています。

**一度限り** は特定の日に通知するリマインダーのような単発のイベントに適しています。実行後に終了し、その後オフにする必要はありません。

選択時の簡単な確認方法：**要件に特定の時刻が記載されていますか？** はいの場合は固定曜日を使用します。頻度のみが指定されている場合は固定間隔を使用します。1回だけの場合は一度限りを使用します。

---

## 3. アクティブ時間帯の用途

このフィールドは簡単にスキップできますが、実際の面倒を解決します：**課題のリズムを維持したいけれど、特定の時間帯には邪魔されたくない場合です。**

典型的な例は間隔タスクです。「2時間ごと」に設定し、アクティブウィンドウが設定されていない場合は、夜間も含めて24時間実行されます。アクティブウィンドウが設定されている場合は、指定した時間だけ実行されます。

空白のままにすると、連続して動作します。したがって、タスクが実行されるべきでない時間に実行された場合は、まずこの欄を確認してください。

---

## 4. 時間が到来したときに実際に何が起こるか

ここで誤解が最も起こりやすいです。多くの人はスケジュールされたタスクを「元の文章をエージェントに再送信すること」と考え、それが原因でコンテキストに偏りすぎたプロンプトを作ることになります。

実際に起こること: スケジューラが目標時間に達すると、**独立したエージェントの実行をトリガーします**。その実行は、タスクが作成された会話を再現するのではなく、タスク指示から作業を完了します。

これは重要な結果をもたらします: **タスク指示には独自のコンテキストを持たせる必要があります。** タスクを作成する際に頭の中で持っていた背景や、以前にエージェントと話し合った詳細は、指示に書かれていない限り、または既に長期メモリに記録されていない限り、実行時には適用されない可能性があります。

2つのバージョンを比較してください:

- **文脈依存**：「さっきやったようにまとめを作ってください。」— 実行時には「さっきやった」は存在しません。
- **自己完結型**：「過去24時間の未読メールを送信者ごとにまとめ、グループごとに最大3件まで表示し、返信が必要なメッセージのみを保持する；各項目を1行で箇条書きにして出力。」

2番目の指示は、目の前に誰もいなくても確実に実行できます。なぜなら目標、範囲、フィルター条件、出力形式がすべてその中に含まれているからです。

## 5. 有効なタスク指示の書き方

上記の仕組みを踏まえると、信頼できるタスク指示は通常、4つの部分を含みます。

**第一に、明確な目標行動。** 「監視する」ではなく、何を*する*かを明示してください。「監視する」が完了したかどうかは判断できませんが、「要約してリスト化する」が完了したかどうかは判断できます。

**第二に、明確な範囲の境界。** 時間範囲（過去24時間）、量の上限（グループごとに最大3件）、フィルター（私の返信が必要なもののみ）などです。境界がなければ、同じタスクでも日によって出力が大きく異なる可能性があります。

**第三に、明確な出力形式。** リスト形式でも散文形式でも、グループ化されていてもフラットでも、項目の長さはどのくらいでも構いません。あなたがその場にいないので、「長すぎるので短くしてください」とその場で言うことはできません。

**第四に、明確な例外処理。** もし何も一致しなかった場合、「今日処理するものはありません」と送るべきか、無言のままでいるべきか？これがないと、「タスクが実行されなかった」ことと「タスクは実行されたが何も見つからなかった」ことを区別できません。

四番目のポイントは最も省略されがちで、タスクが正常かどうかを判断する能力に直接影響します。

## 6. 推奨される展開順序

「タスクを作成する」を1つのステップとして扱わないでください。この順序はほとんどの問題を早期に表面化させます。

1. **まずチャットで手動で確認してください。** 使用する予定のプロンプトを直接エージェントに送信し、出力を確認します。この方法でスケジュールせずにプロンプトを調整します。
2. **その結果に基づいてプロンプトを修正します。** 出力が長すぎる、範囲が広すぎる、形式が不安定 — これらすべてをここで修正します。
3. **タスクを作成し、スケジュールを設定します。** 2章のテストを使用してモードを選びます。
4. **通知チャネルが自分が実際に確認する場所に向けられていることを確認してください。** 見ることのない場所に結果が送られても、結果がないのと同じです。
5. **必要に応じてアクティブな時間帯を設定してください。** 特に間隔タスクの場合、夜間の中断を避けるために重要です。
6. **実際の実行を1回待ってから、実行記録を確認してください。** これは重要なステップです — **「タスク作成済み」を完了とみなさないでください。** 保存が成功したということは、設定が保存されたことを意味し、出力が正しいことを意味しません。
7. **最初の実際の実行に基づいてプロンプトをもう一度洗練してください。** 実際の実行は手動テストと異なる場合があり、この2回目の修正で通常は最大の安定性向上が得られます。

製品はタスクリストからタスクの詳細確認、編集、一時停止、削除をサポートしているため、ステップ7は簡単です。タスクが一時的に不要な場合は、削除するより一時停止を優先してください。設定は再利用可能なままになります。

## 7. 一般的な症状と確認箇所

| 症状 | より可能性の高い原因 | 推奨される対処 |
|---|---|---|
| 予定時刻になっても何も起こらない | タスクが一時停止中、または現在時刻が有効時間外 | タスクの状態とアクティブな時間帯を確認してください |
| 実行されましたが、結果は到着しませんでした | 通知チャネルが設定されていないか、あなたが読まない場所に配信されています | 通知設定を確認してください |
| 出力の長さと形式は大きく異なります | 指示には範囲の制限や出力形式がありません | セクション5の4つの要素を追加してください |
| 出力が手動テストと大きく異なります | 指示は作成時の会話のコンテキストに依存していました | 自己完結型の指示として書き直す |
| 「実行されなかった」と「何も見つからなかった」を区別できない | 指示に例外処理がない | 「何もない場合でも通知を送る」を追加する |
| 夜間に妨害される | 間隔タスクに有効な時間帯がない | 有効な時間帯を設定する |

トラブルシューティングの一般的な原則：**まず「実行されなかった」と「実行されたが間違ったものを出力した」を分けること。** 前者はタスクの状態、アクティブウィンドウ、および通知設定に関連し、後者は指示そのものに関連します。これらは解決方法が全く異なるため、一緒に調査すると時間の無駄になります。

## 8. LightVelaのアプローチ：設定可能でレビュー可能な積極的作業

Hermesはメカニズムレベルでのスケジュール作業をサポートしていますが、ランタイムとスケジューリングの信頼性を維持するのはオペレーターの責任です。LightVelaの方向性は、これを設定可能でレビュー可能な製品機能にすることです：

- **テンプレートは初期コストを下げます** — 何を自動化すべきかわからない場合は、既製のテンプレートから始めて調整してください。
- **タスクのライフサイクルは管理可能です** — 作成後に詳細を表示したり、編集、停止、削除ができ、一つの条件を変更するためにタスクを作り直す必要はありません。
- **配信は選択可能です** — 通知チャネルはオプションの切り替えなので、結果を実際に確認する場所に届きます。
- **他の機能から分離されています** — 自動化、モデル、スキル、クラウドストレージは独立して構成され、モデルを切り替えても自動化設定は変更されません。
- **障害は追跡可能です** — 実行異常と最近のログを診断で組み合わせて原因を特定します。

## 主なポイント

- オートメーションは基本的に、いつ実行するか、何をするか、どこに配信するかの保存された繰り返し可能な設定です。
- フィールドは次の通りです：名前、スケジュール（固定曜日 / 固定間隔 / 一回限り）、作業指示、有効時間帯、通知チャネル。
- **「モデル」フィールドはありません** ので、「切り替え後にオートメーションモデルを再同期する」という表現は不正確です。スケジュールも任意のCron式ではありません。
- トリガーは古い会話の再生ではなく、**独立した実行**を開始するため、指示は自己完結型でなければなりません。
- 信頼できる指示は4つの部分で構成されます：対象のアクション、範囲の境界、出力形式、例外処理。
- 決定的な展開ステップは最後のステップです："タスク作成"で止まるのではなく、**実際の実行を待ち、記録を確認する**ことです。
