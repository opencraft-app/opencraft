# DeepSeek Harness 真实接入 Proposal

**状态：** 本地第一版与在线冻结依赖、五插件原子安装增强均已实现并完成本地验证；北京 Sandbox 真实组合冒烟仍待用户确认后执行。

## 背景与目标

在现有“管理 > 实验室 > DeepSeek Harness”三态演示基础上，接入真实实例状态、幂等安装、重启、同源 WebUI 访问和页面内模型供应商配置。配置卡片采用“已配置列表 + 单项展开编辑 + 完整白名单配置区”，支持 API Key 新增、覆盖修改和删除。保存期间锁定配置交互并等待 `debug/exec` 返回，结果通过顶部居中 Toast 即时反馈。DSH 与 Hermes 运行在同一台实例、同一 `agentuser` 环境中，但使用独立版本目录、`DSH_HOME` 和系统级 `deepseek-harness.service`；DSH 依赖不写入 Hermes runtime 包树，共用的 pnpm 版本由镜像清单固定。

## 范围

- frontend 复用 `BotRepository.execDebugCommand`，经现有 `/v1/instances/:id/debug/exec` 完成状态、安装、任务查询、重启和模型配置。
- Hermes 镜像提供固定版本、幂等、可回滚的安装器、冻结依赖清单与模型供应商配置 helper。
- 安装器在线获取锁文件指定的依赖，并为 DSH `web` profile 全量安装 SkillHub、QQBot、微信、企业微信和 Lark；五个插件全部验证成功后才允许任务完成。
- Provider helper 在实例回环访问 DSH 固定 RPC；WebUI 继续通过登录态 TAT 虚拟 HTTP 访问 `127.0.0.1:3080`。
- 国内站和国际站使用已确认的不同 Provider 白名单；DeepSeek 产品标识映射到 `deepseek-official`。
- 配置下拉始终展示当前站点完整 Provider 白名单；重复保存已配置 Provider 等价于覆盖更新。
- 首批真实安装只进入北京 Sandbox；本需求不新增 service-gateway 路由。

## 非目标

- 不提供具体 model ID 选择、自定义 Provider、Base URL、协议或模型参数。
- 不公开实例 3080，不复用参考机的公网 IP/路径配置。
- 不把 API Key 明文写入 shell、URL、日志、埋点、localStorage 或后端业务数据库；`debug/exec` 命令使用 base64 进行 shell 安全编码，该编码不等同于加密。
- 不新增 DeepSeek Harness 专用 ctl、transport、errcode 或 service-gateway 接口。
- 不在本轮创建 `*.dsh.lightvela.site` 独立域名。
- 不安装 `dsh-auth`、Caddy 或另一套 SkillHub CLI；继续使用 LightVela 登录态 TAT 代理，Hermes 已有工具和渠道插件保持不变。
- 本轮不改为镜像内离线预置，也不新增独立 COS 安装包发布链路。

## 关键决策

- 固定 `@deepseek-ai/dsh@0.1.0-rc.7`、`@cocofhu/skillhub@0.2.13`、`deepseek-harness-qqbot@0.1.5`、`deepseek-harness-weixin@0.2.5`、`deepseek-harness-wecom@0.1.5` 和 `deepseek-harness-lark@0.1.5`。
- DSH runtime 与 `web` profile 分别使用仓库内 `pnpm-lock.yaml` 执行 `--frozen-lockfile` 安装；四个渠道插件固定 COS revision 和 SHA256，registry 依赖使用 lockfile integrity 校验并配置有限重试。
- 安装在任务临时目录完成下载、依赖安装和配置组合检查后再原子切换；任一插件失败即恢复旧 runtime、完整旧 `web` profile 和旧 service unit。
- 已安装 profile 出现非 LightVela 管理的额外 DSH 插件时，安装器保持原状并安全失败，不删除未知插件或退化为非冻结安装。
- 包名、版本、目录、用户、端口和 Provider 白名单由实例侧 helper 固定；前端只选择固定动作与白名单 Provider ID。
- API Key 经 `debug/exec` 传给实例 helper 的 stdin，再由 helper 通过 DSH `credentials.set` 单向写入；设置写入携带 `expectedRevision`。
- 删除经同一 `debug/exec` 通道调用固定 `remove-provider` 动作；只清理可确认由 LightVela 创建且当前可写的凭据，环境变量密钥和自定义引用保持不变。
- WebUI 过渡期复用登录态下的同源 TAT Service Worker 代理。

# 个人助理运行时概览页重构 Proposal

**状态：** 已获得用户对产品方向的明确授权，待按本提案实现并由用户验收。

## 背景

当前概览页仍容易被理解为“创建一个 Bot 的部署介绍”或一张视觉海报：模块名偏后台、卡片密度偏高，记忆、主动性和跨工具执行没有成为用户可感知、可信任的产品能力。

本轮将产品心智改为：

> **LightVela 是一个跨 IM、跨工具、长期在线的个人助理运行时。**

它不是一个单轮聊天机器人，也不是可爱陪伴型 Bot。用户把聊天、链接、截图、文件和语音碎片交给 Hermes；Hermes 将其收进个人 Inbox，形成可见且可控的记忆，按风险分层提醒或建议，并只在授权范围内执行低风险动作。

## 目标

1. 让首次访问者在首屏和一次向下浏览中理解完整链路：**收进来 → 记住 → 分层主动 → 在授权内做出去**。
2. 把“记忆”展示为一个可查看、限定范围、暂停或删除的产品面板，而非后台能力。
3. 把“主动”展示为具备权限边界的工作机制：低风险可自动，高风险始终先确认。
4. 把“技能”翻译成用户能理解的跨工具能力：信息抽取、写作、归档、摘要、提醒和低风险自动化进入工作流。
5. 建立浅青 / 冷白、克制、清晰、有系统感的视觉语言；减少卡片堆叠和无意义动效，提升可信赖感。

## 用户与核心场景

### 目标用户

- 同时在微信、Telegram、Discord、WhatsApp、邮件、文档和网页之间工作的人。
- 需要把临时消息、链接、截图、语音和会议结论变成长期可检索、可跟进信息的人。
- 希望助理主动，但不接受黑箱记忆或未经确认的高风险外部操作的人。

### 用户完成一次浏览后应得到的答案

| 用户问题 | 页面必须回答 |
| --- | --- |
| 它和普通聊天机器人有什么不同？ | 它持续收集跨 IM、跨工具的碎片，并长期运行、整理、提醒、跟进。 |
| 它会记住我什么？ | 偏好、人际关系、项目上下文和长期资料；每一项都可见、可编辑、可限定范围。 |
| 它会不会越权？ | 默认安静记录；提醒、建议、草稿、低风险执行逐层开放；发送、删除、付款、改日历、外部回复均须确认。 |
| 它具体能做什么？ | 抽取信息、写作、归档、摘要、提醒、跟进和在授权范围内跨工具执行。 |

## 范围

### 本次包含

- 重构中文静态概览页 `frontend/public/lightvela-overview.html` 的信息架构、文案、视觉系统与前端演示交互。
- 保留“概览页”的网站属性：固定导航、分段阅读、可见 CTA、页脚和明确的站内入口。
- 构建五段连续产品叙事：Hero、Personal Inbox、Memory、Proactivity + Permissions、跨工具工作台。
- 为四个演示面板提供可点击 / 键盘可用的样例数据交互；交互只切换展示状态，不伪造真实保存、执行或外部发送。
- 更新静态页面回归测试，约束核心产品文案、关键 anchor、可访问性钩子与禁用的旧叙事。
- 完成桌面、移动端和键盘路径的浏览器验收。

### 本次不包含

- 不新增或修改后端 API、数据库、跨 IM 连接器、记忆存储、权限系统或真实自动执行能力。
- 不重做现有 `/agents` 控制台、创建向导、登录、定价或其他营销页面。
- 不把概览页中的示例数据写入本地存储或用户账户。
- 不使用大面积人物 / 娃娃图、单独大 mascot、复杂 3D 海报、全屏视频、星空粒子或无语义光效。
- 不复用“自动任务 / 人设模板 / SkillHub”作为页面一级产品标题；真实控制台的原有能力不在本次改名或迁移。

## 方案比较与选择

### 方案 A：部署教程式页面

以“创建、接入、开始使用”为主线，强调配置步骤。

- 优点：路径直接。
- 缺点：把产品降格为一次性部署工具，无法讲清长期记忆和主动性，也与本轮目标冲突。

### 方案 B：可爱陪伴叙事

以大 Bot 形象、人设和情绪陪伴为主视觉。

- 优点：情感记忆点强。
- 缺点：弱化可靠性与工作能力，容易显得轻浮；用户已明确拒绝大量娃娃和可爱陪伴感。

### 方案 C：个人助理运行时（采用）

以一条连续的信息与授权链路呈现产品：外部碎片进入 Inbox，沉淀为可控记忆，触发分级主动性，再被授权接入工具执行。

- 优点：能完整解释“为什么需要长期在线 Agent”；将 Trust、Memory、Proactivity 和 Execution 统一为一个系统；适合浅青 / 冷白、克制的产品视觉。
- 代价：需要用清晰的状态切换和样例数据承载信息，而不是依靠单张强视觉海报。

## 信息架构与内容原则

1. **Hero：定义运行时，不解释部署。**
   - 主定位：“一个跨 IM、跨工具、长期在线的个人助理运行时。”
   - 次级承诺：懂我、记得我、替我盯事、在授权内执行。
   - 右侧为克制的信息流 / 运行状态，不使用大 Bot。
2. **Personal Inbox：先解释‘收进来’。**
   - 展示微信、Telegram、Discord、WhatsApp、邮件、链接、截图和语音等来源。
   - 选中来源后，展示它被识别成待办、资料、联系人、灵感、日程或项目内容的过程和去向。
3. **Memory：再解释‘记住’。**
   - 展示偏好、关系、项目和长期知识库四类记忆。
   - 清楚展示生效范围、是否生效、是否敏感、可编辑 / 暂停 / 删除的控制入口。
4. **Proactivity + Permissions：解释‘替我盯事’但不越权。**
   - 以安静记录、温和提醒、主动建议、代办草稿、低风险自动执行组成层级。
   - 高风险动作单独列为必须确认，不和低风险动作混淆。
5. **跨工具工作台：解释‘做出去’。**
   - 让用户选择能力类型，展示对应的输入、处理、结果草稿与权限状态。
   - 文案始终从用户获得的结果出发，而不是从后台模块名出发。

## 视觉与体验原则

- 主色为冷白和浅青，正文以深青黑保证可读性；少量蓝青仅用于状态、焦点和交互反馈。
- 留白、细分割线、连续的系统表面替代卡片堆叠；单个面板承载一个完整工作状态。
- 桌面端最大正文宽度约 1180px；标题不超过 Hero 必要规模，后续段落使用清晰但克制的层级。
- 动效仅表达“输入被识别”“记忆状态切换”“权限等级变化”“结果草稿生成”；尊重 reduced-motion。
- 不使用深灰底、纯黑白极简、紫粉梦幻、强玻璃反射、大面积模糊、噪点、粒子或自动滚动造成的注意力干扰。

## 验收标准

1. 用户无需阅读部署教程，即可说明 LightVela 的核心是跨 IM、跨工具、长期在线的个人助理运行时。
2. 页面按“收进来 → 记住 → 分层主动 → 在授权内做出去”连续讲清产品，而非拆成无关联卡片。
3. Personal Inbox 明确展示来源、自动识别类型与输出去向。
4. Memory 面板展示可见、可控、可删除、范围化与敏感信息边界。
5. 主动性面板明确区分五层主动性和六类高风险确认动作。
6. 跨工具能力展示信息抽取、写作、归档、摘要、提醒或低风险自动化如何接入工作流。
7. 页面不出现“三步部署”“创建一个 Agent 教程”“SkillHub”一级叙事、大娃娃、重卡片堆叠或纯装饰性动效。
8. 浅青 / 冷白方案在 1440px 与 390px 宽度下均有清楚阅读层级和足够对比度。
9. 所有演示选择器可用键盘操作，有明确焦点、`aria-pressed` / `aria-controls` / live status；`prefers-reduced-motion` 关闭非必要动效。
10. 静态测试、类型检查和浏览器 smoke 均通过；用户仍需在本地预览中完成最终审美验收。
