# Go 后台应用层架构设计

状态：已批准  
日期：2026-07-30  
范围：Chatserver Platform v1 的 HTTP、应用服务和外部端口

## 1. 目标

平台后台采用 OpenAPI-first：`openapi.yaml` 是 HTTP 协议唯一事实源，由生成器产生
强类型 HTTP 外壳，手写代码只负责业务编排。

本设计解决：

- HTTP 路由、请求解析、响应编码和协议校验如何生成；
- Transport、Application、Domain、Port 和 Adapter 如何分层；
- Human、Runtime 和 Agent credential 如何进入统一认证上下文；
- 应用错误如何稳定映射为 OpenAPI 错误；
- 数据库会话与后台会话如何并行而不互相绑定；
- 腾讯云 IM/TAT、Redis 和 Ent 如何通过端口接入。

本设计不实现：

- Ent Schema、SQLite migration、TDSQL DDL；
- 具体腾讯云调用；
- 任何普通聊天代理、WebSocket 或 Socket.IO；
- Runtime 客户端；
- API 规格之外的新业务能力。

## 2. 固定选型

采用：

```text
Go 标准 net/http
+ Go 1.22+ http.ServeMux
+ oapi-codegen strict std-http server
+ oapi-codegen net/http request validation middleware
```

不采用 Gin、Echo、Fiber、Gorilla Mux。首版也不引入 Chi。

理由：

- Go 1.22 起 `ServeMux` 已支持 method、路径参数、通配符和 405；
- 当前使用的 Go 版本满足标准路由能力；
- `oapi-codegen` 可以直接为标准 `net/http` 生成 strict server；
- 59 个 operation 全部来自 OpenAPI，不需要手写路由分组；
- 标准 `http.Handler` 中间件更容易测试、组合和替换；
- Gin 的 Context、binding、validation 和 rendering 会与生成层重复；
- 后台延迟主要来自数据库、密码哈希和腾讯 IM/TAT，路由器基准不是决策因素。

Chi 保留为未来可逆选择。如果未来出现大量非 OpenAPI 路由、复杂子路由挂载或现有
标准 ServeMux 无法清楚表达的中间件作用域，可以把生成目标切换为 chi-server；
Application、Domain 和 Port 不随之改变。

### 2.1 OpenAPI 版本

正式生成前，把平台自有的 `openapi.yaml` 从 3.1 迁移为 **OpenAPI 3.0.3**，并继续
作为唯一协议事实源。

原因：

- 稳定版 oapi-codegen 当前正式支持 OpenAPI 3.0；
- 当前 3.1 文件使用 `type: [string, null]` 等 JSON Schema union，稳定生成器无法
  直接处理；
- 平台拥有该协议，没有必要同时维护 3.1 源文件和 3.0 生成 overlay；
- 不采用实验性 3.1 parser 或未发布分支。

迁移保持 HTTP 语义不变：

```text
type: [string, null]
→
type: string
nullable: true
```

同时移除或转换 3.1-only 关键字。迁移后的 3.0.3 文件必须同时通过 Redocly、
kin-openapi load/validate 和锁定版本的 oapi-codegen 生成。只有这三个门禁都通过，
才允许开始实现 Handler。

## 3. 总体依赖

```text
platform/v1/openapi.yaml
          │
          ▼
oapi-codegen generated transport contract
          │
          ▼
HTTP Transport Adapter
          │
          ▼
Application Service
     ┌────┼──────────────┐
     ▼    ▼              ▼
 Repository Port   Tencent IM Port   Tencent TAT Port
     │                    │              │
     ▼                    ▼              ▼
 Ent Adapter       Tencent IM Adapter  Tencent TAT Adapter
```

依赖只能向内：

```text
transport → application → domain/ports/shared kernel
adapter   → domain/ports/shared kernel
```

禁止：

```text
application → net/http
application → generated OpenAPI package
application → Ent Client
application → 腾讯 SDK 具体类型
domain      → transport/adapter
```

允许的 shared kernel 只有稳定错误、不可变值对象和纯函数。`apperror` 属于 shared
kernel；Clock、ID generator、Token signer 和 RateLimiter 都是 Port，Application
不得直接依赖系统时间、全局随机源或具体 Redis 客户端。

## 5. 生成代码

### 5.1 生成内容

`oapi-codegen` 生成：

- OpenAPI Schema 对应的请求/响应 DTO；
- path/query/header/body 参数类型；
- 每个 operation 的 request/response object；
- strict server interface；
- 标准 ServeMux 路由注册；
- JSON 请求解码与响应编码；
- 允许的响应 Go 类型、状态和媒体类型。

strict response 类型降低手写错误，但不等于完整运行时响应 Schema 校验。format、
min/max、enum、业务值和遗漏映射仍由契约测试覆盖。

生成目录中的文件不得手工修改。任何 HTTP 字段变化必须先修改
`platform/v1/openapi.yaml`，再重新生成。

### 5.2 不生成的内容

生成器不负责：

- 业务权限；
- 数据库事务；
- 幂等语义；
- Domain 不变量；
- 腾讯云副作用；
- 稳定业务错误；
- Secret 脱敏；
- Repository 查询。

生成 DTO 只属于 Transport。Domain Entity、Application Command/Result 和数据库
Entity 是不同类型，边界处显式转换。

### 5.3 可复现性

- 生成工具版本固定在 `go.mod` tool directive；
- 通过 `go generate` 执行，不依赖开发者全局安装；
- CI 重新生成并验证结果无漂移；
- CI 依次执行 OpenAPI 3.0.3 lint、kin-openapi validate、oapi-codegen 和生成包编译；
- 生成文件包含来源和工具版本注释；
- 不使用浮动 `latest`。

## 6. HTTP 请求链路

```text
http.Server
→ Request ID / tracing
→ panic recovery
→ 可信代理与客户端地址
→ access log
→ security headers / CORS
→ 请求体和 Content-Type 限制
→ Credential extraction + request-local AuthState
→ OpenAPI request validation + authentication hook + validation error handler
→ oapi-codegen strict handler
→ Transport DTO mapping
→ Application Service
→ OpenAPI response mapping
```

所有 middleware 使用标准签名：

```text
func(next http.Handler) http.Handler
```

普通 Middleware 只处理传输级横切关注点，不读取数据库并决定 Server 业务权限。
唯一例外是 OpenAPI authentication hook：它调用统一 Authenticator 完成凭证数据库
当前性校验；它只产生 CurrentPrincipal，不判定 Server 角色或资源权限。

`http.Server` 必须显式配置：

- ReadHeaderTimeout；
- ReadTimeout；
- WriteTimeout；
- IdleTimeout；
- MaxHeaderBytes；
- graceful shutdown；
- 关闭时的请求 drain 上限。

平台没有上传普通聊天附件或流式 HTTP API。请求体使用统一的较小上限，超限返回稳定
错误；以后只有 OpenAPI 明确声明的大请求才能单独放宽。

## 7. Strict Handler

生成的 strict interface 由一个 HTTP Adapter 类型实现。为了避免 59 个方法集中在
一个大文件：

- 同一个 Adapter 类型按 Auth、Server、Agent 等领域拆分多个文件；
- 每个方法只做 Principal 读取、DTO 转换、调用一个 Application 方法和响应转换；
- Handler 不开始数据库事务；
- Handler 不调用腾讯云；
- Handler 不包含领域状态机；
- Handler 不返回内部错误原文。

链路示例：

```text
CreateServerRequestObject
→ CreateServerCommand
→ server.Application.Create(ctx, principal, command)
→ CreateServerResult
→ CreateServer202JSONResponse
```

## 8. 认证与授权

### 8.1 CredentialCandidate 与 CurrentPrincipal

Authorization 解析后先产生候选凭证：

```text
AnonymousCandidate
HumanBearerCandidate(rawToken, parsedClaims?)
RuntimeBearerCandidate(rawToken, parsedClaims?)
AgentCredentialCandidate(rawSecret, routePrefix?)
```

Candidate 不是 Principal，不能被 Application 直接用于授权。

每个请求建立一个私有 typed context key 指向 request-local `AuthState`。OpenAPI
validator 根据 operation 的 security scheme 调用 authentication hook。Hook：

1. 精确匹配 HumanBearer、RuntimeBearer、ComputerBearer 或 ComputerCredentialAuth；
2. 调用统一 `authn.Application.Authenticate`；
3. 校验签名、到期和数据库当前性；
4. 成功后只把 `CurrentPrincipal` 写入当前请求的 AuthState；
5. 失败时由 validator error handler 返回统一 ErrorEnvelope。

```text
AnonymousPrincipal
CurrentHumanPrincipal(accountId, authSessionId, tokenVersion)
CurrentRuntimePrincipal(serverId, agentId, credentialVersion)
CurrentAgentCredentialPrincipal(serverId, agentId, credentialVersion)
```

AuthState 不跨请求复用，不进入日志，不允许 handler goroutine 并发修改。原始 Bearer、
Refresh Token、Agent credential 和 UserSig 不作为 Principal 字段；原始 Secret 只在
当前认证调用内存中短暂存在。

### 8.2 统一 currentness 门禁

Authenticator 负责：

- Token 格式和签名；
- 到期时间；
- AuthSession 未 revoked、family 未撤销；
- Account tokenVersion 与状态当前；
- Runtime Token 的 Agent/Member/Computer 当前；
- Agent credential 完整 Secret hash、version 和 active 状态；
- Human JWT 不能通过 RuntimeBearer，Runtime JWT 不能通过 HumanBearer；
- 从可信 claim 或凭证前缀提取数据库路由候选后再复核事实。

Application Service 负责：

- Runtime URL serverId 是否等于 Token serverId；
- Server 角色和资源归属；
- revision、幂等与能力限制。

Token 自报的 accountId/serverId 只用于路由，不构成授权事实。

所有受保护 strict handler 必须先从 AuthState 取得对应 CurrentPrincipal；不存在、
类型不匹配或未经过 Authenticator 的请求不能调用 Application。架构测试必须证明
Handler 没有绕过该门禁的替代入口。

## 9. 请求校验

请求校验分为三层：

1. OpenAPI middleware：类型、required、格式、路径/query/header/body；
2. Transport：规范化、请求体上限、Content-Type 和跨字段基础语法；
3. Application：业务状态、不变量、权限、revision、幂等和资源归属。

不再维护 Gin `binding` tag 或第二套 HTTP DTO 校验规则。OpenAPI 未表达但属于业务
规则的校验必须进入 Application，不得偷偷留在 Handler。

### 9.1 三类协议错误出口

统一 ErrorEnvelope 分别覆盖：

1. `nethttp-middleware ErrorHandlerWithOpts`：未知路径、错误 method、Schema 和
   security 错误；
2. 生成的 std-http `ErrorHandlerFunc`：path/query/header/body 绑定错误；
3. strict `RequestErrorHandlerFunc/ResponseErrorHandlerFunc`：strict decode、
   Handler 未知错误和非法 response object。

三类 handler 共用一个错误编码器和 requestId。禁止保留 `http.Error` 默认纯文本。
未知路径返回 404，已知路径错误 method 返回 405 并保留 `Allow` Header。

`nethttp-middleware` 对 route lookup error 给出的 status 只作建议。Error handler
必须显式识别 method-not-allowed，依据已加载 OpenAPI 路由表计算 `Allow`；不能直接
照抄建议状态。该行为使用未知 path 与已知 path/错误 method 两组黑盒测试固定。

## 10. 错误模型

Application 返回 `apperror` 稳定错误：

```text
Code
SafeMessage
Details（可公开、结构化）
Cause（仅日志）
RetryAfter
```

HTTP 层集中映射：

| HTTP | 稳定错误码 |
|---:|---|
| 400 | `invalid_request` |
| 401 | `unauthenticated`、`token_expired`、`session_revoked`、`runtime_credential_invalid`、`runtime_credential_revoked` |
| 403 | `permission_denied`、`member_removed`、`channel_membership_required` |
| 404 | `route_not_found`、`server_not_found`、`member_not_found`、`channel_not_found`、`agent_not_found`、`computer_not_found`、`task_not_found`、`reminder_not_found`、`reminder_occurrence_not_found` |
| 405 | `method_not_allowed` |
| 409 | `account_already_exists`、`im_identity_not_ready`、`channel_not_ready`、`agent_not_ready`、`agent_must_be_stopped`、`computer_not_ready`、`computer_offline`、`computer_in_use`、`computer_already_registered`、`registration_expired`、`revision_conflict`、`task_assignment_stale`、`idempotency_conflict`、`cross_partition_operation_denied` |
| 422 | `runtime_config_invalid`、`computer_os_unsupported`、`schedule_invalid`、`routing_key_invalid` |
| 429 | `rate_limited` |
| 503 | `im_session_unavailable`、`runtime_unavailable`、`terminal_session_unavailable`、`tat_operation_failed`、`tat_operation_uncertain`、`tencent_unavailable`、`tencent_rate_limited`、`tencent_operation_uncertain`、`tencent_permission_denied` |
| 500 | `internal_error` |

OpenAPI 请求错误和 Application 错误都使用统一 ErrorEnvelope。requestId 必须进入
错误响应。Cause、SQL、腾讯响应原文、Token、脚本和临时 URL 不得进入响应。

不可枚举策略固定为：

- 未经目标 Server 授权时，无论资源是否存在都返回对应 `*_not_found + 404`；
- 已确认是该 Server active Member，但角色不足时返回 `permission_denied + 403`；
- malformed UUID/route key 在进入 Repository 前返回 422；
- 腾讯管理员权限错误对外返回 503，不能伪装成调用者 403。

错误映射在一个中央 registry 中穷举。测试遍历全部稳定错误码，发现未映射码时失败；
各 Handler 不维护自己的 switch。

response encode/生成 response object 等内部失败对外统一为 `internal_error`，只在
日志中保留内部细分原因。

strict handler 的公共方法：

- 对预期业务错误返回类型化 ErrorEnvelope response；
- 对真正未知错误返回 `error`，由定制 error handler 转为统一 500；
- 不依赖生成器默认的纯文本错误页。

### 10.1 敏感响应缓存

以下响应统一带：

```http
Cache-Control: no-store
Pragma: no-cache
```

- register/login/refresh 的 Access Token 与 Refresh Token；
- Human IM Session/UserSig；
- Runtime Session/Agent UserSig；
- Invite Secret；
- TAT registration script；
- PTY session URL/token。

这些 Header 必须写入 OpenAPI response，生成类型和黑盒测试都要验证。通用 access
log 不能记录上述响应 Body。

## 11. 幂等

HTTP Adapter 不自行实现幂等。Application 使用统一命令执行器：

```text
ExecuteIdempotentCommand
ExecuteNaturallyIdempotentCommand
ExecuteOneShotSecretCommand
```

- 普通写命令保存 request hash 与稳定响应；
- 天然幂等命令重复调用返回相同终态；
- Invite Secret、TAT 注册材料、PTY URL、UserSig 等一次性敏感响应不写
  IdempotencyRecord；
- 幂等 key 的 scope 和 partition key 由 Application 决定；
- HTTP 层只传入 OpenAPI 已声明的 `Idempotency-Key`。

## 12. 限流

限流分两层：

1. 网关/Transport 的粗粒度 IP 防护，用于未认证入口和异常流量；
2. Application 的主体/操作限流，用于稳定产品契约。

Application 通过 RateLimiter Port 使用：

```text
Allow(subjects[], serverId?, operationClass, cost)
→ allowed, retryAfter
```

RateLimitSubject 是 typed union：

```text
IP
LoginHash
AccountID
AgentID(serverId, agentId)
```

register/login 同时使用 IP 与规范化 loginHash；Human 使用 accountId；Runtime 使用
AgentID。多个 Subject 命中任一限制即拒绝，不能把未经认证请求强行表示为
principalId。

顺序严格为：

```text
认证/currentness
→ Server/资源权限
→ 幂等缓存命中检查
→ revision/状态检查
→ RateLimiter
→ 新副作用
```

同一个 Idempotency-Key 命中稳定响应时不重复计费。SQLite 单进程模式使用进程内原子
实现；TDSQL 多实例模式使用 Redis 原子实现。Redis 不可用时：

- 登录尝试、Token/UserSig、Invite、TAT 注册材料和 PTY 等敏感操作使用本地保守限流，
  无法安全判定时拒绝；
- 普通已认证读取可以降级到本地限流；
- 降级行为记录指标，不把 Redis 当业务事实源。

429 必须返回 `Retry-After`。腾讯上游限流映射为 503，也可以携带 `Retry-After`。
OpenAPI 的公共错误响应必须声明该可选 Header，生成响应和黑盒测试共同验证。

## 13. Repository 边界

Repository 接口按应用用例设计，不按 Ent 表逐个暴露 CRUD。

要求：

- Server 域方法显式接收 serverId；
- Account 域方法显式接收 accountId；
- Runtime 请求从已验证 Principal 取得 serverId，不信任客户端覆盖；
- Application 只能通过 Unit of Work 开启事务；
- 事务 callback 只接收受限 Repository 集合；
- Ent Client 只存在于 persistence adapter；
- 不允许应用代码调用无 route key 的 Ent `Get(id)`；
- 唯一冲突、未找到和锁冲突映射为稳定 port error。

数据库会话可以先交付数据基础；Repository interface 由具体 Application 用例逐步
冻结，不要求一次为 21 张表生成全量 Repository。

## 15. Worker 与 API

API、Worker、Scheduler 使用同一个二进制和同一组 Application/Port。部署拓扑由
数据库模式决定。

```text
SQLite:
chatserver serve --roles=api,worker,scheduler

TDSQL:
chatserver serve --roles=api
chatserver serve --roles=worker
chatserver serve --roles=scheduler
chatserver serve --roles=api,worker,scheduler
```

SQLite 模式强制：

- 一个根进程只取得一次 writer lock；
- API、Worker、Scheduler 共享同一个 DB client 和单连接池；
- 缺少任一必要角色时启动失败；
- 禁止启动独立 worker/scheduler 进程连接同一 SQLite 文件；
- 错误返回稳定 `database_mode_role_invalid`，不等待第二个 writer lock 超时；
- 角色内部保持独立 goroutine、健康状态和生命周期，但不是独立进程。

SQLite shutdown 顺序：

1. readiness 变为 false；
2. 同时关闭 HTTP、Scheduler、Worker 的新工作入口；
3. 在同一截止时间内并行 drain HTTP 请求与当前 Worker/Scheduler 工作；
4. 超时后 cancel 并 join 所有角色 goroutine；未确定外部调用保留租约状态，由下次
   reconciliation 恢复；
5. 确认所有角色不再访问数据库后，刷新日志/指标并关闭 DB；
6. 最后释放 writer lock。

TDSQL 模式才允许角色拆进程和水平多实例。角色组合不能改变 Application、Port 或
业务语义。

Worker 不通过 HTTP 回调本服务；它直接调用内部 Application/Port。Worker 的租约、
重试和 supersede 规则沿用 `08-内部任务契约.md`。

## 16. 可观测性

统一使用标准 `log/slog` 结构化日志和 requestId/operationId：

- HTTP access log；
- Application 命令结果；
- Worker attempt 和 lease；
- 腾讯 requestId 与稳定错误码；
- 数据库等待和事务耗时；
- scheduler lag。

日志字段采用 allowlist。禁止把完整 Header、Body、Query、腾讯响应和生成 DTO 自动
序列化进日志。

健康端点与业务 API 分离：

```text
/healthz  进程存活
/readyz   数据库和必要配置就绪
```

健康端点不进入 `/v1` OpenAPI 业务协议，不返回 Secret、版本依赖细节或腾讯资源列表。

## 17. 测试

### 17.1 生成与协议

- OpenAPI 3.0.3 lint + kin-openapi validate；
- oapi-codegen 可重复生成；
- 生成后编译；
- 59 个 operation 都有 strict interface 实现；
- request validation 覆盖非法 path/query/header/body；
- 59 个 operation 每个至少有一个 happy-path contract test；
- 测试把实际 HTTP response 再交给 OpenAPI response validator；
- format、enum、min/max、required 和 nullable 映射必须通过；
- 所有公开错误都是 ErrorEnvelope；
- 内部 Entity/Secret 字段不会被生成 DTO 意外序列化。

### 17.2 HTTP

使用 `httptest` 驱动真实 ServeMux 和完整 middleware：

- Anonymous/Human/Runtime/AgentCredential security；
- revoked session、旧 credential version、removed Member/Agent；
- Human JWT 冒充 Runtime、Runtime JWT 冒充 Human；
- CurrentPrincipal 门禁不可绕过；
- 未知 route/404、错误 method/405 与 `Allow` Header；
- body 上限和 Content-Type；
- requestId；
- panic recovery；
- timeout/cancel；
- Secret 不进入日志；
- 敏感响应包含 `Cache-Control: no-store`；
- 429/腾讯限流包含正确 `Retry-After`；
- validator、std-http bind、strict error 三条路径都返回 ErrorEnvelope；
- stable error registry 穷举全部公开错误码。

### 17.3 Application

使用 Fake Repository、Fake Clock、Fake Token、Fake IM/TAT Port：

- 不启动 HTTP；
- 不启动数据库；
- 每个状态机先写失败测试；
- 验证事务内没有外部调用；
- 验证 route key、revision、幂等和权限；
- 验证命中幂等缓存不重复消耗限流额度；
- 验证 Redis 限流降级策略；
- 验证外部 timeout/uncertain/superseded。

### 17.4 Adapter

## 19. 验收标准

- `openapi.yaml` 是 HTTP 字段和 operation 的唯一事实源；
- 生成代码无手工修改且生成可重复；
- HTTP 使用标准 ServeMux，不依赖 Gin/Chi/Gorilla Mux；
- Application 不导入 `net/http`、OpenAPI generated package 或 Ent；
- Handler 不包含事务、腾讯调用或业务状态机；
- Repository 强制 route key；
- 数据库事务中无网络/Redis/文件调用；
- 一次性 Secret 不进入日志、Outbox、Operation snapshot 或幂等缓存；
- 敏感 HTTP 响应强制 no-store；
- SQLite 下 API/Worker/Scheduler 只允许单进程组合运行；
- TDSQL 下角色可以独立水平运行；
- Human/Runtime/AgentCredential 权限边界有黑盒测试；
- OpenAPI 3.0.3 lint、kin-openapi validate、生成校验、response contract、
  单元测试、集成测试和 race test 通过。
