大部分 AI 助手让人失望的第一个瞬间，不是它答错了什么，而是你不得不问一句："**你上次不是刚跟我说过吗？**"

答案很反直觉：**"记住你"从来不是靠更大的上下文窗口解决的。** 上下文从 8k 涨到 200k、1M，但一次会话里的 200k，会话一断就烟消云散。Hermes Agent 的做法是把"记住"拆成四层持久化存储，每层有明确职责和容量上限，并且**由 Agent 自己决定什么值得写进去**。

## 先定义"记住"到底是什么

在人类语境里，"记住你"至少包含三件事：

1. **知道你是谁**——名字、职业、偏好、常用工具链。
2. **知道我们一起做过什么**——聊过的项目、给过的结论、踩过的坑。
3. **知道该怎么和你打交道**——你要简短还是详细？先结论还是先过程？

只有大上下文窗口的模型，能在**一次对话内**同时做到这三点。但会话一断，第 1、3 点就重置了。

## 四层记忆，各司其职

| 层 | 职责 | 典型容量 | 什么时候加载 |
| --- | --- | --- | --- |
| 用户画像 | 你是谁、偏好、沟通风格 | 约 500 tokens | 每次会话必载 |
| 事实档案 | 事件、决定、结论 | 约 800 tokens | 每次会话必载 + 按需检索 |
| 会话档案 | 任何一句原话的精确回溯 | 无上限（数月历史） | 命中查询时才载入 |
| Skills | 遇到某类场景该怎么做 | 单份 KB 级 | 场景匹配时高优先级装载 |

用日常物件来类比会更好理解：**用户画像是贴在显示器边框的便利贴**（抬眼就看到），**事实档案是桌上的日记本**（内容更多但仍写得克制），**会话档案是书柜里的档案盒**（不常翻，但要找一定找得到），**Skills 是肌肉记忆**（该做的时候身体自己知道）。

### 为什么每层都设死上限？

有人会问：既然上下文窗口这么大，为什么用户画像只给 500 tokens？

三条理由，每条都够硬：

1. **成本**：每次会话必载的内容多 1,000 tokens，一个每天用 50 次的用户，一年就多烧约 1,800 万 tokens。
2. **注意力**：它是系统提示的一部分，臃肿了会挤压真正的任务上下文。
3. **上限逼出取舍**：容量满了不静默丢弃，而是**逼 Agent 主动整合**——这恰恰是记忆质量的保障。

这背后是一句核心哲学：**"记住"不是"存下"，是"经过取舍的存下"。**

## 写入：Agent 主动组织，而不是随手记

Hermes 不是"每说一句就记一条"，而是在四种明确时机由 Agent 自己判断要不要写：

- **上下文将满时**：先把值得跨会话保留的信息抽出来，再压缩当前上下文。
- **任务闭环 / 话题切换时**：做一次记忆盘点。
- **周期性提醒**：系统定期戳一下 Agent——"这一段有什么值得记的吗？"避免长会话里悄悄丢信息。
- **你显式要求时**："以后记住我在 X 项目用的是 Y"会被优先写入。

判断标准也很朴素：可复用吗？稳定吗？够具体吗？涉隐私吗？——"今天想喝拿铁""今天头有点疼"这类一次性信息不写；"我大概比较喜欢简洁一点"这种模糊态度也不写。

**一个训练良好的 Agent，宁可少记，也不乱记。**

## 召回：三条腿走路，不只靠向量相似度

只用向量检索会遇到两个老问题：**重要不等于和 query 相似**，以及**细节被稀释在整段里**。Hermes 用的是混合检索：

| 方式 | 什么场景触发 | 典型延迟 |
| --- | --- | --- |
| 结构化默认加载 | 每次对话启动 | 几乎为零（本就是系统提示的一部分） |
| 全文精确检索 | 问具体事："上次那个报错是啥来着？" | 约 20ms 命中 |
| 语义摘要 | 需要跨条目整合的问题 | 秒级，用便宜模型跑 |

三层配合，"记住你"才从"我们向量相似"变成"**我真的知道你说过什么**"。

## 更新：记忆是活的，不是流水账

一个常被忽视的点：**记忆不仅要能写入，还要能被修改和淘汰。**

- **新旧冲突时优先更新，而不是并列写入**。不能同时存在"用户偏好 Vue / 换成了 React / 又回到了 Vue"三条并列记录——那会让 Agent 出现"分裂人格"。
- **长期没被引用的条目逐步降权**，容量满时优先被合并或删除。
- **你明确否认的信息立刻物理删除**，不是"记录一条相反的"——保持世界模型自洽。

也就是说，好的记忆系统更像"**编辑一份活的档案**"，而不是"追加一本日记"。

## 这套机制想跑通，还差一个前提

再好的记忆机制，都需要一个物理前提：**Agent 得一直活着。**
