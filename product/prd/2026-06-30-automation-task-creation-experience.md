# 产品需求草稿：自动任务创建体验优化

> 日期：2026-06-30
> 分支：`frontsandbox/automation-task-optimization-0630`
> 输入状态：PRD 草稿
> 需求方向：创建体验优化
> TAPD：

---

## 一、来源

- 需求来源：自动任务现有创建流程使用成本偏高，需要让用户更容易完成一个可运行、可通知、可理解的自动任务。
- 相关页面：`/agents/automations`
- 相关实现：`frontend/src/pages/marketing/openclaw-automations-panel.tsx`、`frontend/src/lib/hermes-cron-client.ts`

## 二、背景与问题

自动任务已经支持模板、手动添加、单次/周期/按间隔调度、生效时间段、通知方式、测试消息、编辑、删除和最近执行等能力。但从用户视角看，创建一个任务仍然偏“表单配置”：

- 用户需要先理解“单次 / 周期 / 按间隔”的差异，再判断该选择是否符合自己的任务意图。
- 任务说明输入框只给了一个简单示例，用户不容易知道怎样描述才会得到稳定结果。
- 生效时间段和通知方式是可选能力，但它们对任务是否真的产生用户可感知结果影响很大。
- 提交前缺少聚合确认，用户很难一眼判断“这个任务会在什么时候、做什么、通知到哪里”。
- 模板能降低门槛，但当前模板更像列表选择，还没有把模板选择、二次编辑和最终确认串成完整创建路径。

这次优化聚焦创建体验，不扩大到任务执行可靠性、运行态观测或新的调度系统。

## 三、目标用户与场景

- 目标用户：希望让 Agent 自动提醒、整理、复盘或发送周期性信息的普通用户。
- 典型场景：
  - 创建每天固定时间的日报、复盘、待办整理任务。
  - 创建每隔一段时间的喝水、久坐、关注事项提醒。
  - 从模板开始创建，再根据自己的时间和通知方式稍作调整。
- 频率和重要性：创建链路是自动任务的首次转化入口；如果首次创建不清晰，用户很可能无法感知自动任务的价值。

## 四、目标

- 用户能更快判断自己应该选模板还是空白创建。
- 用户能在填写过程中理解每个配置项对任务结果的影响。
- 用户提交前能看到清晰的任务摘要：执行内容、执行时间、生效范围、通知目标。
- 用户能在创建时完成必要校验，减少创建后才发现时间过期、通知未配置或说明不清的问题。
- 产品上把本次优化界定为“创建体验升级”，不承诺提升 Hermes cron 的底层调度可靠性。

## 五、范围

### 本次包含

- 优化“模板创建”和“空白创建”的入口表达，让用户能理解两种路径差异。
- 优化创建弹窗的信息结构，按用户决策顺序组织：做什么、什么时候做、是否限制生效范围、通知到哪里、提交前确认。
- 为执行时间提供实时人话预览，例如“每天 09:00 执行”“每周一、周三 18:00 执行”“每 2 小时执行一次”。
- 为任务说明提供更明确的写法提示或示例，帮助用户写出可执行的提示词。
- 在创建页增加提交前摘要，集中展示任务名称、任务说明摘要、执行时间、生效时间段和通知方式。
- 强化创建前校验，包括名称必填、任务说明必填、单次时间不能早于当前时间、通知 Chat ID 非法输入、过高频通知提醒。
- 保留现有 Hermes cron / debug exec 通路，不新增后端调度能力。

### 本次不包含

- 不做任务执行记录的深度诊断或失败原因归因。
- 不新增复杂工作流、多步骤编排、条件分支或任务依赖。
- 不新增独立后端任务系统。
- 不改造 Hermes cron 的调度语义。
- 不处理任务运行后的 SLA、重试、补偿、告警或运营观测。

## 六、LightVela 影响面

- 前端页面/路由：`/agents/automations`
- Hermes/OpenClaw/运行时：沿用 `hermes cron create/edit/list/remove` 和 `debug/exec`，不扩大运行时契约。
- SkillHub/MCP/工具：无直接影响。
- SDK/文档/运营：需要补充“如何创建自动任务”的产品帮助文案或运营说明。
- 权限/安全/数据：不新增权限模型；继续遵守现有实例鉴权和 `debug/exec` 安全边界。

## 七、方案

### 1. 创建入口优化

- 页面主操作保留“模板”和“添加”两个入口。
- “模板”定位为快速开始，适合用户不知道怎么写任务。
- “添加”定位为空白创建，适合用户已经知道任务内容。
- 空态引导优先推荐从模板开始，降低首次创建门槛。

### 2. 创建弹窗结构优化

建议将创建弹窗组织为更接近向导的单页流程：

1. 任务内容：名称、任务说明、可参考示例。
2. 执行时间：单次 / 周期 / 按间隔，实时展示人话预览。
3. 生效范围：可选，仅在周期和间隔任务下展示。
4. 通知方式：展示已配置渠道、未配置渠道、可发送测试消息。
5. 创建摘要：提交前固定展示“将会创建什么任务”。

### 3. 调度预览

- 用户修改执行时间时，立即展示预览文案。
- 预览文案不暴露 cron 表达式，除非当前任务来自不可解析表达式。
- 多时间点、周几、每月几日、间隔单位都需要落到用户能读懂的表达。

示例：

- “每天 09:00、18:00 执行”
- “每周一、周三 18:00 执行”
- “每月 1 日、15 日 09:00 执行”
- “每 2 小时执行一次，仅周一至周五生效”

### 4. 任务说明写法提示

- 输入框 placeholder 从单一句子升级为更明确的写法提示。
- 可提供 2-3 个短示例，用户点击后填入或追加到任务说明。
- 示例文案强调“让 Agent 做什么、输出什么、是否通知我”。

### 5. 通知配置引导

- 对未配置渠道保留灰显和“未配置”提示。
- 对已选渠道保留测试消息能力。
- 对可选 Chat ID 说明保持精简，默认推荐 home 对话。
- 当用户未选择任何通知方式时，在摘要中明确提示“仅后台执行，不会主动通知”。

### 6. 提交前摘要

在创建按钮附近展示摘要，让用户提交前确认：

- 任务名称
- 任务说明摘要
- 执行时间预览
- 生效时间段
- 通知目标
- 创建后状态

摘要的目标不是增加步骤，而是减少创建后的不确定感。

## 八、产品原型说明

- 目标页面/入口：`/agents/automations` 页面中的“模板”和“添加”入口。
- 用户主路径：
  1. 用户进入自动任务页。
  2. 用户选择模板或空白创建。
  3. 用户填写任务内容和执行时间。
  4. 用户选择是否设置生效时间段和通知方式。
  5. 用户查看创建摘要并提交。
- 页面结构：保持现有弹窗，不新增独立页面。
- 关键组件：模板选择弹窗、创建/编辑弹窗、执行时间选择器、通知方式区域、测试消息按钮、提交前摘要。
- 状态：加载、空态、未配置通知、非法 Chat ID、过期单次时间、提交中、创建失败。
- 需要设计确认：创建摘要样式、调度预览位置、模板到创建表单的衔接方式。
- 需要前端确认：当前弹窗空间是否足够承载摘要；如空间不足，是否需要分组折叠或右侧摘要栏。

## 九、验收标准

- 从模板创建任务时，模板内容能带入创建表单，用户可继续编辑后提交。
- 从空白创建任务时，用户能按顺序完成名称、任务说明、执行时间、通知方式配置。
- 用户修改执行时间后，页面实时展示人话调度预览。
- 用户未选择通知方式时，页面明确说明任务只会后台执行，不会主动通知。
- 用户选择通知方式后，可以发送测试消息，并看到成功或失败提示。
- 单次任务选择过去时间时，提交前被阻断并给出明确提示。
- Chat ID 输入中文等非法内容时，提交前被阻断或即时提示。
- 创建按钮附近展示提交前摘要，摘要内容随表单变化实时更新。
- 本次改动不影响现有编辑、暂停、恢复、删除和最近执行功能。

## 十、发布与观测

- 灰度/开关：优先作为前端体验优化随版本发布，不要求新增开关。
- 日志/埋点/指标：
  - 自动任务创建入口点击次数：模板 / 空白。
  - 创建弹窗打开到成功创建的转化率。
  - 创建失败原因分布。
  - 测试消息点击次数和失败次数。
- 回滚：如体验异常，前端回滚到原创建弹窗结构即可；不涉及数据迁移。

## 十一、研发交接建议

- 前端关注点：
  - 优先在 `openclaw-automations-panel.tsx` 内小步调整创建弹窗结构。
  - 复用现有 `formatScheduleFriendly`、调度解析和通知测试能力。
  - 涉及文案需同步 i18n 生成文件。
- 后端/运行时关注点：
  - 本期不要求运行时变更。
  - 如发现某些预览无法由前端准确表达，再单独评估 Hermes cron 输出契约。
- Skill/内容/文档关注点：
  - 补充自动任务创建示例文案，尤其是任务说明写法。
- QA/发布/运营关注点：
  - 覆盖模板创建、空白创建、周期任务、间隔任务、单次过期、通知测试、无通知方式这些主路径。

- 是否需要把“创建成功后建议立即发送测试消息”作为默认引导，还是保持用户主动点击？
