# 后端适配器

Backend adapter 把 provider quirks 隔离在边界内。它负责启动 session、发送 input events、取消运行、回应 request，并把 provider raw output 转成 runtime output。

## Adapter Trait

```rust
#[async_trait::async_trait]
pub trait BackendAdapter: Send + Sync {
    async fn stream_user_message(
        &self,
        input: BackendSend,
        sink: BackendOutputSink,
    ) -> anyhow::Result<()>;
}
```

v1 的 adapter contract 是 streaming-only。Runtime 负责 command acceptance、idempotency、`turn.started` 和 event append；adapter 只负责把一次用户消息交给 provider，并把 provider output 通过 sink 持续送回 runtime。不要再增加 “先收集 Vec 后返回” 的兼容路径，因为它会隐藏 backpressure、阻塞和超长输出问题。

## Codex App-Server Boundary

Codex adapter 接的是 **Codex app-server protocol**，不是 `codex exec`。当前默认 host 启动
`codex app-server --stdio`，但这是 transport/host 选择，不是业务边界。

实现必须分成三层：

| Layer | 责任 |
| --- | --- |
| `CodexAppServerHost` / `CodexAppServerConnection` | 启动或连接 app-server，发送 request/notification，读取 JSON-RPC notification |
| `CodexAppServerBackendAdapter` | 管理 Vela session 到 Codex thread 的绑定，调用 `thread/start` 和 `turn/start` |
| `normalize_codex_app_server_notification` | 把 Codex notification 映射成 `BackendOutput`，并保留 raw |

这样以后如果 Codex app-server 可以 in-process 嵌入，只需要替换 host/connection；session 语义、事件转译、runtime/store
都不应该变化。

Day 1 不使用 `codex exec --json` 作为主 backend。`exec --json` 适合 smoke/CI 或 fallback，但它不提供足够好的 rich-client
控制面来承载 permissions、thread lifecycle、interrupt、rewind 和 app-style streaming。

## ACP Generic Backend

ACP 是另一条 generic provider boundary。它的公共 backend kind 是 `acp`；Hermes 只是当前默认本地 ACP server，默认启动为
`hermes acp`。不要把 Hermes 的命令行、模型网关或 provider env 泄露成 client-facing API。

实现分成三层：

| Layer | 责任 |
| --- | --- |
| `AcpHost` / `AcpConnection` | 启动或连接 ACP JSON-RPC transport，发送 `initialize`、`session/new`、`session/prompt`，读取 `session/update` |
| `AcpBackendAdapter` | 管理 Vela session 到 ACP session 的绑定，应用 `agent_config`，处理 prompt streaming |
| `normalize_acp_session_update` | 把 ACP `agent_message_chunk`、`agent_thought_chunk`、`tool_call*` 等更新映射成 `BackendOutput`，并保留 raw |

当前 adapter 使用标准 ACP 方法：

- `initialize`
- `session/new`
- `session/setModel`
- `session/setConfigOption`
- `session/prompt`
- `session/update`
- `session/request_permission`

`session/prompt` 必须作为 streaming request 处理：request 写出后继续读取 `session/update` notification，并把 delta 立即送入 sink，直到 prompt response
返回。不能等待 prompt response 后再批量 replay notification，否则 UI 看到的不是流式输出。

Hermes + CloudAgents 是默认开发配置：`VELA_CLOUDAGENTS_API_KEY` 存在时，`velad` 会给 ACP process 注入 OpenAI-compatible
base URL 和默认模型 `minimax-m2.7`。secret 只能通过 process env 传递，不写入仓库或事件日志。

## Session Agent Config

Session-level `agent_config` 是用户当前偏好；turn-level `resolved_agent_config` 是 runtime 在 `turn.started` 时冻结的实际配置快照。

Adapter MUST NOT invent client-facing config names。OpenAPI 只暴露：

- `model`
- `reasoning_effort`
- `permission_mode`

Adapter 负责把它们映射到 provider-native 参数：

| velaChat config | Codex app-server | Pi RPC / CLI | ACP |
| --- | --- | --- |
| `model` | `thread/start.model` | `--model` 或 runtime `setModel` | `session/setModel.modelId` 或 ACP host env |
| `reasoning_effort` | `thread/start.reasoningEffort` | `thinking` / `setThinkingLevel` | `session/setConfigOption(reasoning_effort)` |
| `permission_mode` | sandbox policy + approval policy | provider-specific permission capability | provider-specific permission/request policy |

运行中的 turn 不读取被修改后的 session config。用户在 turn 运行中切换模型或权限时，runtime 可以立即更新 session view；当前 turn 继续使用自己的 `resolved_agent_config`，下一 turn 使用新的 session `agent_config`。

这比显式 `pending_agent_config` 更简单：session 记录当前偏好，turn 记录历史快照。只有未来需要可撤销的排队配置变更、跨设备确认或 banner 状态时，才需要额外引入 pending resource。

## Adapter 输出

Adapter 输出的是 `BackendRuntimeOutput`，不是 canonical event。canonical ordering 只能由 `vela-runtime + vela-store` 产生。

Adapter 可以输出接近 canonical 的 runtime output，但最终事件名必须由 daemon/sequencer 映射到 [事件词表](/docs/api/event-vocabulary)。

推荐 runtime output family：

- `session.status.changed`
- `turn.started`
- `assistant.message.delta`
- `assistant.reasoning.delta`
- `request.opened`
- `request.resolved`
- `tool.started`
- `tool.updated`
- `tool.output.delta`
- `command.output.delta`
- `diff.updated`
- `warning.raised`
- `turn.completed`

## Provider Lifecycle Normalization

Adapter normalizer 的目标不是完整复刻 provider 的事件词汇，而是把 provider lifecycle 吸收到 Vela 的 canonical lifecycle 中。

| Provider signal | Normalizer behavior |
| --- | --- |
| 普通 agent/session/turn start 信号 | 默认吸收；`turn.started` 由 runtime sequencer 写入 |
| assistant message start/end | 只有 assistant role 且有稳定 message id 时映射为 `assistant.message.started` / `assistant.message.completed` |
| assistant text delta | 映射为 `assistant.message.delta` |
| reasoning/thinking delta | 映射为 `assistant.reasoning.delta` |
| tool start/update/end | 映射为 `tool.started`、`tool.updated`、`tool.completed` 或 `tool.failed` |
| provider turn/agent done | 映射为 `turn.completed` |
| provider process/error exit | 映射为 `turn.failed` |
| unknown / malformed / unsupported control request | 映射为 `warning.raised`，并保留 raw 供 diagnostics 使用 |

正常 lifecycle 被吸收时，不会写入 canonical event log。需要调试 provider 时，应通过 diagnostics/trace 或测试 cassette 观察 raw JSONL，而不是让普通 UI 消费 provider event。

## Message Identity

Streaming UI 依赖稳定 message identity。Normalizer SHOULD 从 provider output 中提取稳定 id，例如 `id`、`messageId`、`responseId` 或 provider 明确标记的 partial response id。

如果 message lifecycle 事件没有稳定 id，adapter MUST 吸收该 lifecycle 事件；如果 text delta 没有稳定 id，runtime/projector 可以继续用 event sequence 维持显示，但这只是降级路径，不能作为长期契约。新的 provider adapter 必须优先补齐稳定 message/tool/request id。

## Runtime Ownership Gate

Runtime MUST treat backend output as untrusted normalized input. Backend output can request canonical events from backend-owned families only; daemon/runtime-owned families are rejected at the runtime boundary and converted to diagnostics.

Allowed backend output families:

- `turn.completed`、`turn.failed`、`turn.cancelled`
- `assistant.message.*`
- `assistant.reasoning.*`
- `tool.*`
- `command.*`
- `task.*`
- `request.opened`、`request.updated`、`request.resolved`
- `diff.updated`
- `usage.updated`
- `warning.raised`、`error.raised`

Runtime-owned or daemon-owned families MUST NOT be accepted from backend output:

- `session.*`
- `backend.status.changed`
- `user.message.accepted`
- `input.*`
- `turn.started`
- `turn.cancel.accepted`
- `request.response.accepted`
- `projection.invalidated`

`turn.started` is normal lifecycle noise and is absorbed because runtime already writes it before the backend side effect. Other forbidden backend output is persisted as `warning.raised` with `code: "backend_event_not_allowed"` so diagnostics can see the adapter violation without corrupting the canonical event log.

## Requirements

### Requirement: Provider 隔离

Provider-specific protocol MUST 被限制在 backend adapter 内。

#### Scenario: 接入 Claude Code

- **WHEN** 增加 Claude Code 支持
- **THEN** adapter 把 Claude 输出转成 vela runtime output
- **AND** 客户端不需要 Claude-specific 分支

### Requirement: Capability discovery

每个 adapter MUST 在启动 session 前声明能力。

#### Scenario: backend 不支持 structured diff

- **WHEN** backend 没有 structured diff 能力
- **THEN** API 暴露该能力不可用
- **AND** UI 降级或隐藏 review panel

### Requirement: Pi 适配 agent harness 而不是模型网关

Pi adapter SHOULD 启动 `pi --mode rpc` 并消费 Pi RPC events，而不是直接调用 MiniMax/TokenHub API。

#### Scenario: Pi 使用 MiniMax extension

- **WHEN** Pi 通过 extension 使用 MiniMax-M2.7
- **THEN** velaChat 只看到 Pi RPC runtime output
- **AND** MiniMax/TokenHub 的模型细节留在 Pi provider 配置中

### Requirement: 普通 lifecycle 不产生 warning

Provider 的正常生命周期事件 MUST 被吸收或映射为 canonical event，MUST NOT 降级成 warning。

#### Scenario: Pi 输出 turn_start

- **WHEN** Pi 输出 `turn_start`
- **THEN** adapter 不产生 `warning.raised`
- **AND** runtime 已经拥有自己的 `turn.started`

### Requirement: Adapter 只走 streaming path

Adapter MUST NOT 实现收集全部 output 后一次性返回的 production path。

#### Scenario: Provider 输出超过 channel buffer

- **WHEN** provider 连续输出大量 delta
- **THEN** adapter 通过 sink 持续发送
- **AND** runtime/projector 可以边接收边 append/read model 更新
