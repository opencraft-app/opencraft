# Velad over SSH Transport

本文定义第一版 `ChannelTransport(kind=ssh)`。它只负责让本地
`velad` 可靠连接目标机器上的远端 `velad`；业务语义、弱网恢复、反压、
会话映射由 `VeladChannel` 负责。

## 目标

- 桌面和 Web UI 永远只连接本地 `velad`。
- 本地 `velad` 通过 SSH transport 管理目标机器上的远端 `velad`。
- SSH 是 transport，不是业务协议，也不是 backend 类型。
- 远端 `velad` 暴露 view/event/control 协议，不暴露 ACP、Codex raw
  protocol 或 backend adapter internals。
- 弱网正确性由 `VeladChannel` 的 cursor、ack、idempotency 和 stale
  snapshot 保证，不靠 SSH tunnel 本身保证业务状态。

## 非目标

- 不做 `KCP over SSH` 或 inner TCP stack。
- 不把 Electron 变成 SSH manager。
- 不把 local `velad` 做成透明 TCP proxy。
- 不 shell out 到系统 `ssh` / OpenSSH 子进程。
- 不让 renderer 看到远端 URL、SSH credential、remote management token。
- 不在第一版解决 public cloud service、multi-hop、共享 runtime ownership。
- 第一版只支持 Unix-like SSH target。Windows SSH target 后续单独设计路径、
  `.exe`、launcher 和进程治理。
- 第一版远端 CPU 架构只支持 x86_64/amd64，不支持 arm/aarch64。
- 第一版 password 默认通过 `keyring` 持久化到本地系统 credential store。普通 node metadata 只保存
  `secret_ref`，不保存明文 password。

## 术语

```text
RuntimeTarget
  运行时执行目标，由节点或本地默认环境派生。

Node
  用户在设置里配置的执行节点，例如 SSH 主机。

NodeProvider
  节点连接器 provider。第一版有 ssh connector provider。

VeladChannel
  两个 velad 之间的语义通道。负责 session/view/event/control、
  cursor resume、ack watermark、反压、幂等、错误分类。

ChannelTransport
  VeladChannel 的底层传输。第一版实现 SshTransport。
```

## 拓扑

```text
Desktop / Web UI
  -> local velad
      -> Node(provider=ssh)
          -> RuntimeTarget(kind=ssh)
          -> VeladChannel
              -> ChannelTransport(kind=ssh)
                  -> remote velad
                      -> backend adapter(ACP/Codex/Vela Engine)
```

远端 `velad` 只监听目标机器的 loopback 地址：

```text
remote velad --listen 127.0.0.1:0
```

本地 `velad` 通过 SSH 建立本地 loopback 到远端 loopback 的连接。renderer
仍然只使用本地 `velad` 的 `/api/v1`。

## 边界

### Electron

Electron 仍然只负责启动本地 bundled `velad`。它不管理 SSH，不解析远端
ready event，不持有远端 management token。

### Local velad

本地 `velad` 是 control plane：

- 保存 Node 配置和 secret refs。
- 保存 runtime target 配置和状态。
- 管理 SSH transport 生命周期。
- 注入或定位远端 `velad`。
- 验证远端 `/api/v1/runtime-info`。
- 维护 local session 到 remote session 的映射。
- 记录 channel/target/relay observability。
- 对 renderer 提供稳定的本地 API。

### Remote velad

远端 `velad` 是 execution + projection daemon：

- 在目标机器执行 backend adapter。
- 访问目标机器文件系统、cwd、工具链和环境。
- 持久化远端 canonical event log。
- 投影 share-safe / view-safe read model。
- 对 local `velad` 暴露 view/event/control 协议。

## 建议模块

第一版放在 Rust `velad` 内部，先不提取 crate：

```text
crates/velad/src/runtime_targets/
  mod.rs
  model.rs
  nodes.rs
  node_provider.rs
  local_secret_store.rs
  store.rs
  channel.rs
  ssh_transport.rs
  remote_view.rs
  errors.rs
  README.md
```

职责划分：

- `model.rs`: `RuntimeTarget`, `TargetStatus`, `ChannelState`,
  `RemoteSessionMapping`, `Node`, `NodeProvider`。
- `nodes.rs`: Node CRUD、设置页数据 shape、safe metadata。
- `node_provider.rs`: connector provider registry。第一版注册 `ssh`。
- `local_secret_store.rs`: 基于 Rust `keyring` crate 的 persisted secret refs；
  不把明文 secret 放进 ordinary settings。
- `store.rs`: target 配置、node refs、session mapping、last known state。
- `channel.rs`: `VeladChannel` trait 和 semantic request/response。
- `ssh_transport.rs`: SSH transport 生命周期。
- `remote_view.rs`: remote view/event/control wire helper。
- `errors.rs`: target/channel/backend 错误分类。

## Node 和 SSH connector provider

设置页使用“节点”作为用户概念。节点是持久化配置；`RuntimeTarget` 是由节点派生
出来的运行时连接状态。

```ts
type Node = {
  node_id: string;
  label: string;
  provider: "ssh";
  enabled: boolean;
  config: SshNodeConfig;
  created_at: string;
  updated_at: string;
};

type SshNodeConfig = {
  host: string;
  port: number;
  username: string;
  auth: {
    type: "password";
    secret_ref: string;
  };
  host_key_policy: "insecure_accept_any";
  remote_os: "unix";
  remote_arch: "x86_64";
};
```

`NodeProvider` 是连接器 provider，不是 agent backend provider。它负责：

- 定义设置表单字段和校验规则。
- 创建、更新、删除节点。
- 解析 secret refs。
- 建立 `RuntimeTarget`。
- 调用对应 `ChannelTransport`。
- 暴露 safe capabilities 给 UI。

第一版只注册：

```ts
type NodeProviderKind = "ssh";
```

password 默认持久化，但只能通过 `secret_ref` 引用。renderer 可以提交新 password，
但读回节点时只能看到 `password_configured: true`，不能读回明文。

### LocalSecretStore

第一版使用 Rust `keyring` crate 作为 `LocalSecretStore` 的实现。它在各平台走
系统 credential store：

- macOS: Keychain。
- Windows: Credential Manager。
- Linux desktop: Secret Service。

`LocalSecretStore` contract：

```rust
pub trait LocalSecretStore {
    fn put_password(&self, secret_ref: &SecretRef, value: SecretString) -> Result<()>;
    fn get_password(&self, secret_ref: &SecretRef) -> Result<SecretString>;
    fn delete_password(&self, secret_ref: &SecretRef) -> Result<()>;
}
```

如果 Linux Secret Service 不可用，返回 `secret_store_unavailable`。不要静默
回退到明文文件。未来如需 headless Linux 支持，再单独设计 encrypted file 或
user-provided secret provider。

## RuntimeTarget 模型

```ts
type RuntimeTarget = {
  target_id: string;
  node_id?: string;
  kind: "local" | "ssh";
  provider?: "ssh";
  label: string;
  status: "disconnected" | "connecting" | "ready" |
    "degraded" | "reconnecting" | "failed";
  generation: number;
  last_seen_at?: string;
  last_error?: RuntimeTargetError;
  runtime_protocol?: "velad.local.v1";
  api_protocol?: "velachat.v1";
  capabilities?: RuntimeTargetCapabilities;
};
```

`generation` 用于拒绝旧连接返回的 stale response。每次 transport 重新
建立成功后递增。

## ChannelTransport 接口

`ChannelTransport` 不理解 session、turn、ConversationView。它只负责建立和
维护到远端 `velad` 的可用连接。

```rust
#[async_trait]
pub trait ChannelTransport: Send + Sync {
    async fn open(&self) -> Result<TransportHandle, TransportError>;
    async fn health(&self) -> Result<TransportHealth, TransportError>;
    async fn close(&self) -> Result<(), TransportError>;
}

pub struct TransportHandle {
    pub generation: u64,
    pub local_base_url: String,
    pub remote_runtime_info: RemoteRuntimeInfo,
}
```

第一版 `SshTransport` 必须使用 native embedded SSH client，不 shell out 到系统
OpenSSH。实现选型固定为 `russh`。无论底层 transport 如何演进，接口必须让后续
替换为 QUIC 或 KCP-over-UDP 时不影响 `VeladChannel`。

## Native SSH Client Strategy

`SshTransport` 是 `velad` 内嵌的 SSH client，不依赖系统 `ssh` binary、用户
OpenSSH control master、shell quoting 或平台特定 `ssh` 参数。

第一版能力范围：

- TCP connect 到 SSH server。
- password authentication。
- default-trust host key policy。第一版不做 known_hosts 严格校验和 host key pinning。
- remote command exec，用于 bootstrap、启动和停止远端 `velad`。
- remote ready file 读取，用于解析 `velad.ready` handshake。stdout/stderr 只做诊断。
- local-to-remote direct tcpip forwarding，用于连接远端 loopback `velad`。
- keepalive / health check / reconnect。

依赖选择原则：

- 使用 `russh` 作为纯 Rust async SSH client，降低 macOS/Windows/Linux 分发差异。
- 不使用包装 OpenSSH 的 crate；那类 crate 仍然会生成系统 `ssh` 子进程。
- 如果纯 Rust client 在算法兼容或 SSH config 解析上不足，先把缺口限制在
  `SshTransport` 内部，不上升到 `VeladChannel`。
- dependency feature 必须显式收敛，不把 SFTP、server、agent forwarding 等非
  MVP 能力默认带进来，除非 bootstrap 确实需要。
- 第一版不实现 private key、ssh-agent、ProxyJump、keyboard-interactive 或
  strict known_hosts。这些是 `SshTransport` 的后续认证策略扩展，不影响
  `VeladChannel`。

## SshTransport 生命周期

### 1. Resolve target

读取 Node 配置：

- host
- port
- user
- password `secret_ref`
- optional ssh config profile imported into Vela's own target config
- remote velad install root，第一版固定为 `$HOME/.vela/bin`
- remote data dir 策略

本地 `velad` 在连接时通过 `LocalSecretStore` / `keyring` 解析 password。renderer 和普通
`GET /api/v1/nodes` 响应只看到 `password_configured` / `secret_ref` 状态，
不会返回明文 password。

### 2. Bootstrap remote velad

本地 `velad` 通过 SSH 执行 bootstrap：

1. 解析远端平台和架构，选择匹配的 bundled `velad` 二进制。第一版只接受
   x86_64/amd64；arm/aarch64 直接返回 unsupported target。
2. 执行 `mkdir -p "$HOME/.vela/bin"`。
3. 计算 exact install path:
   `$HOME/.vela/bin/velad-<build_id>-<target_triple>`。
4. 检查 exact install path 是否存在且 checksum 兼容。
5. 如果缺失或不兼容，上传到临时路径，例如
   `$HOME/.vela/bin/velad-<build_id>-<target_triple>.<nonce>.tmp`。
6. 校验远端临时文件 checksum，执行 `chmod 0755`。
7. 原子 rename 到 exact install path。
8. 可选更新 convenience symlink:
   `$HOME/.vela/bin/velad -> velad-<build_id>-<target_triple>`。
9. 启动远端 daemon，必须使用 exact install path：

```bash
"$HOME/.vela/bin/velad-<build_id>-<target_triple>" \
  --listen 127.0.0.1:0 \
  --database-url <remote-local-db> \
  --management-token <generated-token> \
  --ready-file "$HOME/.vela/run/velad.<remote_instance_id>.ready.json"
```

远端主握手不依赖 stdout。远端 `velad` bind 成功后原子写入 ready file，本地
通过 russh 读取 ready file，拿到真实 `listen_addr`。

上传要求：

- 不要求远端预安装 `velad`。
- 不覆盖正在写入的目标文件；必须先写临时文件再 rename 到 exact install path。
- 传输中断后，下一次 bootstrap 可以清理旧 `.tmp` 文件并重试。
- 不同 build 可以并存，避免多个本地 Vela 版本连接同一远端时互相覆盖。
- convenience symlink 不能作为启动依据；启动必须使用 exact install path。
- 远端路径默认只在用户 home 下使用 `.vela/`，不需要 root 权限。
- 第一版只支持 Unix-like SSH target。Windows 远端后续使用平台等价路径、
  `.exe` 名称和不同 launcher。
- 第一版只支持 x86_64/amd64 远端 CPU 架构。arm/aarch64 后续再加入
  artifact matrix 和 bootstrap 选择逻辑。

### 2.5 Launch remote daemon

第一版远端生命周期使用 `nohup` launcher。代码上不要把 `nohup` 写死在
channel 里，而是通过 launcher strategy 保留后续 `systemd --user` 或
systemd service installer 的扩展空间。

```rust
enum RemoteDaemonLauncherKind {
    Nohup,
    SystemdUser,
    SystemdSystem,
}
```

`Nohup` 启动要求：

- 创建 `$HOME/.vela/run`。
- 为本次启动生成 `remote_instance_id`。
- stdout/stderr 写入
  `$HOME/.vela/run/velad.<remote_instance_id>.log`。
- pid 写入 `$HOME/.vela/run/velad.<remote_instance_id>.pid`。
- ready file 写入 `$HOME/.vela/run/velad.<remote_instance_id>.ready.json`。
- 使用 `nohup "$HOME/.vela/bin/velad-<build_id>-<target_triple>" ... &`
  后让 SSH exec 退出。
- 本地通过 russh exec 读取 ready file，拿到 `listen_addr` 后再建立 tunnel。
- 如果 ready deadline 超时，本地读取 log tail 作为 `target_runtime_error`
  诊断。

`Nohup` 不是长期进程监督方案。它只负责 v1 可用；停止、状态查询、日志读取都
必须走 `RemoteDaemonLauncher` trait，以便未来换成 systemd 不改
`VeladChannel`。

### 2.5.1 Ready file handshake

远端 `nohup` 场景使用 `--ready-file` 作为主握手。日志不是控制协议。

`velad` 启动后：

1. bind listener。
2. 构造 `velad.ready` JSON。
3. 写入 `$ready_file.tmp`。
4. fsync 文件和父目录。
5. 原子 rename 到 `$ready_file`。

Ready file 内容：

```json
{
  "type": "velad.ready",
  "runtime_protocol": "velad.local.v1",
  "api_protocol": "velachat.v1",
  "pid": 12345,
  "listen_addr": "127.0.0.1:49321",
  "api_base_url": "http://127.0.0.1:49321/api/v1",
  "version": "0.1.0",
  "build_id": "abc123",
  "target_triple": "x86_64-unknown-linux-gnu",
  "remote_instance_id": "rt_..."
}
```

本地 `velad` 等待 ready file：

- 周期性用 russh exec 执行 `test -s <ready-file> && cat <ready-file>`。
- 解析 JSON 后校验 `remote_instance_id`、`build_id`、`target_triple`、
  protocol 和 pid。
- 超时后才读取 log tail 作为诊断。

stdout `velad.ready` 继续保留给本地 desktop runtime 使用；远端 managed 模式不
依赖 stdout ready。

### 2.6 Graceful remote shutdown

第一版支持自动尽力优雅关闭，但不承诺完整进程树治理。

触发条件：

- runtime target 空闲超过配置的 idle timeout。
- 用户显式 disconnect target。
- local `velad` 正常退出并尝试清理 remote target。

关闭流程：

1. 本地 `velad` 通过 tunnel 调用远端
   `POST /api/v1/runtime/shutdown`，带 remote management token。
2. 远端 `velad` 停止接受新的 channel/view/control 请求。
3. 远端 `velad` 给正在进行的 HTTP/SSE/DB 写入一个有限 grace window。
4. 远端 `velad` 通知 backend adapter 关闭正在持有的 session/process。
5. 本地通过 `RemoteDaemonLauncher` 等待 pid 退出，并记录 shutdown result。
6. 超时后标记 `shutdown_incomplete`，保留 log/pid 供诊断。

ACP/Codex/工具子进程限制：

- `nohup` launcher 没有 systemd cgroup 或 job object 级别的进程树治理。
- 远端 `velad` 可以对自己直接持有的 backend child handle 做 best-effort
  terminate/wait。
- 如果 ACP server、shell tool 或 adapter 又派生孙进程，v1 不保证全部优雅退出。
- 不为了 v1 引入远端 `pkill`/shell kill 兜底；这会扩大误杀风险。
- 后续 systemd launcher 可以用 cgroup scope 实现更强的 KillMode/timeout 语义。

状态语义：

- `shutdown_requested`: 本地已向远端发送 shutdown。
- `shutdown_accepted`: 远端 runtime endpoint 接受请求。
- `shutdown_complete`: 远端 `velad` pid 已退出。
- `shutdown_incomplete`: grace timeout 后仍不能确认退出，可能存在遗留子进程。

### 3. Open tunnel

建立本地 loopback 到远端 loopback 的 tunnel：

```text
127.0.0.1:<local_port> -> 127.0.0.1:<remote_port>
```

本地 `local_port` 只绑定 `127.0.0.1`。

### 4. Verify runtime

通过 tunnel 请求：

```text
GET /api/v1/runtime-info
```

校验：

- `runtime_protocol == "velad.local.v1"`
- `api_protocol == "velachat.v1"`
- remote pid 与 ready event 一致
- version 兼容
- management token 可用于 shutdown/control

### 5. Ready

Transport 标记 ready，返回 `TransportHandle`。`VeladChannel` 随后使用
`local_base_url` 访问远端 view/event/control API。

## VeladChannel 语义

`VeladChannel` 架在 transport 之上。它不是 TCP clone，而是应用层语义通道。

### Mutation ack

所有修改远端状态的请求必须带 idempotency key：

- create remote session
- send turn
- cancel turn
- permission response
- update session config

远端返回 semantic ack：

```ts
type MutationAck = {
  accepted: boolean;
  idempotency_key: string;
  remote_operation_id: string;
  status: "accepted" | "duplicate" | "rejected";
  reason?: string;
};
```

### View ack

本地 `velad` 消费远端 view/event 后推进水位：

```ts
type ViewAck = {
  target_id: string;
  remote_session_id: string;
  ack_watermark: {
    epoch: number;
    event_id: string;
    seq: number;
  };
};
```

远端可以基于 `ack_watermark` 做 chunk retention 或投影缓存回收，但不应把 UI
是否可见作为 backend 继续运行的前置条件。

### Cursor resume

SSE 或 fetch stream 中断后，本地带 cursor 恢复：

```text
GET /api/v1/sessions/{remote_session_id}/events?after_id=<event_id>
```

如果 cursor 仍可 replay，远端补发；如果 cursor 过旧，远端返回
`sync.reset`，本地重新拉取 `ConversationView` snapshot。

## 反压

远端 `velad` 不应把 ACP/Codex raw output 直接推给本地。它应先落地和投影：

```text
backend adapter
  -> remote canonical event log
  -> remote projection/view store
  -> VeladChannel cursor/window pull
  -> local cache/read-model
  -> UI
```

Channel 请求支持：

- `since`
- `limit`
- `max_bytes`
- `stream_ids`
- `ack_watermark`

大工具输出策略：

- 默认只同步 preview 和 stream summary。
- UI 展开时再按 chunk 拉取。
- chunk API 必须支持 `offset` / `cursor` / `max_bytes`。
- 远端存储耗尽时返回 `view_buffer_full` 或 `chunk_retention_exceeded`，而不是
  泛化为 backend failure。

## 弱网状态机

```text
disconnected
  -> connecting
  -> ready
  -> degraded
  -> reconnecting
  -> ready
```

失败进入：

```text
failed
```

状态含义：

- `degraded`: heartbeat 延迟或部分 view 拉取失败，但已有连接未彻底断开。
- `reconnecting`: transport 断开，正在重新 bootstrap/tunnel/verify。
- `failed`: 超过 deadline 或认证/版本/协议不兼容。

channel 状态不能覆盖 session/turn 状态。断网时远端 turn 可能仍在运行，本地只能
显示 stale/reconnecting，不能直接标记 failed。

## 错误分类

```ts
type RuntimeTargetError =
  | { kind: "transport_error"; code: string; message: string }
  | { kind: "target_runtime_error"; code: string; message: string }
  | { kind: "backend_error"; code: string; message: string }
  | { kind: "protocol_error"; code: string; message: string }
  | { kind: "version_mismatch"; local: string; remote: string };
```

分类规则：

- SSH/tunnel/reset 是 `transport_error`。
- 远端 `velad` 无法启动、runtime-info 不合法是 `target_runtime_error` 或
  `protocol_error`。
- 模型/API/agent adapter 报错是 `backend_error`。
- OpenAPI / channel contract 不兼容是 `protocol_error`。

## 安全

- 远端 `velad` 只绑定 `127.0.0.1`。
- tunnel 本地端只绑定 `127.0.0.1`。
- remote management token 由本地 `velad` 生成和持有，不暴露给 renderer。
- 第一版 SSH authentication 使用 persisted password secret。明文 password 只在
  本地 `velad` 建立连接时通过 `keyring` 从系统 credential store 解析，不进入 share snapshot、
  trace payload、renderer bootstrap 或普通 node/target metadata。
- 第一版 host key policy 是 default trust，不做 strict known_hosts 校验。这个
  是明确的 v1 安全债；后续应通过 `SshTransport` 增加 host key pinning /
  known_hosts policy，而不改变 `VeladChannel`。
- runtime target API 只返回 safe metadata。

## Observability

本地 `velad` 记录以下 spans/logs：

- `runtime_target.connect`
- `ssh_transport.bootstrap`
- `ssh_transport.remote_ready`
- `ssh_transport.tunnel_open`
- `ssh_transport.verify_runtime`
- `velad_channel.request`
- `velad_channel.stream_resume`
- `velad_channel.ack`
- `velad_channel.backpressure`

远端 `velad` 记录 target-local backend spans。第一版不要求完整 trace
replication，但 local span 必须记录 remote trace id / generation / target id，便于定位。

## 第一版 API

UI-facing local API：

```text
GET  /api/v1/node-providers
GET  /api/v1/nodes
POST /api/v1/nodes
GET  /api/v1/nodes/{node_id}
PATCH /api/v1/nodes/{node_id}
DELETE /api/v1/nodes/{node_id}
GET  /api/v1/runtime-targets
POST /api/v1/runtime-targets/{target_id}/connect
GET  /api/v1/backends?target_id=...
POST /api/v1/sessions
```

`POST/PATCH /api/v1/nodes` 可以接收 write-only password 字段；响应必须返回
safe metadata，例如 `password_configured: true`，不能返回明文 password。

设置页命名：

```text
设置 -> 节点 -> 新增 SSH 主机
```

`CreateSessionRequest` 增加：

```ts
{
  runtime_target_id?: string;
}
```

Remote channel-facing API 可以先复用现有 `/api/v1` view endpoints，但必须加
target/channel 内部校验和 bounded 查询参数。后续如果要收紧边界，可引入
`/api/v1/channel/*` internal endpoints。

## 测试计划

Rust 单测优先于真实 SSH：

- fake transport open/close/health。
- node create/update persists password through `LocalSecretStore` / `keyring` and never returns plaintext in safe metadata。
- fake drop channel 在 mutation ack 前断开，重试不重复创建 session。
- fake drop channel 在 SSE 中途断开，重连后从 cursor resume。
- stale generation response 被拒绝。
- channel reconnecting 不会把 session 标记为 failed。
- cancel 在远端 ack 前保持 `cancel_requested`。
- 大工具输出只同步 preview，展开时按 chunk 拉取。
- remote backend error 不被归类为 transport error。

集成测试再接真实 SSH：

- 启动远端 `velad --listen 127.0.0.1:0`。
- 建 tunnel 后校验 `/api/v1/runtime-info`。
- create session 走远端 target。
- 断开 tunnel 后重连并恢复 conversation cursor。

## 实施顺序

1. 新增 `runtime_targets` 模块和模型。
2. 新增 Node / NodeProvider / LocalSecretStore(keyring) 模型和节点 API。
3. 新增 `ChannelTransport` trait 与 fake transport。
4. 新增 `VeladChannel` semantic request/ack/cursor 模型。
5. 用 fake/drop channel 写弱网和反压测试。
6. 接 local target，保持现有行为不变。
7. 实现 `SshTransport` bootstrap/tunnel/verify。
8. 增加 target-scoped backend discovery。
9. `CreateSessionRequest` 接入 `runtime_target_id`。
10. 设置页增加“节点 / 新增 SSH 主机”，新会话页增加 target selector。
