# UI Read Model API

velaChat 的 API 必须分成两层：

- **Agent 基础 API**：面向 daemon/runtime 的事实和控制面。
- **UI Read Model API**：面向 Desktop、Mobile、Web、Embed 的投影读取面。

这两层不是同一个东西。Agent 基础 API 决定系统事实；UI Read Model API 只是把事实整理成具体 UI surface 能直接渲染的形状。

```txt
Agent 基础 API
  -> Input Event API
  -> Runtime Event API
  -> Session History API
  -> Backend Capability API
  -> Diagnostics API

Projector functions
  -> projectTranscript()
  -> projectActivity()
  -> projectRequests()
  -> projectDiffs()

UI Read Model API
  -> /transcript
  -> /activity
  -> /requests
  -> /diffs

Session History / Audit API
  -> /timeline
  -> /trace
```

## 分层原则

### Agent 基础 API

Agent 基础 API 负责“系统发生什么”和“用户要求系统做什么”：

| 类别 | 示例 | 说明 |
| --- | --- | --- |
| Input Event API | `POST /sessions/{id}/events` | 用户意图入口，必须有权威校验和幂等 |
| Runtime Event API | `GET /sessions/{id}/events` | canonical event log，支持恢复、审计、replay |
| Session History API | `GET /sessions/{id}/timeline` | session 综合历史、审计、回放、导出 |
| Backend API | `GET /backends` | 后端能力、健康状态、模型能力 |
| Diagnostics API | `GET /sessions/{id}/trace` | 调试 raw event、normalization、command trace |

Agent 基础 API 不为某个 UI 组件设计。它应该稳定、可审计、可测试。

### UI Read Model API

UI Read Model API 负责“某个 UI surface 现在怎么显示”：

| Read Model | 用途 | 主消费者 |
| --- | --- | --- |
| `SessionListView` | session rail / sidebar | Desktop、Web、Mobile navigation |
| `ChatTranscriptView` | 聊天正文 | Web Chat Engine、Mobile WebView、Embed Chat |
| `ActivityShelfView` | 工具调用、命令、进度、warning | Desktop/Web activity shelf |
| `PendingRequestsView` | 权限、确认、用户输入请求 | Permission dock、Mobile approval |
| `DiffReviewView` | 文件变更和 review | Review panel |

UI Read Model API 可以通过 HTTP/SSE 暴露，也可以在同进程内直接调用 projector 函数。API 只是 transport，本体是 projector。

## Timeline 的位置

Timeline 必须保留，但不能作为普通 UI 的主输入。

```txt
Event Log
  -> ChatTranscriptView        # Chat UI
  -> ActivityShelfView         # 工具/进度
  -> PendingRequestsView       # 权限/确认
  -> DiffReviewView            # 文件变更
  -> SessionTimeline           # 主 API：综合历史/审计/全量历史
  -> SessionTrace              # diagnostics：command/raw/normalization trace
```

`SessionTimeline` 适合：

- DevTools
- audit
- replay
- debugging
- export
- full historical inspection

`SessionTimeline` 和 `SessionTrace` 不适合：

- Chat transcript 主渲染
- Session sidebar 主渲染
- Permission dock 主渲染
- Activity shelf 主渲染
- Mobile 主 UI

## 建议 endpoint 形状

### Agent 基础 API

```txt
POST /sessions
POST /sessions/{session_id}/events
POST /sessions/{session_id}/cancel
POST /sessions/{session_id}/close

GET  /sessions/{session_id}/events
GET  /sessions/{session_id}/events/stream
GET  /events/stream

GET  /backends
GET  /backends/{backend}
POST /backends/{backend}/probe
```

`POST /sessions/{session_id}/events` 是 velaChat 的统一输入面，不要求每个 backend 原生都有同名语义。Backend adapter 负责把 input events 翻译成各后端自己的协议。

例如 Qoder 的公开 API 更偏 event-shaped：

| velaChat Input | Qoder 风格映射 |
| --- | --- |
| `user.message` | `POST /v1/sessions/{id}/events` with `user.message` |
| `user.tool_confirmation` | `POST /v1/sessions/{id}/events` with `user.tool_confirmation` |
| `user.custom_tool_result` | `POST /v1/sessions/{id}/events` with `user.custom_tool_result` |
| `POST /sessions/{id}/cancel` | `POST /v1/sessions/{id}/cancel` |

我们吸收 Qoder 的 event-shaped input 形状，但仍保留 daemon authority：POST 进来的 input events 是用户意图，只有 daemon 接受后才会成为 canonical runtime events。

## Live 订阅和 Read Model 刷新

UI 感知状态变化的方式是：

```txt
Client boots
  -> fetch initial read models
  -> subscribe /sessions/{session_id}/events/stream
  -> receive canonical events in an isolated live adapter
  -> refresh or patch affected read models
  -> render from read models
```

事件流告诉 UI “发生了什么”和“哪些 view 需要刷新”；UI 组件本身不从事件里拼最终界面。Day 0 允许一个隔离的 transcript live adapter 把 canonical events 转成本地 row patch；组件层仍然只消费 transcript rows。Projected transcript stream 是下一阶段 API，不能在组件层提前复制一套 projector。

常见映射：

| Canonical event | UI 刷新 |
| --- | --- |
| `user.message.accepted` | `ChatTranscriptView` |
| `turn.started` / `turn.completed` / `turn.failed` / `turn.cancelled` | `ChatTranscriptView`、`ActivityShelfView`、`SessionView` |
| `assistant.message.delta` | `ChatTranscriptView` |
| `request.opened` | `PendingRequestsView`、可选 `ActivityShelfView` |
| `request.resolved` | `PendingRequestsView`、`ActivityShelfView` |
| `tool.started` / `tool.updated` / `tool.output.delta` / `tool.completed` / `tool.failed` | `ActivityShelfView` |
| `command.started` / `command.output.delta` / `command.completed` | `ActivityShelfView` |
| `diff.updated` | `DiffReviewView` |
| `session.updated` | `SessionListView`、session view |

完整词表见 [事件词表](/docs/api/event-vocabulary)。UI 组件必须以 read model 为主输入，不能跳过 projector 直接解释 runtime event payload。

`ActivityShelfView` MUST 保留所有 projected tool calls。长运行工具和短工具都进入 activity；差异只体现在 render model 的密度、分组、显隐和虚拟化策略。属于某个 turn 的 activity item SHOULD 携带 `turn_id`，用于 client 把 agent work 和 transcript row 归入同一个 conversation segment。`detail` 字段是 normalized tool detail union，例如 `shell`、`read`、`edit`、`write`、`search`、`fetch` 或通用兜底类型；它只能包含 UI-safe projected fields，不能暴露 provider raw event，也不能把所有工具粗暴包装成 `{ type: "tool" }`。完整 raw/debug 信息仍然属于 `/sessions/{session_id}/timeline` 和 `/sessions/{session_id}/trace`。

`ChatTranscriptView.turns` 是 turn lifecycle 的 UI read-model 真相来源。`turn.started`、`turn.completed`、`turn.failed`、`turn.cancelled` 会投影为 window-scoped turn summaries；client render model 可以用它显示 `处理中` / `已处理 Xs` 这类 turn header，但不能从 assistant row 的 streaming 状态、tool activity 数量或 raw timeline 反推 turn 生命周期。

如果 stream 断线，client 使用 `Last-Event-ID` 或 `after_id` 补拉；如果收到 `sync.reset`，按 `views[]` 刷新对应 read models。

### ChatTranscriptView row window

`GET /sessions/{session_id}/views/transcript` 返回 transcript row window，而不是 event window。响应包含 `rows` 和 `turns`：

- `rows` 是 message-like transcript rows，用于 user/assistant/error/activity marker 正文渲染。
- `turns` 是当前 window 内可见 turn 的 lifecycle summaries，用于 turn header、运行时长、完成时长和同 turn activity 的归组锚点。

`turns` 是 required 字段；客户端不得把缺失的 `turns` 当成旧协议兼容处理。

```txt
GET /sessions/{session_id}/views/transcript?direction=tail&limit=80
GET /sessions/{session_id}/views/transcript?direction=before&anchor_row_id=row_x&limit=80
GET /sessions/{session_id}/views/transcript?direction=after&anchor_row_id=row_x&limit=80
GET /sessions/{session_id}/views/transcript?direction=around&anchor_row_id=row_x&limit=80
```

`direction` 控制 view window：`tail` 拉尾部，`before` 拉 anchor 之前，`after` 拉 anchor 之后，`around` 拉 anchor 附近。`direction=before|after|around` 必须提供 `anchor_row_id`；`direction=tail` 不得提供 anchor。都不传时等价于 `direction=tail`。

Transcript window 的分页参数只有 `direction` 和 `anchor_row_id`。OpenAPI 名称是唯一 wire contract。

`row_id` 是 opaque view anchor，client 只能原样传回。未知 row anchor 表示 client window 已过期，daemon 返回 `409 stale_cursor`，client 必须重新拉取 transcript window。

`include_live=false` 会排除 `pending` / `streaming` rows，适合只恢复稳定历史窗口；默认 `true`，适合 chat 首屏和普通尾部窗口。

Response 同时包含两种 cursor：

- `window`：UI list window，用于虚拟列表、上拉旧消息、搜索跳转和滚动恢复。
- `cursor`：canonical event cursor，用于 event stream reconnect、stale detection 和 reset。

Projected transcript stream 的终局形状是 `/sessions/{session_id}/views/transcript/stream?after_event_id=...`，输出 `TranscriptPatch`。当前阶段先不把它作为必选运行时 API；前端 live adapter 必须保持隔离，后续可以无痛下沉到 Rust projector。

### Conversation window composition

OpenAPI 不定义独立的 `ConversationView` wire DTO。对话列表运行时可以把 `ChatTranscriptView` 和 `ActivityShelfView` 合成为 app-side conversation window，但这个合成层属于 client/runtime model，不是新的 daemon contract。

Client 在做上拉旧历史时 MUST 同时考虑 transcript 和 activity 两侧的 window：

- `conversation.has_older = transcript.window.has_older || activity.window.has_older`
- 如果 transcript 仍有旧 row，client 使用 `direction=before&anchor_row_id=<first_row_id>&include_live=false`
- 如果 activity 仍有旧 item，client 使用 `direction=before&anchor_item_id=<first_item_id>`
- 合并 transcript window 时必须同时合并 `turns`，否则分页后的 assistant row 会丢失 turn header 和 timing metadata
- 两侧请求可以并行；任一侧返回 `409 stale_cursor` 时，client 丢弃本地窗口并重新拉 tail

这样可以接近 Paseo-style agent stream 的使用体验，同时保留 Vela 的 provider normalization 边界：正文来自 transcript，agent work 来自 activity，普通 UI 不直接读取 timeline/trace。

### ActivityShelfView item window

`GET /sessions/{session_id}/views/activity` 返回 activity item window。Activity 已经是 projected UI-safe item，不是 raw provider event。

```txt
GET /sessions/{session_id}/views/activity?direction=tail&limit=80
GET /sessions/{session_id}/views/activity?direction=before&anchor_item_id=act_x&limit=80
GET /sessions/{session_id}/views/activity?direction=after&anchor_item_id=act_x&limit=80
GET /sessions/{session_id}/views/activity?direction=around&anchor_item_id=act_x&limit=80
```

`direction=before|after|around` 必须提供 `anchor_item_id`；`direction=tail` 不得提供 anchor。Activity window 是按 projected item 切片，所以 tool lifecycle 合并后的 item 不会因为 canonical event 分页被切碎。

### UI Read Model API

```txt
GET /views/sessions
GET /sessions/{session_id}/views/session
GET /sessions/{session_id}/views/transcript
GET /sessions/{session_id}/views/activity
GET /sessions/{session_id}/views/requests
GET /sessions/{session_id}/views/diffs
```

使用 `/views/*` 是为了避免误解：这些 endpoint 返回的是投影，不是事实源。

### Session History / Audit API

```txt
GET /sessions/{session_id}/timeline
GET /sessions/{session_id}/timeline/{item_id}
GET /sessions/{session_id}/trace
```

使用 `/sessions/{id}/timeline` 是为了明确 timeline 是 CloudAgent-style session history 主资源；使用 `/sessions/{id}/trace` 是为了提供 diagnostics 链路。二者都不是普通 UI surface 的渲染输入。

## Requirements

### Requirement: UI API 不写事实

UI Read Model API MUST NOT 修改 canonical events、session state 或 backend runtime。

#### Scenario: transcript view 被读取

- **WHEN** client 请求 `/sessions/{id}/views/transcript`
- **THEN** daemon 返回 `ChatTranscriptView` row window
- **AND** response 包含 `window` 和 canonical event `cursor`
- **AND** 不追加任何 canonical event

### Requirement: transcript paging 使用 row cursor

Chat transcript pagination MUST 使用 transcript row anchor，不得要求普通 Chat UI 用 event cursor 拼列表窗口。`cursor` 仍然专指 canonical event cursor；view 翻页必须使用 `anchor_row_id`。

#### Scenario: 上拉旧消息

- **WHEN** client 使用 `direction=before&anchor_row_id=...` 请求 `/sessions/{id}/views/transcript`
- **THEN** daemon 返回该 row 之前的 transcript rows
- **AND** `window.has_newer` 为 `true`
- **AND** `cursor` 仍然指向该 session 当前最新 canonical event

#### Scenario: row cursor 过期

- **WHEN** client 使用未知 `anchor_row_id`
- **THEN** daemon 返回 `409 stale_cursor`
- **AND** client 丢弃本地 transcript window
- **AND** client 重新请求 `/sessions/{id}/views/transcript`

### Requirement: UI API 从 projector 派生

UI Read Model API MUST 由 projector functions 或 projector cache 提供。

#### Scenario: activity view cache 丢失

- **WHEN** `ActivityShelfView` cache 丢失
- **THEN** daemon 可以 replay canonical events
- **AND** 重新生成同样的 activity view

### Requirement: Timeline 是 session history 主资源

Session timeline MUST NOT 成为普通 UI surface 的直接数据源，也不应该挂在 UI Read Model API 下。

#### Scenario: Chat UI 加载会话

- **WHEN** Chat UI 打开 session
- **THEN** 它请求 `ChatTranscriptView`
- **AND** 不请求 session timeline 来拼 transcript row

### Requirement: Mobile 使用窄 read model

Mobile clients SHOULD 使用窄 read model，而不是拉完整 timeline 自己拼 UI。

#### Scenario: 手机审批权限

- **WHEN** 手机打开 approval screen
- **THEN** 它读取 `PendingRequestsView`
- **AND** 它通过 Input Event API 提交 approve/deny
- **AND** 不需要读取 session timeline
