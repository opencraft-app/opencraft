# Native groups with an external WeCom connection

The native group remains the group: native title, membership, messages and access
checks have one owner. An optional external connection adds observations and an
ordered delivery journal, not a second writable native group. Relay only performs
provider I/O. Gateway schedules it through existing installation ports. SQLite
commits native mutations and their outgoing operations together.

## Normal group operations

Native controls and the assistant’s `chat rename/add/remove` use the same native
mutation methods and propagation hook. Assistants never need to select `sync request`.
For adopted connections the native Human owner is required. USER remains a registered
RTX identity, resolved through trusted account bindings; unknown people are not
registered or admitted, and native-only people remain native-only. Inbound-only/off
fields stay local rather than falling back to a provider bypass. Unconfigured legacy
bindings retain provider-only behavior until explicitly adopted.

Edits return `receiptId`, `local.state:applied`, and per-change `wecom` results.
Use `wecom status RECEIPT --group GROUP`; only `confirmed` means this operation was
verified, not that the group can never change again. Pending processing is silent;
attention/unconfirmed responses explain the affected outcome without exposing the
journal. No synthetic operation message or canned acknowledgement is posted to the
group. The caller can reply naturally.

Batch edits commit atomically, removals before additions, using native permissions,
capacity checks and idempotency. Detailed receipts retain at most 128 edits / 512
individual changes per connection;
durable native dedupe tombstones outlive this history. Expired results never trigger
a replay. A legacy pre-adoption receipt also cannot execute again as a native edit.

## Connection maintenance (not normal group operation)

The native Human owner can configure the current bound group through the existing
private CLI. No deployment or existing group is silently activated.

```sh
wecom sync status --group GROUP
wecom sync configure '{"name":"both"}' --group GROUP --idempotency-key names-v1
wecom sync configure '{"name":"both","members":"both","historyAccess":"full"}' --group GROUP --idempotency-key group-v1
wecom sync request '{"kind":"name","name":"Incident #123"}' --group GROUP --idempotency-key rename-123
wecom sync request '{"kind":"member","userId":"T0001A","present":true}' --group GROUP --idempotency-key add-1
wecom sync cancel OPERATION_ID --group GROUP --idempotency-key cancel-1
```

The scope/actor come from the private CLI binding; users cannot select another
person's identity. Existing native owner title/member controls use the same
transactional journal. Local operations take effect immediately, including while
WeCom is unavailable or a preceding delivery has an uncertain outcome. Native
owner/capacity/eligibility failures roll back the outgoing operation as well.
Cancelling a queued delivery does not undo the native change. Retry a terminal
failed operation using a new explicit request/key. Never report queued as delivered.

Configuration is a complete policy: `name` is `off`/`inbound`/`both`, `members` is
`observe`/`inbound`/`both`. Inbound-only does not disable native editing; those edits
simply aren't exported. `members:observe` never grants or revokes access. Automatic
member import requires `historyAccess:full`, acknowledging the native group's
existing full-history permission model. This does not create/admit accounts or
verify identities. Unknown identities and native-only Humans/Bots are not guessed
into external identities. Member capacity remains 64, including Bots.

`initial:preserve` (default) establishes an external baseline without overwriting
native title/membership or treating the initial roster as join events. Differences
remain visible in `sync status`; explicit native operations can export them.
`initial:external` imports the first external title and eligible members, preserving
native-only members. It never replaces the whole native roster. Select this when
connecting an existing WeCom group and intending to import its current participants.
Changing `initial` after the baseline exists does not replay bootstrap.

## Changes, confirmation and recovery

- Native operations are journaled in acceptance order. Each outgoing command changes
  one title or one member; adding someone never replaces a full roster.
- Complete external snapshots are diffed against the prior observation. An unrelated
  external join can be imported while a native add is pending. No reverse operation
  is generated by an external projection.
- A command's own field in its response is a receipt, not a new remote edit. It cannot
  overwrite a newer local edit. Other fields in that same snapshot are still diffed.
- Local changes pending delivery protect their affected fields. A fresh provider
  preflight checks the field against the last observation; conflicts/rejections are
  recorded without rolling back the successful native operation. Later actual remote
  changes can be imported normally. Unchanged snapshots do not repeatedly overwrite
  native state. `sync status` contains both native state and the confirmed observation.
- An uncertain operation blocks later outbound operations for that connection, not
  local group use. First dispatch is durably claimed; recovery first verifies. An expired 30-second dispatch grant with no Relay receipt
  inside its guaranteed retention window proves the attempt never started and can
  be retried. A missing receipt after retention proves nothing. Relay
  freezes the operation before provider I/O. Network loss/restarts cannot turn an
  old unknown operation into a fresh write, even after Relay receipt expiry.
- A local removal is not a permanent ban. Pending removal cannot be undone by stale
  unchanged presence; after confirmed absence, a later observed rejoin can create a
  new native membership epoch. Old assistant scopes and queued replies stay invalid.
- External identity unlink/reassignment revokes imported access. Independently
  authorized native membership survives identity unlink and provider outages.
- An external member departure removes the corresponding native member. Native
  owner departure is reported as `native_owner_retained`, never silently orphaning
  the native group or fabricating a new owner. Provider mutations may then reject
  because the external requester is absent; native ownership remains usable.
- Wrong-room, duplicate-ID or malformed snapshots are rejected wholesale. Failed
  queries never mean an empty roster. Binding/source epochs and observation tickets
  reject delayed results from earlier connections or reads.
- Capacity failures are listed and retried after space frees; valid removals still
  apply. No external participant is kicked to fit native capacity.
- Default polling is 30 seconds; message intake runs independently. Errors and the
  last successful observation time are available through `sync status`.

The provider supplies no member events, revision/CAS or mutation idempotency key in
our supplied API specification. Polling can miss a leave/rejoin between reads;
preflight cannot prevent someone changing the same field between GET and POST.
We guarantee local transactional ordering and verifiable delivery states, not
cross-platform atomicity, instantaneous revocation or unconditional convergence.
A conflict, unsupported identity, permission failure or indefinitely unknown write
can require an explicit corrective operation. Disconnecting never deletes the
native group. Existing messages and their delivery pipeline are unchanged.

## 群设置中的同步属性与手动检查

外部绑定群的群设置展示同步方向、上次**成功**同步时间及当前状态；纯原生群不显示。
成员可以查看轻量状态，只有已验证企业微信身份的原生群主可点击“立即同步”。
断开、暂停或退休的绑定不能手动同步。状态不公开外部成员ID、身份映射或操作日志。

“立即同步”写入原有统一同步层的持久刷新请求，绕过下次自动轮询等待；连续点击会合并，
同一请求ID重试不会创建第二轮。请求提交只表示排队，不表示成功。网络失败、未知写入结果
或校验失败不会刷新成功时间；旧的后台读取也不能完成后来才提交的手动请求。
待发送的原生改动仍使用已有幂等回执，不强制重放不确定的写入、不覆盖更新的原生编辑。

维护 CLI：`wecom sync refresh --group ID --idempotency-key KEY`。
未配置的外部群可手动做一次安全检查：仅创建关闭群名同步、仅观察成员的默认配置，
不自动启用双向同步、不授予完整历史访问、不导入/移除成员。要实际导入群名/成员仍须先
显式配置同步方向；成员同步仍要求 `historyAccess: "full"`。
该首次检查记录是 observation-only，不接管旧有群操作路径，检查结束后不启动持续轮询；
之后显式启用同步时会重新建立基线，仍遵循 `initial: preserve/external` 的首次导入选择。

## Connection recovery and results

A saturated delivery journal rejects only the new external delivery (with an
explicit attention result), never the authorized local mutation. Existing uncertain
writes are retained. Reconnecting with a new source epoch initializes a fresh
observation/delivery authority; old writes are retired, uncertain outcomes remain
explicitly unknown, and no old write is replayed. Reconfiguration remains owner-only.

Terminal partial/failed business receipts are returned durably to the original
assistant scope. The runtime submits a stable outcome input to that agent, then
acknowledges the exact result revision. It does not post a canned group notice;
the agent decides whether the outcome warrants a natural-language explanation.
Successful operations stay silent. Detailed outcomes share the bounded receipt
retention and cannot cross a revoked membership/scope.

Assistant-created Relay bindings carry a trusted native-group marker. After the
first durable native message admission creates the native source, title sync is
initialized automatically and idempotently. Member observation does not grant
membership or history access; enabling imports still requires explicit owner
configuration. Existing policy is never overwritten by a repeated delivery.
This initialization occurs on first native intake, not before anyone sends a message.


## Mention capability boundary

Member projections label mentions as linked only with a verified current native
Actor/corporation identity binding. Otherwise the composer warns that the mention
remains inside OpenCraft. This readiness is not proof of provider delivery; the
outbound path still verifies the current external roster.

The supplied inbound callback contract has only service-level MentionedType, not
ordinary human mention recipients/ranges. The status view exposes
`mentionIngress: "text-only"` and explains that inbound ordinary names remain
text. Never infer a target Actor by display name or reuse the outbound rich_text
recipient schema as an undocumented inbound field.


## Provider operation diagnostics

`sync status` operations and ordinary `status group-edit:...` change receipts retain
bounded `diagnostics` in the existing JSON storage (no schema migration). The Relay
stores write evidence before confirmation reads; restart, verify and same-key replay
reuse it without another provider mutation. The optional `updateChatDetailed` method
is used only by the sync provider; legacy `updateChat` keeps its string/throw contract.

Diagnostics identify the operation, action, API pathname, provider errcode, cleaned
errmsg, elapsed time and separate write/readback outcomes. A confirmed read wins even
when the provider response rejected; timeout/network uncertainty remains unknown.
No payload, response object, stack, credential or URL query is logged. Messages are
limited to 300 characters, known credentials and credential fields are redacted and
URLs are removed. One structured log is emitted per attempted mutation, not for
successful periodic reads. Generic private CLI failures expose only a correlation ID
and retain a bounded server-side category, never the original exception.

Old receipts without diagnostics cannot reconstruct historical provider errors.

## Provider permissions and visible delivery failures

Native ownership authorizes local editing, not the service account's external
privileges. Judge rename, addition and removal independently using provider write
receipts. WeCom `86101` means that particular operation requires group owner
privileges; it does not disable all group synchronization. The deployed Tencent
`chat/get` response may omit the owner entirely. Do not infer it from the native
owner, roster order, requester or display names, and never invent an operator to
impersonate. Readback confirmation remains authoritative, including when rights
change after a check. No permanent permission-denied cache is introduced.

Member-visible status projects a bounded `deliveryIssue` with action and reason,
never provider identities or raw error text. A successful read or unrelated
successful edit cannot clear a failed latest intent on another field. A fresh
snapshot satisfying that intent or a newer intent for the same field clears the
current warning; the historical business receipt still records its actual result.
The UI distinguishes a local change from failed external delivery, and offers
"Check now", not a retry of the rejected mutation. Terminal failures are not
replayed by refresh. Ask the external group owner to resolve owner-only actions.

## Native leave and dissolution

Native lifecycle is independent of this adapter. Ordinary native members can
leave without leaving WeCom; a durable native departure fence excludes them from
later automatic roster imports, including a remote remove/re-add transition.
The native owner may explicitly invite them back with a new membership epoch.

Only the native owner can dissolve the native group, with an observed-revision
confirmation. This does not invoke a WeCom leave/dissolve endpoint. Existing
members retain authorized native read-only history; departed members do not.
Sources become inactive tombstones, metadata polling cannot project changes, and
pending provider creations cannot reconnect the dissolved group. A creation
already in flight can complete externally: its acknowledged room identity is
retained inactive to prevent a second automatic native mirror. Provider writes
already handed off remain potentially externally effective, never falsely
reported as rolled back. Bots, environments and other groups are not deleted or
stopped by these operations.
