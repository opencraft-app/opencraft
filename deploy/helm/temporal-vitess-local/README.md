# Temporal on Vitess external MySQL Helm chart

This chart runs Temporal through Vitess while keeping MySQL lifecycle management
in cloud-managed MySQL, such as TencentDB for MySQL CDB or TDSQL-C.

Vitess is responsible for topology, VTGate routing, VTTablet query service,
VSchema, VReplication, and resharding. MySQL primary/standby, backups, PITR,
parameters, and failover belong to the cloud database service.

## Shape

- Vitess Operator is installed in the release namespace.
- VitessCluster `temporal-vitess` is external MySQL only.
- Each keyspace must provide `externalShards`.
- The chart never renders managed `mysqld`, tablet PVCs, VTOrc, or Vitess
  xtrabackup storage.
- Temporal default and visibility stores connect through VTGate.
- `values-sharded-fresh.yaml` defines the Temporal/VSchema sharding rules for
  `temporal_sharded`; it does not provision MySQL shards.
- Environment-specific values, usually generated by Terraform, provide the real
  CDB/TDSQL-C endpoints.

The vendored Temporal subchart under `charts/temporal/` contains a small
readiness override hook needed by TKE Serverless. Do not run
`helm dependency build` unless you intentionally re-apply that patch.

## External MySQL values

The environment overlay must provide all Vitess keyspaces as external shards:

```yaml
vitess:
  cluster:
    externalDatastore:
      user: vt_dba
      credentialsSecret:
        create: false
        name: temporal-vitess-external-mysql
        key: credentials.json
    keyspaces:
      - name: temporal
        externalShards:
          - keyRange: {}
            host: 10.80.48.16
            port: 3306
            database: temporal
      - name: temporal_sharded
        externalShards:
          - keyRange:
              end: "80"
            host: 10.80.48.15
            port: 3306
            database: temporal_sharded
          - keyRange:
              start: "80"
            host: 10.80.64.5
            port: 3306
            database: temporal_sharded
      - name: temporal_visibility
        externalShards:
          - keyRange: {}
            host: 10.80.64.4
            port: 3306
            database: temporal_visibility
```

The password secret consumed by Vitess has this shape:

```json
{
  "vt_dba": ["<password>"]
}
```

Store it as `temporal-vitess-external-mysql/credentials.json`. In production,
source this from SOPS/SSM or another secret manager; do not commit the value.

## Install

Create the namespace and credentials secret first:

```bash
kubectl create namespace temporal-vitess

kubectl -n temporal-vitess create secret generic temporal-vitess-external-mysql \
  --from-file=credentials.json=/path/to/vitess-mysql-credentials.json \
  --dry-run=client -o yaml | kubectl apply -f -
```

Install with the base values, sharded Temporal profile, external MySQL values,
and any cloud-specific overlay:

```bash
helm upgrade --install temporal-vitess \
  deploy/helm/temporal-vitess-local \
  --namespace temporal-vitess \
  -f deploy/helm/temporal-vitess-local/values.yaml \
  -f deploy/helm/temporal-vitess-local/values-sharded-fresh.yaml \
  -f /path/to/values-env-external.yaml \
  -f deploy/helm/temporal-vitess-local/values-tke-serverless.yaml \
  --timeout 30m
```

The `values-env-external.yaml` file should normally come from Terraform output.
For the Beijing validation stack, this is
`temporal_vitess_helm_values_yaml`.

## Single-MySQL E2E

Before the four-MySQL production-like topology, use
`values-e2e-single-mysql-template.yaml` to validate the basic chain with one
external MySQL instance and four schemas:

- `temporal`
- `temporal_sharded_00_80`
- `temporal_sharded_80_ff`
- `temporal_visibility`

This keeps cost low while still exercising the `temporal_sharded` two-keyrange
shape. See [E2E_SINGLE_MYSQL.md](E2E_SINGLE_MYSQL.md) for bootstrap and smoke
commands.

## Smoke checks

```bash
kubectl -n temporal-vitess get pods,jobs

kubectl -n temporal-vitess exec deploy/temporal-admintools -c admin-tools -- \
  temporal operator cluster health --address temporal-frontend:7233

VTCTLD_POD="$(kubectl -n temporal-vitess get pod \
  -l planetscale.com/component=vtctld \
  -o jsonpath='{.items[0].metadata.name}')"

kubectl -n temporal-vitess exec "$VTCTLD_POD" -- \
  /vt/bin/vtctldclient --server=vitess-vtctld:15999 GetRoutingRules
```

Schema versions can be checked through VTGate:

```bash
VTGATE_POD="$(kubectl -n temporal-vitess get pod \
  -l planetscale.com/component=vtgate \
  -o jsonpath='{.items[0].metadata.name}')"

for db in temporal temporal_sharded temporal_visibility; do
  kubectl -n temporal-vitess exec "$VTGATE_POD" -- \
    mysql -h vitess-vtgate-mysql -P 3306 -u user -D "$db" \
      -e "select curr_version from schema_version"
done
```

## Argo CD handoff

Use the same value-file order:

```yaml
source:
  repoURL: git@git.woa.com:wisp/mono2.git
  targetRevision: gitops
  path: deploy/helm/temporal-vitess-local
  helm:
    releaseName: temporal-vitess
    valueFiles:
      - values.yaml
      - values-sharded-fresh.yaml
      - values-env-external.yaml
      - values-tke-serverless.yaml
```

## Production notes

- Pin Vitess images instead of using `latest`.
- Use HA topology etcd, not the single-node validation `topologyEtcd`.
- Keep `numHistoryShards` immutable after the first Temporal deployment.
- Treat `4096` in `values-sharded-fresh.yaml` as the first-install production
  planning value; do not lower or raise it after the Temporal database is
  initialized.
- Keep VSchema/schema Jobs as Argo hooks; do not manage them as TTL-deleted
  ordinary Jobs.
- Use [RESHARDING.md](RESHARDING.md) for 2 -> 4 -> 8 -> 16 shard expansion.
- CDB/TDSQL-C owns backups, PITR, MySQL failover, and parameter baselines.
- Validate CDB/TDSQL-C failover recovery through VTGate before production
  traffic.
