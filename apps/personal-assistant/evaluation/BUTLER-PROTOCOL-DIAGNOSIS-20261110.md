# 管家协议失败：先定位，再做一次有针对性的纠正

此前三轮的四次失败只留了通用错误，无法追溯每次具体字段。这轮先增加诊断、保持提示词和验收不变，完整重跑六题；随后只改协议纠正反馈，再用同六题、同模型配置复测。历史失败不覆盖，也不把新发现冒充所有旧失败的确切原因。

## 已确认的问题

诊断轮 4/6 通过，出现 7 次结构化拒绝：全部是 **JSON 合法、平铺 wire schema 合法，但具体命令契约不合法**，没有观测到 JSON 语法错误。

| 字段问题                            | 次数 | 影响                                                                   |
| ----------------------------------- | ---- | ---------------------------------------------------------------------- |
| `expectedRevision` 留空             | 4    | 并行题回答问题两次留空而失败；取消题纠正后仍留空；记忆题一次纠正后恢复 |
| `key` 留空                          | 1    | 记忆题第一次尝试失败，纠正后恢复                                       |
| 不属于所选命令的 `commands` 非空    | 1    | 取消题第一次尝试失败                                                   |
| 不属于所选命令的 `maxParallel` 非空 | 1    | Goal 题纠正后恢复                                                      |

主因是两层契约的表达落差：为兼容约束生成，原生输出 schema 将命令联合展平为可空字段超集，因此允许某命令的必填字段为 null，也允许其它命令的字段非空；宿主去 null 后仍按原始封闭命令联合校验，这是必须保留的保护。原纠正只说“JSON 或 schema 不符合”，没有反馈具体字段，导致同一错误可连续出现。

回答问题所需的 revision 已在 `pendingInteractions[].revision` 中提供，取消等操作也有查询和版本校验路径。不能因此给 revision 填默认值，或在宿主侧猜测用户意图。目标验收缺少逐条证据是独立的业务校验问题，不因本次语法/契约反馈而自动解决。

## 本次修改

- 解码器保留原接受规则，增加 `StructuredOutputError`，区分 JSON / wire / command contract 阶段，附有限错误码和 schema 字段路径。
- 诊断路径只允许 schema 定义过的名称，未知键替换为 `<unknown>`，不记录值、提示词、模型原文或原始 JSON 解析异常。诊断遍历有深度/步数上限。
- 本地 OTel 增加白名单 `app.schema_stage`、`app.schema_issue`、`app.schema_path`。
- 仅在原有一次纠正中反馈具体错误，说明命令必填字段和跨分支 null 规则，要求从原输入/观察中取值，信息不足时沿允许的只读查询，不猜 ID 或 revision。
- 非协议异常不再被误当成可纠正的 schema 错误。原请求截止、纠正次数、业务权限/CAS/原子提交、模型配置均不变；不部署 Join。

## 验证与边界

真实模型条件：Codex CLI 0.162.1，主助理/委托 `deepseek-v4.1-flash-1017`，原 provider-default 思考；显式独立 profile 配置。后台仍 hy4/none，自动记忆学习关闭。每题独立 profile，题间串行、内部并发2，截止240秒、模型60秒、执行120秒、16步。两轮均预声明 failure-limit=6，以完整观察六题；评测器不追加纠正或重试。

## 修复轮结果：仍未达到可靠管家的标准

| 场景               | 只加诊断       | 增加字段纠正反馈   |
| ------------------ | -------------- | ------------------ |
| 并行等待和回答     | 协议失败       | 通过               |
| 含糊及定向取消     | 协议失败       | 原断言失败，见下节 |
| 目标依赖和暂停恢复 | 通过，108.5 秒 | 场景截止，240.2 秒 |
| 记忆更正和遗忘     | 通过           | 通过               |
| 重放恢复           | 通过           | 通过               |
| 无渠道不虚报       | 通过           | 通过               |

两轮原分数均为 **4/6**。诊断轮累计 219.3 秒，修复轮 372.9 秒。结构化拒绝尝试从 7 次变为 3 次，修复轮的三次均经原有一次纠正完成解码：一次多余 `maxParallel`、两次查询混入 `params.match`。样本很小、模型随机性及执行路径不同，不能据此证明修复提升总体通过率或降低时延，也不能把未完成整题追认为通过。

修复轮 Goal 的两次 `model-timeout exceeded 60000 ms` 实际是**整个 ReceptionPlanner 回合的共享截止**。`ReceptionCoordinator` 给整个模型/查询循环 60 秒，`modelRequest` 同时给单次模型交换最多60秒；内层被外层取消，不等于每个原生模型调用都耗时60秒。第一次失败前，原生生成约50.0秒，字段纠正约3.5秒，下一次生成约5.5秒即被剩余预算中断；第二次也是累计多轮后截止。后续报告重试放大了整题尾延迟，最终碰到240秒场景上限。机器 summary 将应用层 `Scenario deadline exceeded` 归为 failed，因此 summary.timeout=0 只表示没有触发进程组硬超时，不能解读成没有超时。

当前用户接待 schema 有26个 proposal 字段槽、序列化约20KB；报告 schema 约5.6KB。它们包含跨命令/查询的条件约束，平铺本身无法表达全部条件。字段反馈是诊断与恢复改进，未根治第一次生成负担。下一步宜收敛命令/查询契约的生成表达，并单独评估规划预算及查询轮次；不能只增加重试/放宽验收来提高分数。

两轮来源指纹分别为 `46c61f5ed6356d2d8c627bb67b2ce293dbd2fa430de04298977798b56a8a0d92`、`6a62245e96b0cc1a6a77840566a3d990c6322ddf7e8c939eec2ef985ad6a3245`；完整逐文件指纹在 plan。没有变更模型或授权范围。诊断轮后做了格式化，语义变更仅为协议纠正反馈。

这六题是合成工作场景。首次通过、最终通过、业务正确性和人工语义评阅分别记录，不能凭单轮通过宣称无人值守可靠，也不代表记忆系统综合能力。

## 额外发现：含糊取消断言混入了计划形状

修复轮 `ambiguous-cancel` 的失败为 `ambiguity-causes-no-write`，不是协议拒绝。完整记录显示助理返回 `clarify`，明确询问 TRIP-A 还是 DINNER-B，没有取消事件；两项等待中的工作仍保持 revision 1。

此前创建阶段，助理把每件短笔记拆成了一个三节点 Goal：问日期、发布笔记、报告。因此还存在四个依赖未满足的 queued 子任务。评测器的 `works.every(waiting_input && revision===1)` 把“所有工作必须在等待回答”混进了“含糊时不改变工作”的判断，导致此次断言失败。

本轮保留原始失败分数，未将整题追认为通过：后续定向取消/迟到答案/重启断言因提前退出没有运行。也不把它报告为误取消。后续应分别评估：短任务是否过度提升为 Goal，以及含糊指令前后工作/目标状态是否不变；无写入检查应比较前后快照，而非假设所有子工作状态一致。
