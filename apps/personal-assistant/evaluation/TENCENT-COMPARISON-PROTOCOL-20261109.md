# 腾讯两套记忆方案与本方案：受控小规模对照

2026-11-09。用户明确选择 Hy-Memory、TencentDB Agent Memory 与本方案三方对照。独立实验，不部署或重启 Join。

本轮运行：[固定计划](runs/tencent-memory-comparison-20261109-v2/plan.json)。初次发布结果前不根据分数改变提示词、选择题目、重试或调整检索。

## 固定项

- PersonaMem v1 32k，沿用已固定的数据与官方选项评分移植。一个已知回归人物6题；按固定种子独立选取两个新人物5题、6题，共17题。所有因果前缀与角色保持；新人物不按成绩、长度或类别重新抽取。
- 相同 reader：DeepSeek `deepseek-v4.1-flash-1017`，Codex 原生 Responses，provider 默认思考。相同后台：混元4 `hy4`，Codex 原生 Responses，reasoningEffort=none。
- 两套腾讯引擎共用本地 fastembed 0.9.1、量化 ONNX 多语 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`，384维，模型128 token输入截断。保留模型文件哈希。本方案保留当前词面读取能力，不为评测新增检索实现。
- 同一公共答题指令、只读回合协议、最多6次查询/7轮模型、初始上下文128000字节、查询每次12000/累计48000字节。初始记忆形态与可用查询契约按引擎真实能力表达，不伪装为同一种搜索语义。
- 每个引擎/人物新建独立存储。gold、类别、人物与数据集标识仅在父评测器；子进程只接收角色/正文及问题/选项。回答不回流为学习证据。
- 三方 memory 分支均禁止原始历史追读。controls与各memory引擎使用独立进程；完整历史/无历史两种control在其进程中各使用全新的同一reader原生线程；system背景各分支一致，只作为背景，不伪装为用户事实。
- 同一天的合成单调历史时间，不伪造数据集日期。每12个用户交流或因果检查点提交新增源材料；各引擎保留自己的内部拆批与处理策略。
- 每个引擎/人物900秒；每个人物controls独立300秒；原生模型单次调用最多120秒，原引擎阶段内部更短/更长的阶段预算和有限重试继续记实，TDB多工具阶段最多180秒/20次工具。不是相同总调用次数或相同推理费用实验。

## 原生实现与适配

- 本方案直接调用既有 `evaluateMemorySystem`，生产提炼、复核、存储、初始视图和查询均不改。仅评测读取循环支持 await，以接收异步外部引擎查询。
- Hy-Memory 固定 `9737431cf8965124b115f0e26cb0ff1e5cafa323`，pro + hybrid，图关闭，local rerank关闭，agentic改写关闭；通过 SDK add/search，显式限定派生事实/摘要/基础资料层，单独取得基础画像，禁止RAW层。
- TencentDB 固定 `2002196f2d7c22ea267cfcaf67c5a6fa861df681`，本地SQLite/FTS5 +同一embedding；调用原 capture、L1 runner、L2/L3 runner及 auto-recall。离线在读取前排空派生任务，L3触发条件沿原实现；不把该排空耗时冒充在线默认实时行为。
- Hy与TDB L1通过只转输文本的本地OpenAI兼容接口调用同一个原生Codex后台。TDB L2/L3使用窄LLMRunner适配，Codex原生动态工具调用原版sandbox文件工具；生成副本只在原工具模块末尾增加导出，不修改原记忆策略、提示词或文件操作。
- 初始回忆：本方案沿当前画像/近期视图，Hy沿search，TDB沿auto-recall。这是各方案的组成部分；不宣称是只改变某一检索算法的因果消融。
- 各自请求的temperature/max_tokens会记录，但原生Codex传输没有将这些SDK字段当作相同的实际硬上限。不宣称确定性生成。统一的是实际模型、原生reasoning设置、读协议及外部截止。

## 预检与运行分开

第一版预跑在尚未计分腾讯分支时发现调用方投影会把SDK诊断与重复统计事实注入reader，因此中断保留；v2只将SDK正式记忆/画像上下文送入reader，原始响应另存。v2运行版本的种子随版本号变化，最终独立抽样为5题和6题；在新人物读取与任何腾讯题目计分前即固定，未按分数挑选/替换人物。两次计划和中断记录均保留，首版不与正式v2合并或挑选答案。

预检发现TDB工具转译格式下画像任务循环/超时，保留setup-v3失败；正式运行前改为原生动态工具，setup-v4完成场景/画像写入与召回。预检不计分，不混入正式准备开销。SDK文本桥的通用工具封装代码不被正式TDB L2/L3使用。

官方依赖在隔离目录安装，不启动常驻产品服务。SDK尝试向 `/data/log` 写文件时报权限失败，进程stderr由评测器完整收集；不把该日志路径警告当成记忆内容失败。

## 读数边界

首先分别报告已知回归6题与未见人物11题，再看合计。保留准备失败、模型超时、未启动题目、格式失败；不将未完成题当作已回答错误来伪造完整准确率。报告每阶段调用/token、准备时间、问答时间及工具调用。没有价格表时金额留空，embedding成本单独标为本地CPU。

本轮只是一遍、三个独立人物的小规模组件对照，既不等于厂商原生最佳配置，也不能直接与官网PersonaMem或其他版本的百分比分数比较。不对统计显著性或长期多用户可用性作结论。

## 恢复与适配审计补充（运行后追加，非原预声明）

用户恢复后台服务后，v3 从干净存储重跑；保留 v2 的 17 题、种子、模型设置和 embedding。就绪检查通过，原生后台仍为 `hy4 / none`，没有换模型。v3 的逐文件源码另行归档；旧402运行不合并计分。两个独立抽取人物在 v2 中已有部分暴露，不能称为从未看过的盲测。

源码审计确认 Hy 的默认 Chroma 后端 `keyword_search` 返回空列表，因此本配置虽选择 hybrid reader，实际为 dense-only；不能称为完整 BM25+向量混合检索。

v3 运行中发现腾讯云适配边界有三类问题：一次 capture 写入约24条消息会触发原生仅按毫秒游标与20行查询上限的边界，原生提炼又只取最后10条新消息加5条背景；追问搜索错误地复用 auto-recall，重复附带画像而超过12000字节；场景路径校验没有对齐实际 profile 目录。v3 的结果与输入覆盖重建保留，不把这些失败归为记忆算法质量差。

为此增加独立 `v4-tdb-correction` 补跑：外层仍为每12个用户交流投递，适配内部通过最多10条消息的原生 capture 调用逐批排空；同时处理原生 `hasMore` 和 `hasFullBacklog`。初始仍为原 auto-recall，追问改用原 `executeMemorySearch + formatSearchResponse`；场景读取接受索引返回的绝对路径，但只能落在该隔离 profile 的 canonical `scene_blocks` 目录，保留分页/返回预算。提炼、复核、画像提示词与更新算法均未修改。

补跑前通过无付费调用的原生流水线契约检查：同一外层批次26条消息全部进入L1输入；追问走独立搜索；绝对场景文件可读，越界和负偏移拒绝。真实运行结束再用原生日志/SQLite重建实际输入覆盖，不以该fixture代替模型质量。

v4 仅重跑腾讯云全部17题，并明确复用 v3 的本方案、Hy 与两种control作为参考，避免重复付费；**不是同时全新三方重跑**。不根据题目对错修改提示词、gold、阈值或选题。修正是多项适配的合并补跑，不能从前后成绩变化证明某一项修正的单变量因果收益，也不能排除随机生成差异。
