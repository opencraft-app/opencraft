## 真模型完成的链路

1. 一条用户消息经主助理 batch 创建两项独立工作，各自拥有 Execution。
2. A 用 ask_user 等待范围，B 同时发布短笔记并完成；概览计数为 waiting_input=1、completed=1。
3. 关闭并重新打开同一 profile。上述状态保留。
4. 用户通过定向 say 回答 A 的问题。主模型返回 answer，原 Work/revision 和原生线程保持不变；笔记实际包含 COORD-A 与“本周”。
5. 定向修改 B，主模型返回 amend；Work ID 保持，revision 从 1 到 2，使用新原生线程执行。A 没有被修改。
6. 用户要求状态汇总，主模型只读查询真实工作后回复。最终仍只有两项工作，均 completed，没有待答问题。汇总区分了本地 mailbox 接受和用户已读。

共三份实际笔记，分别属于 A、B 原版本、B 新版本。B 修改保留了原完成检查，因此新笔记同时保留原 literal 要求；没有通过删除旧检查伪造完成。已观察总 token 为 111,254，含缓存，价格未知。这里不是公开 benchmark，不计算准确率或宣称长期可靠性。

## 接待输出的诊断与修复

只读线请求观察确认，完整指令已到达模型；模型推理准备生成两项 delegate，最终结构化消息却为无关 routine.create 占位命令。对同一份合成请求做独立 wire 重放：只保留 batch 的对象联合仍产生错误 project.leave；改为普通 JSON 对象输出则得到两项正确委托；平铺 nullable record 同样产生正确委托。

这是当前端点与复杂对象联合约束生成路径的失配证据，不能据此断言提供方内部根因、Codex 调度器有问题或所有模型均如此。诊断重放不执行任何提议，也没有改写失败 profile。原始请求正文不含认证头，保留在[诊断目录](../evidence/work-coordination-20261110/)。

最终实现将接待的**生成线格式**与**命令契约**分开：生成使用平铺 record；解码仍严格验证原 kind 分支，跨分支非空字段、未知字段、缺少必填项全部拒绝，随后继续应用层归属和 CAS 校验。旧 wire 兼容读取，记忆提炼/复核/摘要协议不变。没有靠正文关键词强制选择 delegate，也没有对错误提议做静默修复。

## 验证边界

多工作专项七项覆盖全量计数与首屏截断、分页/范围隔离、定向问题首屏之外、重开、错误目标/旧版本、原子回滚、系统报告上下文，以及真实 CLI 和 Pi 同会话恢复。原生 schema 测试增加平铺记录往返、跨分支字段拒绝和真实 Codex app-server 协议。

机制测试使用真实 SQLite、文件、socket 和原生进程，但模型替身不计入真模型质量。本次真模型只有一个明确、有界场景；自动记忆集成、含糊指代、任意复杂并发、用户优先级、依赖 DAG、运行中线程直接追加消息、外部渠道及长期运行不在通过范围。

最终源码 `11855b0`：全量回归 360/360、评测机制回归 35/35，均无 skip；160 个模块语法检查及额外探针语法检查通过，格式检查通过（不是 TypeScript 类型检查）。相关文档本地链接检查通过。首版 `e10ddee` 的 358 项回归也通过，但其真模型验收失败，说明机制测试不能代替模型验收。

本机没有 npm 可执行文件，因此测试直接运行 package.json 中等价的 Node 命令，没有因此跳过测试。日志及机器回执见[收尾证据](../evidence/work-coordination-20261110/validation.json)。原始和归档 profile、诊断文件共 537 个文件扫描未发现提供方密钥原文；没有修改权威凭据文件。
