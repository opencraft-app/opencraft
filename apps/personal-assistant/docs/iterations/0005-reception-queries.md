日期：2026-11-02。提出人身份未确认。用户原话：「可以搞起来，但是你必须要注意，本身功能模块要高内聚低耦合」。本轮继续独立runner，落实路线图第二项的有界查询；未集成或部署Join。

## 职责、依赖与状态归属

| 组件                               | 单一职责                                                          | 只依赖                                                      | 不拥有                               |
| ---------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------ |
| ReceptionContextBuilder            | 按原输入锚点构建有限初始上下文                                    | 历史读取port、查询初始投影                                  | 命令提交、执行、数据库驱动           |
| ReceptionQueries / 每次查询session | 解析允许的只读请求、投影结果、分页、限制返回量并生成真实读取trace | SELECT-only读取port、资料只读port、ScopePolicy只读权限facet | 工作/记忆/交付修改权、原生工具任务   |
| ReceptionPlanner                   | 反复交换模型建议与只读观察，最后返回待提交建议                    | 模型port、查询port                                          | repository、事务、写入服务、运行进程 |
| ReceptionService                   | 持久接收和最终命令/回执提交；记录host产生的trace                  | 既有输入/历史/业务owner、上下文builder                      | 模型网络请求或查询循环实现           |
| SqliteReceptionReadModel           | 明确列集合和关联条件的SELECT投影                                  | 私有SQLite连接                                              | 事务/连接生命周期、命令方法          |
| ScopePolicy                        | 原输入资料范围捕获、当前范围与实际binding校验                     | 助理身份、当前能力配置、纯领域grant                         | 模型建议或资料正文                   |

Query模块只接收ScopePolicy的forTurn/permits读取facet，不接收整个权限服务或应用对象。真实SQLite驱动为适配器私有字段，不向query模块暴露；资料port只给reference/list/read。fixture单独置于模型adapter，避免继续往生产模型适配器堆固定分支。

这些是实际代码边界，不能理解为对进程内任意恶意JS的安全沙箱。模型接收的是可序列化数据，没有对象句柄或方法调用权。

## 查询与提交的路径

`用户输入持久化 + 捕获query grant → 有限初始上下文 → 模型返回query → 只读port返回观察 → 模型最终建议 → ReceptionService事务提交 → 原业务owner校验并执行`

支持works.list、work.get、questions.list、memory.get、materials.list、material.read。工作和问题仅限原主会话已关联事项；未知工作与会话外工作返回相同不可用结果。记忆读取保留墓碑revision，删除正文不召回。资料只使用接收时配置的资源ID与binding，拒绝越界、链接和后续目录替换。

接待随后创建后台工作时，ScopePolicy也沿用捕获的原资料范围；不能通过“先接待、再委托后台”间接取得新根目录。原范围与当前binding不一致则拒绝提交。迁移前没有query grant的旧消息只获得元数据查询；其后续委托也不会自动获得新资料源。

每条消息最多6次查询、7轮模型调用，单响应12,000 UTF-8字节，累计查询响应48,000字节；列表最多12项，单次正文最多2,000个JavaScript文本单位，初始上下文最多128,000字节。分页/截断明确标记，文件adapter仍限制64KiB、文本格式与前100项目录清单；sourceListingMayBeCapped不承诺穷尽全目录。

上述是接待协议的局部界限，不是完整token/金额预算，也没有据此宣称所有provider都满足墙钟期限。完整执行预算仍在后续。

查询是无业务写入的观察，不持锁等待模型。observedAt和资料SHA256说明读取时的事实；命令提交仍检查最新revision、会话归属及权限，不能把刚查询过当作乐观锁通过。查询失败不会转换成“没有数据”或“已成功”。

## 恢复、trace和迁移

查询trace由宿主生成，包含请求、时间、结果等级、返回量及必要来源/哈希，不保存整份资料正文。ReceptionService随最终decision_json提交；规划失败、命令CAS失败时也保留已产生的trace。模型提供的queries字段不作为证明接受。

进程在查询后、最终事务前退出，恢复只会重新查询和推理；尚未提交的命令没有发生。重新读取可以看到改变后的资料，最终trace记录本次实际使用的哈希，最终回复仍按输入身份只提交一次。

schema4→5仅新增reception.query_scope_json及历史窗口索引。旧任务/条件/快照/接收身份不变，不给旧接待填造新授权。历史上下文通过稳定user message ID定位，再读锚点之前的有限窗口，修复旧输入被1000条后续消息挤出后找不到原文的问题。
