现状与风险

现状：Agent 能弄坏整台 VM

每个用户一台 VM；Agent、工具、系统配置、连接器、用户数据都在同一块系统盘上，Agent 有 root。

Agent 和它要保护的东西在同一个故障域里——自己弄坏自己，就没人能修。
改进思路

改进思路：缩小破坏范围，坏了能恢复

先把 VM 里的东西分成三类，再各自安排去处；具体怎么落地，见后面两套方案。

  • 核心一 · 缩小破坏范围：Hermes 配置和外部服务凭证交给控制面；VM 里只放平台签发、可随时更换的凭证
  • 核心二 · 坏了能恢复：用户数据独立存放并做快照；环境坏了就重建，再挂回用户盘、按账本补装软件
方案一 · 参考 Meta Muse

方案一：单 VM + Sandbox 已实测

把 Agent 关进 Sandbox；用户数据放在一块可以换机的用户数据盘上。

  • 破坏范围收缩到 Sandbox，宿主层 Agent 碰不到；用户盘挂在 Sandbox 里，Agent 能读写，误删靠快照找回（活跃期快照建设中）
  • Sandbox 重建后按软件账本补装软件（参考 Muse 的做法，尚未实测）；账本覆盖不到的部分由 Agent 自行恢复，据公开资料同类产品也可能丢这部分内容
  • 可扩展 · 闲置回收：同一套挂盘机制，也能释放闲置 VM、保留用户盘
第三方架构为公开资料与我们的理解
方案二 · 参考 Manus

方案二：大脑与工作台分离 已实测

Agent Loop 跑在 Runtime VM（程序与配置只读，会话和记忆写在数据盘），借助 Hermes 的 SSH 能力，远程操作可替换的 Workspace VM。

  • 已实测：借助 Hermes 的 SSH 能力分开大脑和工作台；工作台坏了大脑照常在线，大脑坏了也能换机恢复
  • 两类 VM + 远程连接，架构更复杂；其他种类 Agent 要接入远程访问工具，适配中
第三方架构为公开资料与我们的理解
预热（Preboot）· 加速故障恢复

预热：换机恢复，目标最快约 10 秒

待命 VM 平时就起好 Sandbox 和 Hermes（无用户身份）；出故障换机时，只需挂盘、下发平台凭证、加载用户会话。

  • 方案一：用户 VM 坏了，从待命池取一台已启动 Hermes 的 VM，挂上用户盘、下发平台凭证、加载用户会话即可用
  • 方案二：大脑（Runtime VM）也可能故障，同样可以换一台预热好的 Runtime
“目标”尚无实测，不代表已达成；分段数字为 POC 实测
两套方案对比

两套方案对比：各有取舍

两套都把 Agent 的破坏范围收小了；区别在架构复杂度和落地成本。

建在方案一之上

再往上一层：管家 Agent 已跑通 POC

执行 Agent 负责干活，管家负责让事情有交代。

  • 一个沟通入口：用户只跟管家说，不必反复交代、追问多个执行 Agent
  • 持续负责：管家记录事项、跟进阻塞、汇总结果；执行 Agent 中断或更换，事情仍有人接着负责（工作簿为调研设计，未实测）
  • 已跑通（Hermes）：多个执行 Agent 同时干活，任何一个坏了，都不影响整体对话
