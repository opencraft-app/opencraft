# 2026-07-17 BrainStorm：Hermes 看板与自动任务场景化

> 来源：2026-07-17 LightVela 脑暴会逐字稿。本文用于沉淀产品探索思路，不直接等同于已排期需求。

## 总览

本次脑暴主要围绕两个方向展开：

1. Hermes 看板能力是否值得被 LightVela 产品化吸收。
2. 自动任务如何从“功能入口”进一步演进为更容易被用户理解和使用的场景化体验。

整体共识是：Hermes 看板的工程化能力值得研究，但现阶段不宜直接搬运；LightVela 更应该先从团队自用、真实用户场景和少量高确定性自动任务入手，验证场景价值后再决定是否产品化。

## 方向一：Hermes 看板与多 Agent 协作

### 观察到的能力

Hermes 看板本质上是对多 Agent 协作过程的可视化呈现，核心能力包括：

- 通过 Profile 定义不同角色的 Agent，例如 researcher、writer。
- 将一个总任务自动拆解为多个子任务，并分配给不同 Agent。
- 通过看板呈现任务状态，例如 to do、ready、in progress、done。
- 支持 auto/manual 两种推进方式。
- 支持任务上下游依赖，后续任务会等待前置任务完成后再执行。
- 所有任务状态、Profile、上下文会持久化到本地数据库，支持中断后继续执行。
- 总任务会在所有子任务完成后再次执行整体审查，类似最终验收。

### 体验判断

正向价值：

- 多 Agent 协作过程可视化，用户能看到任务如何被拆解、分配、执行和验收。
- 对调研报告、内容创作、资料整理等复杂任务有潜在价值。
- 不依赖 Chat 也能闭环完成任务，提供了另一种 Agent 使用方式。
- 工程化机制较完整，包含任务拆解、调度、状态流转、持久化和最终验收。

主要问题：

- 概念暴露过多，包括 Profile、Agent、auto/manual、目录配置、任务状态等，对普通用户门槛较高。
- 场景案例偏开发者和极客，不够面向泛用户。
- 一些关键边界不够友好，例如输出目录未填时没有及时拦截，而是在执行中后段才阻塞。
- 如果直接放到 LightVela，可能会变成“功能很强但用户不知道怎么用”的复杂入口。

### 对 LightVela 的启发

LightVela 不应直接复制 Hermes 看板，而应先吸收其中的产品理念：

- 把复杂 Agent 执行过程变得可见，而不是只给用户一个黑盒结果。
- 让用户围绕任务目标启动流程，而不是先理解一堆底层概念。
- 将多 Agent 协作封装在场景背后，减少 Profile、目录、状态流转等配置暴露。
- 优先验证“多 Agent 是否真的比单 Agent 产出更好”，再决定是否做成产品能力。

### 初步结论

现阶段不建议马上把 Hermes 看板搬到 LightVela。

更合理的路径是：

1. 团队内部先在真实工作中使用 Hermes 看板，例如竞品调研、增长策略分析、长文内容生产。
2. 对比单 Agent 和多 Agent 在同一任务下的产出质量、稳定性和成本。
3. 找到确实因为多 Agent 协作而变好的场景，再抽象为 LightVela 面向用户的产品形态。
4. 如果后续产品化，应做强封装，只让用户填写任务目标和少量必要信息。

## 方向二：自动任务场景化

### 当前探索

自动任务库当前设想包括：

- 未登录用户也能看到任务库，点击使用时再引导登录和开通 Agent。
- 任务分为一次性任务和长期任务。
- 提供社区共建、投票、榜单等轻量互动能力，用于理解用户需求。
- 场景示例包括情绪记录、背古诗、喝水提醒、资料链接提醒等。
- 用户配置后，可在“我的任务”中查看已生效和最近执行的任务。

### 主要分歧与风险

当前任务库的页面和场景丰富度已经有雏形，但距离可上线状态还有差距：

- 场景数量多不等于可用价值强，用户未必会选择或持续使用。
- 自动任务底层目前仍偏“定时”，缺少事件触发等更丰富的基础能力。
- 任务可用性不能只看一次测试跑通，还要看是否能在真实环境中持续稳定运行。
- 某些任务在一个 Agent 或一台机器上可跑通，换环境后可能失败。
- 现有场景需要进一步筛选，不能把大量未经验证的模板一次性暴露给用户。

### 建议路径

短期先做两条线：

1. 基础能力补强：
   - 解决用户切换模型后自动任务失效的问题。
   - 研究 Hermes 原生事件触发机制，确认 LightVela 是否能暴露为控制台能力。
   - 探索自动任务绑定技能，让任务执行更稳定。

2. 场景小步验证：
   - 先选 3-4 个最确定、最容易跑通、团队自己也会用的场景。
   - 不只做一次性测试，而是让团队成员连续使用一段时间验证真实效果。
   - 从团队自用和线上用户真实任务中收集场景，而不是只靠 AI 生成模板。
   - 通过首页或概览页提供场景化入口，让用户直接感知“我能用它做什么”。

### 可优先验证的场景标准

适合优先进入第一版的自动任务场景，应满足：

- 用户目标明确，不需要复杂解释。
- 输入字段少，能快速完成配置。
- 执行结果容易被用户感知。
- 对定时能力依赖明确，能体现云端长期运行价值。
- 团队内部有人真实连续使用过，并验证稳定性。

## 后续待研究问题

### Hermes 看板方向

- 多 Agent 在调研、写作、运营分析等任务上，是否显著优于单 Agent？
- Hermes 看板是否有可复用 API，还是只能参考其实现重新产品化？
- 如果 LightVela 做类似能力，入口应放在独立页面、任务页，还是场景化流程中？
- 哪些概念必须隐藏，哪些状态应该保留给用户感知？

### 自动任务方向

- Hermes 事件触发机制具体如何工作，能否在 LightVela 控制台中稳定暴露？
- 切换模型导致任务失效的问题，应通过 Hermes 机制修复，还是通过 LightVela 层做兜底？
- 第一批 3-4 个场景具体选哪些，谁负责连续使用验证？
- 是否需要建立一个“团队自用自动任务清单”，持续反哺产品场景库？
