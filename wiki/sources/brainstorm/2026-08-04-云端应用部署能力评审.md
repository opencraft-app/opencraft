# 2026-08-04 BrainStorm：云端应用部署能力评审

> 来源：2026-08-04 LightVela 脑暴/评审会逐字稿。本文用于沉淀“云端应用部署”能力的产品形态、技术路径、配额设计、成本估算，以及会议中暴露的计费与国际站协议风险，不直接等同于已排期需求。

## 总览

本次讨论聚焦 LightVela 的一个新场景方向：让云端 Agent 帮用户部署和托管应用。

核心背景是：近期在内测群、工作群和付费用户沟通中，多次出现“把 AI 写的代码部署到云端、让别人能访问”的诉求。但当前 LightVela 实例没有公网 IP，防火墙也不对用户开放，大多数用户无法自行跑通部署链路。

初步方案是：复用腾讯云成熟能力，优先接入 TCB 静态网站托管，通过 Skill + Agent 对话完成部署。用户只感知“让 Agent 帮我部署网站”，底层由 LightVela 大账号封装 TCB API，部署完成后返回可访问域名。

会议形成的阶段判断：

1. 该场景有真实用户需求，且与 LightVela “云端长期运行 / 个人智能管家”方向契合。
2. 一期优先支持静态网页托管，先验证用户是否愿意使用和持续迭代。
3. 后续可扩展到 DB、应用预览、二次编辑、数据统计、多模态作品等能力。
4. 需要明确套餐配额、成本、风控、用户隔离和后续商业化口径。
5. 国际站计费和服务条款仍有外部风险，需要单独跟进。

## 方向一：云端应用部署能力

### 用户需求背景

已观察到的用户诉求：

- 希望把 AI 生成的代码部署到云端。
- 希望生成一个别人可以访问的网页或应用。
- 希望由 Agent 帮忙处理环境和部署，而不是自己管理服务器。
- 部分高阶用户会自行把 LightVela 实例流量转发到其他有公网 IP 的服务器，但大多数用户做不到。

当前阻塞：

- LightVela 实例没有对用户暴露公网 IP。
- 防火墙和网络配置不面向用户开放。
- 用户把 LightVela 当作“可部署服务的云端 Agent”时，容易在最后一步卡住。

产品判断：

- “Agent 帮我部署应用”是云端 Agent 的天然场景。
- 与其让用户直接管理服务器，不如复用成熟云产品，通过 Agent 封装成更低门槛的能力。
- 该能力可以作为 LightVela 与普通云主机、普通 Agent Chat 的差异化能力之一。

### 一期产品形态

一期目标是跑通最小闭环：

1. 用户在对话中提出部署需求，例如“帮我做一个生日祝福网页并部署”。
2. Agent 生成静态网站代码。
3. Agent 调用 LightVela 预置 Skill。
4. Skill 将构建产物上传到 TCB 静态网站托管。
5. 部署完成后返回一个可访问域名。
6. 用户可以在后台的作品/网站列表中看到已部署项目。

触发方式包括：

- 从零生成网站并部署。
- 上传已有网站项目文件，由 Agent 进行部署。

底层能力：

- 一期选用 TCB 静态网站托管。
- 使用 LightVela 统一服务和大账号封装底层 API。
- 用户不需要自行开通 TCB，不需要管理腾讯云账号和资源。

产品入口：

- 当前 Demo 暂时有“我的网站”入口。
- 后续更倾向命名为“作品”，因为未来可能不仅包含网站，还可能包含图片、视频、多模态生成物等。

### Demo 状态

Demo 已实现的能力：

- 后台出现网站/作品入口。
- 根据套餐展示站点数、流量、存储空间等配额概念。
- Agent 可尝试生成静态网站并调用部署流程。
- 部署完成后，列表中能看到网站记录。
- 后端保存网站数据，后续理论上可支持继续修改并重新部署。
- 测试环境已有测试账号，团队可体验操作流程。

当前 Demo 暴露的问题：

- 部分模型不会稳定触发 Skill，演示中出现过 Agent Chat 插件卡住、模型未调用 Skill 的情况。
- 需要使用现网用量较高的模型（如 DeepSeek V4 Flash）验证真实成功率。
- 当前前端仍有临时入口和未完成交互。
- 返回域名前缀较长，后续可能需要短链或自定义域名策略。

### 存量用户与新用户安装

Skill 分发设想：

- 新建用户默认具备该 TCB 部署 Skill。
- 存量用户通过下发方式补安装。

需要进一步确认：

- Skill 安装失败或调用失败时如何提示。
- 不同模型对 Skill 调用的成功率。
- 存量用户实例状态不一致时，如何做安全下发和回滚。

## 方向二：交互与产品边界

### 对话入口与作品管理

当前倾向：

- 创建和部署动作主要在对话中完成。
- 管理和查看动作放到后台“作品”入口。

作品入口可以承载：

- 网站列表。
- 访问域名。
- 套餐额度。
- 站点数量。
- 后续可能的访问数据、编辑入口、重新部署入口。

需要继续设计的问题：

- 用户如何对已有网站发起修改。
- Agent 如何识别用户所说的“修改 birthday website”对应哪个站点。
- 是否需要在对话框中提供快速选择已创建应用的能力。
- 是否在作品页内提供“继续编辑 / 重新部署”的入口。

### 与 Agent Chat / TCB 原生能力的关系

会议中对比了 Agent Chat 侧已有规划：

- Agent Chat 也曾规划接入 TCB。
- Agent Chat 更像通过专家角色承载，例如“程序员专家”上下文更干净。
- Agent Chat 方案可能需要用户自行授权或创建免费环境。

LightVela 当前方案的差异：

- 使用 LightVela 大账号封装，不让用户感知 TCB 开通流程。
- 用户只需要和自己的 Agent 对话。
- 能作为套餐权益被 LightVela 统一包装。
- 更符合“个人云端 Agent 帮我完成事情”的产品心智。

潜在问题：

- 如果长期放在通用对话中，后续二次编辑、预览、选择应用等细节可能不够顺滑。
- 如果做重，就需要在作品页或专门场景中补交互，而不是完全依赖 Agent Chat SDK。

### 能力演进路径

会议中形成的粗略阶段：

1. 一期：静态网页部署。
2. 二期：增加 DB 能力，支持更复杂的应用。
3. 三期：考虑应用预览、二次编辑、访问数据统计、基于已有应用继续修改等能力。

关于 DB：

- TCB 本身具备 DB 能力。
- 从底层调用看，接入工作量可能与静态托管差异不大。
- 但产品体验、用户选择、成本和安全边界需要更多设计。

关于数据统计：

- 如果要做成完整网站托管能力，用户会关心 PV/UV、访问来源、运行状态等数据。
- 一期暂不做重，但后续可能成为作品管理页的重要能力。

## 方向三：配额与成本设计

### 配额项

当前主要考虑三个限制：

- 托管应用数。
- 项目空间。
- 月度流量。

其中：

- 项目空间指上传网页项目的总大小。
- TCB 自身对单个文件大小有限制，当前约 50MB。
- 月度流量是主要成本项。

### 套餐配额草案

当前仅有启航、巡游两档草案：

| 套餐 | 托管应用数 | 项目空间 | 月度流量 |
| --- | --- | --- | --- |
| 启航 | 1 个 | 5GB | 10GB |
| 巡游 | 3 个 | 20GB | 25GB |

产品处理原则：

- 用户优先感知“可部署几个网页 / 应用”。
- 存储空间和流量可在套餐权益和文档中说明。
- 一期内测阶段可先不做非常重的底层硬限制，但后端需要能控制用户限额。

### 成本估算

按 TCB 刊例价粗估：

- 启航：1 个项目 + 5GB 空间 + 10GB 流量，约 2.69 元/月。
- 巡游：3 个项目 + 20GB 空间 + 25GB 流量，约 7.6 元/月。

实际判断：

- LightVela 通过套餐形式采购 TCB 能力，实际成本可能更低。
- TCB 套餐本身包含一定积分，可用于抵扣。
- 如果用户流量较低，实际成本会明显低于上限估算。

大账号资源设计：

- 先在大账号内采购多个 TCB 套餐。
- LightVela 后端统一调度和抵扣。
- 避免短时间内单个套餐用量打满。

## 方向四：上线前需要补齐的事项

### 后端与产品设计

上线前需要刷新：

- 后端限额设计。
- 大账号资源调度方案。
- 用户与项目的映射关系。
- Skill 调用和错误处理。
- 存量用户 Skill 下发机制。
- 新用户默认安装机制。
- 套餐权益展示。
- 作品列表和域名展示。

### 前端与交互

需要补齐：

- “我的网站”入口命名和定位，倾向改成“作品”。
- 作品列表基础交互。
- 额度展示。
- 部署成功后的反馈。
- 修改/重新部署路径。
- 如果一期不做重，需要明确哪些是后续能力，避免用户误解。

### 测试与评审

下一步节奏：

- 基于 Demo 做后端和用户面交互调整。
- 调整完成后再拉团队做上线前评审。
- 上线前重点走查：
  - 不同模型是否能稳定触发 Skill。
  - 用户上传项目是否能正确部署。
  - 部署失败时是否有清晰提示。
  - 配额耗尽时如何提示。
  - 存量用户 Skill 下发是否稳定。
  - 成本和用量是否可观测。

## 额外风险一：计费接入方式争议

会议后半段同步了计费风险：

1. AI 积分包单独售卖可能不能继续按包年包月方式走流程，而需要走计量计费接入。
2. 国内站和国际站的 AI 积分包都可能受影响。
3. WorkBuddy、MiiOra 等已有成熟方案，可作为参考，因此该风险相对可控。
4. 更大的争议是：有计费同学提出常规套餐也要按计量方式结算。

当前判断：

- AI 积分包走计量计费可以接受，需要尽快对齐成熟方案。
- 常规套餐也改成计量结算，LightVela 侧暂时不能接受，需要继续和计费/财务侧讨论。
- 昨日会计侧曾明确常规套餐可先按市场抵扣方式推进，今日又出现相反意见，需要重新拉齐口径。

后续动作：

- walkercao 继续和计费、财务对齐。
- 优先确保国际站支付和套餐上线不被“常规套餐计量化”卡住。

## 额外风险二：国际站服务条款跳转

当前发现：

- 国际站隐私协议已单独放了一份。
- 但服务条款目前仍跳到国内站 / Lighthouse 相关文档，体验和合规都不合理。

处理建议：

- 至少先改到国际站文档。
- 如果暂时没有 LightVela 国际站专属服务条款，可先跳到腾讯云国际站统一条款。
