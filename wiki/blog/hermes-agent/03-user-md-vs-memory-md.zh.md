# 为什么 Hermes Agent 要把记忆分成两类？USER.md 与 MEMORY.md 的职责

在 Hermes Agent 里，最容易让人搞混的两个文件是：

- **USER.md**
- **MEMORY.md**

乍一看它们都在"记东西"，都在"关于你"，但真正上手用一段时间就会发现：**如果把它们合成一份，整个 Agent 会变得又啰嗦又不聪明。**

为什么？我们从各自的定位开始讲。

## 一、USER.md：一份"关于你是谁"的画像

USER.md 的定位是 **持久的、结构化的用户画像**。你可以把它理解成 Agent 心里那份"关于你"的档案卡：

- 姓名 / 称呼
- 角色 / 职业
- 常用技术栈、工具链
- 沟通偏好（简洁 vs 详细、先结论 vs 先分析）
- 长期目标 / 关注领域
- 团队与协作关系

它的两个关键特征：

1. **稳定**：这里的内容变化频率极低。你不会每周换一个职业，也不会每天换一种沟通风格。
2. **默认加载**：每次会话启动，USER.md 都会**整份**被喂给模型，作为对话的底色。

因为要"每次都加载"，USER.md 必须**短、准、结构化**。它不适合放"我们上周聊过的那个 bug"，那会污染整份画像。

## 二、MEMORY.md：一份"我们一起经历了什么"的档案

MEMORY.md（以及背后的 `memories/` 目录）承担的是**事实性记忆**：

- 具体发生过的事件
- 得出过的结论、做出过的决定
- 用户明确要 Agent 记住的知识点
- 项目相关的上下文（这个 repo 用什么框架、CI 走哪条流水线）
- 之前踩过的坑与解决方案

它的特点正好和 USER.md 相反：

1. **易变**：随会话增长，条目会不断新增、更新、淘汰。
2. **按需召回**：不是每次都整份加载，而是通过全文索引 / 摘要 / 语义匹配，**按当前话题命中相关片段**。

MEMORY.md 更像一个"日志 + 备忘录"，规模会随时间增长；USER.md 更像一张"名片 + 使用说明"，本身要控制在小而稳定的范围。

## 三、为什么不能合成一份？

有人会想："都是记东西，为什么不合起来？"三个原因。

### 1. 加载策略不同

USER.md **每次必载**，MEMORY.md **按需召回**。合并后你面临两难：

- 全部每次载入 → context 被大量历史事实撑爆，token 成本飙升。
- 全部按需召回 → Agent 常常"想不起你是谁"，因为画像没命中关键词。

### 2. 更新策略不同

USER.md 的更新逻辑是"**编辑同一段**"：新版本覆盖旧版本，保证画像自洽。  
MEMORY.md 的更新逻辑是"**追加条目 + 老条目降权**"：历史事件不能被凭空抹掉，但可以被标记为过时。

这两种更新策略混在一起，很容易把画像写成日记，或者把日记写成画像。

### 3. 用户体验不同

用户会问："Agent 关于我有什么印象？" —— 想看的是 USER.md。  
用户会问："上次我们决定用哪个方案来着？" —— 想找的是 MEMORY.md 里的具体条目。

两类信息一旦搅在一起，前端就没法给用户提供"记忆管理"这类清晰的产品能力。

## 四、一个具体的例子

假设你告诉 Agent：

> "我叫 Jasmin，是一名前端工程师，喜欢结论先行的沟通风格。最近在做 mono2 项目的国际站，用 Next.js。上周我们把 hero 区改成了动态渐变。"

一个训练良好的 Hermes Agent 会做这样的拆分：

**写入 USER.md：**
```md
## Identity
- Name: Jasmin
- Role: 前端工程师

## Preferences
- 沟通风格：结论先行
- 常用技术栈：Next.js
```

**写入 MEMORY.md：**
```md
- [2026-07-30] mono2 项目：国际站 hero 区改为动态渐变。
- 相关项目：mono2 / 国际站 (global region)
```

看到区别没？"你是什么样的人"进画像，"我们一起做了什么"进档案。**分开写，才能各自演化。**

## 五、这对产品意味着什么？

对 Agent 产品而言，USER.md / MEMORY.md 的分层不只是工程细节，它决定了三件事：

1. **能不能给用户看"你对我的印象"** —— 需要一份稳定、可读、可编辑的画像。
2. **能不能长期不失忆** —— 需要一份可增长、可召回的事实档案。
3. **成本能不能被约束** —— 分层加载才能既"记得你是谁"又不烧掉一整个 context。

## 六、LightVela 是怎么做的？

LightVela 内部的 Agent 记忆体系，借鉴的正是这种分层思路，但做了两点产品化的落地：

- **画像层可视化**：用户能在界面上直接看到"Agent 记得我的哪些画像"、"这些画像来自哪次对话"，并支持一键修正。画像不再是黑盒。
- **事实层可组织**：事实记忆不只是一堆条目，而是能被打上项目、任务、时间等标签，方便召回与清理。团队场景下还能把"团队记忆"和"个人记忆"分层管理。

换句话说：**Hermes 给了"分层记忆"的工程蓝本，LightVela 想把它做成每个人都用得上的产品体验。**

## 小结

- USER.md：稳定、结构化、每次必载的**用户画像**。
- MEMORY.md：可增长、按需召回的**事实档案**。
- 二者不能合并，因为**加载策略、更新策略、产品语义**都不同。
- 分层是好 Agent 记忆系统的底层能力，也是 LightVela 记忆能力产品化的起点。
