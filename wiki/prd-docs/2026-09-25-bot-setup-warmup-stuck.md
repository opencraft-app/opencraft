### 问题一：首页创建入口误入等待流程

**现象与影响范围**：已订阅、首页读取到的 Bot 列表为空时，首页按钮进入 `/agents?creating=true`。该路径用于等待已发起创建的实例，本身没有发起创建；用户提交引导后可能停在「喂咖啡」，等待一个尚未创建的 Bot。国内站和国际站共用该分流逻辑，属于特定入口与账号状态下的共性缺陷，不是所有用户必现。

**本轮修复**：将首页、登录后分流和订阅页同类兜底入口统一改为 `/agents?create=1`，打开真正的创建向导，由用户提交后调用创建接口、完成配置并进入总览。已有 Bot 的用户仍进入 `/agents`；携带实例 ID 的 `creating` 等待流程继续保留。

**引入过程**：通过 `git blame`、`git log` 和提交 diff 核对，当前共用错误分流来自 **2026-09-15 的 `bde7d8812`（MR !3990：登录按钮与 Hero/Footer CTA 按订阅状态分流）**。该提交同时进行了两项改动：

1. 移除订阅成功收尾中的自动 `addBot`，改为让用户进入向导、命名后创建，新增 `/agents?create=1`。
2. 首页与登录后的共用分流、订阅页同类兜底入口仍使用 `/agents?creating=true`，没有同步迁移到新的创建入口。

因此，创建动作已迁移到新向导，部分入口却仍进入只负责等待实例的旧流程，形成了断点。兼容 `LandingPage` 的同类旧路径更早可追溯到 **2026-06-25 的 `4e3be51c0`**，不能把所有旧路径的首次出现都归为 9 月 15 日。

**为什么测试没有发现**：`bde7d8812` 中的 `cta-journey` 测试把 `getAgentCreatingPath(true)` 当作正确期望，只检查分流结果和跳转地址，没有验证从该入口提交后是否真正调用 `addBot`。本轮新增跨入口组件回归，验证实际消费 URL 参数、创建接口调用一次、执行配置并进入新 Bot 总览；国内与国际流程均验证了旧路径失败、修复后通过。

### 问题二：探活请求的超时未覆盖响应正文

**现象**：非流式 `execDebugCommand` 在 `fetch()` 收到响应头后就清除了超时计时器，随后才执行 `response.json()`。如果响应正文迟迟不返回，读取操作就失去超时保护，页面可能持续等待，超出单次探活预算。

**引入过程**：缺口来自 **2026-07-20 的 `77daa6f731`（优化技能搜索、安装与已安装列表）**。该提交为 `fetch` 增加 `AbortController` 和超时计时器，但在读取正文之前的 `finally` 中执行 `clearTimeout`，遗漏了正文接收阶段。

**本轮修复**：将响应正文读取移入同一超时保护范围，完整读取或异常退出后再清理计时器；超时仍返回既有 `debug_exec_timeout:<ms>`，交由预热流程处理。新增 HTTP 200 / 500 正文悬挂回归，验证按时中止，并保留正常响应和业务失败结果的原有语义。

## 需求背景

用户创建 Bot 后跳转到 `/agents?creating=true`，页面显示咖啡杯动画与「正在给 LightVela Bot 喂咖啡，唤醒大脑中」，下方「配置进度」清单列出 6-7 个步骤。实际表现是：

1. 进度长期停在 `0/7`，所有步骤都是灰色未开始状态，页面看不出任何进展；
2. 等待约 3 分钟后，主文案被替换为「实例尚未就绪，请稍后在设置页重试配置」，并出现 Retry 按钮，进度仍为 `0/N`。

从代码看，这不是「进度条不动」的渲染问题，而是**整条配置计划确实一步都没开始**：

- `agent-onboarding-panel.tsx:652` 在执行第 1 个步骤之前，先 `await waitForSandbox(...)` 等沙箱可执行命令。
- `waitForSandbox`（L357-373）循环调用 `execDebugCommand(botId, "true", { timeoutMs: 15_000 })` 探活，直到 `exitCode === 0` 才返回 true，最长等 `SANDBOX_READY_TIMEOUT_MS = 180_000`。
- 这段等待**完全没有 UI 表达**：`steps` 在进入 `creating` 阶段就已全量铺成 `pending`，而 `doneCount` 只统计 `status === "done"`（`agent-creating-loading.tsx:107`），所以预热期间必然恒为 `0/N` 全灰。
- `waitForSandbox` 的 `catch {}` 是**空吞**（L365-367）。这意味着 401/403/404、`resolveBotScope` 取不到 instanceId、后端 envelope 解析不出 `data`（`http-repositories.ts:1442` 会给出 `exitCode: -1`）这些**永不会自愈**的错误，同样会被当作「沙箱还没起好」继续空转满 180s。
- 超时后统一抛出 `t("实例尚未就绪，请稍后在设置页重试配置")`（L655），真实失败原因（HTTP 状态码、后端 code、request_id）全部丢弃。

不做会怎么样：创建 Bot 是新用户的第一个关键动作，也是订阅后的首个体验。用户在此处只能看到一个不动的进度条和一句无信息量的报错，无法判断是网络问题、权限问题还是需要继续等待，只能反复 Retry 或流失；同时客服与研发拿不到任何可定位的线索，每例都要人工去诊断中心复现。

用户价值：等待期间知道系统在做什么、大概还要多久；失败时知道原因和下一步该做什么。

业务价值：降低首次创建 Bot 的流失与重试率，减少「创建失败」类客诉的排查成本。

## 目标用户与场景

目标用户画像：
- 订阅后首次创建 Bot 的新用户（单 bot 路径，实例由后端随订阅创建）。
- 已有 Bot、在 `/agents` 通过多 Bot 入口再建一个 Bot 的存量用户（`onCreateBot` 路径）。

典型场景：
1. 新用户完成订阅 → 自动进入创建引导 → 选模板填资料 → 点「创建」→ 实例容器仍在冷启动，需等待数十秒到数分钟。
2. 用户账号权限异常 / 实例已被回收 / 鉴权态失效 → 探活请求持续返回 4xx，但用户看到的是「正在喂咖啡」。
3. 用户网络经代理（whistle 等）→ 探活请求被空闲超时切断。

当前卡点：预热阶段零反馈，失败原因被掩盖，用户无法区分「还要等」和「已经废了」。

## 目标

产品结果：
- 创建 Bot 的等待阶段全程可解释，不再出现「看起来卡死」的静默窗口。
- 失败时给出可行动的具体原因，而不是统一的「实例尚未就绪」。

业务目标（定性为主，本次不引入新埋点口径）：
- 预热阶段用户主动刷新/重试的次数下降。
- 「创建 Bot 卡住」类客诉可凭页面信息直接定位，无需研发复现。

## 范围

本次包含：
1. 把「等待实例就绪」显性化为配置清单里的第一个步骤，让它能进入 `running` 态并在完成后计入进度。
2. 预热等待期间展示已等待时长，让用户确认系统在推进。
3. `waitForSandbox` 探活错误分级：可恢复错误继续等待；永久性错误立即中止并透出真实原因。
4. 拆分三个共用同一句报错的失败点（等不到 botId / 沙箱未就绪 / 等不到 profileId），各自给出可行动文案。
5. 超时兜底文案带上最后一次探活失败原因，便于用户自查与客服定位。
6. 调整冷启动等待参数：提高探测密度，覆盖海外节点镜像拉取的慢冷启动。

本次不包含：
- 不改动 `buildBuddySetupPlan` 产出的业务步骤（soul / profile-meta / user-profile / skill / cron / gateway）的顺序与命令内容。
- 不新增后端实例状态查询接口（继续用 `debug/exec` 执行 `true` 探活）。
- 不改动 `runBuddySetupPlan` 的重试策略与 required 语义。
- 不做创建流程的埋点体系建设，不做实例冷启动本身的性能优化。
- 不改动断点续跑（`completedKeys` / sessionStorage 快照）机制。

优先级：P0（阻断新用户首次核心动作）

已知依赖：
- `POST /v1/instances/{instanceId}/debug/exec` 的既有行为与错误语义。
- `resolveBotScope` 能正确解析 botId → instanceId。

## 功能详细描述

### 功能点 1：预热步骤显性化

在配置清单最前面增加一个 `warmup` 步骤「正在唤醒 Bot 实例」：
- 进入 `creating` 阶段即为 `running`（带 spinner），不再是灰色 pending。
- 沙箱探活成功 → 置 `done`，计入 `doneCount`，进度立即从 `0/N` 变为 `1/N`。
- 探活失败或超时 → 置 `failed` 并在该行下方显示真实原因。
- 该步骤为 `required`：它失败则整条计划不再往下走（与现状一致）。

> 这一步不执行任何用户配置命令，只反映「实例是否已经能跑命令」这一既有等待，因此它不改变实际写入沙箱的内容，只是把已存在的等待暴露出来。

### 功能点 2：等待时长提示

`warmup` 处于 `running` 时，在步骤行右侧或下方展示已等待秒数（如「已等待 35s」），每秒刷新。用户由此确认页面是活的。

### 功能点 3：探活错误分级

`waitForSandbox` 不再 `catch {}` 空吞，按错误类型分流：

| 错误类型 | 判定 | 处理 |
| --- | --- | --- |
| 沙箱未就绪 | `exitCode !== 0`、`debug_exec_timeout:*`、`network_error`、`Failed to fetch` | 继续轮询等待 |
| **实例状态未就绪** | **`DEBUG_NOT_SUPPORTED` 或 HTTP 409** | **继续轮询等待（见下方说明）** |
| 请求超时 / 限流 | HTTP 408、429 | 继续轮询等待 |
| 鉴权失效 | HTTP 401 | 立即中止，提示重新登录 |
| 无权限 | HTTP 403 | 立即中止，提示账号无权配置该实例 |
| 实例不存在 | HTTP 404 | 立即中止，提示实例不存在或已回收，请返回列表重试 |
| 其他 4xx | `status >= 400 && status < 500` | 立即中止，透出后端 message / code / request_id |
| 5xx 或未知 | 其余 | 继续轮询（服务端可能正在拉起） |

立即中止时抛出的错误消息即为页面主文案，不再覆盖成「实例尚未就绪」。

**关于 409 / `DEBUG_NOT_SUPPORTED`**：后端 `ctl/pkg/instance/logic.go` 在 `entity.Status != Running` 时返回该错误（`ctl/pkg/errcode/debug.go`，HTTP 409），文案为 `debug command not supported in this instance state`。它描述的恰恰是「实例当前状态还不能跑 debug 命令」——正是预热要等的那个状态本身，实例起好后就不再出现。新账号首次开通实例必然先经历这一阶段，因此它是 4xx 里必须排除的例外。同一约定在微信登录链路（`agent-settings-page.tsx`）中已经存在。

分级判定的通用原则：**加新的 fatal 判定前先确认「这个错误在实例启动完成后还会不会出现」，会的话它就不是 fatal。**

同理，`isRetriableSetupFailure` 也纳入 409 / `DEBUG_NOT_SUPPORTED`：预热探活通过只说明「那一刻」能跑命令，紧接着的第一条配置命令仍可能撞上状态回退，而 SOUL 是 `required` 步骤，不重试会让整条计划当场中止。

### 功能点 4：区分三种「尚未就绪」

原先 `waitForBotId` 超时、`waitForSandbox` 失败、`waitForProfileId` 超时**三个完全不同的原因**都抛同一句「实例尚未就绪，请稍后在设置页重试配置」，用户与客服无法区分。改为各自独立文案：

| 失败点 | 含义 | 文案 |
| --- | --- | --- |
| `waitForBotId` 超时 | 路由没带回 botId | 等不到 Bot 实例，请返回列表后重新进入配置 |
| `waitForSandbox` 失败 | 沙箱未就绪或探活被拒 | 见功能点 3 / 功能点 5 |
| `waitForProfileId` 超时 | 拿不到 profileId | 等不到 Bot 的人设档案，请返回列表后重新进入配置 |

前后两者都是「返回列表重进」而非「稍后在设置页重试」—— 它们不是实例没起来，等下去也不会好转。

### 功能点 5：超时原因透出

等满超时仍未就绪时，文案从

> 实例尚未就绪，请稍后在设置页重试配置

变为（存在最后一次失败原因时）

> 实例尚未就绪，请稍后在设置页重试配置（最后一次探测：{{reason}}）

`reason` 取最后一次探活的异常消息或 `status/exitCode`，截断到合理长度。无原因时保持原文案。

### 功能点 6：等待参数调整

- `SANDBOX_READY_TIMEOUT_MS`：180s → 300s（覆盖海外节点冷启动镜像拉取）。
- 单次探活 `timeoutMs`：15s → 8s（探活只是跑一个 `true`，8s 足够；缩短后单轮更快，失败能更早被分级判定）。
- `SANDBOX_PROBE_INTERVAL_MS`：5s → 3s（提高探测密度，实例刚就绪时更快进入下一步）。

### 边界条件与异常处理
- 用户中途离开页面（组件卸载）：`cancelled()` 生效，不写任何状态，与现状一致。
- Retry：沿用现有 `resume` 快照机制。`warmup` 不进 `completedKeys`（它不是幂等配置写入，而是一次实时探测），每次重试都重新探活。
- 步骤数变化：`warmup` 使 `steps.length` 由 N 变为 N+1，进度分母相应变化，属预期。
- 部分失败清单页、「进入 Bot」出口逻辑不变。

### 数据埋点需求
本次不新增埋点。失败原因已通过 UI 与控制台可见，满足当前定位需求。

## 方案决策

采用方案：**方案 A —— 预热步骤显性化 + 探活错误分级**

选择理由：
- 直接命中两个真实缺陷：静默等待窗口、错误原因被吞。
- 不改动实例创建与配置编排链路，`buildBuddySetupPlan` 的业务步骤与 `runBuddySetupPlan` 的执行语义完全不动，回归面小。
- 错误分级让永久性故障从「等 180s 再报一句废话」变成「立刻报出真实原因」，是排查成本下降最大的一项。

备选方案与取舍：
- 方案 B：只加等待提示文案，不做错误分级。代价小，但 401/403/404 仍要空转满超时并给出误导性报错，客诉排查成本不变，没有解决核心问题。
- 方案 C：新增后端实例状态接口，前端轮询 `instance.status` 判断就绪。语义最准确，但需要后端排期、接口设计与联调，且 `status === active` 本身不等于沙箱容器可执行命令（现有注释已说明这点），收益不确定而成本高。列为后续方向。

延后或不做：

## 验收标准
- 验收 1：进入创建配置阶段后，清单第一行「正在唤醒 Bot 实例」立即为 `running`（spinner 转动）并显示递增的已等待秒数，进度不再长时间停在 `0/N` 全灰。
- 验收 2：沙箱探活成功后该步骤变为 `done`，进度至少推进到 `1/N`，随后业务步骤依次进入 `running`。
- 验收 3：探活返回 HTTP 401/403/404 时，**不再等待到超时**，立即中止并在主文案处显示对应的具体原因（重新登录 / 无权限 / 实例不存在）。
- 验收 4：探活遇到 `Failed to fetch`、`debug_exec_timeout:*`、`network_error`、`exitCode !== 0` 或 5xx 时，继续轮询直到就绪或超时，行为与现状一致。
- 验收 4.1：**新账号注册后首次开通 Bot**（实例状态为 `creating`/`starting`，探活前几轮返回 409 `DEBUG_NOT_SUPPORTED`）时，预热持续等待并在实例转为 `running` 后跑完整条计划，不出现阻断错误。
- 验收 5：等满超时时，错误文案包含最后一次探测失败原因；Retry 按钮仍可用，且点击后预热行重新回到 `running`（重新探活，不沿用上一轮结果）。
- 验收 6：等不到 botId 与等不到 profileId 分别给出各自文案，不再与「实例尚未就绪」混用。
- 验收 7：`agent-onboarding-setup-runs-once.test.tsx`、`agent-onboarding-recovery.test.tsx` 等既有用例全部通过；新增用例覆盖验收 3 与验收 4 的分流判定。
- 验收 8：新增文案在 en-US / zh-Hant / ja-JP / ko-KR / es / id-ID 六个语言包中均已补齐，`i18n:check` 与 `i18n:validate` 通过。
